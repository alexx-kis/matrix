# search flow

- `Search flow` в IndexedDB — это то, как приложение ищет нужную запись внутри базы данных здесь важно понять не конкретный метод, а общий путь, который проходит запрос

## Общая схема

- если нам нужно найти пользователя, путь выглядит примерно так

```
database
   ↓
transaction
   ↓
object store
   ↓
search
   ↓
request
   ↓
result
```

- например, хотим найти пользователя с `id = 42`

```js
const searchTransaction = database.transaction('users', 'readonly');

const searchStore = searchTransaction.objectStore('users');

const userRequest = searchStore.get(42);
```

- `get(42)` не возвращает пользователя напрямую

- это важный момент

```js
const userRequest = searchStore.get(42);

console.log(userRequest);
```

- здесь мы получим не объект пользователя, а IDBRequest
- `IndexedDB` работает асинхронно, поэтому результат появится позже

## Получение результата

- результат можно получить через `onsuccess`

```js
userRequest.onsuccess = (event) => {
  const foundUser = event.target.result;

  console.log(foundUser);
};
```

- если запись существует, например

```js
{
  id: 42,
  name: 'Alex'
}
```

- именно этот объект попадёт в `event.target.result`

- если записи с таким ключом нет, результатом будет `undefined`

```
get(42)
   ↓
IDBRequest
   ↓
поиск в object store
   ↓
┌───────────────────────┐
│ запись найдена?       │
└───────────┬───────────┘
            │
       да   │   нет
       ↓    │    ↓
   object   │ undefined
```

## Поиск по ключу

- самый простой вариант поиска — искать запись по её ключу

```js
const keyRequest = searchStore.get(42);
```

- если object store был создан так

```js
database.createObjectStore('users', {
  keyPath: 'id',
});
```

- тогда id является ключом записи

```
users

key     record
42   →  { id: 42, name: "Alex" }
43   →  { id: 43, name: "John" }
```

- поэтому `get(42)` означает примерно: "найди запись, ключ которой равен 42"

## А если нужно искать не по id?

- допустим, нам нужно найти пользователя по имени

```
name = "Alex"
```

- `get()` для этого не подходит, потому что get() ищет именно по ключу

- здесь появляются indexes

```
users
  ↓
key: id
  ↓
index: name
```

- индекс позволяет создать дополнительный способ поиска записей
- например

```
id → 42 → Alex
```

- и одновременно

```
name → Alex → запись пользователя
```

- это очень важная концепция IndexedDB

## `get()` и `getAll()`

- get() нужен, когда мы ожидаем одну конкретную запись

```js
const singleRequest = searchStore.get(42);
```

- `getAll()` позволяет получить несколько записей

```js
const allRequest = searchStore.getAll();
```

- например, если в users находятся три записи, getAll() вернёт массив:

```js
[
  { id: 1, name: 'Alex' },
  { id: 2, name: 'John' },
  { id: 3, name: 'Anna' },
];
```

## Более сложный поиск

- когда нам нужно не просто найти запись по точному ключу, можно использовать:

```
key
  ↓
get()

index
  ↓
get()
getAll()

cursor
  ↓
перебор записей
```

- cursor особенно важен, когда нужно пройти по нескольким записям и обработать их по очереди

## Главное отличие от SQL

- в SQL мы привыкли писать что-то вроде:

```sql
SELECT * FROM users WHERE name = 'Alex';
```

- в IndexedDB нет такого SQL-запроса
- вместо этого мы используем API базы:

```
objectStore
    ↓
key / index
    ↓
get / getAll / cursor
```

- поэтому Search flow в IndexedDB — это не написание SQL-запроса, а выбор правильного механизма поиска

## Что нужно запомнить

- сначала создаём transaction
- затем получаем нужный objectStore
- затем выполняем операцию поиска
- операция возвращает IDBRequest, а не результат напрямую
- результат получаем асинхронно через onsuccess
- get() ищет по ключу
- getAll() получает несколько записей
- для поиска по другим полям используются indexes
- для последовательного перебора записей используется cursor
- итоговая схема:

```
database
   ↓
transaction
   ↓
objectStore
   ↓
┌───────────────┐
│ search method │
└───────┬───────┘
        ↓
    IDBRequest
        ↓
    onsuccess
        ↓
      result
```

- для собеседования особенно важно понимать, почему get() не возвращает данные сразу — потому что IndexedDB работает асинхронно, и обращение к локальной базе не блокирует основной поток JavaScript
