# browser dependent styles

- browser dependent styles — это CSS-правила или отдельные варианты оформления, которые используются из-за различий между браузерами, их движками или версиями

- основная проблема в том, что один и тот же CSS может интерпретироваться немного по-разному, а некоторые возможности могут отсутствовать или работать с особенностями

## зачем они нужны

- исторически браузеры имели очень много различий в реализации CSS

- например, один браузер мог поддерживать свойство, другой ещё не поддерживал его, а третий поддерживал, но с другим поведением

- поэтому разработчикам приходилось писать разные варианты одного и того же правила

```css
.example {
  -webkit-appearance: none;
  appearance: none;
}
```

- здесь `appearance` — стандартное CSS-свойство, а `-webkit-appearance` — vendor-prefixed вариант, связанный с WebKit/Blink-браузерами

## vendor prefixes

- vendor prefix — специальный префикс перед CSS-свойством, который исторически использовался браузерами для экспериментальных или ещё не стандартизированных возможностей

- наиболее известные префиксы выглядят так

```
-webkit-   → WebKit / Blink
-moz-      → Firefox
-ms-       → старый Internet Explorer
-o-        → старый Opera
```

- например

```css
.search-field {
  -webkit-appearance: none;
  appearance: none;
}
```

- раньше подобный подход встречался гораздо чаще

```css
.demo {
  -webkit-transform: translateX(20px);
  -moz-transform: translateX(20px);
  -ms-transform: translateX(20px);
  transform: translateX(20px);
}
```

- сегодня большинство таких префиксов уже не нужны, потому что стандартизированные свойства достаточно хорошо поддерживаются браузерами

## откуда вообще берутся различия

- основная причина — разные браузерные движки

- например, Chrome и другие Chromium-браузеры используют Blink, Firefox использует Gecko, а Safari использует WebKit

- движок отвечает в том числе за разбор HTML и CSS и построение отображения страницы

- поэтому ситуация может выглядеть примерно так

```
CSS
 ↓
браузер
 ↓
движок
 ↓
layout / painting / compositing
 ↓
результат на экране
```

- разные движки могут поддерживать CSS-возможности в разные моменты времени или иметь отличия в их реализации

## feature detection

- современный подход обычно заключается не в том, чтобы определять конкретный браузер, а в том, чтобы определить наличие нужной возможности

- для CSS для этого используется `@supports`

```css
@supports (display: grid) {
  .product-gallery {
    display: grid;
  }
}
```

- этот код означает: если браузер понимает `display: grid`, применить соответствующее правило

- можно сделать fallback для браузеров без поддержки

```css
.result-tile {
  display: block;
}

@supports (display: grid) {
  .result-tile {
    display: grid;
  }
}
```

- браузер сначала получает базовый вариант, а затем при поддержке Grid применяет более современный вариант

## почему feature detection лучше browser detection

- browser detection пытается ответить на вопрос «какой это браузер»

- feature detection отвечает на более полезный вопрос «поддерживает ли этот браузер нужную возможность»

- например, плохая идея — строить CSS-логику вокруг названия браузера

```
если Chrome → один CSS
если Firefox → другой CSS
если Safari → третий CSS
```

- гораздо надёжнее проверять конкретную возможность

```css
@supports (backdrop-filter: blur(10px)) {
  .glass-surface {
    backdrop-filter: blur(10px);
  }
}
```

- это особенно важно потому, что браузеры обновляются, появляются новые версии и новые движки, а конкретная CSS-возможность может поддерживаться независимо от названия браузера

## fallback

- fallback — запасной вариант оформления, который используется, если основной способ не поддерживается

- например

```css
.summary-layout {
  display: block;
}

@supports (display: grid) {
  .summary-layout {
    display: grid;
    grid-template-columns: 240px 1fr;
  }
}
```

- здесь `display: block` является fallback

- браузер с поддержкой Grid использует Grid, а браузер без такой поддержки всё равно получает рабочий базовый layout

- хороший CSS часто строится именно по принципу

```
базовый вариант
      ↓
более современная возможность
      ↓
улучшение интерфейса
```

## progressive enhancement

- progressive enhancement — подход, при котором сначала создаётся базовая рабочая версия интерфейса, а затем для браузеров с необходимыми возможностями добавляются улучшения

```css
.feedback-field {
  padding: 10px;
}

@supports (field-sizing: content) {
  .feedback-field {
    field-sizing: content;
  }
}
```

- пользователь со старым браузером получает рабочий базовый вариант, а современный браузер получает дополнительную возможность

- это отличается от подхода «современный браузер обязателен для работы сайта»

## браузерные значения по умолчанию

- ещё один источник browser-dependent поведения — стандартные стили браузера, которые называются user-agent styles

- например, браузер сам задаёт стили для заголовков, параграфов, списков, кнопок и других элементов

```css
h1 {
  margin-block: 0.67em;
}

p {
  margin-block: 1em;
}
```

- конкретные значения и детали могут отличаться между браузерами

- поэтому разработчики часто используют CSS reset или normalize-подход

```css
* {
  box-sizing: border-box;
}

body {
  margin: 0;
}
```

- идея заключается в том, чтобы уменьшить влияние браузерных значений по умолчанию и получить более предсказуемую отправную точку

## prefix vs fallback

- это разные вещи

- prefix говорит: «попробуй этот вариант свойства, связанный с конкретной реализацией»

```css
.example {
  -webkit-appearance: none;
  appearance: none;
}
```

- fallback говорит: «если современный вариант недоступен, используй другой способ»

```css
.dashboard-layout {
  display: block;
}

@supports (display: flex) {
  .dashboard-layout {
    display: flex;
  }
}
```

## autoprefixer

- вручную добавлять vendor prefixes сегодня обычно не требуется

- для этого существуют инструменты вроде Autoprefixer, которые анализируют CSS и автоматически добавляют необходимые префиксы в зависимости от целевых браузеров

- например, разработчик пишет

```css
.widget {
  user-select: none;
}
```

- инструмент сборки может добавить необходимые префиксы для выбранного набора браузеров

- это одна из причин, почему в современных проектах разработчик обычно не пишет десятки `-webkit-` и `-moz-` вручную

## браузерные хаки

- browser hack — специальный приём, который использует особенность конкретного браузера, чтобы применить или не применить определённый CSS

- исторически такие техники использовались для исправления проблем старых браузеров

- сегодня их стараются избегать, если проблему можно решить стандартным CSS, feature detection или нормальным fallback

- особенно плохой вариант — строить значительную часть архитектуры CSS на наборе browser hacks

## что важно помнить для собеседования

- browser dependent styles нужны для обработки различий в поддержке и поведении CSS между браузерами

- исторически для этого широко использовались vendor prefixes вроде `-webkit-`, `-moz-` и `-ms-`

- современный подход — по возможности использовать стандартный CSS и feature detection через `@supports`

- для неподдерживаемых возможностей используются fallback и progressive enhancement

- определять конкретный браузер обычно хуже, чем проверять наличие конкретной возможности

- browser-dependent проблемы также могут возникать из-за user-agent styles, поэтому для предсказуемого результата применяют reset или normalize-подход

- vendor prefixes сегодня во многих случаях автоматически добавляются инструментами вроде Autoprefixer

### что ответить на собеседовании

- «Browser dependent styles нужны для обработки различий между браузерами в поддержке и реализации CSS, но современный подход старается не определять браузер напрямую, а использовать feature detection через `@supports`, fallback и progressive enhancement, а vendor prefixes при необходимости обычно генерируются инструментами сборки»
