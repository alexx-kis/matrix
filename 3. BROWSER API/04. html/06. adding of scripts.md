# adding of scripts

- в HTML JavaScript подключается или прямо через `<script>`, или через внешний файл с помощью `src`
- главное, что нужно понимать для собеседования, — **где находится `<script>`, когда он загружается и когда выполняется**

## базовый вариант

- самый простой способ подключить внешний JavaScript — указать путь в `src`

```html
<script src="./app.js"></script>
```

- браузер при обработке такого элемента должен загрузить `app.js`, а затем выполнить его
- если это обычный классический script без специальных атрибутов, его выполнение **блокирует дальнейший разбор HTML**

```html
<head>
  <script src="./app.js"></script>
</head>

<body>
  <h1>Hello</h1>
</body>
```

- здесь браузер встретит `<script>` во время разбора `<head>`, остановит разбор HTML, загрузит JavaScript, выполнит его и только после этого продолжит разбирать документ
- поэтому такое размещение без `defer` обычно плохо влияет на скорость загрузки страницы

---

## inline script

- JavaScript можно написать непосредственно внутри HTML

```html
<script>
  console.log('page started');
</script>
```

- в этом случае отдельная загрузка файла не требуется

- код выполняется непосредственно в момент обработки `<script>`

- можно использовать и внешний файл, и inline-код в одном документе

```html
<script src="./analytics.js"></script>

<script>
  console.log('application initialized');
</script>
```

- при этом для production-кода обычно предпочитают отдельные JavaScript-файлы, потому что их проще кешировать, поддерживать и разделять по ответственности

---

## где размещать `<script>`

- исторически JavaScript часто размещали в конце `<body>`

```html
<body>
  <h1>Profile</h1>

  <script src="./profile-page.js"></script>
</body>
```

- преимущество такого подхода в том, что к моменту выполнения скрипта HTML выше него уже разобран

- недостаток в том, что загрузка JavaScript начинается только тогда, когда браузер дойдёт до этого места

- современный вариант для обычного внешнего скрипта — использовать `defer` и размещать его в `<head>`

```html
<head>
  <script defer src="./dashboard.js"></script>
</head>
```

- тогда браузер может загружать JavaScript параллельно с разбором HTML, но выполнит его после завершения разбора HTML

---

# `defer`

- `defer` говорит браузеру: **не выполнять классический внешний script сразу, а загрузить его параллельно с разбором HTML и выполнить после завершения parsing**

```html
<head>
  <script defer src="./first-module.js"></script>
  <script defer src="./second-module.js"></script>
</head>
```

- пока HTML разбирается, оба файла могут загружаться

```text
HTML parsing ────────────────────────────────►
             │                 │
             ├─ download JS ───┤
             │                 │
             │                 └─ JS execute
             │
             └───────────────── parsing finished
```

- после завершения разбора HTML deferred-скрипты выполняются
- несколько `defer`-скриптов сохраняют порядок выполнения

```html
<script defer src="./alpha.js"></script>
<script defer src="./beta.js"></script>
```

- сначала выполнится `alpha.js`

- затем выполнится `beta.js`

- это важное отличие от `async`

---

## `defer` и `DOMContentLoaded`

- `defer` связан с событием `DOMContentLoaded`
- deferred scripts выполняются до `DOMContentLoaded`

```html
<script defer src="./page-logic.js"></script>

<script>
  document.addEventListener('DOMContentLoaded', () => {
    console.log('DOM ready');
  });
</script>
```

- браузер не отправляет `DOMContentLoaded` до завершения выполнения deferred scripts

- поэтому если код должен работать с уже разобранным DOM, `defer` часто является удобным вариантом

---

# `async`

- `async` также позволяет загружать внешний script параллельно с parsing HTML

```html
<script async src="./statistics.js"></script>
```

- но принципиальное отличие заключается в моменте выполнения
- как только файл загрузился, браузер **сразу выполняет его**

```text
HTML parsing ─────────────────────────────────►
       │
       │ download JS
       │───────────────┐
       │               │
       │               ▼
       │          JS execute
       │               │
       └───────────────┴──────────────────────►
```

- выполнение `async`-скрипта может произойти до завершения parsing HTML или после него
- порядок выполнения нескольких `async`-скриптов не гарантируется

```html
<script async src="./slow-service.js"></script>
<script async src="./fast-service.js"></script>
```

- если `fast-service.js` загрузился первым, он может выполниться первым
- HTML-порядок здесь не определяет порядок выполнения

---

# `defer` vs `async`

| Характеристика                      | `defer`                 | `async`             |
| ----------------------------------- | ----------------------- | ------------------- |
| параллельная загрузка               | да                      | да                  |
| блокирует parsing во время загрузки | нет                     | нет                 |
| выполнение после parsing            | да                      | не обязательно      |
| сохраняет порядок скриптов          | да                      | нет                 |
| ждёт другие `defer`                 | да, в порядке документа | нет                 |
| влияет на `DOMContentLoaded`        | да                      | нет                 |
| типичный сценарий                   | основной application JS | независимые скрипты |

- если несколько скриптов зависят друг от друга, обычно нужен `defer`

```html
<script defer src="./library-core.js"></script>
<script defer src="./application-shell.js"></script>
```

- если скрипт полностью независим от остальных и его можно выполнить в любой момент, может подойти `async`

```html
<script async src="./metrics.js"></script>
```

- хорошая практическая ассоциация для собеседования такая: **`defer` сохраняет порядок, `async` — нет**

---

# почему обычный `<script>` блокирует HTML

- рассмотрим такой документ

```html
<body>
  <h1>Products</h1>

  <script src="./catalog.js"></script>

  <p>More information</p>
</body>
```

- браузер разбирает HTML сверху вниз
- когда он встречает обычный `<script>`, parsing HTML приостанавливается
- браузер загружает script
- script выполняется
- только после этого parsing продолжается

```
<h1>Products</h1>
        ↓
<script>
        ↓
HTML parsing остановлен
        ↓
загрузка JS
        ↓
выполнение JS
        ↓
HTML parsing продолжается
        ↓
<p>More information</p>
```

- именно поэтому большой синхронный script в `<head>` может существенно задерживать отображение страницы

---

# `src`

- атрибут `src` указывает внешний JavaScript-файл

```html
<script src="./main.js"></script>
```

- путь может быть относительным

```html
<script src="./scripts/navigation.js"></script>
```

- или абсолютным

```html
<script src="https://cdn.example.com/widget.js"></script>
```

- если у `<script>` присутствует `src`, содержимое между открывающим и закрывающим тегами не используется как JavaScript

```html
<script src="./main.js">
  console.log('this will not execute')
</script>
```

- если нужен inline-код, его следует написать в отдельном `<script>`

---

# `type`

- для обычного JavaScript сегодня достаточно написать

```html
<script src="./main.js"></script>
```

- указывать

```html
<script type="text/javascript" src="./main.js"></script>
```

- для современного HTML обычно не нужно, потому что JavaScript является стандартным типом содержимого для `<script>`

- `type` особенно важен для модулей

```html
<script type="module" src="./app-module.js"></script>
```

- `type="module"` переключает script в модульный режим, где работают `import` и `export`

---

# module scripts

- модульный script отличается от классического не только синтаксисом JavaScript

```html
<script type="module" src="./main-module.js"></script>
```

- module scripts по умолчанию ведут себя во многом подобно `defer`
- они не блокируют parsing HTML во время загрузки
- выполняются после того, как HTML будет разобран
- при этом браузер учитывает зависимости модулей

например, `main-module.js` может содержать

```js
import { calculateTotal } from './cart-utils.js';

console.log(calculateTotal());
```

- браузер должен загрузить и обработать зависимость `cart-utils.js` перед выполнением соответствующего кода

- поэтому для современных приложений часто встречается именно такой вариант

```html
<head>
  <script type="module" src="./application-entry.js"></script>
</head>
```

---

# `async` для module scripts

- у module script тоже можно указать `async`

```html
<script type="module" async src="./independent-module.js"></script>
```

- тогда обычное поведение ожидания завершения parsing и порядок выполнения изменяются в сторону независимого выполнения

- это имеет смысл, когда модуль не должен ждать остальную страницу или другие module scripts

- для обычного application entry point чаще используется просто

```html
<script type="module" src="./application-entry.js"></script>
```

---

# влияние на `DOMContentLoaded`

- это один из популярных вопросов на собеседовании

```
обычный script
    ↓
может задерживать parsing

defer
    ↓
выполняется до DOMContentLoaded
    ↓
DOMContentLoaded

module
    ↓
по умолчанию deferred
    ↓
DOMContentLoaded

async
    ↓
не обязан ждать DOMContentLoaded
```

- если `async`-скрипт загрузился быстро, он может выполниться до `DOMContentLoaded`

- если загрузился поздно, `DOMContentLoaded` может произойти раньше него

- поэтому нельзя говорить, что `DOMContentLoaded` всегда ждёт абсолютно все `<script>`

---

# `defer` работает не со всеми scripts одинаково

- классический `defer` применяется к внешним scripts

```html
<script defer src="./external-code.js"></script>
```

- наличие `defer` у inline script не превращает его в отложенный внешний script

```html
<script defer>
  console.log('inline code');
</script>
```

- поэтому не стоит запоминать правило как «`defer` откладывает любой JavaScript»
- корректнее помнить: **`defer` предназначен для внешних классических scripts**

---

# динамическое добавление script

- JavaScript может сам создать новый `<script>` и добавить его в документ

```javascript
const dynamicScript = document.createElement('script');

dynamicScript.src = './feature-extra.js';

document.head.append(dynamicScript);
```

- после добавления браузер начнёт загружать указанный ресурс

- такой механизм используется, например, для ленивой загрузки дополнительного функционала

- при динамической загрузке можно дополнительно реагировать на успешную загрузку

```js
const lazyScript = document.createElement('script');

lazyScript.src = './optional-tools.js';

lazyScript.onload = () => {
  console.log('optional tools loaded');
};

lazyScript.onerror = () => {
  console.log('optional tools failed');
};

document.head.append(lazyScript);
```

- это уже более продвинутый сценарий, но принцип полезно знать

# безопасность внешних scripts

- внешний JavaScript фактически получает возможность выполнять код в контексте страницы

- поэтому подключать произвольные сторонние scripts без необходимости опасно

- для внешних ресурсов может использоваться Subresource Integrity

```html
<script src="https://cdn.example.com/library.js" integrity="sha384-..." crossorigin="anonymous"></script>
```

- `integrity` позволяет браузеру проверить, что загруженный ресурс соответствует ожидаемому криптографическому хэшу

- это защищает от ситуации, когда содержимое внешнего файла неожиданно изменилось

- также в production-среде часто используется Content Security Policy, которая позволяет ограничивать источники, откуда странице разрешено загружать scripts

---

# `nomodule`

- иногда можно встретить такую конструкцию

```html
<script type="module" src="./modern-app.js"></script>
<script nomodule src="./legacy-app.js"></script>
```

- идея заключается в том, чтобы современные браузеры использовали module version, а старые браузеры — legacy version
- для современного frontend-разработчика этот механизм полезно узнавать при чтении старого или legacy-кода, хотя в новых проектах он нужен значительно реже

# типичная структура

- современный HTML-документ часто выглядит примерно так

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />

    <script defer src="./application-main.js"></script>
  </head>

  <body>
    <main>
      <h1>Dashboard</h1>
    </main>
  </body>
</html>
```

- здесь JavaScript начинает загружаться достаточно рано благодаря размещению в `<head>`
- при этом parsing HTML не блокируется загрузкой файла благодаря `defer`
- после завершения parsing браузер выполняет script
- к этому моменту DOM уже построен

---

# что важно знать на собеседовании

- `<script>` используется для подключения и выполнения JavaScript
- обычный классический внешний `<script>` блокирует parsing HTML во время загрузки и выполнения
- `defer` позволяет загружать внешний script параллельно с parsing и выполнить его после завершения parsing
- несколько `defer`-скриптов выполняются в порядке появления в HTML
- `async` также загружает script параллельно с parsing, но выполняет его сразу после загрузки
- порядок нескольких `async`-скриптов не гарантируется
- `defer` связан с `DOMContentLoaded`, а `async` — нет
- `type="module"` включает JavaScript modules и по умолчанию ведёт себя как deferred script
- `src` указывает внешний JavaScript-файл
- inline script можно написать непосредственно внутри `<script>`
- `type="text/javascript"` для современного обычного JavaScript обычно не нужен

## главное сравнение

```
<script src="app.js">
    ↓
блокирует parsing
    ↓
загрузить → выполнить → продолжить parsing


<script defer src="app.js">
    ↓
загружать параллельно с parsing
    ↓
parsing завершён
    ↓
выполнить
    ↓
DOMContentLoaded


<script async src="app.js">
    ↓
загружать параллельно с parsing
    ↓
как только загрузился → выполнить
    ↓
порядок с другими async не гарантирован


<script type="module" src="app.js">
    ↓
по умолчанию deferred
    ↓
загрузить module dependencies
    ↓
выполнить после parsing
```

- если на собеседовании спросят, **что выбрать для основного JavaScript приложения**, хороший базовый ответ — `defer` для классического внешнего script или `type="module"` для модульного JavaScript
- если скрипт независимый и порядок его выполнения не важен, например сторонняя аналитика, часто подходит `async`
