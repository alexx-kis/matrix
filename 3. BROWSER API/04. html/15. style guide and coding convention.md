# style guide и coding convention

- **Style guide** — это набор договорённостей о том, **как именно писать код в проекте**, чтобы разные разработчики оформляли его единообразно

- **Coding convention** — более конкретные правила написания кода: именование, отступы, кавычки, структура HTML, порядок атрибутов, использование определённых элементов и так далее

- главная цель этих правил не в том, чтобы код выглядел «красиво», а в том, чтобы его было **легко читать, поддерживать и изменять**

## зачем это нужно

- представь проект, в котором один разработчик пишет `<DIV CLASS="Header">`, другой использует `<div class='header'>`, а третий строит всё через `<div>` без семантических элементов

- браузер в большинстве случаев сможет это обработать, но человеку будет гораздо сложнее понимать и поддерживать такой код

- единый стиль уменьшает количество ненужных решений и делает код предсказуемым

- кроме того, часть правил помогает не только читаемости, но и **доступности, SEO, производительности и предотвращению ошибок**

---

## хорошие практики HTML

### использовать семантические элементы

- если у HTML уже существует элемент с подходящим смыслом, лучше использовать его вместо универсального `<div>`

```html
<header>
  <nav>
    <a href="/products">Products</a>
  </nav>
</header>

<main>
  <article>
    <h1>Frontend development</h1>
    <p>Learning semantic HTML</p>
  </article>
</main>

<footer>
  <p>© 2026</p>
</footer>
```

- плохой вариант — строить всю страницу исключительно из `<div>`

```html
<div class="page-header">
  <div class="navigation">
    <div class="navigation-link">Products</div>
  </div>
</div>

<div class="main-content">
  <div class="article">
    <div class="article-title">Frontend development</div>
  </div>
</div>
```

- второй вариант может выглядеть визуально так же, но он теряет смысловую структуру документа

- семантическая разметка помогает браузерам, поисковым системам, скринридерам и другим инструментам понять структуру страницы

---

## использовать элементы по их назначению

- одна из самых важных практик — **не выбирать HTML-элемент только по тому, как он выглядит**

- ссылка используется для перехода

```html
<a href="/profile">Open profile</a>
```

- кнопка используется для действия

```html
<button type="button">Open profile</button>
```

- плохой вариант — делать кнопку из `<div>`

```html
<div class="action-button">Open profile</div>
```

- такой `<div>` сам по себе не получает нормального поведения кнопки с клавиатуры, семантики и стандартной доступности

- не стоит исправлять неправильный элемент большим количеством ARIA-атрибутов, если существует подходящий нативный HTML-элемент

---

## правильно работать с классами

- классы должны описывать **роль или назначение элемента**, а не его текущее визуальное состояние

- хороший вариант

```html
<button class="user-actions__submit">Save</button>
```

- плохой вариант

```html
<button class="green-button">Save</button>
```

- проблема `.green-button` в том, что завтра кнопка может стать синей, но её класс всё ещё будет называться `green-button`

- ещё хуже использовать названия вроде:

```html
<div class="red">
  <div class="big-text">
    <div class="left-block"></div>
  </div>
</div>
```

- такие имена описывают внешний вид или расположение, а не смысл компонента

---

## не злоупотреблять `<div>` и `<span>`

- `<div>` и `<span>` — универсальные элементы без собственной семантики

- они нужны, когда действительно требуется структурная оболочка или стилизация

- плохой код часто выглядит примерно так

```html
<div class="page">
  <div class="header">
    <div class="menu">
      <div class="menu-item">
        <span class="menu-link">Home</span>
      </div>
    </div>
  </div>
</div>
```

- если часть этих элементов можно заменить на `<header>`, `<nav>`, `<ul>`, `<li>` и `<a>`, структура станет понятнее

---

## соблюдать правильную вложенность

- HTML-элементы должны находиться в корректной структуре

- хороший вариант

```html
<p>
  Read the
  <strong>important</strong>
  information
</p>
```

- нельзя бездумно помещать интерактивные элементы друг в друга

```html
<a href="/profile">
  <button type="button">Profile</button>
</a>
```

- здесь сразу возникает конфликт семантики: и ссылка, и кнопка представляют разные интерактивные действия

---

## использовать уникальные `id`

- значение `id` должно идентифицировать конкретный элемент и не должно повторяться на странице

```html
<label for="account-email">Email</label> <input id="account-email" type="email" />
```

- плохо

```html
<input id="email" /> <input id="email" />
```

- `class` обычно используется для группировки и повторного применения стилей, а `id` — для уникальной идентификации конкретного элемента

---

## связывать `label` и `input`

- для формы важно, чтобы пользователь и вспомогательные технологии понимали, какое название относится к какому полю

```html
<label for="billing-email">Email</label> <input id="billing-email" name="email" type="email" />
```

- `for` у `<label>` должен соответствовать `id` у `<input>`

- ещё один хороший вариант — вложить поле непосредственно в `<label>`

```html
<label>
  Email
  <input name="email" type="email" />
</label>
```

---

## не использовать placeholder вместо label

- `placeholder` предназначен для примера или подсказки внутри поля, а не для постоянного названия поля

- плохой вариант

```html
<input type="email" placeholder="Email" />
```

- хороший вариант

```html
<label for="contact-email">Email</label>
<input id="contact-email" name="email" type="email" placeholder="name@example.com" />
```

- placeholder исчезает после ввода значения, поэтому он не должен быть единственным способом понять назначение поля

---

## использовать правильный `type` у кнопок

- внутри `<form>` кнопка без явно указанного `type` по умолчанию ведёт себя как `submit`

- поэтому если кнопка должна выполнять обычное действие, лучше явно написать

```html
<button type="button">Show details</button>
```

- а отправку формы обозначать явно

```html
<button type="submit">Submit</button>
```

- это предотвращает случайную отправку формы

---

## изображения должны иметь `alt`

- если изображение является содержательным, `alt` должен описывать его смысл

```html
<img src="team-photo.jpg" alt="Frontend team during a conference" />
```

- декоративное изображение может иметь пустой `alt`

```html
<img src="decorative-line.svg" alt="" />
```

- отсутствие `alt` и пустой `alt` — не одно и то же

- `alt=""` сообщает вспомогательной технологии, что изображение является декоративным и его можно пропустить

---

## указывать размеры изображений

- для изображений часто полезно заранее указывать `width` и `height`

```html
<img src="article-cover.jpg" width="800" height="450" alt="Laptop with frontend code" />
```

- это позволяет браузеру заранее зарезервировать место под изображение и уменьшает вероятность неожиданного смещения страницы при загрузке

---

## не использовать устаревшие HTML-подходы

- не следует использовать устаревшие элементы и атрибуты вроде `<font>`, `<center>` и подобных способов оформления

- внешний вид должен контролироваться CSS

- HTML отвечает прежде всего за **структуру и смысл**, CSS — за **представление**

---

## не помещать JavaScript непосредственно в HTML без необходимости

- такой подход работает

```html
<button onclick="openMenu()">Menu</button>
```

- но в современных проектах обычно предпочтительнее отделять структуру от поведения

```html
<button type="button" id="menu-trigger">Menu</button>
```

```javascript
const menuTrigger = document.querySelector('#menu-trigger');

menuTrigger.addEventListener('click', () => {
  // изменение состояния меню
});
```

- конкретный способ организации JavaScript зависит от архитектуры проекта, но идея одна — HTML не должен превращаться в смесь структуры, стилей и логики

---

## форматирование HTML

- отступы должны быть единообразными

- например, если проект использует два пробела, не стоит в одном файле смешивать два и четыре

```html
<section>
  <h2>Articles</h2>
  <article>
    <h3>HTML basics</h3>
    <p>Introduction to semantic HTML</p>
  </article>
</section>
```

- атрибуты обычно записываются в кавычках

```html
<input type="text" name="username" />
```

- вместо нестабильного смешивания разных стилей

```html
<input type="text" name="username" />
```

- конкретные правила кавычек, отступов и порядка атрибутов могут отличаться между проектами, поэтому на собеседовании важно понимать, что **главное — консистентность**

---

## не делать чрезмерно длинные строки

- если элемент содержит много атрибутов, его можно разбить на несколько строк

```html
<img src="conference-photo.jpg" width="1200" height="800" loading="lazy" alt="Developers attending a conference" />
```

- так изменения и code review становятся удобнее

---

## комментарии должны объяснять причину

- плохой комментарий просто повторяет код

```html
<!-- Create button -->
<button type="button">Save</button>
```

- такой комментарий практически бесполезен

- гораздо полезнее объяснять неочевидную причину

```html
<!-- Kept outside the lazy-loaded section because it is needed immediately -->
<div class="critical-notice">Important information</div>
```

- хороший комментарий отвечает на вопрос **«почему здесь именно так?»**, а не **«что здесь написано?»**

---

## accessibility как часть coding convention

- доступность не должна рассматриваться как отдельная функция, которую добавляют в самом конце

- хорошие HTML-практики уже сами по себе значительно улучшают accessibility

- например, вместо

```html
<div class="submit-control">Submit</div>
```

- следует использовать

```html
<button type="submit">Submit</button>
```

- вместо кликабельного `<div>` использовать `<button>` или `<a>` в зависимости от назначения

- вместо визуального текста без семантики использовать заголовки `<h1>`–`<h6>`

- для полей формы использовать `<label>`

- для изображений использовать корректный `alt`

- интерактивные элементы должны быть доступны с клавиатуры

---

## ARIA не должна заменять HTML

- распространённая ошибка — пытаться исправить плохую семантику ARIA-атрибутами

- например, технически можно написать

```html
<div role="button" tabindex="0">Save</div>
```

- но обычная кнопка намного правильнее

```html
<button type="button">Save</button>
```

- принцип можно сформулировать так: **сначала нативный HTML, затем ARIA только там, где нативной семантики недостаточно**

---

## хорошие и плохие практики в одном примере

- плохой вариант

```html
<div class="red-big-text">
  <div onclick="sendData()">Send</div>
  <img src="photo.jpg" />
</div>
```

- здесь сразу несколько проблем: нет семантики, используется `<div>` вместо кнопки, присутствует inline JavaScript, отсутствует `alt`, класс описывает внешний вид

- более правильный вариант

```html
<section class="feedback">
  <h2 class="feedback__title">Feedback</h2>

  <img src="photo.jpg" width="600" height="400" alt="Customer feedback form" />

  <button type="button" class="feedback__submit">Send</button>
</section>
```

- здесь HTML описывает структуру и назначение элементов, а внешний вид и поведение можно независимо реализовать через CSS и JavaScript

---

## инструменты, которые помогают соблюдать convention

- на практике style guide редко поддерживается только внимательностью разработчиков

- **formatter** автоматически приводит код к единому формату

- популярный пример — Prettier

- **linter** проверяет потенциальные ошибки и нарушения правил

- для JavaScript часто используется ESLint

- для HTML также могут использоваться специализированные линтеры

- благодаря этому часть style guide превращается из договорённости «старайся писать правильно» в автоматически проверяемое правило

---

## что важно понимать на собеседовании

- style guide — это **общие правила оформления и организации кода**

- coding convention — это **конкретные соглашения, которым разработчики следуют при написании кода**

- хороший HTML должен быть семантичным, предсказуемым и доступным

- `<button>` используется для действия, `<a>` — для навигации

- `class` предназначен для повторно используемых групп элементов, `id` должен быть уникальным

- HTML отвечает за структуру и смысл, CSS — за внешний вид, JavaScript — за поведение

- нужно избегать ненужных `<div>`, inline-стилей, inline-JavaScript, устаревших элементов и дублирующихся `id`

- accessibility лучше обеспечивать правильной HTML-семантикой, а не пытаться везде компенсировать ошибки ARIA

- конкретные правила форматирования могут отличаться от проекта к проекту, поэтому **важна не универсальная форма, а единообразие внутри проекта**

### главное, что стоит запомнить

- хороший HTML — это не тот HTML, который просто «выглядит правильно»

- хороший HTML — это код, в котором **структура, смысл, доступность и назначение элементов очевидны как браузеру, так и другому разработчику**
