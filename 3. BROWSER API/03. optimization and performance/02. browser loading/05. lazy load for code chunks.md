# lazy load for code chunks

- Lazy loading — это подход, при котором мы загружаем ресурс не сразу, а только тогда, когда он действительно становится нужен
- в контексте JavaScript речь идёт о code chunks — отдельных частях JavaScript-приложения

## сначала: что такое code chunk

- когда мы собираем frontend-приложение, например с помощью Webpack, Vite или другого bundler, множество JS-модулей могут быть объединены в несколько файлов

```
много модулей
   ↓
bundler
   ↓
chunks
   ↓
app.js
vendor.js
profile.js
admin.js
```

- например, приложение имеет страницы:
  - Home
  - Profile
  - Admin
  - Settings

- пользователю при открытии Home совершенно необязательно сразу загружать код Admin и Settings
- поэтому приложение можно разделить на отдельные chunks
  - main.js
  - home.js
  - profile.js
  - admin.js
  - settings.js

## проблема обычной загрузки

- без lazy loading браузер может скачать весь необходимый JavaScript сразу

```
открываем Home
     ↓
скачиваем
     ↓
main.js
profile.js
admin.js
settings.js
     ↓
пользователь получил много JS
```

- часть этого кода может вообще никогда не понадобиться
- например, пользователь посетил только Home и закрыл сайт
- получается, мы потратили сетевой трафик и время на загрузку кода, который пользователь даже не использовал

## lazy loading

- при lazy loading мы загружаем chunk только в момент, когда он становится нужен

```
открываем Home
     ↓
загружаем main.js
     ↓
пользователь работает с Home
     ↓
переходит на Admin
     ↓
загружаем admin.js
```

- таким образом, первоначальная загрузка приложения становится меньше

## как это выглядит в JavaScript

- для этого часто используется dynamic import()

```js
import('./admin.js');
```

- в отличие от обычного статического импорта

```js
import adminPanel from './admin.js';
```

- dynamic `import()` возвращает `Promise`

```js
const adminModulePromise = import('./admin.js');
```

- bundler видит такой dynamic import и обычно создаёт отдельный chunk

```
main.js
   +
   └── admin.js → отдельный chunk
```

- этот chunk можно загрузить позже

## пример с кнопкой

- допустим, тяжёлый модуль нужен только после нажатия кнопки

```js
button.addEventListener('click', async () => {
  const editorModule = await import('./editor.js');

  editorModule.openEditor();
});
```

- при первоначальной загрузке editor.js не обязан скачиваться
- он понадобится только после click

```
страница загружается
        ↓
     main.js
        ↓
пользователь нажимает кнопку
        ↓
import('./editor.js')
        ↓
browser → server
        ↓
 editor.js chunk
        ↓
    execute
```

## lazy loading и routing

- один из самых распространённых вариантов — lazy loading страниц
- допустим, есть приложение
  - Home
  - Products
  - Profile
  - Admin

- вместо загрузки кода всех страниц сразу можно загружать код конкретной страницы при переходе на неё

```
Home
 ↓
home chunk

Profile
 ↓
profile chunk

Admin
 ↓
admin chunk
```

- поэтому при первом посещении пользователь получает только необходимый минимум JavaScript

## почему это улучшает performance

- предположим, приложение содержит 2 MB JavaScript
- из них для первой страницы нужны только 300 KB
- без code splitting браузер может получить значительно больший объём кода
- с lazy loading можно сделать примерно так

```
initial load
↓
300 KB

переход в Admin
↓
+500 KB

открытие Editor
↓
+700 KB
```

- пользователь не платит временем загрузки за функциональность, которой пока не использует
- но lazy loading не означает «загрузка бесплатно»
- когда пользователь наконец попросит lazy-loaded chunk, браузеру всё равно придётся его скачать
- например:

```
первый экран
→ быстро

открыли Editor
→ возник дополнительный network request
→ загрузили editor chunk
→ выполнили его
```

- поэтому появляется небольшой loading delay в момент использования функциональности
- задача разработчика — найти хороший баланс

## слишком много маленьких chunks тоже плохо

- нельзя просто сказать: «чем больше chunks, тем лучше»
- если мы разделим приложение на огромное количество крошечных файлов, браузеру придётся делать много отдельных загрузок

```
chunk 1
chunk 2
chunk 3
chunk 4
chunk 5
...
chunk 100
```

- современные HTTP-протоколы сильно уменьшают стоимость множества запросов, но это всё равно не означает, что бесконечное дробление бесплатно
- поэтому bundler обычно пытается разумно группировать модули

## lazy loading vs обычный code splitting

- эти понятия связаны, но не идентичны
- code splitting — разделение JavaScript-кода на отдельные chunks
- lazy loading — загрузка конкретного chunk только тогда, когда он нужен

```
code splitting
↓
создали отдельные chunks

lazy loading
↓
не загружаем chunk до момента необходимости
```

- code splitting создаёт возможность для lazy loading

## lazy loading vs caching

- эти механизмы тоже дополняют друг друга
- первый пользователь может сделать так:

```
Admin
 ↓
download admin chunk
 ↓
cache
```

- при следующем обращении браузер может взять этот chunk из cache
- поэтому комбинация получается очень эффективной:

```
code splitting
      ↓
lazy loading
      ↓
compression
      ↓
caching
```

## где особенно полезен lazy loading

- большие страницы и приложения
- редко используемые функции
- административные панели
- тяжёлые редакторы
- графики и визуализации
- модальные окна со сложной функциональностью
- страницы, которые пользователь посещает редко

## что важно не перепутать

- lazy loading не означает, что JavaScript перестаёт существовать до момента использования
- код уже присутствует в собранном приложении, но находится в отдельном chunk

```
source code
   ↓
bundler
   ↓
main chunk + lazy chunk
                     ↓
              загружается позже
```

- то есть bundler заранее создаёт файл, а браузер получает его только при необходимости

## что нужно запомнить для собеседования

- Lazy loading for code chunks — загрузка отдельных частей JavaScript только тогда, когда они нужны
- обычно это реализуется через dynamic import()
- dynamic import() возвращает Promise
- bundler может превратить dynamic import в отдельный chunk
- часто lazy loading используется для маршрутов и больших компонентов
- преимущество — уменьшается объём JavaScript при initial load
- недостаток — при первом обращении к lazy chunk появляется дополнительная загрузка
- code splitting разделяет код на chunks, а lazy loading откладывает загрузку этих chunks
- хорошая формула для собеседования:

```
Code Splitting
    ↓
разделяем приложение на chunks
    ↓
Lazy Loading
    ↓
загружаем нужный chunk только при необходимости
    ↓
меньше JavaScript при initial load
```
