# subworkers

- **Subworker** — это Worker, который был создан **другим Worker**
- то есть обычно мы представляем такую структуру

```
Main Thread
     │
     │ new Worker()
     ▼
   Worker A
     │
     │ new Worker()
     ▼
   Worker B
```

- здесь `Worker A` называется родительским Worker, а `Worker B` — его subworker

## зачем вообще нужны subworkers

- главный смысл — позволить одному Worker **разделить большую или сложную работу между несколькими Worker**
- например, представим приложение, которому нужно обработать огромный набор данных

```
Main Thread
     │
     ▼
Worker A
     │
     ├────► Worker B — часть данных
     │
     └────► Worker C — другая часть данных
```

- тогда Worker A может выступать координатором, а несколько subworkers выполнять отдельные части вычислений
- это позволяет строить более сложную параллельную обработку

## как Worker создаёт subworker

- внутри обычного Worker можно использовать конструктор `Worker` так же, как в main thread
- например, `worker.js`

```js
const sortingWorker = new Worker('./sorting-worker.js');

sortingWorker.postMessage([5, 2, 8, 1]);
```

- `worker.js` сам является Worker-кодом
- он создаёт ещё один Worker — `sorting-worker.js`

```
Main Thread
     │
     │ new Worker('worker.js')
     ▼
Worker A
     │
     │ new Worker('sorting-worker.js')
     ▼
Worker B
```

- поэтому название **subworker** буквально означает дочерний Worker

## как они взаимодействуют

- communication между ними происходит через тот же механизм сообщений, который мы уже разобрали
- родительский Worker может отправить данные subworker

```js
sortingWorker.postMessage([5, 2, 8, 1]);
```

- subworker получает их

```js
self.onmessage = (event) => {
  const sortedValues = event.data.sort((firstItem, secondItem) => {
      return firstItem - secondItem;
  });

  self.postMessage(sortedValues);
};
```

- затем родительский Worker получает результат

```js
sortingWorker.onmessage = (event) => {
  self.postMessage(event.data);
};
```

- а затем уже отправляет результат main thread

```
Main Thread
     │
     │ данные
     ▼
Worker A
     │
     │ данные
     ▼
Worker B
     │
     │ результат
     ▼
Worker A
     │
     │ результат
     ▼
Main Thread
```

## важный момент: main thread не общается с subworker напрямую

- в такой архитектуре subworker создаётся и контролируется родительским Worker

```
Main Thread
     │
     ▼
Worker A
     │
     ▼
Worker B
```

- поэтому типичный путь коммуникации выглядит так

```
Main Thread
      ↕
 Worker A
      ↕
 Worker B
```

- Worker A выступает посредником между main thread и Worker B
- при этом технически коммуникацию можно организовывать и другими способами через доступные механизмы коммуникации, но для базового понимания важно запомнить именно иерархию создания

## subworker тоже имеет собственный контекст

- Worker B не наследует переменные Worker A
- например, если в Worker A есть

```js
const batchSize = 1000;
```

- Worker B не сможет просто обратиться к

```js
console.log(batchSize);
```

- потому что Worker B тоже работает в собственном JavaScript-контексте

```
Worker A
│
├── batchSize
├── свои переменные
└── свой глобальный контекст

Worker B
│
├── свои переменные
└── свой глобальный контекст
```

- данные между ними также нужно передавать через сообщения

## сколько subworkers можно создать

- браузер не устанавливает универсальное правило вроде «у одного Worker может быть ровно N subworkers»
- Worker может создавать другие Worker, но фактическое количество разумно ограничивать архитектурой приложения и доступными ресурсами устройства
- каждый дополнительный Worker потенциально создаёт дополнительную нагрузку

```
Main Thread
     │
     ▼
Worker A
  ├── Worker B
  ├── Worker C
  ├── Worker D
  └── Worker E
```

- поэтому создание большого количества Worker не означает автоматически, что приложение станет быстрее
- если создать слишком много потоков, они начнут конкурировать за CPU и память

## важное ограничение: origin

- для создания subworker применяются требования безопасности браузера
- URL скрипта subworker должен удовлетворять правилам загрузки ресурсов для Worker
- в частности, нельзя просто считать, что Worker может без ограничений загрузить любой JavaScript-файл из любого места
- в реальных проектах это особенно важно при работе с bundler'ами, CSP и разными origin

## зачем это может понадобиться на практике

- subworkers могут быть полезны, когда задача естественным образом разбивается на независимые части
- например

```
огромный массив
      │
      ▼
Worker A — распределяет работу
      │
      ├────► Worker B — элементы 0–999
      ├────► Worker C — элементы 1000–1999
      └────► Worker D — элементы 2000–2999
```

- после завершения Worker A может объединить результаты

```
Worker B ──┐
Worker C ──┼──► Worker A ──► Main Thread
Worker D ──┘
```

- это уже напоминает простую модель распределённых вычислений внутри браузера

## но есть важный практический нюанс

- в современном frontend-разработке не стоит воспринимать subworkers как способ автоматически «ускорить любой код»
- создание потоков, передача данных между ними, копирование данных и координация результатов тоже требуют ресурсов
- поэтому сначала нужно понять, действительно ли задача является CPU-bound и хорошо ли она параллелится
- например, если работа занимает 1 миллисекунду, создание дополнительного Worker может оказаться дороже самой работы
- если же нужно обработать огромный объём независимых данных, параллелизация уже может иметь смысл

## жизненный цикл

- subworker живёт независимо от main thread, но его жизненный цикл связан с родительским Worker
- условно

```
Main Thread
     │
     ▼
Worker A создан
     │
     ▼
Worker A создаёт Worker B
     │
     ▼
Worker B работает
     │
     ▼
Worker A завершает работу
```

- здесь важно помнить, что Worker B является ресурсом, который тоже нужно учитывать при завершении архитектуры

## главное для собеседования

- **Subworker — это Worker, созданный другим Worker**
- Worker может создавать другие Worker через `new Worker(...)`
- subworker имеет собственный JavaScript-контекст
- переменные родительского Worker автоматически subworker не видит
- обмен данными между Worker и subworker также выполняется через messaging
- subworkers позволяют разбивать тяжёлую работу на несколько независимых частей
- создание большого количества Worker не гарантирует ускорение и может увеличить расход CPU и памяти
- концептуально нужно держать в голове такую картину

```
       Main Thread
            │
            ▼
       Worker A
      /    |    \
     /     |     \
    ▼      ▼      ▼
Worker B Worker C Worker D
```
