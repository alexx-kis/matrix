# dependencies duplication в npm

- Dependencies duplication — это ситуация, когда в проекте одна и та же библиотека оказывается установленной несколько раз, иногда в разных версиях
- это важно для performance, потому что дублирующийся код увеличивает размер node_modules, а иногда и размер итогового JavaScript bundle
- сначала разберём, почему вообще возникает duplication
- представим, что наше приложение напрямую использует библиотеку library-a

```
my-app
└── library-a
```

- но library-a сама зависит от library-b

```
my-app
└── library-a
    └── library-b
```

- теперь представим, что наше приложение ещё напрямую использует library-b

```
my-app
├── library-a
│   └── library-b
└── library-b
```

- здесь уже потенциально получается две установки library-b

### а если версии разные

- вот здесь duplication становится особенно очевидной

```
my-app
├── library-a
│   └── library-b@1.0.0
└── library-b@2.0.0
```

- library-a требует library-b версии 1.x
- наше приложение требует library-b версии 2.x
- npm не может просто заменить одну версию другой, потому что library-a может зависеть от конкретного API версии 1.x
- поэтому обе версии могут оказаться установленными

```
node_modules/
├── library-a/
│
└── library-b/          ← версия 2.x

library-a/node_modules/
└── library-b/          ← версия 1.x
```

- получается две копии одной dependency

## почему npm не всегда может объединить зависимости

- npm пытается deduplicate зависимости, то есть использовать одну установку там, где это безопасно
- но сделать это можно только если версии совместимы с требованиями всех зависимостей
- например

```
app
├── library-a → library-b ^1.0.0
└── library-c → library-b ^1.2.0
```

- обе зависимости допускают одну и ту же версию library-b
- npm может установить одну общую копию

```
node_modules/
├── library-a/
├── library-c/
└── library-b/
```

- это уже deduplication

### пример, когда deduplication невозможна

- допустим

```
library-a → library-b ^1.0.0
library-c → library-b ^2.0.0
```

- одна dependency требует 1.x
- другая требует 2.x
- одна версия не может одновременно удовлетворять обоим требованиям
- поэтому структура может выглядеть так

```
node_modules/
├── library-a/
│   └── node_modules/
│       └── library-b@1.x
│
├── library-c/
│   └── node_modules/
│       └── library-b@2.x
```

## почему это проблема

- первая проблема — размер node_modules
- если одна dependency занимает 500 KB, а мы установили две её версии, потенциально получаем примерно

```
500 KB + 500 KB = 1 MB
```

- для самого node_modules это может быть не очень страшно, особенно на диске разработчика
- гораздо важнее другое — может ли дублированный код попасть в production bundle
- duplication в node_modules ≠ duplication в bundle
- это очень важное различие
- две версии пакета могут существовать в node_modules

```
node_modules/
├── library-b/
└── library-a/
    └── node_modules/
        └── library-b/
```

- но это не означает автоматически, что обе версии попадут в browser bundle
- bundler анализирует реальные imports и dependency graph
- если используется только одна версия, другая может вообще не попасть в production bundle
- поэтому нужно разделять

```
dependency duplication
        ↓
несколько копий пакета в dependency tree

bundle duplication
        ↓
несколько копий кода реально попали в итоговый JavaScript bundle
```

## почему duplication особенно неприятна для browser bundle

- представим, что две разные библиотеки используют разные версии одной utility-библиотеки

```
app
├── library-a
│   └── utility-lib@1
│
└── library-b
    └── utility-lib@2
```

- bundler может быть вынужден включить обе версии

```
bundle.js
├── utility-lib@1
├── utility-lib@2
├── library-a
└── library-b
```

- тогда один и тот же функционал в разных версиях фактически присутствует дважды
- это увеличивает размер bundle и, соответственно, количество данных, которые браузер должен скачать и обработать

## что такое npm deduplication

- npm предоставляет команду `npm dedupe`
- она пытается изменить dependency tree так, чтобы совместимые версии зависимостей использовали общие установки
- например было

```
node_modules/
├── library-a/
│   └── node_modules/
│       └── utility-lib@1.2.0
│
└── utility-lib@1.2.0
```

- если обе зависимости совместимы с одной версией, npm может поднять зависимость выше

```
node_modules/
├── library-a/
└── utility-lib@1.2.0
```

- теперь library-a тоже может использовать общую копию utility-lib

## почему это вообще работает

- здесь важно понимать механизм поиска модулей в Node.js
- когда dependency выполняет `require("utility-lib");`, Node.js ищет пакет в соответствующих node_modules
- если подходящий пакет найден выше по дереву, его можно использовать
- поэтому не обязательно иметь отдельную копию внутри каждого пакета
- в современных npm-проектах конкретная структура зависит от версии npm и алгоритма установки, но общая идея именно такая — совместимые зависимости можно поднять выше и разделить между пакетами

## package-lock.json

- ещё одна важная часть темы — package-lock.json
- он фиксирует конкретное dependency tree проекта
- например, package может требовать

```
{
  "dependencies": {
    "utility-lib": "^1.2.0"
  }
}
```

- символ ^ означает, что допустимы определённые совместимые версии
- npm при установке выбирает конкретную версию и записывает результат в lockfile
- поэтому два проекта с одинаковым package.json могут без lockfile получить немного разные dependency trees

## как обнаружить duplication

- один из удобных инструментов npm `npm ls`
- он показывает dependency tree
- например

```
npm ls utility-lib
```

- можно увидеть, где именно используется utility-lib и какие версии установлены
- также полезна команда `npm dedupe --dry-run`
- она позволяет посмотреть, какие изменения npm потенциально может выполнить при deduplication

## duplication и semver

- здесь очень важно понимать связь с SemVer
- допустим dependency требует `utility-lib ^1.2.0`
- другая требует `utility-lib ^1.5.0`
- эти требования могут быть удовлетворены одной версией, например 1.8.0

```
^1.2.0 → подходит 1.8.0
^1.5.0 → подходит 1.8.0
```

- тогда npm может использовать одну копию
- но если требования такие

```
^1.2.0
^2.0.0
```

- одной версии уже недостаточно

```
1.x ≠ 2.x
```

- поэтому duplication становится необходимой

## почему нельзя просто всегда поставить последнюю версию

- потому что разные версии dependency могут иметь несовместимые изменения API
- например library-a ожидает `utilityLib.oldMethod();`
- а новая версия библиотеки этот метод удалила
- если npm принудительно заменит старую версию на новую, library-a может перестать работать
- поэтому наличие нескольких версий иногда является правильным и необходимым поведением, а не ошибкой npm

## связь с performance

- здесь появляется связь с предыдущей темой

```
dependencies
      ↓
dependency tree
      ↓
duplicate packages
      ↓
potentially duplicate code
      ↓
larger bundle
      ↓
more bytes over network
      ↓
worse loading performance
```

- поэтому при оптимизации production bundle разработчик может искать дублирующиеся dependencies
- особенно неприятно, когда одна и та же большая библиотека попала в bundle в нескольких версиях

## как уменьшать duplication

- сначала нужно понять, действительно ли существуют разные версии `npm ls`
- затем можно попробовать deduplication `npm dedupe`
- иногда нужно обновить зависимости, чтобы они использовали совместимые версии одной библиотеки
- иногда можно заменить dependency на более лёгкую альтернативу
- иногда проблему решает настройка bundler'а, который умеет разрешать одинаковые модули к одному источнику

## связь с tree shaking

- это две разные оптимизации

```
tree shaking
    ↓
удаляет НЕИСПОЛЬЗУЕМЫЙ код

deduplication
    ↓
старается не иметь НЕСКОЛЬКО КОПИЙ одного и того же кода
```

- например, у нас есть библиотека

```
utility-lib
├── add
├── subtract
├── multiply
└── divide
```

- tree shaking может оставить только

```
utility-lib
└── add
```

- а deduplication решает другую проблему

```
utility-lib@1
utility-lib@1
```

- и пытается превратить её в

```
utility-lib@1
```

- поэтому они прекрасно могут работать вместе

```
deduplication
       ↓
одна версия dependency
       ↓
tree shaking
       ↓
из неё остаётся только нужный код
       ↓
minification
       ↓
код становится компактнее
       ↓
Brotli
       ↓
меньше данных по сети
```

## что нужно запомнить для собеседования

- Dependencies duplication — наличие нескольких копий одной dependency, часто разных версий, в dependency tree
- duplication возникает, когда разные пакеты требуют несовместимые версии одной зависимости
- npm старается выполнять deduplication, когда это безопасно
- npm dedupe пытается уменьшить количество дублирующихся установок
- наличие нескольких версий в node_modules не означает автоматически, что несколько копий попадут в browser bundle
- если разные версии реально попали в bundle, это может увеличить его размер
- `npm ls <package>` помогает увидеть, где и какие версии dependency используются
- tree shaking удаляет неиспользуемый код, а deduplication старается устранить несколько копий одной dependency
- duplication иногда неизбежна, потому что разные пакеты могут требовать несовместимые версии
