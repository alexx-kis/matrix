# tree shaking for dependencies

- Tree shaking — это оптимизация, при которой bundler удаляет из итогового bundle тот JavaScript-код, который фактически нигде не используется
- название происходит от идеи «встряхнуть дерево» и оставить только те ветки, которые нужны
- для production это важно, потому что мы можем установить большую библиотеку, использовать из неё только несколько функций, а в итоговый bundle постараться положить только используемый код
- сначала разберём проблему
- представим, что у нас есть файл библиотеки

```js
export function addNumbers(firstValue, secondValue) {
  return firstValue + secondValue;
}

export function subtractNumbers(firstValue, secondValue) {
  return firstValue - secondValue;
}

export function multiplyNumbers(firstValue, secondValue) {
  return firstValue * secondValue;
}
```

- а в нашем приложении нужна только addNumbers

```js
import { addNumbers } from './mathUtils.js';

console.log(addNumbers(2, 3));
```

- без tree shaking bundler потенциально мог бы положить в bundle весь mathUtils.js
- тогда в bundle окажутся и subtractNumbers, и multiplyNumbers, хотя приложение их вообще не использует

## что делает tree shaking

- bundler анализирует зависимости и определяет, какой экспорт реально используется
- в нашем примере используется только `addNumbers`
- поэтому неиспользуемые части можно удалить

```
mathUtils.js
│
├── addNumbers       ← используется
├── subtractNumbers  ← не используется
└── multiplyNumbers  ← не используется
```

- после tree shaking логически остаётся только

```js
function addNumbers(firstValue, secondValue) {
  return firstValue + secondValue;
}
```

- именно поэтому tree shaking можно воспринимать как удаление мёртвого кода из dependency graph

## почему здесь слово dependencies

- dependencies — это сторонние библиотеки, которые наше приложение устанавливает и использует
- например, условно у проекта есть

```
my-app
│
├── react
├── lodash
├── date-fns
└── some-ui-library
```

- мы можем использовать только небольшую часть функциональности каждой библиотеки
- tree shaking позволяет bundler'у попытаться исключить неиспользуемые части из production bundle

## dependency graph

- чтобы понять tree shaking, важно вспомнить, что bundler строит граф зависимостей
- например

```
main.js
   │
   ├── mathUtils.js
   │      ├── addNumbers
   │      ├── subtractNumbers
   │      └── multiplyNumbers
   │
   └── userUtils.js
```

- bundler начинает с entry point и анализирует, какие модули и какие exports нужны

- всё, что невозможно достичь через используемые импорты, потенциально можно удалить

## почему import и export здесь особенно важны

- tree shaking особенно хорошо работает с ES Modules

```js
export function addNumbers(firstValue, secondValue) {
  return firstValue + secondValue;
}

export function subtractNumbers(firstValue, secondValue) {
  return firstValue - secondValue;
}
```

- затем

```js
import { addNumbers } from './mathUtils.js';
```

- здесь структура зависимости понятна уже на этапе анализа кода
- bundler видит, что из mathUtils.js импортируется именно addNumbers
- это одна из причин, почему ES Modules хорошо подходят для tree shaking

## почему `import *` не обязательно ломает tree shaking

- часто возникает неправильная мысль, что tree shaking работает только при таком импорте

```js
import { addNumbers } from './mathUtils.js';
```

- а при таком обязательно забирается всё

```js
import * as mathUtils from './mathUtils.js';
```

- на самом деле всё зависит от того, как именно используется namespace и насколько хорошо bundler может проанализировать код
- поэтому правильнее запомнить не правило «`import *` ломает tree shaking», а принцип: bundler должен иметь возможность статически определить, какие exports реально нужны

## почему CommonJS сложнее

- старый CommonJS использует конструкцию

```js
const mathUtils = require('./mathUtils.js');
```

- здесь анализ зависимостей может быть сложнее, потому что CommonJS допускает более динамические конструкции
- например

```js
const moduleName = getModuleName();
const selectedModule = require(moduleName);
```

- bundler заранее не обязательно знает, какой именно модуль будет загружен
- поэтому статический анализ и tree shaking становятся значительно сложнее
- именно поэтому для tree shaking особенно удобны статические ES Modules

## tree shaking не означает «удалить всё неиспользуемое на глаз»

- bundler должен учитывать side effects
- например

```js
console.log('module loaded');

export function addNumbers(firstValue, secondValue) {
  return firstValue + secondValue;
}
```

- здесь addNumbers может вообще не использоваться
- но импорт самого модуля может иметь побочный эффект

```js
import './mathUtils.js';
```

- при удалении всего файла мы потеряем

```js
console.log('module loaded');
```

- поэтому bundler должен понимать, какие части можно безопасно удалить, а какие могут иметь side effects

## что такое side effect

- side effect — действие, которое происходит просто из-за выполнения кода и может влиять на окружающий мир

```js
document.body.classList.add('loaded');
```

- этот код ничего не экспортирует, но он изменяет DOM
- поэтому просто сказать «никто эту функцию не импортировал — удаляем файл» было бы неправильно

## sideEffects в package.json

- библиотеки могут сообщать bundler'у информацию о side effects через package.json

- например

```
{
    "sideEffects": false
}
```

- это означает примерно "модули этого пакета не должны иметь побочных эффектов при импорте, поэтому неиспользуемый код можно безопаснее удалять"

- это очень важная информация для tree shaking dependencies

- также можно указать конкретные файлы, которые имеют side effects

```
{
    "sideEffects": [
        "*.css"
    ]
}
```

- тогда bundler понимает, что CSS нельзя просто выбросить как неиспользуемый JavaScript-модуль

## tree shaking и minification

- эти две темы связаны, но это разные оптимизации

```
source code
     ↓
bundle
     ↓
tree shaking
     ↓
удаление неиспользуемого кода
     ↓
minification
     ↓
сокращение оставшегося кода
     ↓
compression
     ↓
сжатие для передачи по сети
```

- например, tree shaking может удалить

```js
function subtractNumbers() {
  // ...
}

function multiplyNumbers() {
  // ...
}
```

- а minification уже может превратить оставшийся код

```js
function addNumbers(firstValue, secondValue) {
  return firstValue + secondValue;
}
```

- в

```
function addNumbers(e,t){return e+t}
```

- то есть tree shaking уменьшает количество кода, а minification уменьшает размер самого оставшегося кода

## важный практический пример с библиотекой

- допустим, dependency предоставляет много функций

```
some-library
│
├── formatDate
├── parseDate
├── addDays
├── subtractDays
├── formatCurrency
├── formatNumber
└── ...
```

- наше приложение использует только

```js
import { formatDate } from 'some-library';
```

- при хорошо поддерживаемом tree shaking bundler может включить в production bundle только необходимые части dependency
- остальные функции не попадут в итоговый bundle
- но tree shaking не всегда может спасти большую dependency
- если библиотека устроена так, что весь её код должен выполняться или она использует динамические конструкции, bundler может быть не способен безопасно удалить ненужные части
- поэтому две библиотеки с одинаковой функциональностью могут давать совершенно разный размер production bundle
- например, условно

```
library A
100 KB
↓
tree shaking
↓
10 KB

library B
100 KB
↓
tree shaking
↓
90 KB
```

- это одна из причин, почему при выборе dependencies важно смотреть не только на API библиотеки, но и на то, насколько хорошо она поддерживает современные module formats и tree shaking

## что нужно запомнить для собеседования

- Tree shaking — удаление неиспользуемого кода из итогового bundle
- особенно полезен для больших dependencies
- лучше всего работает со статически анализируемыми ES Modules
- bundler анализирует import и export и строит dependency graph
- неиспользуемые exports могут быть удалены
- bundler должен учитывать side effects, поэтому нельзя просто удалить любой неиспользуемый модуль
- поле sideEffects в package.json помогает bundler'у принимать такие решения
- tree shaking и minification — разные вещи
- tree shaking уменьшает количество кода
- minification уменьшает размер оставшегося кода
- после этого compression вроде Brotli дополнительно уменьшает объём данных при передаче по сети
