# dynamic compression vs static

- здесь мы продолжаем тему compression, но теперь разбираемся не в том, как сжимать данные, а в том, когда именно сервер выполняет compression
- есть два основных подхода — **dynamic compression** и **static compression**

## dynamic compression

- Dynamic compression — это когда сервер получает обычный файл, сжимает его во время обработки HTTP-запроса, а затем отправляет клиенту сжатую версию

```
browser
   │
   │ GET /app.js
   ↓
server
   │
   │ читает app.js
   │ сжимает его
   ↓
compressed app.js
   │
   ↓
browser
```

- например, на сервере лежит

```
app.js
300 KB
```

- браузер запрашивает его
- сервер запускает алгоритм Brotli или gzip
- получает, например `app.js → 90 KB`
- и отправляет эти 90 KB

## преимущество dynamic compression

- главное преимущество — гибкость
- сервер может принимать решение о compression непосредственно во время запроса
- например, браузер сообщает

```
Accept-Encoding: br, gzip
```

- сервер может выбрать Brotli
- другой клиент может поддерживать только gzip
- тогда сервер может сжать тот же ресурс с помощью gzip

```
          app.js
            │
    ┌───────┴───────┐
    ↓               ↓
supports br     supports gzip
    ↓               ↓
Brotli          gzip
```

- поэтому dynamic compression особенно удобна для контента, который генерируется или изменяется динамически

## недостаток dynamic compression

- compression требует вычислительных ресурсов
- сервер должен выполнить работу при каждом запросе, если сжатая версия не была закэширована

```
request 1 → compress → response
request 2 → compress → response
request 3 → compress → response
```

- если сервер получает тысячи запросов, ему приходится выполнять много одинаковой работы
- особенно бессмысленно постоянно заново сжимать файл, который вообще не изменился

## static compression

- Static compression — это когда файл сжимается заранее, например во время build/deploy, а сервер потом просто отдаёт уже готовую сжатую версию

```
build time
    │
    ↓
 app.js
    │
    ↓
 Brotli
    │
    ↓
app.js.br
    │
    ↓
 deploy
    │
    ↓
 server
```

например, после production build у нас может быть

```
dist/
├── app.js
└── app.js.br
```

- `app.js.br` — уже заранее сжатая версия app.js

- когда приходит запрос:

```
browser
   │
   │ GET /app.js
   ↓
server
   │
   │ берёт app.js.br
   ↓
browser
```

- серверу не нужно заново запускать Brotli для каждого запроса

## почему static compression хорошо подходит для frontend

- production JavaScript обычно является статическим ресурсом
- после build файл вроде `app.js` обычно не меняется до следующего deployment, поэтому имеет смысл сделать

```
app.js
   ↓
Brotli
   ↓
app.js.br
```

- один раз во время build/deploy, а затем использовать готовый результат для большого количества пользователей

## главное различие

### dynamic compression

```
request
   ↓
compress
   ↓
response
```

### static compression

```
build/deploy
   ↓
compress
   ↓
compressed file
   ↓
request
   ↓
response
```

- в dynamic compression работа выполняется во время запроса
- в static compression работа выполняется заранее

### сравним на примере

- допустим, production bundle имеет размер 1 MB

#### dynamic compression

```
build
 ↓
app.js = 1 MB

request
 ↓
server compresses 1 MB
 ↓
200 KB
 ↓
browser
```

- следующий пользователь снова делает запрос

```
request
 ↓
server compresses 1 MB
 ↓
200 KB
 ↓
browser
```

- если нет подходящего кэша, сервер снова выполняет compression

#### static compression

```
build
 ↓
app.js = 1 MB
 ↓
Brotli
 ↓
app.js.br = 200 KB
 ↓
deploy
```

- затем

```
user 1 → app.js.br → 200 KB
user 2 → app.js.br → 200 KB
user 3 → app.js.br → 200 KB
```

- сервер просто отдаёт уже подготовленный файл

#### но static compression не означает, что существует только одна версия

- здесь появляется важный нюанс
- браузеры могут поддерживать разные алгоритмы
- например

```
Accept-Encoding: br, gzip
```

- поэтому build-система может заранее создать несколько вариантов

```
dist/
├── app.js
├── app.js.gz
└── app.js.br
```

- сервер выбирает подходящий вариант

```
browser supports Brotli
        ↓
app.js.br

browser supports gzip
        ↓
app.js.gz

browser supports neither
        ↓
app.js
```

## зачем вообще оставлять исходный файл

- потому что не каждый клиент обязательно поддерживает конкретный алгоритм compression
- сервер должен иметь возможность отправить обычный файл, если сжатый вариант использовать нельзя
- поэтому итоговая структура может выглядеть так

```
app.js
app.js.br
app.js.gz
```

## dynamic и static можно комбинировать

- на практике это не обязательно строгое «или/или»
- например, CDN или reverse proxy может использовать заранее созданные .br и .gz файлы, а если подходящего варианта нет — выполнить compression динамически

```
             request
                ↓
             server
                │
       ┌────────┴────────┐
       ↓                 ↓
precompressed file   no precompressed
       ↓                 ↓
  отдаём сразу       compress
       │                 │
       └────────┬────────┘
                ↓
             browser
```

## как это связано с frontend build

- для frontend-приложения типичный production pipeline может выглядеть так

```
    source code
          ↓
      bundling
          ↓
    tree shaking
          ↓
    minification
          ↓
       app.js
          ↓
   Brotli / gzip
          ↓
app.js.br / app.js.gz
          ↓
    CDN / server
          ↓
       browser
```

- здесь особенно хорошо видно различие между предыдущими темами
- tree shaking удаляет неиспользуемый код
- minification уменьшает размер JavaScript-кода
- static compression заранее сжимает получившийся файл
- dynamic compression сжимает файл непосредственно во время HTTP-запроса

## что выгоднее

- для больших статических frontend-файлов обычно очень выгодна static compression, потому что ресурсы можно сжать один раз и затем многократно отдавать
- dynamic compression полезна, когда контент создаётся динамически или заранее создавать все варианты файлов неудобно

|                                         | dynamic compression | static compression |
| --------------------------------------- | ------------------- | ------------------ |
| когда сжимается                         | во время запроса    | заранее            |
| нагрузка на сервер                      | выше                | ниже               |
| подходит для статических JS/CSS         | можно               | очень хорошо       |
| подходит для динамического контента     | очень хорошо        | хуже               |
| нужны заранее подготовленные файлы      | нет                 | да                 |
| одинаковый файл можно сжимать много раз | да                  | нет                |

## что нужно запомнить для собеседования

- Dynamic compression — ресурс сжимается во время HTTP-запроса
- Static compression — ресурс заранее сжимается во время build/deploy
- dynamic compression гибче, но требует CPU во время обработки запросов
- static compression позволяет один раз выполнить дорогую операцию и потом отдавать готовый результат
- для статических frontend-ресурсов вроде JS, CSS и HTML static compression часто очень эффективна
- могут заранее создаваться app.js.br и app.js.gz
- сервер выбирает подходящий вариант в зависимости от Accept-Encoding
- важно не путать static compression с HTTP caching — compression отвечает за размер передаваемых данных, а caching позволяет вообще не передавать ресурс повторно, если он уже есть у клиента
