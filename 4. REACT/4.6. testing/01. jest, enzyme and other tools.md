# testing в React: Jest, Enzyme и другие инструменты

- этот блок посвящён тестированию React-приложений: от понимания того, зачем нужны тесты, до проверки компонентов, утилит, HOC, модальных окон и проектирования стратегии тестирования

## 1. что такое тестирование и зачем оно нужно

- тестирование — это проверка того, что программа ведёт себя ожидаемым образом при определённых входных данных, действиях пользователя и условиях выполнения
- представим, что в приложении есть функция расчёта скидки, React-компонент кнопки и форма регистрации — все три сущности можно тестировать, но подходы будут различаться

```js
function calculateDiscount(price, discountPercent) {
  return price - (price * discountPercent) / 100;
}

console.log(calculateDiscount(1000, 20)); // 800
```

- для этой функции можно проверить, что при цене `1000` и скидке `20%` результат равен `800`
- для React-компонента можно проверить, что кнопка отображается с правильным текстом и вызывает обработчик при нажатии
- для формы можно проверить, что пользователь видит ошибку при некорректном вводе и может отправить корректные данные

### 1.1. основные виды тестирования

- unit-тесты (модульные тесты) проверяют небольшие изолированные единицы кода: функции, преобразования данных, отдельные алгоритмы или простые модули
- integration-тесты (интеграционные тесты) проверяют взаимодействие нескольких частей системы, например React-компонента с контекстом, Redux store или API-слоем
- end-to-end-тесты (E2E) проверяют сценарии приложения с точки зрения пользователя, обычно через браузер: открытие страницы, заполнение формы, отправку запроса и отображение результата
- границы между уровнями не абсолютно строгие — тестирование компонента с несколькими дочерними компонентами может быть интеграционным, хотя технически он запускается в тестовом окружении React

### 1.2. что даёт тестирование

- регрессионная защита — тесты помогают обнаружить ситуацию, когда изменение существующего кода сломало ранее работавшую функциональность
- быстрая обратная связь — вместо ручной проверки десятков сценариев разработчик может запустить автоматические проверки
- документация поведения — тесты показывают, как предполагается использовать функцию или компонент и какой результат ожидается
- поддержка рефакторинга — тесты позволяют менять внутреннюю реализацию, проверяя, что внешнее поведение осталось прежним
- уверенность при разработке — при этом тесты не доказывают отсутствие всех ошибок, а только проверяют конкретные сценарии и утверждения

## 2. Jest, Enzyme и другие инструменты

- Jest и Enzyme решают разные задачи, и важно не смешивать их роли

### Jest

- тестовый фреймворк: запускает тесты, предоставляет assertions, mocks, spies и инструменты для организации тестового окружения
- может тестировать обычный JavaScript, утилиты и React-компоненты

### Enzyme

- библиотека для тестирования React-компонентов, исторически популярная в проектах с классовыми компонентами
- предоставляет API для поверхностного рендеринга и исследования структуры компонентов
- сейчас это преимущественно инструмент для понимания legacy-проектов: поддержка современных версий React ограничена

### React Testing Library

- помогает тестировать компоненты через то, что доступно пользователю: текст, роли элементов, подписи и взаимодействия
- обычно используется вместе с Jest или Vitest
- для новых React-проектов часто предпочтительнее Enzyme

### Playwright и Cypress

- инструменты для браузерных и E2E-тестов
- позволяют взаимодействовать с реальной страницей, проверять навигацию, пользовательские сценарии и интеграцию с сервером

### 2.1. что именно предоставляет Jest

- Jest объединяет несколько инструментов, которые в других экосистемах могут предоставляться разными библиотеками
- test runner — находит тесты и выполняет их
- assertions — проверяет ожидаемые результаты через `expect`
- mocks — позволяют заменить реальную функцию или зависимость контролируемой реализацией
- spies — позволяют отслеживать вызовы функции, переданные аргументы и количество вызовов
- setup и teardown — выполняют подготовку и очистку до или после тестов
- snapshot testing — позволяет сравнивать сериализованное представление результата с сохранённым эталоном
- coverage — собирает информацию о том, какой код был выполнен во время тестирования
- Jest сам по себе не является браузером и не превращает любой тест в полноценный E2E-тест
- React-компоненты обычно тестируют в DOM-окружении, например `jsdom`, которое имитирует значительную часть браузерного DOM, но не является полноценным браузером

### 2.2. базовая структура Jest-теста

```js
function sumNumbers(a, b) {
  return a + b;
}

describe('sumNumbers', () => {
  test('adds two numbers', () => {
    expect(sumNumbers(2, 3)).toBe(5);
  });
});
```

- `describe` группирует связанные тесты
- `test` или его псевдоним `it` описывает отдельный сценарий
- `expect` получает фактический результат
- `toBe(5)` — matcher, который проверяет ожидаемое значение
- когда Jest запускает тест, он выполняет функцию внутри `test` и считает проверку успешной, если ни одна проверка не завершилась ошибкой и тест не выбросил необработанную ошибку
- в реальном проекте этот тест обычно располагают в файле вроде `sumNumbers.test.js` или `sumNumbers.spec.js`, а запускают через настроенный npm-скрипт, например `npm test`

### 2.3. основные matchers

```js
expect(2 + 3).toBe(5);
expect({ name: 'Alex' }).toEqual({ name: 'Alex' });
expect(['react', 'jest']).toContain('jest');
expect(null).toBeNull();
expect(true).toBeTruthy();
expect(() => {
  throw new Error('Invalid input');
}).toThrow('Invalid input');
```

- `toBe` обычно проверяет примитивные значения через `Object.is` и идентичность ссылок для объектов
- `toEqual` сравнивает структуру значений
- `toContain` проверяет наличие элемента в массиве или подстроки в строке
- `toBeNull` проверяет именно `null`
- `toBeTruthy` проверяет truthy-значение, но не доказывает, что оно равно конкретному ожидаемому значению
- `toThrow` проверяет, что вызов функции выбрасывает ошибку
- типичная ошибка — использовать слишком общие assertions, которые пропускают дефекты: например, проверять только, что значение truthy, когда по требованиям оно должно равняться `5`

### 2.4. setup и teardown

- иногда перед тестом необходимо создать объект, подготовить данные, очистить DOM или сбросить mock-функции
- Jest предоставляет `beforeEach`, `afterEach`, `beforeAll` и `afterAll`

```js
describe('user service', () => {
  let userStore = [];

  beforeEach(() => {
    userStore = [];
  });

  test('stores a user', () => {
    userStore.push({ id: 1, name: 'Alex' });

    expect(userStore).toHaveLength(1);
  });

  test('starts with an empty store', () => {
    expect(userStore).toHaveLength(0);
  });
});
```

- `beforeEach` выполняется перед каждым тестом в группе
- это помогает не зависеть от порядка запуска тестов
- в примере `userStore` сбрасывается перед каждым тестом, поэтому изменение в первом тесте не влияет на второй
- важно отличать очистку DOM от очистки mock-функций: например, `jest.clearAllMocks()` очищает историю вызовов, но не обязательно сбрасывает реализацию mock-функции
- `jest.resetAllMocks()` сбрасывает реализации mock-функций, а `jest.restoreAllMocks()` восстанавливает оригинальные реализации для совместимых spies, созданных через `jest.spyOn`

### 2.5. mocks и spies

- при тестировании полезно контролировать внешние зависимости, чтобы тест проверял нужное поведение и не зависел от сети, таймеров или стороннего сервиса

```js
function loadUserName(fetchUser, userId) {
  return fetchUser(userId).then((user) => user.name);
}

test('returns the user name', async () => {
  const fetchUserMock = jest.fn().mockResolvedValue({
    id: 7,
    name: 'Alex',
  });

  await expect(loadUserName(fetchUserMock, 7)).resolves.toBe('Alex');

  expect(fetchUserMock).toHaveBeenCalledWith(7);
});
```

- `jest.fn()` создаёт mock-функцию, вызовы которой можно проверять
- `mockResolvedValue` задаёт результат в виде успешно разрешённого Promise
- `toHaveBeenCalledWith(7)` проверяет, что зависимость была вызвана с аргументом `7`
- `resolves` позволяет проверить значение, которое вернёт Promise после успешного завершения
- mock полезен, когда нужно изолировать код от API, времени или нестабильной зависимости
- но если замокать почти всё приложение, тест может проверять только согласованность mock-объектов между собой, а не реальное поведение системы

### 2.6. Enzyme: как тестировали React-компоненты

- Enzyme — библиотека, которая предоставляет API для рендеринга React-компонентов и исследования их структуры
- исторически она была особенно популярна в проектах, где тесты часто обращались к внутренней структуре компонентов, их props и state
- в Enzyme есть три основных способа рендеринга

`shallow()` — поверхностный рендеринг

- рендерит компонент без полноценного рендеринга его дочерних React-компонентов
- подходит для изолированного исследования компонента, но не проверяет полностью взаимодействие родителя с реальным поведением дочерних компонентов

`mount()` — полный рендеринг

- монтирует компонент в DOM-окружение и позволяет исследовать взаимодействия с дочерними компонентами, состоянием и DOM
- полезен для тестирования более сложного поведения, но может требовать дополнительной настройки окружения и очистки

`render()` — статический HTML

- рендерит компонент в статическое HTML-представление, традиционно с использованием Cheerio для исследования результата
- не предоставляет полноценного интерактивного React-окружения для проверки событий и изменений состояния
- пример теста на Enzyme выглядит следующим образом

```js
import { shallow } from 'enzyme';
import Counter from './Counter';

test('renders the counter value', () => {
  const wrapper = shallow(<Counter initialCount={3} />);

  expect(wrapper.find('[data-testid="count"]').text()).toBe('3');
});
```

- `shallow` создаёт обёртку над поверхностно отрендеренным компонентом
- `find` ищет элемент по селектору
- `text` извлекает текстовое содержимое найденного элемента
- важный нюанс: Enzyme-тесты нередко привязаны к внутренней реализации компонента — например, к конкретной структуре дерева, именам дочерних компонентов или способу хранения состояния
- после рефакторинга такой тест может сломаться, хотя пользовательское поведение не изменилось
- для современных проектов с новыми версиями React обычно выбирают React Testing Library, а Enzyme изучают прежде всего для поддержки старого кода и понимания существующих тестовых наборов

### 2.7. React Testing Library: тестирование поведения

- React Testing Library (RTL) предлагает другой подход: тестировать компонент так, как с ним взаимодействует пользователь, а не исследовать его внутреннее устройство
- вместо проверки внутреннего state мы проверяем отображаемый текст, доступность элементов, действия пользователя и результат этих действий
- например, компонент счётчика можно проверить следующим образом

```js
import { useState } from 'react';
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <section>
      <p>Count: {count}</p>
      <button onClick={() => setCount((current) => current + 1)}>Increment</button>
    </section>
  );
}

test('increments the counter when the user clicks the button', async () => {
  const user = userEvent.setup();

  render(<Counter />);

  expect(screen.getByText('Count: 0')).toBeInTheDocument();

  await user.click(screen.getByRole('button', { name: 'Increment' }));

  expect(screen.getByText('Count: 1')).toBeInTheDocument();
});
```

- `render` помещает компонент в тестовое DOM-окружение
- `screen` предоставляет методы поиска элементов в этом DOM
- `getByRole('button', { name: 'Increment' })` находит кнопку по доступной роли и имени
- `userEvent.setup()` создаёт объект для имитации пользовательских действий
- `await user.click(...)` выполняет взаимодействие, после которого React может обновить интерфейс
- `toBeInTheDocument()` проверяет, что элемент присутствует в DOM; этот matcher предоставляется библиотекой `@testing-library/jest-dom`
- здесь тест проверяет не то, что `setCount` вызван или что внутреннее состояние равно `1`, а то, что пользователь действительно видит новое значение
- при этом `userEvent` не является полноценным браузером: некоторые особенности реального браузерного поведения, layout и интеграции с окружением требуют E2E-тестов

### 2.8. основные методы поиска элементов в RTL

- `getBy...` — ищет элемент сразу и выбрасывает ошибку, если найдено ноль или больше одного элемента
- `queryBy...` — возвращает `null`, если элемент отсутствует; удобно проверять, что что-то не отображается
- `findBy...` — возвращает Promise и ждёт появления элемента в течение заданного времени; используется для асинхронных обновлений интерфейса
- `getAllBy...`, `queryAllBy...`, `findAllBy...` — соответствующие варианты для поиска нескольких элементов
- пример проверки отсутствующего сообщения

```js
expect(screen.queryByText('Loading...')).not.toBeInTheDocument();
```

- пример ожидания результата после асинхронной загрузки

```js
expect(await screen.findByText('User loaded')).toBeInTheDocument();
```

- частая ошибка — использовать `getByText` сразу после действия, если нужный элемент появляется асинхронно; в таких сценариях лучше подходит `findBy...` или `waitFor`, в зависимости от того, что именно проверяется
- для поиска элементов обычно предпочтительны доступные пользователю признаки: `getByRole`, `getByLabelText`, `getByPlaceholderText`, `getByText`
- `getByTestId` полезен, когда подходящего пользовательского признака нет, но не должен автоматически становиться первым выбором

## 3. базовое понимание написания тестов

- тест обычно состоит из трёх логических частей: Arrange → Act → Assert, то есть подготовка условий, выполнение действия и проверка результата

### Arrange — подготовка

- создаём тестовые данные, настраиваем mocks, рендерим компонент или подготавливаем зависимости

### Act — действие

- вызываем функцию, нажимаем кнопку, вводим текст или выполняем другое действие, поведение которого проверяется

### Assert — проверка

- проверяем возвращаемое значение, DOM, вызовы зависимостей или другое наблюдаемое поведение

- этот шаблон помогает делать тесты понятными: из теста должно быть легко увидеть исходные условия, действие и ожидаемый результат

### 3.1. как выбирать тестовые сценарии

- обычно проверяют не каждую строку кода, а значимые варианты поведения
- позитивный сценарий — корректные входные данные приводят к ожидаемому результату
- негативный сценарий — некорректные данные, ошибки или запрещённые действия обрабатываются правильно
- граничные случаи — пустой массив, ноль, минимальное или максимальное значение, отсутствие необязательного параметра
- переходы состояний — компонент правильно ведёт себя до и после действия пользователя
- асинхронные сценарии — загрузка, ожидание, успешный ответ и ошибка
- например, для функции расчёта скидки стоит проверить обычное значение, скидку `0%`, скидку `100%` и поведение при недопустимых входных данных, если такие ограничения предусмотрены контрактом функции

### 3.2. хорошие и плохие тесты

- хороший тест проверяет конкретное требование и обнаруживает нарушение этого требования
- плохой тест может быть формально успешным, но почти не защищать приложение от реальных дефектов
- например, проверка того, что компонент вообще отрендерился, не гарантирует правильность его содержимого
- проверка вызова внутренней функции не гарантирует, что пользователь увидел результат
- проверка точного HTML или огромного snapshot может создавать много шума при изменениях, не влияющих на поведение
- важно соблюдать баланс: тест должен быть достаточно конкретным, чтобы обнаруживать дефекты, но не настолько привязанным к реализации, чтобы ломаться при безвредном рефакторинге

## 4. тестирование различных сущностей

- в требованиях отдельно указаны компоненты, утилиты, HOC и модальные окна — это важные категории, потому что у каждой из них свой контракт и свои типичные ошибки

### 4.1. тестирование утилит

- утилиты — это функции, которые выполняют самостоятельные операции: преобразование данных, фильтрацию, форматирование, валидацию и вычисления
- обычно их проще всего тестировать, потому что они не требуют React, DOM и браузерного окружения
- рассмотрим функцию фильтрации товаров

```js
function filterProducts(products, query) {
  const normalizedQuery = query.trim().toLowerCase();

  return products.filter((product) => product.name.toLowerCase().includes(normalizedQuery));
}

describe('filterProducts', () => {
  const products = [
    { id: 1, name: 'React Book' },
    { id: 2, name: 'JavaScript Guide' },
    { id: 3, name: 'React Patterns' },
  ];

  test('returns products matching the query', () => {
    expect(filterProducts(products, 'react')).toEqual([
      { id: 1, name: 'React Book' },
      { id: 3, name: 'React Patterns' },
    ]);
  });

  test('ignores surrounding whitespace and letter case', () => {
    expect(filterProducts(products, '  REACT  ')).toHaveLength(2);
  });

  test('returns all products for an empty query', () => {
    expect(filterProducts(products, '')).toEqual(products);
  });
});
```

- первый тест проверяет результат фильтрации
- второй проверяет обработку пробелов и регистра
- третий проверяет поведение при пустом поисковом запросе
- у утилит особенно важно тестировать граничные случаи и контракт функции
- например, в этом примере предполагается, что `products` — массив объектов с полем `name`, содержащим строку; если функция должна принимать произвольные данные, ей понадобится дополнительная обработка ошибок
- не стоит автоматически добавлять десятки тестов на очевидные операции: приоритет имеют условия, в которых возможны реальные дефекты, и поведение, от которого зависят другие части приложения

### 4.2. тестирование React-компонентов

- компонент тестируют через его публичный контракт: props, отображение, действия пользователя, доступность и взаимодействие с зависимостями
- допустим, компонент `SaveButton` принимает `disabled` и `onSave`

```js
function SaveButton({ disabled = false, onSave }) {
  return (
    <button disabled={disabled} onClick={onSave}>
      Save
    </button>
  );
}
```

- основные сценарии здесь следующие
- кнопка отображается с текстом `Save`
- при клике вызывается `onSave`
- при `disabled={true}` кнопка становится недоступной для обычного пользовательского нажатия
- компонент корректно работает, когда `disabled` не передан
- пример тестирования поведения

```js
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

test('calls onSave when the user clicks Save', async () => {
  const user = userEvent.setup();
  const onSaveMock = jest.fn();

  render(<SaveButton onSave={onSaveMock} />);

  await user.click(screen.getByRole('button', { name: 'Save' }));

  expect(onSaveMock).toHaveBeenCalledTimes(1);
});

test('disables the button when disabled is true', () => {
  render(<SaveButton disabled onSave={jest.fn()} />);

  expect(screen.getByRole('button', { name: 'Save' })).toBeDisabled();
});
```

- первый тест проверяет связь между пользовательским действием и переданным callback
- второй проверяет состояние элемента с точки зрения DOM
- здесь нет необходимости проверять, как именно React хранит props или каким способом компонент построен внутри
- для более сложных компонентов добавляются проверки условного отображения, состояний загрузки и ошибки, обработки клавиатуры, взаимодействия с контекстом и других частей публичного поведения

### 4.3. тестирование HOC

- HOC (Higher-Order Component) — функция, которая принимает компонент и возвращает новый компонент, расширяющий или изменяющий его поведение
- типичный пример — HOC для проверки авторизации, добавления дополнительных props или управления доступом к странице

```js
function withAuthorization(WrappedComponent) {
  return function AuthorizedComponent({ isAuthorized, ...props }) {
    if (!isAuthorized) {
      return <p>Access denied</p>;
    }

    return <WrappedComponent {...props} />;
  };
}
```

- здесь HOC отвечает за решение о том, отображать ли исходный компонент
- поэтому тестировать нужно как минимум два сценария: доступ разрешён и доступ запрещён

```js
import { render, screen } from '@testing-library/react';

function PrivatePage({ title }) {
  return <h1>{title}</h1>;
}

const AuthorizedPage = withAuthorization(PrivatePage);

test('renders the wrapped component when authorized', () => {
  render(<AuthorizedPage isAuthorized title='Dashboard' />);

  expect(screen.getByRole('heading', { name: 'Dashboard' })).toBeInTheDocument();
});

test('does not render the wrapped component when unauthorized', () => {
  render(<AuthorizedPage isAuthorized={false} title='Dashboard' />);

  expect(screen.getByText('Access denied')).toBeInTheDocument();
  expect(screen.queryByRole('heading', { name: 'Dashboard' })).not.toBeInTheDocument();
});
```

- тест проверяет результат применения HOC, а не внутреннюю реализацию обёртки
- в реальных проектах также полезно проверять передачу props, если они являются частью контракта HOC
- важный нюанс: в современных React-приложениях часть задач, которые раньше решались HOC, часто реализуют через hooks, context и композицию компонентов
- тем не менее HOC встречаются в legacy-коде, библиотеках и некоторых архитектурных решениях, поэтому понимание их тестирования полезно

### 4.4. тестирование модальных окон

- модальное окно — хороший пример компонента, поведение которого нельзя свести к простому отображению JSX
- необходимо проверить открытие, закрытие, взаимодействие с содержимым, доступность и иногда работу через React Portal
- типичный набор сценариев:
- модальное окно отображается при `open={true}`
- модальное окно отсутствует или скрыто при `open={false}` — в зависимости от контракта компонента
- нажатие кнопки закрытия вызывает `onClose`
- нажатие `Escape` закрывает окно, если такое поведение предусмотрено
- клик по backdrop закрывает окно, если это предусмотрено дизайном
- клик внутри окна не закрывает его случайно
- при наличии формы внутри окна корректно обрабатываются отправка и ошибки
- пример простого модального компонента

```js
import { useEffect } from 'react';

function Modal({ open, onClose, children }) {
  useEffect(() => {
    if (!open) return;

    function handleKeyDown(event) {
      if (event.key === 'Escape') {
        onClose();
      }
    }

    window.addEventListener('keydown', handleKeyDown);

    return () => {
      window.removeEventListener('keydown', handleKeyDown);
    };
  }, [open, onClose]);

  if (!open) return null;

  return (
    <div data-testid='modal-backdrop' onClick={onClose}>
      <section role='dialog' aria-modal='true' aria-label='Confirm action' onClick={(event) => event.stopPropagation()}>
        {children}
        <button onClick={onClose}>Close</button>
      </section>
    </div>
  );
}
```

- здесь backdrop закрывает модальное окно, а `stopPropagation()` предотвращает всплытие клика из содержимого к backdrop
- обработчик `Escape` устанавливается при открытии и снимается при закрытии или размонтировании компонента
- атрибуты `role="dialog"` и `aria-modal="true"` помогают описать назначение окна для вспомогательных технологий, хотя полноценная доступность требует также управления фокусом
- пример тестирования закрытия по `Escape`

```js
import { render, screen, waitFor } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

test('closes the modal when Escape is pressed', async () => {
  const user = userEvent.setup();
  const onCloseMock = jest.fn();

  render(
    <Modal open onClose={onCloseMock}>
      <p>Confirm deletion</p>
    </Modal>,
  );

  expect(screen.getByRole('dialog')).toBeInTheDocument();

  await user.keyboard('{Escape}');

  await waitFor(() => {
    expect(onCloseMock).toHaveBeenCalledTimes(1);
  });
});
```

- в данном тесте проверяется, что пользовательское действие приводит к вызову callback
- компонент сам не меняет `open`: это ответственность родителя, который получает `onClose` и обновляет props
- если требуется проверить исчезновение окна, тест должен включать родительский компонент, управляющий `open`, либо другой способ изменить этот prop
- при тестировании Portal следует учитывать, что его DOM может находиться вне контейнера, в который был отрендерен исходный компонент
- `screen` обычно ищет элементы во всём доступном документе, поэтому часто позволяет проверять содержимое Portal без привязки к контейнеру родительского компонента

### 4.5. тестирование асинхронных компонентов

- интерфейс часто зависит от Promise, API-запросов, таймеров или отложенных обновлений состояния
- в таких тестах важно проверять не только конечный результат, но и корректность переходов между состояниями, если они значимы для пользователя
- например, компонент загрузки пользователей может иметь три состояния: загрузка, успех и ошибка
- для каждого состояния стоит определить ожидаемое поведение и проверить его отдельно
- если компонент вызывает настоящий сетевой API, тест может стать медленным и нестабильным, а его результат — зависеть от внешней системы
- обычно сетевой уровень изолируют с помощью mocks или инструментов перехвата HTTP-запросов, например MSW (Mock Service Worker), чтобы контролировать ответы и проверять поведение приложения на успех и ошибку
- важно не использовать произвольные задержки вроде `setTimeout` в надежде, что интерфейс успеет обновиться
- предпочтительнее ждать конкретного наблюдаемого условия через `findBy...` или `waitFor`, а для тестирования таймеров использовать контролируемые fake timers, если это действительно необходимо

## 5. базовые тестовые паттерны

- паттерн тестирования — это повторяемый способ организовать проверки, который делает их предсказуемыми, понятными и удобными для поддержки

### 5.1. Arrange–Act–Assert

- это базовый паттерн, который мы уже использовали выше
- он особенно полезен для небольших unit-тестов и пользовательских сценариев компонентов, поскольку отделяет подготовку данных от проверяемого действия и результата

### 5.2. Given–When–Then

- похожий подход, часто используемый в BDD (Behavior-Driven Development)
- `Given` описывает исходные условия, `When` — событие, `Then` — ожидаемый результат
- например: «дана авторизованная сессия → пользователь открывает страницу профиля → отображается профиль»
- такой формат помогает писать тесты на языке требований и согласовывать поведение между разработчиками, тестировщиками и продуктовой командой

### 5.3. parametrized tests

- когда одну и ту же функцию нужно проверить на множестве входных значений, не обязательно копировать почти одинаковые тесты
- Jest предоставляет `test.each` и `it.each`, которые позволяют передавать наборы тестовых данных

```js
test.each([
  [100, 0, 100],
  [100, 10, 90],
  [100, 100, 0],
])('calculates discount for price %i and discount %i', (price, discount, expected) => {
  expect(calculateDiscount(price, discount)).toBe(expected);
});
```

- каждый набор данных становится отдельным тестовым случаем
- такой подход особенно полезен для форматирования, валидации, вычислений и преобразования данных
- однако не стоит объединять в параметризованный тест сценарии с совершенно разной логикой и смыслом — отдельные тесты зачастую понятнее

### 5.4. тестовые двойники: mock, stub и spy

- эти термины связаны, но не полностью взаимозаменяемы
- stub — заменяет зависимость заранее заданным ответом, например возвращает объект пользователя вместо настоящего API
- mock — в широком смысле заменяет зависимость контролируемой реализацией; в строгом смысле также может задавать ожидания относительно взаимодействия с ней
- spy — отслеживает вызовы реальной или специально обёрнутой функции, а в Jest `jest.spyOn` также позволяет временно заменить её реализацию
- например, при тестировании компонента, который сохраняет данные, можно подменить API-запрос, проверить переданные данные и отдельно убедиться, что интерфейс показывает результат сохранения
- при этом не нужно проверять каждый внутренний вызов каждой функции: проверять взаимодействие стоит там, где оно является частью контракта или существенно влияет на поведение

### 5.5. snapshot testing

- snapshot-тест сохраняет сериализованное представление результата, а при последующем запуске сравнивает его с текущим результатом
- Jest может использовать snapshots для сериализуемых значений и React-деревьев
- snapshots полезны, когда структура результата сама по себе важна, например для небольших сериализованных объектов или определённых видов генерируемой разметки
- но большой snapshot компонента часто оказывается хрупким: изменение текста, атрибутов или структуры может приводить к масштабным обновлениям, которые приходится просматривать вручную
- важно понимать, что обновление snapshot после падения теста не означает автоматического исправления дефекта
- сначала нужно выяснить, ожидаемо ли изменилось поведение, и только затем обновлять эталон

### 5.6. изоляция и независимость тестов

- тесты должны по возможности запускаться независимо друг от друга и не зависеть от порядка выполнения
- для этого изолируют изменяемые данные, сбрасывают mocks, очищают DOM и не используют общие состояния без необходимости
- если один тест проходит только после выполнения другого, это обычно указывает на проблему с подготовкой или очисткой окружения
- полезно также избегать чрезмерного mocking: чем больше реального поведения проверяется без лишней изоляции, тем больше шансов обнаружить ошибку взаимодействия компонентов
- оптимальный уровень изоляции зависит от тестируемой сущности: unit-тест утилиты должен быть простым и изолированным, а интеграционный тест формы может намеренно включать несколько связанных компонентов

## 6. testing pyramid — пирамида тестирования

- пирамида тестирования — это модель распределения тестов по уровням, которая помогает выбирать баланс между скоростью обратной связи, стоимостью поддержки и уверенностью в работоспособности приложения

схематично, от большого количества тестов к меньшему

```
             E2E
     сценарии в браузере
              ↓
         Integration
взаимодействие частей системы
              ↓
             Unit
функции и изолированная логика
```

- нижний уровень обычно содержит больше всего тестов, потому что они быстрые и сравнительно дешёвые в поддержке
- средний уровень проверяет взаимодействие компонентов, модулей и зависимостей
- верхний уровень содержит меньше E2E-тестов, поскольку они обычно медленнее, требуют более сложного окружения и чаще зависят от состояния всей системы

### 6.1. unit-тесты

- проверяют небольшую единицу логики изолированно
- примеры: форматирование даты, вычисление цены, фильтрация списка, проверка валидности значения
- преимущества: скорость, простота локализации ошибки, небольшая стоимость выполнения
- ограничения: сами по себе не гарантируют, что модули правильно взаимодействуют между собой

### 6.2. integration-тесты

- проверяют, что несколько частей приложения работают вместе
- например, форма регистрации взаимодействует с валидацией, отправляет данные через API-слой и отображает ошибку сервера
- такие тесты помогают обнаружить ошибки контрактов между компонентами, некорректную передачу данных и неправильную обработку состояний
- React Testing Library особенно хорошо подходит для интеграционных тестов UI, в которых несколько компонентов работают вместе

### 6.3. E2E-тесты

- запускают приложение в браузере и проверяют полноценные пользовательские сценарии
- например, пользователь открывает страницу входа, вводит данные, нажимает кнопку и попадает в личный кабинет
- для этого часто используют Playwright или Cypress

* E2E-тест проверяет больше реальных связей системы, но если он падает, причиной может быть ошибка в интерфейсе, сети, конфигурации окружения или серверной логике
* поэтому такие тесты обычно сложнее отлаживать, чем unit-тесты

### 6.4. как применять пирамиду на практике

- представим, что приложение содержит каталог товаров с поиском и оформлением заказа
- фильтрацию товаров и вычисление итоговой суммы разумно покрыть unit-тестами
- работу поиска с состоянием React и отображением результатов — интеграционными тестами
- полный сценарий покупки от выбора товара до подтверждения заказа — несколькими критически важными E2E-тестами

* пирамида не является строгим законом, предписывающим конкретные проценты для каждого уровня
* в некоторых проектах используется модель testing trophy, где особое внимание уделяется интеграционным тестам
* главное — не количество тестов каждого типа, а способность тестового набора обнаруживать значимые дефекты с приемлемой стоимостью поддержки

## 7. TDD — Test-Driven Development

- TDD (Test-Driven Development) — подход к разработке, при котором тест пишется до реализации функциональности
- смысл подхода не в том, чтобы сначала написать все тесты на проект, а затем реализовать приложение, а в том, чтобы развивать код небольшими итерациями

### 7.1. цикл Red–Green–Refactor

1. Red — красный

- пишем тест для ещё не реализованного поведения и убеждаемся, что он падает по ожидаемой причине

2. Green — зелёный

- пишем минимальный код, необходимый для прохождения теста

3. Refactor — рефакторинг

- улучшаем структуру кода, устраняем дублирование и упрощаем реализацию, сохраняя зелёные тесты

### 7.2. пример TDD на JavaScript

- допустим, требуется реализовать функцию, которая определяет, может ли пользователь оформить заказ
- по требованиям заказ разрешён, если сумма больше нуля
- сначала пишем тест, хотя функции ещё нет

```js
test('allows checkout when the total is positive', () => {
  expect(canCheckout(100)).toBe(true);
});
```

- на этапе Red тест не проходит, потому что `canCheckout` ещё не определена
- теперь добавляем минимальную реализацию

```js
function canCheckout(total) {
  return total > 0;
}
```

- на этапе Green тест проходит
- затем добавляем граничный сценарий и уточняем контракт функции

```js
test.each([
  [100, true],
  [0, false],
  [-10, false],
])('canCheckout(%i) returns %s', (total, expected) => {
  expect(canCheckout(total)).toBe(expected);
});
```

- после появления дополнительных тестов можно рефакторить реализацию, если это необходимо
- в этом простом примере рефакторинг может вообще не потребоваться — это нормально, поскольку цель не в том, чтобы обязательно переписать код, а в том, чтобы поддерживать понятную и корректную реализацию

### 7.3. зачем писать тест до кода

- прояснение требований — приходится заранее определить ожидаемое поведение, включая граничные случаи
- проектирование API — тест помогает увидеть, насколько удобно вызывать функцию или компонент
- раннее обнаружение дефектов — неправильное поведение обнаруживается непосредственно при разработке
- защита при рефакторинге — после изменения реализации тесты проверяют, что контракт сохраняется
- TDD особенно хорошо подходит для функций с чёткими входами и выходами, сложной бизнес-логики, расчётов и обработки данных
- его можно применять и к React-компонентам: сначала описать ожидаемое поведение интерфейса, затем реализовать его и улучшить структуру

### 7.4. типичные ошибки при использовании TDD

- писать тесты, которые проверяют только текущую реализацию, а не требуемое поведение
- пытаться заранее описать абсолютно все возможные сценарии, из-за чего разработка становится медленной
- писать чрезмерно сложные mocks, которые повторяют устройство самого приложения
- воспринимать прохождение тестов как доказательство отсутствия ошибок
- пропускать этап Red и писать тест уже после реализации, называя это TDD
- важное уточнение: тесты, написанные после реализации, тоже полезны — просто последовательность разработки в этом случае не соответствует строгому циклу TDD

## 8. coverage — покрытие тестами

- покрытие показывает, какая часть кода была выполнена во время запуска тестов
- Jest умеет собирать coverage и показывать несколько видов метрик
- statement coverage — доля выполненных инструкций
- branch coverage — доля пройденных ветвей условий, например обоих исходов `if`
- function coverage — доля вызванных функций
- line coverage — доля выполненных строк
- пример: функция содержит условие `if (total > 0)`, но тест проверяет только положительную сумму
- строка с условием может быть выполнена, однако ветвь для нулевой или отрицательной суммы останется непроверенной
- высокий процент coverage не гарантирует хорошее тестирование: можно выполнить весь код, не проверив правильность результата
- coverage полезен для поиска непроверенных участков и оценки пробелов, но не должен становиться единственной целью

## 9. как организовать тестирование в React-проекте

- один из распространённых подходов — располагать тесты рядом с тестируемым модулем

```
src/
  components/
    SaveButton/
      SaveButton.jsx
      SaveButton.test.jsx
  utils/
    calculateDiscount.js
    calculateDiscount.test.js
  services/
    userService.js
    userService.test.js
```

- этот подход облегчает поиск тестов и позволяет изменять реализацию вместе с проверками
- в больших проектах также встречается отдельная директория `tests` или `__tests__` — выбор зависит от соглашений команды
- для запуска тестов обычно настраивают npm-скрипты, например `npm test` и `npm run test:coverage`
- Jest поддерживает конфигурацию окружения, трансформацию JSX и TypeScript через соответствующие инструменты; конкретная настройка зависит от сборщика и версии React
- для React-компонентов на практике часто используют Jest или Vitest вместе с React Testing Library и `@testing-library/user-event`
- для интеграции с HTTP удобно применять MSW, а для сквозных браузерных сценариев — Playwright или Cypress
- не обязательно использовать все инструменты одновременно: набор выбирают под архитектуру проекта, существующую инфраструктуру и типы рисков

## 10. что важно понимать на собеседовании

- Jest и Enzyme — не одно и то же: Jest запускает тесты и предоставляет проверки и mocks, а Enzyme исторически предоставляет API для рендеринга и исследования React-компонентов
- Enzyme и React Testing Library отличаются философией: первый часто позволяет исследовать структуру и внутренние детали компонента, второй ориентирован на наблюдаемое пользовательское поведение
- Arrange–Act–Assert помогает организовывать тесты так, чтобы были понятны подготовка, действие и ожидаемый результат
- unit, integration и E2E различаются масштабом проверяемого поведения, степенью изоляции и стоимостью выполнения
- HOC, утилиты, компоненты и модальные окна требуют разных сценариев проверки, соответствующих их публичному контракту
- mocks позволяют изолировать зависимости, но чрезмерное mocking может сделать тесты оторванными от реального поведения
- testing pyramid помогает распределять проверки по уровням, но не предписывает обязательные проценты
- TDD строится на цикле Red–Green–Refactor и предполагает написание теста до реализации
- coverage помогает обнаружить непроверенный код, но высокий процент покрытия сам по себе не означает высокое качество тестов
- с твоим опытом frontend-разработки хорошим практическим ориентиром будет умение написать тесты для утилиты, интерактивного React-компонента, формы с асинхронной отправкой и модального окна, объяснить выбор уровня тестирования и обосновать, где нужны mocks, а где лучше проверить реальное взаимодействие нескольких частей системы
