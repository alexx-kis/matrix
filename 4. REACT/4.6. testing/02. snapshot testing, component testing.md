# snapshot testing и testing React-компонентов

- в этом блоке нужно разобраться в двух связанных, но разных вещах: snapshot testing — проверке соответствия результата рендеринга сохранённому снимку, и component testing — тестировании поведения и корректности работы React-компонентов
- snapshot testing — лишь один из способов тестировать компоненты, поэтому важно понимать не только его преимущества, но и ограничения по сравнению с обычными assertions

## 1. что такое snapshot testing

### основная идея

- snapshot testing — это подход, при котором результат работы тестируемого кода сохраняется в виде снимка, а при последующих запусках сравнивается с ранее сохранённым результатом
- в React обычно сохраняют представление отрендеренного компонента, например его структуру, текст, атрибуты и вложенные элементы
- если результат изменился, тест сообщает о расхождении между текущим и сохранённым снимком
- важно понимать, что snapshot сам по себе не знает, является изменение правильным или ошибочным — он только фиксирует различие

### как это работает

- предположим, есть компонент `UserGreeting`

```js
function UserGreeting({ name }) {
  return <h1>Hello, {name}!</h1>;
}
```

- тест рендерит компонент с определёнными props, получает результат и сравнивает его со snapshot

```js
import { render } from '@testing-library/react';
import { expect, it } from 'vitest';
import UserGreeting from './UserGreeting';

it('matches the snapshot', () => {
  const { container } = render(<UserGreeting name='Alex' />);

  expect(container.firstChild).toMatchSnapshot();
});
```

- здесь используется Vitest, но аналогичный подход поддерживается Jest
- при первом запуске тестовый раннер создаёт snapshot, который становится эталоном для последующих запусков
- для данного примера снимок может выглядеть приблизительно так:

```js
<h1>Hello, Alex!</h1>
```

- в последующих запусках React-компонент рендерится заново, а полученный результат сравнивается с сохранённым снимком

```
первый запуск
    ↓
рендер компонента
    ↓
создание snapshot
    ↓
сохранение эталона

следующие запуски
    ↓
рендер компонента
    ↓
сравнение с эталоном
    ↓
совпадение → тест проходит
расхождение → тест падает
```

- в примере используется `container.firstChild`, чтобы сравнивать непосредственно DOM-элемент компонента, а не весь контейнер, созданный Testing Library
- snapshot может храниться в отдельном файле, например `UserGreeting.test.jsx.snap`, либо быть встроенным в исходный тест с помощью inline snapshot

### как выглядит сохранённый snapshot

- Jest генерирует файлы примерно следующего вида:

```js
// Jest Snapshot v1

exports[`UserGreeting matches the snapshot 1`] = `
<h1>
  Hello, Alex!
</h1>
`;
```

- форматирование может отличаться в зависимости от версии Jest и способа сериализации результата
- файл snapshot обычно коммитят в Git вместе с тестами, чтобы изменения эталона проходили code review

## 2. почему snapshot testing используют

- основная задача — обнаруживать непреднамеренные изменения структуры отрендеренного компонента
- например, разработчик случайно удалил заголовок, изменил текст кнопки или убрал необходимый атрибут, а snapshot-тест обнаружил изменение результата
- особенно полезен такой подход, когда нужно отслеживать достаточно большие структурированные результаты, которые неудобно полностью описывать вручную

### пример обнаружения регрессии

- исходный компонент:

```js
function SubmitButton() {
  return <button type='submit'>Save</button>;
}
```

- сохранённый snapshot соответствует следующей разметке:

```js
<button type='submit'>Save</button>
```

- затем компонент случайно изменили:

```js
function SubmitButton() {
  return <button type='button'>Save</button>;
}
```

- snapshot обнаружит изменение `type="submit"` на `type="button"`
- однако он не понимает семантику HTML и не знает, что кнопка должна отправлять форму
- он лишь показывает, что текущая разметка отличается от сохранённой
- именно поэтому snapshot способен обнаружить потенциальную регрессию, но не может самостоятельно доказать корректность поведения компонента

## 3. когда snapshot testing полезен

- snapshot хорошо подходит для компонентов, у которых есть стабильное структурное представление и важно отслеживать изменения этого представления

- типичные случаи применения:
  - небольшие презентационные компоненты, например `Badge`, `Avatar`, `Breadcrumbs`
  - сложные статические блоки разметки, например карточки или информационные панели
  - сериализуемые результаты работы форматтеров и других утилит
  - проверка структуры компонента при различных наборах props
  - регрессионные тесты, когда изменение разметки должно быть явно замечено при ревью

- при этом snapshot не обязательно должен быть единственным тестом компонента

- например, для кнопки полезно иметь snapshot, но проверку того, что обработчик `onClick` вызывается, лучше написать отдельным поведенческим тестом

## 4. недостатки snapshot testing

### 4.1. snapshot может быть слишком большим

- если компонент содержит много вложенных компонентов, длинные списки, SVG и сложную разметку, снимок становится громоздким
- в результате разработчик может перестать внимательно читать изменения и начать автоматически обновлять snapshots
- это снижает ценность теста: он продолжает проходить, но больше не гарантирует, что изменения были осмысленно проверены

### 4.2. snapshot не проверяет бизнес-логику

- предположим, кнопка должна вызывать обработчик при нажатии

```js
function SaveButton({ onSave }) {
  return <button onClick={onSave}>Save</button>;
}
```

- snapshot может подтвердить, что кнопка присутствует в разметке, но не доказывает, что нажатие вызывает `onSave`
- для этого нужен отдельный тест поведения:

```js
import { fireEvent, render, screen } from '@testing-library/react';
import { expect, it, vi } from 'vitest';

it('calls onSave when clicked', () => {
  const onSave = vi.fn();

  render(<SaveButton onSave={onSave} />);

  fireEvent.click(screen.getByRole('button', { name: 'Save' }));

  expect(onSave).toHaveBeenCalledTimes(1);
});
```

- здесь `vi.fn()` создаёт mock-функцию, вызовы которой можно проверять в assertions
- в Jest аналогичная функция называется `jest.fn()`
- в современных тестах React Testing Library часто предпочитают `userEvent` для имитации пользовательских действий, поскольку он моделирует взаимодействие более реалистично, чем отдельный низкоуровневый DOM event

### 4.3. snapshot может закрепить неправильное поведение

- если компонент уже содержит ошибку, snapshot успешно сохранит её как эталон
- после этого тест будет проходить до тех пор, пока результат не изменится
- следовательно, snapshot подтверждает стабильность результата относительно эталона, но не его соответствие требованиям

### 4.4. обновление snapshots может скрыть ошибку

- когда тест падает, Jest позволяет обновить снимки командой:

```bash
npx jest -w
```

- в зависимости от версии Jest для обновления snapshots также используется флаг `-u` или `--updateSnapshot`
- обновлять снимок следует только после анализа различий и подтверждения, что новое поведение ожидаемо
- бездумное обновление всех снимков превращает тесты в формальную процедуру, не обеспечивающую полезной проверки

## 5. что такое component testing

- component testing — это тестирование отдельного UI-компонента в изоляции или в контролируемом окружении, чтобы убедиться, что он правильно отображает данные и реагирует на взаимодействия

- компонент может проверяться по нескольким направлениям:
  - рендеринг — отображается ли необходимый текст и нужные элементы
  - props — корректно ли компонент реагирует на разные входные значения
  - взаимодействия — работают ли клики, ввод текста и отправка форм
  - состояния — правильно ли отображаются loading, error, empty и success
  - интеграция — корректно ли компонент взаимодействует с контекстом, состоянием или другими компонентами

- snapshot testing относится к одному из способов проверки результата рендеринга, тогда как component testing охватывает более широкую область

### пример тестирования разных props

- рассмотрим компонент, который показывает сообщение в зависимости от переданного имени

```js
function WelcomeMessage({ name }) {
  return (
    <section>
      <h2>Welcome, {name}</h2>
    </section>
  );
}
```

- поведенческий тест может проверять, что компонент отображает правильный текст:

```js
import { render, screen } from '@testing-library/react';
import { expect, it } from 'vitest';

it('renders the provided name', () => {
  render(<WelcomeMessage name='Maria' />);

  expect(
    screen.getByRole('heading', {
      name: 'Welcome, Maria',
    }),
  ).toBeInTheDocument();
});
```

- здесь тест проверяет не точное внутреннее представление всего DOM, а конкретный результат, важный для пользователя
- если разработчик добавит обёртку `<div>`, изменит количество промежуточных элементов или переставит незначимые узлы, такой тест продолжит проходить, если доступный пользователю результат останется прежним
- это одно из главных преимуществ проверок через пользовательские сценарии по сравнению с большими snapshots

## 6. snapshot testing и обычные assertions — в чём разница

- обычные assertions проверяют конкретные условия, которые разработчик явно сформулировал

```js
expect(screen.getByText('Hello, Alex!')).toBeInTheDocument();
```

- snapshot testing сравнивает весь выбранный результат с сохранённым представлением

```js
expect(container.firstChild).toMatchSnapshot();
```

- разница не в том, что один способ проверяет компонент, а другой нет, а в том, что именно является контрактом теста
- при использовании обычного assertion контракт выражен конкретным условием: например, заголовок должен существовать или кнопка должна вызывать callback
- при использовании snapshot контракт выражен эталонным представлением: текущий результат должен совпадать с ранее сохранённым
- обычные assertions обычно точнее выражают намерение теста и легче диагностируют конкретные нарушения
- snapshots могут быстрее охватывать большое количество структурных деталей, но при этом часто чувствительнее к несущественным изменениям реализации

## 7. как тестировать компонент с несколькими состояниями

- рассмотрим компонент уведомления, который может показывать сообщение или ничего не отображать

```js
function StatusMessage({ status }) {
  if (status === 'loading') {
    return <p>Loading...</p>;
  }

  if (status === 'error') {
    return <p role='alert'>Something went wrong</p>;
  }

  if (status === 'success') {
    return <p>Saved successfully</p>;
  }

  return null;
}
```

- для него можно использовать комбинацию поведенческих тестов и snapshots

```js
import { render, screen } from '@testing-library/react';
import { expect, it } from 'vitest';

it('shows the loading state', () => {
  render(<StatusMessage status='loading' />);

  expect(screen.getByText('Loading...')).toBeInTheDocument();
});

it('shows the error state', () => {
  render(<StatusMessage status='error' />);

  expect(screen.getByRole('alert')).toHaveTextContent('Something went wrong');
});

it('matches the success snapshot', () => {
  const { container } = render(<StatusMessage status='success' />);

  expect(container.firstChild).toMatchSnapshot();
});
```

- первые два теста явно проверяют ожидаемое поведение для loading и error
- третий фиксирует структурное представление success-состояния
- это пример разумного разделения обязанностей: каждый тест отвечает на определённый вопрос, а не пытается проверить всё сразу
- для простого текста snapshot здесь необязателен — обычный assertion мог бы оказаться понятнее

## 8. как устроен snapshot testing в Jest

- Jest предоставляет встроенную поддержку snapshots, поэтому для базового использования не требуется отдельная библиотека
- основные методы:
  - `toMatchSnapshot()` — сравнивает значение с сохранённым snapshot
  - `toMatchInlineSnapshot()` — хранит snapshot непосредственно в тестовом файле
  - `toThrowErrorMatchingSnapshot()` — проверяет представление выброшенной ошибки относительно snapshot
- пример inline snapshot:

```js
import { render } from '@testing-library/react';
import { expect, it } from 'vitest';

it('matches an inline snapshot', () => {
  const { container } = render(<UserGreeting name='Alex' />);

  expect(container.firstChild).toMatchInlineSnapshot(`
    <h1>
      Hello, Alex!
    </h1>
  `);
});
```

- при первом запуске тестовый раннер может автоматически записать фактический snapshot в тестовый файл
- последующие запуски будут сравнивать результат с сохранённым текстом
- inline snapshots удобны, когда результат небольшой, а отдельный `.snap`-файл был бы избыточен
- внешние snapshots удобнее для большого количества тестов и более объёмных результатов
- в современных проектах также стоит различать snapshot React-элемента и snapshot DOM-результата: например, `react-test-renderer` мог сериализовать дерево React, а React Testing Library обычно используется для проверки реального DOM-представления

## 9. как организовать component testing в реальном проекте

- практический подход — строить тесты вокруг пользовательского поведения и использовать snapshots только там, где структурное сравнение приносит дополнительную пользу
- например, для компонента формы можно проверить:
  - наличие полей и кнопки отправки
  - корректное отображение ошибок валидации
  - вызов обработчика с правильными данными
  - состояние загрузки во время отправки
  - отображение результата после успешной операции
- при этом нет необходимости создавать snapshot для каждого состояния автоматически
- для компонента, который показывает список из ста элементов, полный snapshot может оказаться менее полезным, чем проверка нескольких ключевых элементов и граничных состояний
- для компонентов, зависящих от контекста, маршрутизации или Redux, следует подготовить тестовое окружение с необходимыми providers либо использовать вспомогательную функцию рендеринга, которая подключает эти зависимости
- чем ближе тест к реальному способу использования компонента, тем выше вероятность обнаружить ошибки, которые действительно заметит пользователь

## 10. важные нюансы и типичные ошибки

- не считать snapshot доказательством корректности — он фиксирует совпадение с эталоном, а не соответствие бизнес-требованиям
- не обновлять snapshots автоматически без анализа — сначала необходимо понять причину различия
- не создавать snapshots для всего подряд — слишком большое количество громоздких снимков усложняет поддержку
- не привязывать тесты к внутренней реализации без необходимости — тесты, проверяющие DOM через пользовательские роли и доступные имена, обычно устойчивее к рефакторингу
- учитывать динамические данные — даты, случайные идентификаторы, нестабильная сортировка и другие переменные значения могут вызывать постоянные расхождения; лучше стабилизировать входные данные, время или генераторы, чем бездумно исключать проверки
- помнить о внешних зависимостях — snapshot компонента, зависящего от API, контекста или глобального состояния, отражает только результат в конкретно подготовленном тестовом окружении
- проверять доступность, а не только разметку — корректное наличие `button` в snapshot ещё не гарантирует правильное имя элемента, доступность с клавиатуры или работоспособность взаимодействия

## 11. что нужно уметь на собеседовании

- на базовом уровне следует уметь объяснить, что snapshot testing сохраняет эталонное представление результата и сравнивает с ним последующие рендеры
- на практическом уровне — написать snapshot-тест компонента, запустить его, разобраться с падением и безопасно обновить эталон после ожидаемого изменения
- на хорошем уровне — выбирать между snapshot и обычными assertions, тестировать несколько состояний компонента и понимать, почему snapshot не заменяет проверку поведения
- главный принцип: snapshot testing помогает обнаруживать изменения, а component testing в целом помогает проверять корректность поведения компонентов
- в современном React-проекте разумно сочетать snapshots с React Testing Library и тестами пользовательских сценариев, а не строить всю стратегию тестирования исключительно на снимках
