# e2e-тестирование в React

- e2e (end-to-end) testing — это тестирование приложения целиком, с точки зрения пользователя, чтобы убедиться, что основные пользовательские сценарии работают корректно от начала до конца

- в контексте React нужно понимать не только то, как написать e2e-тест, но и то, чем он отличается от unit- и integration-тестов, как браузер выполняет тестовые действия, как проверяются результаты и какие проблемы возникают в реальных проектах

## 1. что такое e2e-тесты и для чего они нужны

### основная идея

- представим интернет-магазин на React, в котором пользователь может авторизоваться, открыть каталог, добавить товар в корзину и оформить заказ

- unit-тест может проверить функцию расчёта стоимости заказа, integration-тест — взаимодействие корзины с компонентами и состоянием приложения, а e2e-тест — весь сценарий оформления заказа через браузер

```
     [пользователь открывает приложение]
  React-приложение загружается в браузере
                    ↓
      [взаимодействие с интерфейсом]
  клики, ввод текста, переходы, отправка форм
                    ↓
        [взаимодействие с системой]
API, сервер, база данных или тестовые заглушки
                    ↓
      [проверка конечного результата]
 заказ создан, пользователь видит подтверждение
```

- принципиальный момент: e2e-тест проверяет не внутреннюю реализацию конкретного React-компонента, а то, что пользовательский сценарий работает через реальные границы системы

- при этом e2e не обязательно означает, что все внешние системы должны быть настоящими: API, платежи и другие зависимости можно подменять, если это соответствует цели теста

### что именно проверяют в React-приложении

- маршрутизацию — переходы между страницами, работу прямых ссылок, редиректы
- формы — ввод данных, валидацию, отправку и отображение ошибок
- авторизацию — вход, выход, доступ к защищённым страницам
- асинхронные операции — загрузку данных, отображение состояния загрузки и ошибок
- интеграцию с API — корректное отображение полученных данных и реакцию на ответы сервера
- критические пользовательские сценарии — покупку товара, регистрацию, создание документа, отправку сообщения

- e2e-тесты особенно ценны для сценариев, которые затрагивают сразу несколько компонентов, роутер, глобальное состояние и серверное API

## 2. отличие unit, integration и e2e

- эти виды тестирования различаются прежде всего масштабом проверяемой системы и тем, какие зависимости участвуют в тесте

### unit-тесты

- проверяют небольшую изолированную единицу: функцию, хук или отдельную логику компонента
- обычно выполняются быстро и позволяют точно локализовать ошибку
- пример: `calculateTotal()` возвращает правильную сумму заказа

  инструменты: Jest, Vitest, React Testing Library

### integration-тесты

- проверяют взаимодействие нескольких частей системы
- например, форма авторизации, состояние React-приложения и обработка ответа API
- помогают обнаруживать проблемы на стыках компонентов и модулей

  инструменты: Jest, Vitest, React Testing Library

### e2e-тесты

- проверяют пользовательский сценарий через браузер и несколько слоёв приложения
- могут охватывать UI, маршрутизацию, сеть и серверную часть
- позволяют обнаруживать ошибки конфигурации, интеграции и реального пользовательского потока

  инструменты: Playwright, Cypress

### пример одной функциональности на трёх уровнях

- допустим, в приложении есть форма авторизации

```js
// Unit: проверяем бизнес-логику
function isEmailValid(email) {
  return /^[^s@]+@[^s@]+.[^s@]+$/.test(email);
}

// Integration: проверяем взаимодействие формы и UI
// Пользователь вводит некорректный email,
// нажимает кнопку, и появляется сообщение об ошибке

// E2E: проверяем весь пользовательский сценарий
// Пользователь открывает /login,
// вводит учётные данные, отправляет форму
// и попадает на /dashboard
```

- второй и третий примеры описаны словами, потому что конкретный тест зависит от устройства приложения, а не только от самой функции

### сравнение на практике

| Критерий             | Unit              | Integration      | E2E                       |
| -------------------- | ----------------- | ---------------- | ------------------------- |
| Масштаб              | Небольшая единица | Несколько частей | Пользовательский сценарий |
| Скорость             | Обычно высокая    | Средняя          | Обычно ниже               |
| Изоляция             | Высокая           | Частичная        | Часто низкая              |
| Поиск причины ошибки | Обычно простой    | Средний          | Может быть сложным        |
| Проверка браузерного | Необязательна     | Возможна         | Основная задача           |
| поведения            |                   |                  |                           |

- это не строгая классификация: границы между unit- и integration-тестами зависят от проекта, а некоторые e2e-сценарии используют подменённые API

## 3. testing pyramid и место e2e

- testing pyramid — модель распределения тестов, которая помогает балансировать скорость обратной связи, стоимость поддержки и уверенность в работоспособности системы

```
             /\
            /  \
           /    \
          /  E2E \   Мало
         /--------\
        /          \
       / Integration\   Умеренно
      /--------------\
     /                \
    /    Unit tests    \   Много
   /____________________\
```

- в классической пирамиде много быстрых unit-тестов, меньше integration-тестов и ещё меньше e2e-тестов
- причина не в том, что e2e менее полезны, а в том, что они обычно дороже в запуске и сопровождении, сильнее зависят от окружения и сложнее диагностируются при падении
- в современных frontend-проектах доля integration-тестов может быть довольно большой, а распределение зависит от архитектуры и критичности приложения
- практический подход — проверять большое количество вариантов бизнес-логики на нижних уровнях, а e2e использовать для небольшого набора самых важных пользовательских сценариев

## 4. инструменты для e2e-тестирования

### Cypress

- предоставляет API для взаимодействия с браузером, проверки DOM, перехвата сетевых запросов и работы с тестовым окружением
- имеет интерактивный Test Runner, который удобен для отладки и наблюдения за действиями теста
- часто встречается в проектах с React и подходит для знакомства с e2e

  официальная документация: [Cypress Docs](https://docs.cypress.io/?utm_source=chatgpt.com)

### Playwright

- поддерживает Chromium, Firefox и WebKit
- предоставляет удобные локаторы, автоматическое ожидание готовности элементов и изоляцию тестовых контекстов
- часто используется для полноценного браузерного тестирования и запуска в CI

  официальная документация: [Playwright Docs](https://playwright.dev/docs/intro?utm_source=chatgpt.com)

- для подготовки к собеседованию не требуется одинаково глубоко изучать оба инструмента: лучше уверенно освоить один, а второй понимать на уровне основных отличий

## 5. пишем e2e-тест для React-приложения на Cypress

- рассмотрим минимальный, но практически полезный сценарий: пользователь открывает страницу входа, вводит данные и после успешной авторизации видит dashboard

### установка и настройка

- предполагается, что React-приложение уже создано и доступно локально

```bash
npm install --save-dev cypress
npx cypress open
```

- первая команда устанавливает Cypress, вторая запускает интерактивный интерфейс, в котором можно настроить E2E Testing и выбрать браузер
- в типичном проекте тесты размещаются в `cypress/e2e/`, а конфигурация — в `cypress.config.js` или `cypress.config.ts`

```js
// cypress.config.js
const { defineConfig } = require('cypress');

module.exports = defineConfig({
  e2e: {
    baseUrl: 'http://localhost:5173',
  },
});
```

- `baseUrl` — базовый адрес приложения, позволяющий в тестах писать `cy.visit('/login')`, а не повторять полный URL
- порт `5173` часто используется Vite, но здесь нужно указать реальный порт своего приложения

### пример теста

- допустим, у приложения есть страница `/login`, поля с доступными именами `Email` и `Password`, кнопка `Sign in` и страница `/dashboard`, на которой после авторизации отображается заголовок `Dashboard`

```js
// cypress/e2e/login.cy.js
describe('Login flow', () => {
  it('logs in and opens the dashboard', () => {
    cy.visit('/login');

    cy.findByRole('textbox', { name: /email/i }).type('user@example.com');

    cy.findByLabelText(/password/i).type('test-password');

    cy.findByRole('button', { name: /sign in/i }).click();

    cy.url().should('include', '/dashboard');

    cy.findByRole('heading', { name: /dashboard/i }).should('be.visible');
  });
});
```

- в этом примере используются команды Testing Library для Cypress, поэтому дополнительно нужно установить и настроить соответствующий пакет, например `@testing-library/cypress`; сами команды `cy.findByRole` и `cy.findByLabelText` не входят в базовый API Cypress

```bash
npm install --save-dev @testing-library/cypress
```

- без дополнительного плагина можно использовать стандартные команды Cypress, например `cy.get('[data-testid="email"]')`, если такие атрибуты присутствуют в приложении

### разберём последовательность выполнения

- `cy.visit('/login')` открывает страницу в управляемом браузере
- `cy.findByRole(...).type(...)` находит поле по доступному имени и вводит значение так, как это делал бы пользователь
- `cy.findByRole(...).click()` нажимает кнопку
- `cy.url().should(...)` проверяет URL после перехода
- `should('be.visible')` проверяет, что ожидаемый заголовок действительно отображается
- здесь важно, что тест не вызывает обработчик `onSubmit` напрямую и не подменяет React-компонент его собственной функцией: он взаимодействует с интерфейсом приложения
- локаторы по доступным ролям и именам обычно предпочтительнее хрупких CSS-селекторов, поскольку они ближе к тому, как пользователь воспринимает интерфейс, и одновременно помогают обнаруживать проблемы доступности

### откуда берётся успешная авторизация

- приведённый тест предполагает, что сервер принимает тестовые учётные данные и действительно выполняет вход; без подготовленного тестового пользователя он может завершиться ошибкой
- есть два распространённых подхода

вариант 1 — тестовый backend

- поднимается тестовое окружение с подготовленным пользователем и изолированными данными
- запросы проходят через настоящий backend, поэтому проверяется больше интеграций
- такой подход особенно полезен для критических сценариев, но требует управления тестовыми данными

вариант 2 — подмена API

- Cypress перехватывает запрос авторизации и возвращает контролируемый ответ
- это позволяет проверить поведение UI при успешном входе, не завися от доступности настоящего сервера

```js
// Пример для API, который ожидает POST /api/login
cy.intercept('POST', '/api/login', {
  statusCode: 200,
  body: {
    user: {
      id: 'test-user',
      email: 'user@example.com',
    },
  },
}).as('loginRequest');

cy.visit('/login');

// Здесь тест вводит данные и нажимает кнопку входа

cy.wait('@loginRequest').its('response.statusCode').should('equal', 200);
```

- этот фрагмент нужно встроить в сценарий с реальными действиями пользователя и адаптировать к контракту API приложения
- если frontend ожидает токен, cookie или другие поля ответа, их тоже нужно предусмотреть в заглушке
- тест с подменённым API проверяет взаимодействие UI с ожидаемым ответом, но не подтверждает, что настоящий backend умеет авторизовывать пользователя

## 6. как работают автоматические ожидания

- одна из наиболее важных особенностей e2e — асинхронность: React может перерисовать компонент, запрос может выполняться несколько сотен миллисекунд, а переход на другую страницу может завершиться не сразу
- например, такой тест ненадёжен:

```js
cy.get('[data-testid="submit"]').click();

cy.wait(2000);

cy.get('[data-testid="success"]').should('be.visible');
```

- фиксированная задержка не гарантирует, что результат появится через две секунды: на быстром окружении тест будет ждать зря, а на медленном может завершиться ошибкой
- Cypress автоматически повторяет проверки некоторых команд и assertions до успеха или истечения тайм-аута

```js
cy.get('[data-testid="submit"]').click();

cy.get('[data-testid="success"]').should('be.visible');
```

- здесь Cypress будет повторять поиск и проверку элемента, пока он не станет видимым или не закончится допустимое время ожидания
- автоматические ожидания не означают, что Cypress умеет самостоятельно определить завершение любой бизнес-операции: для сетевых запросов можно использовать `cy.intercept()` вместе с `cy.wait('@alias')`, а для интерфейса — проверять конкретный ожидаемый результат
- типичная ошибка — проверять только факт клика или отправки запроса, не проверяя результат, который должен увидеть пользователь

## 7. как сделать e2e-тесты стабильными

- нестабильный тест (flaky test) — тест, который при неизменном коде может то проходить, то падать из-за таймингов, окружения, сетевых задержек или состояния данных
- основные причины нестабильности и способы их устранения:

1. хрупкие селекторы

- плохо: `cy.get('.app > div:nth-child(2) > button')`
- лучше: `cy.findByRole('button', { name: /save/i })` либо устойчивый `data-testid`

2. произвольные задержки

- плохо: `cy.wait(3000)`
- лучше: ожидать конкретный элемент, URL или сетевой запрос

3. неуправляемые тестовые данные

- каждый тест должен получать предсказуемое начальное состояние
- не следует рассчитывать на то, что другой тест уже создал нужного пользователя или товар

4. зависимость от порядка запуска

- тесты должны по возможности проходить независимо друг от друга
- запуск одного теста не должен требовать успешного выполнения другого

5. внешние сервисы

- нестабильные сторонние API, платежи и почтовые сервисы лучше подменять в обычных UI-тестах
- критические интеграции проверять отдельно в подходящем окружении

## 8. запуск e2e в CI/CD

- в реальном проекте e2e-тесты обычно запускаются автоматически при создании pull request или в процессе сборки, чтобы обнаружить регрессии до релиза
- типичная последовательность выглядит так:

```
Разработчик создаёт pull request
             ↓
Установка зависимостей
             ↓
Сборка React-приложения
             ↓
Запуск приложения и тестового backend
             ↓
Запуск e2e-тестов в браузере
             |
       ┌-----+-----┐
       |           |
     Успех       Ошибка
       ↓           ↓
   CI проходит   CI падает,
                 сохраняются логи
                 и скриншоты
```

- для Cypress в CI можно использовать команду `cypress run`, которая запускает тесты в автоматическом режиме без интерактивного Test Runner

```bash
npx cypress run
```

- при настройке CI нужно учитывать запуск самого приложения, подготовку тестовых данных, переменные окружения и сбор артефактов при падениях
- конкретные команды запуска сервера зависят от сборщика, backend и конфигурации проекта

## 9. e2e и React: важные нюансы для собеседования

### проверка через DOM, а не внутреннего состояния

- тесты должны в первую очередь проверять то, что доступно пользователю: текст, состояние кнопок, видимость ошибок, URL и итоговый результат
- прямое чтение внутренних переменных React или зависимость от реализации компонента делает тесты хрупкими: рефакторинг без изменения поведения пользователя может сломать их

### роутинг и прямое открытие URL

- недостаточно проверить, что переход на `/dashboard` работает после клика по ссылке
- полезно отдельно проверить, что защищённая страница корректно открывается по прямому URL, а неавторизованный пользователь перенаправляется на `/login`
- такие сценарии могут выявлять проблемы с конфигурацией сервера, маршрутизацией и восстановлением сессии

### тестирование ошибок

- e2e нужны не только для happy path
- стоит проверить ошибки авторизации, пустые формы, сетевые сбои и пустые результаты поиска, если эти сценарии важны для продукта
- однако множество комбинаций ошибок проще проверять на уровне unit- и integration-тестов, оставляя e2e только наиболее значимые сценарии

### тестирование модальных окон

- для модального окна можно проверить открытие, доступность основных действий, закрытие по кнопке и ожидаемое поведение после подтверждения
- если модальное окно использует React Portal, пользовательские события и видимый DOM всё равно можно проверять через браузер, не привязываясь к внутреннему устройству дерева React

### запуск в разных браузерах

- браузерное поведение может отличаться, поэтому кросс-браузерные проверки полезны для критичных сценариев
- не обязательно запускать каждый тест во всех браузерах на каждом коммите: иногда достаточно выбрать основной браузер для быстрых проверок и запускать расширенный набор отдельно

## 10. что важно знать на каждом уровне требований

- в твоём списке e2e-тестирование разделено на три уровня владения, поэтому ориентироваться стоит на следующие результаты

### уровень 1

понимать назначение e2e и отличия от других тестов

- объяснять, зачем проверять приложение через пользовательские сценарии
- различать unit, integration и e2e на примерах
- понимать место e2e в testing pyramid
- объяснять, почему e2e-тесты обычно дороже и медленнее

### уровень 2

использовать Cypress или другой фреймворк

- самостоятельно настроить Cypress в React-проекте
- написать сценарий с навигацией, вводом данных и проверкой результата
- использовать устойчивые локаторы и автоматические ожидания
- работать с `cy.intercept()`, тестовыми данными и диагностикой падений
- запускать тесты локально и понимать базовую интеграцию с CI

### уровень 3

регулярно писать e2e в реальных проектах

- выбирать сценарии, которые действительно нужно проверять на уровне браузера
- поддерживать тестовые окружения, пользователей и данные
- устранять flaky tests и диагностировать причины падений
- разделять проверки UI и проверки настоящих интеграций с backend
- учитывать время выполнения тестов, параллельный запуск, отчёты и артефакты CI

## 11. как ответить на собеседовании

- пример ответа, который объединяет основные понятия:

- e2e-тестирование проверяет приложение с точки зрения пользователя и охватывает полный пользовательский сценарий, например авторизацию или оформление заказа
- в отличие от unit-тестов, которые проверяют изолированную логику, и integration-тестов, которые проверяют взаимодействие нескольких частей системы, e2e-тесты обычно работают через настоящий браузер и могут затрагивать frontend, API и backend
- в React-проектах для e2e часто используют Cypress или Playwright
- тесты выполняют действия пользователя, проверяют DOM, URL, сетевые взаимодействия и конечный результат
- чтобы тесты оставались стабильными, необходимо использовать надёжные селекторы, автоматические ожидания, изолированные тестовые данные и по возможности независимые сценарии
- e2e обычно покрывают наиболее критичные пользовательские потоки, а детальные варианты бизнес-логики проверяются более быстрыми unit- и integration-тестами

- с учётом твоего опыта frontend-разработки примерно в четыре года, для уверенного прохождения интервью я бы сделал акцент не только на определениях, но и на практическом понимании того, почему e2e-тест может быть нестабильным, какие части системы он действительно проверяет и как правильно выбрать границу между e2e и integration-тестом
