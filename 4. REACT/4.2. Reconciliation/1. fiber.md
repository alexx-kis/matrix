# что такое Fiber в React

- `Fiber` — это внутренняя архитектура React, которая отвечает за то, **как React вычисляет изменения в UI и выполняет обновление дерева**

- проще всего воспринимать Fiber не как отдельный API, а как **структуру данных + алгоритм reconciliation**, который позволяет React разбивать работу по обновлению интерфейса на небольшие части

- до Fiber React в основном выполнял reconciliation как одну большую непрерывную работу

- если дерево было большим, React мог надолго занять главный поток JavaScript

- пока эта работа выполнялась, браузер не мог нормально обрабатывать другие задачи, например ввод с клавиатуры, события или перерисовку

- Fiber был создан в React 16 именно для того, чтобы React мог **контролировать выполнение reconciliation и при необходимости прерывать его**

## главная идея

- представим, что React получил новое состояние компонента

```js
setState(...)
```

- React должен понять, что изменилось

```
старое дерево React
        ↓
новое дерево React
        ↓
сравнить их
        ↓
понять изменения
        ↓
изменить Browser DOM
```

- вот эта работа по сравнению старого и нового дерева называется **reconciliation**

- Fiber превращает эту работу из условного «обработать всё дерево сразу» в работу с отдельными **fiber-узлами**

- условно вместо такого подхода

```
начали reconciliation
        ↓
обработали всё дерево
        ↓
закончили
```

- появляется возможность работать примерно так

```
fiber A
  ↓
fiber B
  ↓
fiber C
  ↓
пауза
  ↓
браузер делает свою работу
  ↓
fiber D
  ↓
fiber E
```

- это и есть одна из главных идей Fiber

## что такое Fiber-узел

- Fiber-узел — это объект JavaScript, который описывает **конкретную единицу работы React**
- например, если у нас есть

```jsx
<App>
  <Header />
  <Main />
  <Footer />
</App>
```

- React может иметь соответствующие Fiber-узлы примерно такого вида

```
App Fiber
├── Header Fiber
├── Main Fiber
└── Footer Fiber
```

- Fiber хранит информацию, необходимую React для работы с конкретной частью дерева

- например, там есть информация о типе компонента, его `props`, состоянии, связях с другими Fiber-узлами и результате reconciliation

- очень грубо можно представить Fiber так

```js
const fiberNode = {
  type: SomeComponent,
  props: {...},
  stateNode: ...,

  child: ...,
  sibling: ...,
  return: ...,

  alternate: ...,

  flags: ...,
  subtreeFlags: ...,
}
```

- это **сильно упрощённая модель**, а не точное описание актуального внутреннего исходного кода React

## почему Fiber называется Fiber

- название связано с идеей «волокна» или маленькой единицы работы

- раньше reconciliation можно было представить как большую непрерывную задачу

- Fiber позволяет представить её как множество небольших задач, которые можно обрабатывать отдельно

- поэтому полезная аналогия такая

```
reconciliation
       ↓
   большая работа
       ↓
┌──────┬──────┬──────┬──────┐
│fiber │fiber │fiber │fiber │
└──────┴──────┴──────┴──────┘
```

## как устроено Fiber-дерево

- Fiber-дерево по смыслу соответствует React-дереву, но технически устроено интереснее обычного дерева
- вместо массива детей Fiber использует связи

```
child
sibling
return
```

- `child` указывает на первого ребёнка

- `sibling` указывает на следующего брата

- `return` указывает обратно на родителя

- например, React-дерево

```
App
├── Header
├── Main
└── Footer
```

- может быть представлено через такие связи

```
        App
         |
       child
         ↓
      Header
         |
      sibling
         ↓
       Main
         |
      sibling
         ↓
      Footer

Header
  ↑
return
  |
 App
```

- благодаря этому React может обходить дерево без необходимости хранить полноценный стек рекурсивных вызовов

## что происходит при обновлении

- допустим, у нас есть компонент

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  return <div>{count}</div>;
}
```

- пользователь вызывает

```js
setCount(1);
```

- React получает сигнал, что часть дерева должна быть обновлена

- дальше React должен определить, какой результат должен получиться после обновления

- условно процесс выглядит так

```
setCount(1)
    ↓
React получает update
    ↓
создаётся/обновляется work
    ↓
начинается reconciliation
    ↓
строится новая версия Fiber-дерева
    ↓
React определяет изменения
    ↓
commit
    ↓
изменяется Browser DOM
```

## самое важное: render phase и commit phase

- это одна из ключевых вещей, которую стоит знать для собеседования

- работа React условно разделяется на две большие фазы

```
Render phase
     ↓
Commit phase
```

### render phase

- во время render phase React **вычисляет**, каким должно быть новое дерево

- здесь React вызывает компоненты, сравнивает элементы и определяет необходимые изменения

- именно здесь Fiber особенно важен

- например

```jsx
<div className='counter'>{count}</div>
```

- после изменения `count` React должен вычислить новый результат

```
старый результат
<div className="counter">0</div>

новый результат
<div className="counter">1</div>
```

- render phase определяет примерно следующее

```
"нужно изменить текст с 0 на 1"
```

- принципиально важно, что render phase может быть **прервана, продолжена или выполнена заново**
- поэтому код во время render должен быть чистым и не должен рассчитывать на то, что React обязательно выполнит его ровно один раз

### commit phase

- после того как React закончил вычислять изменения, начинается commit phase
- здесь React уже применяет необходимые изменения к реальным системам, например к DOM

```
Render phase
"что нужно изменить?"
        ↓
Commit phase
"применяем изменения"
```

- commit phase нельзя просто произвольно прервать посередине так же, как render phase
- пользователь должен увидеть согласованное состояние интерфейса

## почему нельзя просто сразу менять DOM

- потому что React сначала должен определить **все необходимые изменения**

- если бы он менял DOM прямо во время обхода дерева, промежуточное состояние могло бы быть частично обновлённым

- Fiber позволяет сначала подготовить изменения

```
старое дерево
      ↓
вычисление
      ↓
подготовленное новое состояние
      ↓
commit
      ↓
DOM
```

- поэтому render phase можно рассматривать как подготовку результата, а commit phase — как его применение

## как Fiber обходит дерево

- здесь начинается более глубокая часть темы

- Fiber использует обход дерева, который можно условно представить как

```
begin
  ↓
child
  ↓
child
  ↓
...
  ↓
complete
```

- у каждого Fiber есть этап, когда React **начинает работу с ним**, и этап, когда React **завершает работу с ним**

- условно

```
        A
       / \
      B   C
     / \
    D   E
```

- обход может выглядеть примерно так

```
A begin
  ↓
B begin
  ↓
D begin
  ↓
D complete
  ↓
E begin
  ↓
E complete
  ↓
B complete
  ↓
C begin
  ↓
C complete
  ↓
A complete
```

- это важная деталь Fiber
- React не просто рекурсивно вызывает функцию для каждого элемента и забывает о ней
- он хранит состояние обхода непосредственно в Fiber-структуре

## beginWork

- `beginWork` — внутренняя операция React, которая начинает работу над Fiber

- здесь React может понять, что нужно сделать с данным узлом и какие дочерние Fiber нужно обработать

- например, для компонента React может получить его новый результат

```jsx
<Main />
```

- затем продолжить обработку дочерних элементов

## completeWork

- после обработки дочерних Fiber React возвращается к родительскому Fiber

- происходит `completeWork`

- здесь React завершает обработку текущего узла и подготавливает информацию, необходимую для дальнейшего commit

- поэтому можно запомнить

```
beginWork
    ↓
спускаемся вниз

completeWork
    ↓
поднимаемся вверх
```

## где здесь прерывание

- представим большое дерево

```
App
├── Header
├── Sidebar
├── Main
│   ├── List
│   ├── Item
│   ├── Item
│   └── Item
└── Footer
```

- React начинает обход

```
App
 ↓
Header
 ↓
Sidebar
 ↓
Main
 ↓
List
```

- если работы много, React может остановиться между единицами работы
- браузер получает возможность выполнить другие задачи
- затем React может продолжить

```
React
 ↓
Fiber
 ↓
Fiber
 ↓
пауза
 ↓
browser
 ↓
React
 ↓
Fiber
 ↓
Fiber
```

- именно это делает React более **конкурентным**
- термин `concurrent` здесь не означает, что JavaScript внезапно начал выполняться параллельно на нескольких потоках
- JavaScript обычно всё ещё выполняется на одном main thread
- React просто получает возможность **управлять тем, какую работу выполнять сейчас, а какую позже**

## scheduler

- чтобы решать, какую работу выполнять и когда, React использует систему планирования
- условно можно представить её так

```
updates
   ↓
scheduler
   ↓
какая работа важнее?
   ↓
Fiber work
```

- например, обновление, связанное с пользовательским вводом, может быть важнее менее срочной работы

- поэтому React может отдавать приоритет определённым обновлениям

- здесь важно не смешивать понятия

```
Fiber = структура и механизм выполнения reconciliation

Scheduler = механизм планирования работы
```

- они тесно связаны, но это не одно и то же

## зачем нужен alternate

- одна из очень важных деталей Fiber — поле `alternate`

- React фактически работает с двумя связанными версиями Fiber-дерева

```
current tree
      ↕
workInProgress tree
```

- `current` — дерево, которое сейчас считается отображённым

- `workInProgress` — дерево, над которым React сейчас работает

- условно

```
        current
           ↓
       App Fiber
       /       \
    Header     Main


     alternate

        workInProgress
              ↓
          App Fiber
          /      \
      Header     Main
```

- после завершения работы React может сделать подготовленное дерево новым current

```
до commit

current
   ↓
старое дерево

workInProgress
   ↓
новое дерево


после commit

current
   ↓
новое дерево
```

- это одна из причин, почему React может сначала подготовить новое состояние, а уже потом применить его

## flags

- Fiber также содержит информацию о том, какие действия необходимо выполнить

- исторически это называлось `effectTag`, в современных версиях используется система `flags`

- например, условно Fiber может иметь информацию

```
Placement
Update
Deletion
```

- смысл примерно такой

```
Placement → нужно добавить узел

Update → нужно обновить существующий узел

Deletion → нужно удалить узел
```

- поэтому во время render phase React не обязательно сразу изменяет DOM
- он может пометить Fiber соответствующим `flag`

```
Fiber
  ↓
flags: Update
```

- а потом во время commit phase React применит эти изменения

## пример полного процесса

- допустим, было

```jsx
<App>
  <h1>Hello</h1>
  <p>Count: 0</p>
</App>
```

- после обновления стало

```jsx
<App>
  <h1>Hello</h1>
  <p>Count: 1</p>
</App>
```

- React начинает с update

```
state changed
     ↓
schedule update
```

- затем работает с Fiber

```
App Fiber
   ↓
beginWork
   ↓
children
```

- React доходит до `p`

```
<p>Count: 0</p>
        ↓
<p>Count: 1</p>
```

- обнаруживает изменение
- Fiber получает соответствующую информацию об обновлении

```
p Fiber
flags → Update
```

- после завершения render phase React имеет подготовленный результат

```
workInProgress tree
        ↓
    Update flag
        ↓
    commit phase
        ↓
Browser DOM
        ↓
Count: 1
```

## самое глубокое понимание Fiber

- если на собеседовании попросят объяснить Fiber своими словами, я бы формулировал так

- **Fiber — это внутренняя архитектура React, которая представляет React-дерево в виде набора связанных Fiber-узлов и позволяет React выполнять reconciliation небольшими единицами работы, приостанавливать и продолжать эту работу, расставлять ей приоритеты, а затем отдельной commit-фазой применять подготовленные изменения к DOM**

- ещё короче

```
React update
     ↓
Fiber tree
     ↓
маленькие units of work
     ↓
можно планировать / прерывать / продолжать
     ↓
получаем изменения
     ↓
commit
     ↓
DOM
```

## что нужно знать для собеседования

- если вопрос звучит **What is Fiber?**, ответ должен включать архитектуру и возможность контролировать reconciliation

- если спрашивают **why was Fiber introduced?**, основная причина — сделать rendering более управляемым и позволить React не блокировать интерфейс большой непрерывной работой

- если спрашивают **can Fiber pause rendering?**, отвечаем — render/reconciliation work может быть прервано и продолжено, а commit должен выполняться согласованно

- если спрашивают **does Fiber use multiple threads?**, отвечаем — нет, Fiber сам по себе не делает JavaScript многопоточным

- если спрашивают **what is a Fiber node?**, отвечаем — это объект, представляющий единицу работы React и содержащий информацию, необходимую для reconciliation

- если спрашивают **what are child, sibling and return?**, отвечаем

```
child → первый ребёнок

sibling → следующий сосед

return → родитель
```

- если спрашивают **what are render and commit phases?**, отвечаем

```
render → вычислить, что должно измениться

commit → применить вычисленные изменения
```

- если спрашивают **what are current and workInProgress trees?**, отвечаем

```
current → уже отображённая версия

workInProgress → версия, которую React сейчас готовит
```

- если спрашивают **what are flags?**, отвечаем — это информация на Fiber о том, какие действия должны быть выполнены во время commit

## важный нюанс

- не стоит говорить, что Fiber — это просто «виртуальный DOM»

- Virtual DOM — более высокоуровневое понятие, обозначающее представление UI в виде JavaScript-структур

- Fiber — конкретная внутренняя архитектура React, которая среди прочего используется для reconciliation этих структур

- поэтому связь лучше держать в голове так

```
JSX
 ↓
React elements
 ↓
Fiber tree
 ↓
reconciliation
 ↓
prepared changes
 ↓
commit
 ↓
Browser DOM
```

- и ещё важнее — **Fiber не равен reconciliation**

- Fiber — архитектура, которая позволяет React организовать и выполнять reconciliation определённым образом

- на следующем уровне глубины стоит отдельно разобрать **как именно React проходит Fiber-дерево через `beginWork → child → sibling → completeWork`, где возникает возможность прерывания и как из этого получается commit**, потому что именно там находится самая интересная внутренняя механика Fiber
