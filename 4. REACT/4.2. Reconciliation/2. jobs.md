# jobs в React

- в React `job` — это отдельная работа, которую React должен выполнить, например обновить конкретную часть UI, пересчитать дерево компонентов или применить изменения к DOM
- ключевая идея здесь в том, что React не обязан выполнять всю работу сразу и строго в том порядке, в котором она появилась
- вместо этого React может определить, **какая работа сейчас важнее**, выполнить её раньше, а менее важную отложить

## зачем React вообще нужна приоритизация

- представим, что пользователь печатает в `<input>`

- одновременно React должен выполнить большое обновление дерева из нескольких тысяч компонентов

- если React начнёт полностью выполнять это большое обновление прямо сейчас и не сможет его прервать, браузер может надолго перестать реагировать на ввод

- пользователь почувствует задержку между нажатием клавиши и появлением символа

- поэтому React старается разделять работу по приоритету

- условно можно представить несколько задач

```
обработка ввода пользователя       → очень важно
обновление интерфейса после ввода   → важно
перерисовка второстепенного списка  → менее важно
фоновое обновление                  → ещё менее важно
```

- React стремится сначала выполнить работу, которая сильнее влияет на непосредственное взаимодействие пользователя с интерфейсом

## что именно является job

- важно не воспринимать `job` как конкретный объект или конкретный API React
- в контексте внутреннего устройства React это скорее **единица работы**, которую React должен выполнить
- например, React получил обновление состояния

```js
setCount(nextCount);
```

- после этого появляется работа, связанная с обработкой этого обновления

- React должен понять, какие компоненты нужно пересчитать, какие Fiber-ноды нужно обновить и какие изменения в итоге необходимо применить

- поэтому упрощённо можно представить

```
update
  ↓
создание работы
  ↓
определение приоритета
  ↓
выполнение работы
  ↓
commit изменений
```

- при этом реальная внутренняя архитектура React сложнее, поэтому `job` не стоит представлять как буквально один объект с полями `priority` и `callback`

## откуда React знает приоритет

- приоритет зависит прежде всего от **того, что вызвало обновление**

- обновление, связанное с непосредственным взаимодействием пользователя, обычно имеет более высокий приоритет

- обновление, которое можно выполнить позже без заметного ущерба для UX, может получить более низкий приоритет

- например, React различает ситуации вроде

```
пользователь нажал кнопку
пользователь печатает
пользователь навёл мышь
обычное обновление состояния
transition
```

- это позволяет React понимать, что разные обновления не обязательно одинаково срочные

## связь jobs с Fiber

- здесь важно связать несколько тем, которые мы уже разбирали

```
Fiber
  ↓
представляет работу над конкретным участком React-дерева

Scheduler
  ↓
решает, когда эту работу выполнять

Priority
  ↓
определяет, насколько эта работа срочная

Job
  ↓
сама работа, которую необходимо выполнить
```

- Fiber сделал возможным представление рендеринга как набора небольших частей работы
- благодаря этому React может не обязательно пройти всё дерево целиком за один непрерывный JavaScript-вызов
- он может обработать часть Fiber-дерева, остановиться и позже продолжить

## важный момент: priority ≠ порядок выполнения

- наличие высокого приоритета не означает, что React буквально создаёт очередь вида

```
job A
job B
job C
```

- а затем всегда выполняет их строго по приоритету

- реальная система React использует более сложную модель, связанную с **lanes**, временем, доступностью браузера и типом обновления

- главное понимать принцип

```
есть несколько обновлений
        ↓
React определяет их срочность
        ↓
срочная работа получает возможность выполниться раньше
        ↓
несрочная работа может быть отложена
```

## lanes

- в современном React приоритизация во многом реализована через механизм **lanes**

- lane можно представить как своеобразный канал, которому соответствует определённый уровень приоритета

- обновление получает одну или несколько lanes

- по этим lanes React понимает, какую работу сейчас имеет смысл выбирать

- поэтому хорошая модель для собеседования выглядит так

```
update
  ↓
lane
  ↓
priority
  ↓
React выбирает подходящую работу
  ↓
render
  ↓
commit
```

- при этом lanes позволяют не просто сказать «это обновление важное», а более гибко группировать и отслеживать разные виды работы

## может ли job быть прервана

- да, именно здесь появляется одно из главных преимуществ Fiber
- если React выполняет работу низкого приоритета и появляется более срочное обновление, React может остановить текущую работу и заняться более важной

```
low priority job
      ↓
работа началась
      ↓
появилось срочное обновление
      ↓
low priority job откладывается
      ↓
high priority job выполняется
      ↓
React возвращается к low priority job
```

- это и есть одна из ключевых идей **concurrent rendering**

## render и commit здесь очень важны

- React может прерывать и переигрывать работу на этапе `render`

- но `commit` устроен иначе

- когда React уже решил, какие изменения нужно применить к реальному DOM, этот этап должен выполняться согласованно

- поэтому упрощённо

```
render
↓
может быть прерван
может быть продолжен
может быть отброшен
может быть выполнен повторно

commit
↓
применение готовых изменений
```

- именно поэтому нельзя говорить, что React «прерывает изменение DOM в любой момент»
- React в первую очередь делает прерываемым **вычисление следующего состояния UI**

## простой пример

- допустим, есть большой список

```js
function LargeList({ items }) {
  return items.map((item) => <Item key={item.id} item={item} />);
}
```

- пользователь запускает обновление, которое приводит к перерасчёту большого количества `Item`
- React начинает проходить Fiber-дерево
- если работа достаточно большая, её можно разбить на части
- во время этой работы пользователь может выполнить другое действие
- если новое обновление имеет более высокий приоритет, React может переключиться на него

```
обработка большого списка
        ↓
Fiber 1
Fiber 2
Fiber 3
Fiber 4
        ↓
пришло срочное обновление
        ↓
обработка срочного обновления
        ↓
возвращаемся к списку
```

- именно это позволяет React не блокировать пользовательский интерфейс большой синхронной работой

## что важно сказать на собеседовании

- React представляет обновления как работу, которую необходимо выполнить над React-деревом
- эта работа может иметь разный приоритет в зависимости от типа обновления и контекста, в котором оно произошло
- современный React использует механизм `lanes` для отслеживания и приоритизации обновлений
- Fiber позволяет представить работу над деревом в виде небольших частей, которые можно обрабатывать постепенно
- поэтому React может начать менее приоритетную работу, остановить её при появлении более срочной и продолжить позже
- особенно важна возможность прерывать `render`-работу, потому что именно вычисление нового дерева может быть большим
- `commit` является отдельной фазой, где React применяет уже подготовленные изменения
- благодаря этому приоритизации и прерываемому render React может сохранять отзывчивость интерфейса даже при больших обновлениях

## короткая модель для запоминания

```
update
  ↓
получает приоритет / lane
  ↓
React выбирает наиболее подходящую работу
  ↓
Fiber разбивает работу на части
  ↓
render может быть прерван
  ↓
более срочная работа может получить управление
  ↓
готовый результат попадает в commit
  ↓
изменения применяются
```

- если сформулировать совсем коротко, **jobs — это работа, которую React должен выполнить, а приоритизация определяет, какую работу имеет смысл выполнять сейчас, какую можно отложить и какую можно прервать ради более срочной**
