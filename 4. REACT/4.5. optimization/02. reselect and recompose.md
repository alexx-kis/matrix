# Reselect и Recompose в React

- в этом блоке важно понять две библиотеки, которые решали разные задачи в React-приложениях: Reselect помогала эффективно вычислять производные данные из Redux state, а Recompose — переиспользовать логику компонентов с помощью функциональных композиционных утилит
- обе библиотеки особенно актуальны для понимания legacy-кода, старых Redux-приложений и истории развития React, хотя их идеи по-прежнему полезны и в современном React

## 1. Reselect — зачем нужна библиотека

### базовая проблема: вычисляемые данные в Redux

- представим, что в Redux хранится список пользователей, а компоненту нужны только активные пользователи

```js
const usersState = {
  users: [
    { id: 1, name: 'Анна', active: true },
    { id: 2, name: 'Иван', active: false },
    { id: 3, name: 'Мария', active: true },
  ],
};
```

- можно отфильтровать пользователей прямо внутри `useSelector`

```js
const activeUsers = useSelector((state) => state.users.filter((user) => user.active));
```

- проблема заключается в том, что при каждом вызове селектора `filter()` создаёт новый массив, даже если исходные данные не изменились
- React-Redux по умолчанию сравнивает результат `useSelector` с предыдущим результатом через `===`, поэтому новый массив может вызвать лишний рендер компонента

```js
[1, 2, 3] === [1, 2, 3]; // false
```

- это не означает, что любой вызов селектора автоматически вызывает рендер: компонент перерисовывается, когда сравнение показывает изменение выбранного значения, либо по другим причинам, например при изменении его props или собственного state

### что делает Reselect

- Reselect позволяет создавать мемоизированные селекторы — функции, которые вычисляют результат на основе входных данных и повторно используют ранее вычисленный результат, если входы не изменились
- вместо того чтобы фильтровать пользователей при каждом вызове, можно объявить селектор один раз

```js
import { createSelector } from 'reselect';

const selectUsers = (state) => state.users;

const selectActiveUsers = createSelector([selectUsers], (users) => users.filter((user) => user.active));
```

- здесь `selectUsers` — входной селектор, который извлекает исходные данные, а функция `users => users.filter(...)` — функция вычисления результата, которую часто называют `resultFunc`
- при первом вызове `selectActiveUsers(state)` Reselect получает массив пользователей и вычисляет активных пользователей
- при следующем вызове, если входные значения остались прежними с точки зрения используемого механизма сравнения, библиотека возвращает закэшированный результат, не выполняя фильтрацию повторно

```js
const firstResult = selectActiveUsers(state);
const secondResult = selectActiveUsers(state);

console.log(firstResult === secondResult); // true
```

- в примере предполагается, что между вызовами состояние не изменилось и используется стандартная конфигурация селектора

## 2. как работает мемоизация в Reselect

- чтобы уверенно объяснять Reselect на собеседовании, важно понимать не только назначение `createSelector`, но и то, что именно библиотека запоминает
- в упрощённом виде механизм выглядит так

```
Redux state
    ↓
input selectors
    ↓
полученные входные значения
    ↓
проверка кэша
    |
    └─────входы прежние ----> вернуть прошлый результат
    |
    └──── входы изменились -> выполнить resultFunc
                                  ↓
                           сохранить результат
```

- Reselect не сравнивает произвольно всё дерево Redux state и не отслеживает изменения вложенных объектов самостоятельно — он получает значения из входных селекторов и использует механизм мемоизации для определения необходимости повторного вычисления

### почему важна иммутабельность

- допустим, Redux state содержит массив пользователей, а reducer изменяет его напрямую

```js
state.users[0].active = false;
```

- ссылка на массив `state.users` при этом остаётся прежней, поэтому селектор, зависящий только от этой ссылки, может не заметить изменение
- при иммутабельном обновлении создаётся новый массив, и входной селектор возвращает новую ссылку

```js
const nextUsers = state.users.map((user) => (user.id === 1 ? { ...user, active: false } : user));
```

- именно поэтому иммутабельность Redux state важна не только для предсказуемости состояния, но и для корректной работы селекторов, основанных на ссылочном сравнении

### входные селекторы и результирующая функция

- рассмотрим пример с поиском пользователей по запросу

```js
import { createSelector } from 'reselect';

const selectAllUsers = (state) => state.users;
const selectSearchQuery = (state) => state.searchQuery;

const selectMatchingUsers = createSelector([selectAllUsers, selectSearchQuery], (users, query) =>
  users.filter((user) => user.name.toLowerCase().includes(query.toLowerCase())),
);
```

- `selectAllUsers` и `selectSearchQuery` — input selectors, которые извлекают необходимые значения из состояния
- последняя функция — `resultFunc`, которая получает результаты входных селекторов в том же порядке и вычисляет итоговый массив
- если изменится `searchQuery`, результат потребуется пересчитать, потому что изменился один из входов
- если изменится несвязанная часть Redux state, например `state.theme`, а пользователи и запрос останутся прежними, результирующая функция сможет вернуть предыдущий массив без повторной фильтрации
- здесь есть важный нюанс: в зависимости от версии Reselect, конфигурации мемоизации и характера вызовов могут существовать несколько уровней кэширования; поэтому не стоит сводить внутренний механизм ко всему лишь к одной проверке аргументов

## 3. основные API Reselect

### `createSelector`

- это основной API библиотеки, позволяющий объединять входные селекторы и функцию вычисления результата

```js
const selectUserCount = createSelector([selectAllUsers], (users) => users.length);
```

- возвращаемый селектор можно вызывать как обычную функцию и использовать внутри `useSelector`

```js
const userCount = useSelector(selectUserCount);
```

- селектор с несколькими входами получает значения в порядке объявления селекторов

```js
const selectActiveUserCount = createSelector(
  [selectAllUsers, selectSearchQuery],
  (users, query) => users.filter((user) => user.active && user.name.toLowerCase().includes(query.toLowerCase())).length,
);
```

- в этом примере `query` участвует в вычислении, поэтому изменение запроса может потребовать повторного подсчёта

### селекторы с параметрами

- селектору можно передавать дополнительные аргументы, например идентификатор пользователя

```js
const selectUserById = createSelector([selectAllUsers, (state, userId) => userId], (users, userId) =>
  users.find((user) => user.id === userId),
);
```

- использование выглядит так

```js
const user = selectUserById(state, 42);
```

- все input selectors получают исходные аргументы селектора, поэтому их сигнатуры должны быть совместимы с вызовом `selectUserById(state, 42)`
- если входные селекторы возвращают одинаковые значения, мемоизация может повторно использовать результат; однако эффективность кэширования при множестве разных аргументов зависит от конфигурации memoizer и версии Reselect

### композиция селекторов

- селекторы можно строить друг на друге, благодаря чему логика извлечения данных остаётся изолированной и переиспользуемой

```js
const selectActiveUsers = createSelector([selectAllUsers], (users) => users.filter((user) => user.active));

const selectActiveUserNames = createSelector([selectActiveUsers], (users) => users.map((user) => user.name));
```

- `selectActiveUserNames` не знает, как устроен исходный Redux state: он использует другой селектор как источник данных
- это позволяет разделять ответственность: одни селекторы извлекают данные, другие преобразуют их, а компоненты получают уже готовое представление данных

### дополнительные API и возможности

- в зависимости от версии Reselect также доступны дополнительные инструменты для настройки мемоизации и диагностики
- `createSelectorCreator` — позволяет создавать селекторы с пользовательской конфигурацией мемоизации
- `lruMemoize` — мемоизатор с кэшем, ограниченным по размеру; в старых версиях он был известен как `defaultMemoize`
- `weakMapMemoize` — мемоизатор, который строит кэш на основе аргументов с использованием `WeakMap` там, где это возможно
- `createStructuredSelector` — помогает собрать объект из нескольких селекторов, хотя для простых случаев часто достаточно обычного объекта с вызовами селекторов
- `recomputations()` и `resetRecomputations()` — позволяют узнать число вычислений результирующей функции и сбросить этот счётчик
- конкретные настройки и значения по умолчанию зависят от версии библиотеки, поэтому при работе с legacy-кодом важно учитывать установленную версию

## 4. когда Reselect действительно нужен

- Reselect особенно полезен, когда селектор выполняет дорогие вычисления или возвращает новые объекты и массивы, от стабильности ссылок которых зависит поведение компонентов
- например, он подходит для фильтрации и сортировки больших списков, объединения данных из разных частей Redux state, подготовки данных для графиков и вычисления агрегированных значений
- при этом не каждый селектор нужно оборачивать в `createSelector`: простое чтение `state.users` не создаёт нового массива и обычно не требует мемоизации

```js
const selectUsers = (state) => state.users;
```

- если вычисление дешёвое, а результат не создаёт проблем со стабильностью ссылок, дополнительная мемоизация может быть избыточной
- также важно помнить, что Reselect не предотвращает все рендеры React-компонента — он оптимизирует вычисление производных данных и позволяет сохранять ссылку на результат, а решение о рендере зависит и от других механизмов React

# 5. Recompose — зачем нужна библиотека

- Recompose — библиотека функциональных утилит для композиции React-компонентов, особенно популярная до широкого распространения Hooks
- её основная идея заключалась в том, чтобы выносить логику компонента в небольшие функции и объединять их, вместо того чтобы постоянно добавлять новые методы, состояние и lifecycle-методы в классы
- сегодня многие задачи Recompose решаются с помощью React Hooks, но библиотека остаётся полезной для понимания старых React-проектов

### проблема, которую решала Recompose

- представим компонент, который должен хранить состояние счётчика

```js
function CounterView({ count, onIncrement }) {
  return <button onClick={onIncrement}>Счётчик: {count}</button>;
}
```

- сам компонент только отображает данные, но где-то необходимо хранить состояние и передавать обработчик изменения
- в современном React это естественно решается через `useState`, а в старом подходе с Recompose можно было использовать `withState` и `withHandlers`

```js
import { compose, withState, withHandlers } from 'recompose';

const enhanceCounter = compose(
  withState('count', 'setCount', 0),
  withHandlers({
    onIncrement:
      ({ count, setCount }) =>
      () =>
        setCount(count + 1),
  }),
);

const EnhancedCounter = enhanceCounter(CounterView);
```

- `withState` добавляет компоненту props `count` и `setCount`, связанные с внутренним состоянием
- `withHandlers` добавляет prop `onIncrement`, содержащий обработчик события
- `compose` объединяет эти функции в одну функцию, которая принимает компонент и возвращает улучшенный компонент
- в результате `CounterView` не управляет собственным состоянием — он получает данные и обработчик через props
- это пример так называемого higher-order component (HOC): функции, которая принимает компонент и возвращает новый компонент с дополнительным поведением

## 6. основные категории API Recompose

- API библиотеки удобнее запоминать не как случайный набор функций, а как группы по назначению

### управление props

- `withProps` — добавляет props, вычисленные из существующих props
- `mapProps` — преобразует весь объект props перед передачей компоненту
- `withPropsOnChange` — пересчитывает дополнительные props при изменении выбранных входных props
- `defaultProps` — задаёт значения props по умолчанию
- `renameProp` — переименовывает один prop
- `flattenProp` — разворачивает свойства вложенного объекта в общий объект props
- например, `withProps` можно использовать для вычисления производного значения

```js
import { withProps } from 'recompose';

const enhanceGreeting = withProps(({ firstName }) => ({
  greeting: `Привет, ${firstName}`,
}));
```

- если компоненту передан `firstName: 'Анна'`, HOC добавит prop `greeting` со значением `Привет, Анна`

### работа с состоянием и обработчиками

- `withState` — добавляет локальное состояние и функцию его обновления
- `withStateHandlers` — позволяет описывать обработчики, обновляющие состояние на основе текущего состояния и переданных props
- `withHandlers` — создаёт обработчики событий, доступные через props
- `withReducer` — добавляет состояние, обновляемое через reducer, по аналогии с `useReducer`
- `withStateHandlers` был полезен, когда хотелось объединить состояние и логику его обновления, сохранив компонент представления максимально простым

### жизненный цикл и обновления

- `lifecycle` — позволяет описывать lifecycle-методы компонента в объекте, например `componentDidMount` и `componentWillUnmount`
- `shouldUpdate` — задаёт условие, по которому определяется необходимость обновления компонента
- `pure` — применяет поверхностную проверку props и state, чтобы пропускать некоторые ненужные обновления
- `onlyUpdateForKeys` — ограничивает обновления проверкой выбранных props
- `branch` — выбирает одну из веток композиции в зависимости от условия
- `renderComponent` и `renderNothing` — позволяют задать поведение при выборе соответствующей ветки
- эти утилиты помогали организовать поведение без непосредственного написания классов, но не устраняли все сложности жизненного цикла и сравнения ссылок

### контекст и композиция

- `getContext` и `withContext` — утилиты для работы с legacy Context API React
- `nest` — позволяет вложить несколько компонентов или обёрток
- `compose` — объединяет несколько HOC в одну функцию
- `getDisplayName` и `wrapDisplayName` — помогают формировать имена компонентов для отладки
- `toClass` — преобразует функциональный компонент в class-компонент, когда это требовалось библиотеке или конкретному сценарию
- этот перечень покрывает основные категории API, а не все функции библиотеки

## 7. `compose` — как объединять HOC

- одна из ключевых идей Recompose — не создавать огромную функцию-обёртку вручную, а собирать поведение из независимых HOC
- без `compose` пример со счётчиком выглядел бы так

```js
const EnhancedCounter = withState(
  'count',
  'setCount',
  0,
)(
  withHandlers({
    onIncrement:
      ({ count, setCount }) =>
      () =>
        setCount(count + 1),
  })(CounterView),
);
```

- при большом количестве обёрток такая конструкция становится трудной для чтения, поэтому используется `compose`

```js
const enhanceCounter = compose(
  withState('count', 'setCount', 0),
  withHandlers({
    onIncrement:
      ({ count, setCount }) =>
      () =>
        setCount(count + 1),
  }),
);

const EnhancedCounter = enhanceCounter(CounterView);
```

- `compose` позволяет читать композицию как последовательность преобразований компонента, а не как набор вложенных скобок
- важно учитывать порядок: композиция функций обычно работает справа налево, а порядок обёрток влияет на то, какие props доступны каждому HOC

## 8. Recompose и современный React

- многие сценарии, для которых раньше использовали Recompose, теперь решаются с помощью Hooks
- для сравнения возьмём тот же счётчик

### старый подход: Recompose

```js
const enhanceCounter = compose(
  withState('count', 'setCount', 0),
  withHandlers({
    onIncrement:
      ({ count, setCount }) =>
      () =>
        setCount(count + 1),
  }),
);

const EnhancedCounter = enhanceCounter(CounterView);
```

### современный подход: Hooks

```js
import { useState } from 'react';

function CounterWithHooks() {
  const [count, setCount] = useState(0);

  function handleIncrement() {
    setCount((previousCount) => previousCount + 1);
  }

  return <button onClick={handleIncrement}>Счётчик: {count}</button>;
}
```

- в современном варианте состояние и его обновление находятся непосредственно в функциональном компоненте, а отдельная библиотека для композиции поведения не нужна
- обрати внимание на функциональное обновление `setCount(previousCount => previousCount + 1)`: оно использует актуальное предыдущее значение состояния и не зависит от значения `count`, захваченного замыканием
- Hooks не заменяют HOC полностью: HOC по-прежнему может быть полезен для интеграции с существующими компонентами, предоставления общего поведения или работы с библиотеками, чей API построен вокруг обёрток

## 9. типичные ошибки и нюансы на собеседовании

- Reselect не хранит Redux state целиком — он мемоизирует вычисления на основании входных значений, которые извлекают input selectors
- Reselect не исправляет мутации — если входные ссылки не изменились, селектор может не обнаружить изменение вложенных данных
- не каждый селектор требует `createSelector` — обычный селектор, который возвращает существующее значение из state, часто вполне достаточен
- Reselect и Recompose решают разные задачи — первая библиотека занимается мемоизацией селекторов, вторая — композицией React-компонентов и их поведения
- Recompose не является обязательной частью современного React — её API во многом исторический, а для новых компонентов обычно предпочтительнее Hooks, если нет конкретной причины использовать HOC
- `pure` в Recompose и `createSelector` — не одно и то же — `pure` оптимизирует обновление компонента на основе поверхностного сравнения, тогда как Reselect мемоизирует вычисление результата селектора

## 10. как отвечать на собеседовании

### что такое Reselect?

- Reselect — библиотека для создания мемоизированных селекторов, преимущественно используемых с Redux
- она позволяет вычислять производные данные и повторно использовать предыдущий результат, пока входные значения не изменились
- это помогает избежать лишних вычислений и сохранять стабильность ссылок на результаты

### что такое Recompose?

- Recompose — библиотека функциональных утилит для композиции React-компонентов, популярная до появления Hooks
- с помощью HOC и функций вроде `withState`, `withHandlers`, `withProps` и `lifecycle` она позволяла переиспользовать состояние, обработчики и другое поведение между компонентами
- в современных проектах большую часть этих задач решают Hooks, но Recompose всё ещё встречается в legacy-коде

### в чём главное различие?

- Reselect оптимизирует вычисление данных, а Recompose помогает организовывать и переиспользовать логику компонентов

## 11. что нужно знать на уровне deep understanding

- по Reselect: `createSelector`, input selectors, `resultFunc`, мемоизация, иммутабельность Redux state, селекторы с параметрами, композиция селекторов и диагностика повторных вычислений
- по Recompose: концепция HOC, `compose`, `withState`, `withStateHandlers`, `withHandlers`, `withProps`, `mapProps`, `lifecycle`, `pure`, `shouldUpdate`, `branch` и понимание того, как эти утилиты соотносятся с Hooks
- для твоего уровня подготовки наиболее важно не просто запомнить названия API, а уметь объяснить, какую конкретную проблему решает каждая библиотека, как устроен её механизм и в каких ситуациях её использование оправдано
