# Concurrent Mode и Suspense в React

- этот блок посвящён тому, как React управляет приоритетами обновлений, прерывает и возобновляет работу над интерфейсом, а также организует отображение UI, когда необходимые данные или код ещё не готовы
- важный нюанс: Concurrent Mode — историческое название концепции, а не актуальный режим, который нужно включать отдельным флагом; начиная с React 18 concurrent rendering используется отдельными возможностями React, когда они необходимы

## 1. что такое Concurrent Rendering

### базовые понятия

- в React рендеринг — это процесс, в ходе которого React вызывает компоненты, вычисляет новое дерево элементов и определяет, какие изменения необходимо внести в DOM
- при обычном синхронном рендеринге React начинает работу и выполняет её до завершения, не позволяя браузеру отрисовать кадр посередине этого JavaScript-вызова
- если обновление требует много вычислений, браузер может надолго потерять возможность реагировать на ввод пользователя, прокручивать страницу и отображать анимации

Например, компонент отображает 10 000 элементов списка, и обновление списка требует значительных вычислений

```js
function ProductList({ products }) {
  return (
    <ul>
      {products.map((product) => (
        <li key={product.id}>{product.name}</li>
      ))}
    </ul>
  );
}
```

- сам по себе этот компонент не обязательно будет медленным, но если подобное дерево большое, сложное и требует много вычислений, обновление может блокировать основной поток браузера

### как работает concurrent rendering

- Concurrent Rendering позволяет React начать вычисление нового UI, приостановить его, отдать управление браузеру и при необходимости продолжить работу позже

Упрощённо процесс выглядит так:

```
обновление состояния
        ↓
React начинает render phase
        ↓
вычисление нового дерева
        ↓
работа приостанавливается, если нужно
        ↓
браузер получает возможность обработать другие задачи
        ↓
React продолжает или перезапускает вычисления
        ↓
React завершает render phase
        ↓
commit phase: изменения применяются к DOM
```

- эта схема концептуальная: React не обязан приостанавливать каждое обновление, а браузер может выполнять другие задачи в промежутках между порциями работы React
- важно понимать, что React может отбросить результат незавершённого рендеринга и начать вычисление заново, например, если поступило более приоритетное обновление

### render phase и commit phase

- разделение на две фазы — основа понимания конкурентного рендеринга

#### Render phase

- React вызывает компоненты, вычисляет новое дерево и определяет необходимые изменения
- эта фаза может быть прервана, повторена или отброшена
- поэтому код рендеринга должен быть чистым: нельзя выполнять побочные эффекты непосредственно в теле компонента

#### Commit phase

- React применяет подготовленные изменения к DOM и выполняет связанные с фиксацией обновления действия
- commit не прерывается посередине так же, как render phase: React должен согласованно применить подготовленные изменения
- после commit браузер может отобразить обновлённый интерфейс

```js
function Counter() {
  const [count, setCount] = React.useState(0);

  // render phase: чистое вычисление UI
  const label = `Count: ${count}`;

  React.useEffect(() => {
    // побочный эффект после commit
    document.title = label;
  }, [label]);

  return <button onClick={() => setCount((value) => value + 1)}>{label}</button>;
}
```

- в примере вычисление `label` безопасно повторять, а изменение заголовка документа вынесено в эффект

### что concurrent rendering не означает

- это не означает, что React запускает компоненты параллельно в нескольких потоках JavaScript
- это не означает, что каждый рендеринг автоматически становится быстрее
- это не означает, что DOM изменяется частично по мере вычисления нового дерева
- это не означает, что любое обновление можно прервать в произвольной точке JavaScript-кода компонента
- основная идея — управление временем и приоритетами вычисления UI, а не обязательное параллельное выполнение кода

## 2. приоритеты обновлений и отзывчивость интерфейса

- одна из главных целей concurrent rendering — не дать дорогостоящему обновлению интерфейса мешать более важным действиям пользователя

### Представим поле поиска, которое фильтрует тысячи результатов

- обновление значения input должно происходить немедленно
- обновление большого списка может быть менее приоритетным

- Если оба обновления выполняются как срочные, React может тратить много времени на пересчёт списка при каждом введённом символе

- Для решения этой задачи в React 18 появились, в частности, `startTransition` и `useTransition`

### startTransition

- `startTransition` помечает обновления состояния внутри переданного callback как переходные, то есть не срочные

```js
import { startTransition, useState } from 'react';

function SearchPage() {
  const [query, setQuery] = useState('');
  const [appliedQuery, setAppliedQuery] = useState('');

  function handleChange(event) {
    const nextQuery = event.target.value;

    // срочное обновление: ввод пользователя
    setQuery(nextQuery);

    // переходное обновление: фильтрация результатов
    startTransition(() => {
      setAppliedQuery(nextQuery);
    });
  }

  const results = searchProducts(appliedQuery);

  return (
    <>
      <input value={query} onChange={handleChange} />
      <ProductResults products={results} />
    </>
  );
}
```

- здесь `query` управляет значением поля ввода, а `appliedQuery` — состоянием, от которого зависит потенциально тяжёлый список
- React может отдать предпочтение срочному обновлению `query`, а вычисление интерфейса для `appliedQuery` обработать позже или прервать ради более срочной работы
- `searchProducts` в примере — условная функция поиска; если сама она выполняет тяжёлые вычисления синхронно до возврата JSX, `startTransition` не сделает её выполнение прерываемым
- ещё один нюанс: обновления состояния, выполненные после `await`, обычно требуют отдельного `startTransition`, если их тоже нужно пометить как переходные

### useTransition

- `useTransition` предоставляет похожий механизм, но дополнительно позволяет узнать, выполняется ли переход

```js
import { useState, useTransition } from 'react';

function Catalog() {
  const [category, setCategory] = useState('all');
  const [isPending, startTransition] = useTransition();

  function selectCategory(nextCategory) {
    startTransition(() => {
      setCategory(nextCategory);
    });
  }

  return (
    <>
      <CategorySelect value={category} onChange={selectCategory} />

      {isPending && <p>Updating catalog...</p>}

      <CatalogResults category={category} />
    </>
  );
}
```

- `isPending` показывает, что переходное обновление ещё не завершено
- это позволяет показать ненавязчивый индикатор загрузки, не блокируя всё приложение
- `useTransition` не является универсальным индикатором загрузки HTTP-запросов: он отражает состояние перехода, а не произвольную сетевую активность

## 3. Suspense — что это и зачем нужно

- `Suspense` — механизм React, позволяющий показать резервный интерфейс, пока дочерняя часть дерева не готова к отображению

Простейший пример:

```js
import { Suspense, lazy } from 'react';

const UserProfile = lazy(() => import('./UserProfile'));

function App() {
  return (
    <Suspense fallback={<p>Loading profile...</p>}>
      <UserProfile />
    </Suspense>
  );
}
```

- `lazy` откладывает загрузку кода компонента до момента, когда этот компонент впервые понадобится
- пока модуль загружается, React может отобразить `fallback`
- после загрузки модуля React повторно пытается отрендерить компонент
- здесь есть важная связь с предыдущей темой: `lazy` отвечает за отложенную загрузку кода, а `Suspense` — за поведение интерфейса, пока компонент не готов

### как Suspense работает концептуально

```
React пытается отрендерить компонент
                  ↓
компонент приостанавливает рендеринг
                  ↓
ближайший подходящий Suspense
                  ↓
показывается fallback
                  ↓
ресурс становится доступен
                  ↓
React повторно рендерит компонент
                  ↓
показывается основной интерфейс
```

- технически механизм зависит от того, как именно дочерний компонент сообщает React о своей готовности
- при использовании `lazy` React отслеживает ожидание загрузки модуля
- с данными Suspense работает только при использовании совместимого источника данных или поддерживаемого интеграционного механизма

### чего Suspense не делает автоматически

- он не перехватывает произвольный `fetch`, запущенный в `useEffect`
- он не превращает любой асинхронный компонент в Suspense-совместимый
- он не заменяет обработку ошибок: для ошибок загрузки обычно нужен Error Boundary
- он не управляет сетевыми запросами сам по себе

- Например, такой код не заставит `Suspense` автоматически показывать `fallback` на время запроса:

```js
function UserCard() {
  const [user, setUser] = useState(null);

  useEffect(() => {
    fetch('/api/user')
      .then((response) => response.json())
      .then(setUser);
  }, []);

  if (!user) {
    return <p>Loading...</p>;
  }

  return <p>{user.name}</p>;
}
```

- этот компонент самостоятельно отображает состояние загрузки, поскольку запрос выполняется внутри эффекта после commit
- Suspense не отслеживает такой запрос автоматически

## 4. Suspense boundaries и организация UI

- граница Suspense определяет, какая часть интерфейса может быть заменена резервным содержимым

```js
function Dashboard() {
  return (
    <main>
      <DashboardHeader />

      <Suspense fallback={<p>Loading profile...</p>}>
        <UserProfile />
      </Suspense>

      <Suspense fallback={<p>Loading recommendations...</p>}>
        <Recommendations />
      </Suspense>
    </main>
  );
}
```

- отдельные границы позволяют организовать независимые области ожидания
- загрузка рекомендаций не обязательно должна скрывать профиль пользователя
- если несколько компонентов находятся внутри одной границы и один из них приостанавливает рендеринг, резервный интерфейс может появиться для всей этой границы
- на практике границы стоит размещать в соответствии с UX: какие части страницы должны загружаться независимо, а какие логично показывать только вместе

### Suspense и transitions

- между Suspense и конкурентным рендерингом есть важная связь: во время переходного обновления React может сохранить уже показанный интерфейс, пока готовится новый, вместо немедленной замены его на `fallback`

```js
function ProfileTabs() {
  const [tab, setTab] = React.useState('overview');
  const [isPending, startTransition] = React.useTransition();

  function openTab(nextTab) {
    startTransition(() => {
      setTab(nextTab);
    });
  }

  return (
    <>
      <button onClick={() => openTab('overview')}>Overview</button>

      <button onClick={() => openTab('activity')}>Activity</button>

      {isPending && <span> Updating...</span>}

      <React.Suspense fallback={<p>Loading tab...</p>}>
        {tab === 'overview' ? <Overview /> : <Activity />}
      </React.Suspense>
    </>
  );
}
```

- если `Activity` приостанавливает рендеринг, React может сохранить ранее отображавшийся контент во время перехода и обновить его, когда новое дерево будет готово
- точное поведение зависит от дерева компонентов и того, где расположены границы Suspense
- такой подход полезен для переключения вкладок, страниц и фильтров, когда мгновенное исчезновение уже отображаемого содержимого ухудшало бы пользовательский опыт

## 5. Concurrent API: что нужно знать

- под Concurrent API обычно подразумевают набор возможностей React, связанных с конкурентным рендерингом и управлением ожиданием

Основные API, которые важно различать:

- `startTransition` — помечает обновления состояния как переходные
- `useTransition` — позволяет помечать переходные обновления и отслеживать их состояние через `isPending`
- `useDeferredValue` — позволяет отложить обновление значения, используемого менее приоритетной частью UI
- `Suspense` — определяет резервное отображение для приостанавливающей рендеринг части дерева
- `lazy` — загружает код компонента по требованию и использует механизм Suspense при ожидании модуля

### useDeferredValue

- `useDeferredValue` полезен, когда нельзя или неудобно менять место, где обновляется исходное значение, но нужно позволить тяжёлой части интерфейса отставать от него

```js
function SearchResults({ query }) {
  const deferredQuery = useDeferredValue(query);

  const results = searchProducts(deferredQuery);

  const isStale = query !== deferredQuery;

  return (
    <section aria-busy={isStale}>
      {isStale && <p>Updating results...</p>}
      <ProductList products={results} />
    </section>
  );
}
```

- `query` может обновляться при каждом вводе символа, тогда как `deferredQuery` некоторое время может сохранять предыдущее значение
- React получает возможность отдать приоритет более срочному обновлению
- `useDeferredValue` не устанавливает фиксированную задержку, как debounce, и сам по себе не уменьшает количество запросов к серверу

### startTransition или useDeferredValue

- `startTransition` подходит, когда ты контролируешь обновление состояния и хочешь явно обозначить его как несрочное
- `useDeferredValue` подходит, когда у тебя уже есть значение из props или state и нужно отложить обновление зависимого от него интерфейса
- оба механизма помогают управлять приоритетами, но не заменяют виртуализацию, оптимизацию алгоритмов или устранение лишних вычислений

## 6. типичные ошибки и нюансы

- считать, что Concurrent Rendering означает многопоточность — это управление выполнением и приоритетами работы React, а не автоматическое распараллеливание JavaScript
- ожидать, что `startTransition` ускорит тяжёлую синхронную функцию — он позволяет React управлять приоритетом обновления интерфейса, но не делает произвольную функцию прерываемой
- использовать Suspense для любого запроса — Suspense работает только с совместимыми источниками ожидания
- помещать все компоненты под одну границу Suspense — это может привести к исчезновению слишком большой части интерфейса при ожидании
- вызывать побочные эффекты во время рендеринга — render phase может повторяться или отбрасываться, поэтому эффекты должны находиться в подходящих механизмах вроде `useEffect`
- использовать `useTransition` для состояния контролируемого input — обновление самого значения поля ввода должно оставаться срочным; переходным можно сделать обновление тяжёлой части UI

## 7. что изменилось с появлением React 18

- в React 17 и более ранних версиях некоторые конкурентные возможности не были доступны в том виде, в котором они появились в React 18
- React 18 представил concurrent rendering как основу для новых возможностей, включая transitions и улучшенную интеграцию Suspense
- при использовании `createRoot` React получает возможность применять эти механизмы в соответствующих сценариях
- при этом React не переводит все обновления в переходный режим автоматически: обычные обновления состояния по-прежнему остаются срочными, если не указано иное
- исторический термин Concurrent Mode часто встречается в старых материалах, но для современного React правильнее обсуждать concurrent rendering и конкретные API, которые его используют

## 8. как объяснить тему на собеседовании

- Concurrent Rendering — это механизм React, который позволяет управлять приоритетами рендеринга, прерывать менее приоритетную работу и отдавать браузеру возможность обрабатывать взаимодействие с пользователем
- React может повторно вычислять дерево компонентов, поэтому render phase должна быть чистой, а изменения DOM выполняются на этапе commit
- `startTransition` и `useTransition` помогают помечать обновления как несрочные, а `useDeferredValue` позволяет менее приоритетной части интерфейса отставать от срочного значения
- Suspense позволяет показывать резервный UI, когда дочерняя часть дерева приостанавливает рендеринг, например при загрузке компонента через `lazy`
- transitions и Suspense дополняют друг друга: React может сохранять текущий интерфейс во время подготовки следующего, улучшая воспринимаемую отзывчивость приложения
- главное, что стоит запомнить: Concurrent Rendering отвечает за управление работой React, а Suspense — за то, как организовать отображение интерфейса, когда часть дерева ещё не готова
