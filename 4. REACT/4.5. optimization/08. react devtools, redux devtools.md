# React DevTools и Redux DevTools

- этот блок посвящён не столько написанию кода, сколько умению исследовать уже работающий React application: понимать, почему компонент перерендеривается, откуда пришло конкретное значение, какое действие изменило состояние и где возникают проблемы производительности

## 1. React DevTools: что это и для чего нужно

- React DevTools — это инструмент разработчика для инспектирования React-приложения, просмотра дерева компонентов, их props, state, контекста и анализа рендеринга

- обычные браузерные DevTools и React DevTools решают разные задачи

### Chrome DevTools

- исследование DOM, CSS, сетевых запросов, JavaScript, call stack, памяти и событий браузера

### React DevTools

- исследование React component tree, props, state, hooks, контекста и причин рендеринга компонентов

### Redux DevTools

- исследование Redux state, actions, изменений состояния между dispatch, а также повторное воспроизведение истории действий

- Redux DevTools и React DevTools дополняют друг друга, но не заменяют друг друга: первый исследует поток состояния Redux, второй — дерево и поведение React-компонентов

## 2. основные возможности React DevTools

- основная вкладка для повседневной работы — Components, а для анализа производительности — Profiler

### Components: дерево компонентов

- вкладка Components показывает иерархию React-компонентов, а не просто DOM-элементов
- например, React-приложение может выглядеть так:

```js
function ProductPage() {
  return (
    <PageLayout>
      <ProductList />
    </PageLayout>
  );
}

function ProductList() {
  return (
    <ul>
      <ProductItem />
      <ProductItem />
    </ul>
  );
}
```

- в React DevTools дерево будет примерно таким:

```
ProductPage
└── PageLayout
    └── ProductList
        ├── ProductItem
        └── ProductItem
```

- в Elements при этом будут отображаться DOM-узлы: `div`, `ul`, `li` и другие реальные элементы
- выбор компонента в Components позволяет исследовать его props, state, доступные hooks и другие сведения, которые предоставляет React DevTools
- это особенно полезно, когда значение отображается неправильно: вместо того чтобы сразу искать проблему по всему приложению, можно выбрать компонент и проверить, какие данные он фактически получил

### поиск причины через props и state

- допустим, компонент получает цену товара через props:

```js
function ProductPrice({ price }) {
  return <span>{price} ₽</span>;
}
```

- если вместо ожидаемых `1500` отображается `0`, можно проверить `price` в DevTools и определить, на каком уровне проблема становится видимой: значение уже неправильное на входе компонента или ошибка возникает внутри его логики
- важно понимать, что DevTools показывает наблюдаемое состояние, но сам по себе не доказывает, почему оно стало таким: причину изменения нужно искать в коде, обработчиках, родительских компонентах или источнике данных

### hooks и состояние функциональных компонентов

- у функциональных компонентов нет экземпляра класса с полями `this.state` и `this.props`, поэтому при исследовании важно понимать, какие hooks используются и какие значения они содержат

```js
function CartSummary({ items }) {
  const [discount, setDiscount] = useState(0);

  const total = items.reduce((sum, item) => sum + item.price, 0);

  const finalTotal = total - discount;

  return <p>{finalTotal} ₽</p>;
}
```

- в Components можно исследовать состояние `discount`, props `items` и доступную информацию о hooks компонента
- при отладке полезно различать три вещи: исходные props, локальное состояние компонента и значения, вычисляемые из них во время рендера
- `total` и `finalTotal` здесь не являются state: это вычисляемые значения, которые пересчитываются при выполнении функции компонента

### изменение значений через DevTools

- в зависимости от версии React DevTools и типа значения инспектор позволяет изменять некоторые props и state прямо во время отладки
- это удобно для быстрой проверки гипотезы, например посмотреть, как компонент поведёт себя при другом значении `discount`, не проходя каждый раз через интерфейс
- однако такое изменение не следует путать с исправлением источника данных: для воспроизводимого сценария нужно изменить код, action или исходное состояние приложения

## 3. Redux DevTools: исследование потока состояния

- Redux DevTools позволяет наблюдать за действиями Redux, состоянием до и после каждого действия, а также историей изменений
- его ключевая идея заключается в том, что Redux предоставляет последовательность действий, которые приводят к изменению состояния

### Рассмотрим простой пример:

```js
const initialCartState = {
  items: [],
};

function cartReducer(state = initialCartState, action) {
  switch (action.type) {
    case 'cart/itemAdded':
      return {
        ...state,
        items: [...state.items, action.payload],
      };

    default:
      return state;
  }
}
```

- при dispatch действия `cart/itemAdded` Redux вызывает reducer, получает новое состояние, а Redux DevTools позволяет исследовать action и результат его обработки

```js
store.dispatch({
  type: 'cart/itemAdded',
  payload: {
    id: 1,
    title: 'Keyboard',
    price: 5000,
  },
});
```

- в DevTools можно увидеть примерно такую последовательность:

```
@@INIT
  state: { items: [] }

cart/itemAdded
  payload: { id: 1, title: "Keyboard", price: 5000 }

  state:
    items: [
      { id: 1, title: "Keyboard", price: 5000 }
    ]
```

- конкретное представление зависит от версии инструмента и конфигурации приложения, но принцип остаётся тем же: сопоставлять action и изменение состояния

### основные возможности Redux DevTools

- Action history — просмотр списка отправленных действий, их payload и времени выполнения
- State inspection — исследование текущего состояния и состояния на разных шагах истории
- Diff — просмотр различий между состоянием до и после действия, если соответствующее представление доступно
- Time-travel debugging — выбор предыдущего действия и просмотр состояния приложения на этом шаге
- Dispatch — отправка тестового действия через интерфейс инструмента, если это поддерживается текущей конфигурацией
- Import/export — сохранение и загрузка истории действий или состояния для воспроизведения и анализа проблем, если соответствующие функции включены

### time-travel debugging

- допустим, пользователь добавил товар, изменил количество, а затем удалил товар, и после этого корзина стала отображаться неправильно

```
cart/itemAdded
       ↓
cart/quantityChanged
       ↓
cart/itemRemoved
       ↓
неправильное отображение
```

- с помощью истории можно вернуться к предыдущим шагам и проверить, после какого действия состояние приобрело неправильную форму
- это существенно упрощает поиск ошибки по сравнению с ручным воспроизведением всех действий пользователя
- важно: time travel в Redux DevTools не означает, что инструмент автоматически откатывает любые внешние эффекты, серверные запросы или изменения вне Redux; в первую очередь он позволяет исследовать историю состояния и действий

### как подключить Redux DevTools

- при использовании Redux Toolkit стандартная настройка обычно уже включает интеграцию с Redux DevTools Extension в development-режиме

```js
import { configureStore } from '@reduxjs/toolkit';
import cartReducer from './cartSlice';

export const store = configureStore({
  reducer: {
    cart: cartReducer,
  },
});
```

- для обычного `configureStore` Redux Toolkit обычно не требует дополнительного middleware только ради подключения DevTools
- в production-инфраструктуре нужно отдельно учитывать настройки сборки, конфиденциальность данных и необходимость отключения диагностических возможностей

## 4. React DevTools Profiler: как искать проблемы производительности

- Profiler — одна из важнейших частей этого блока, потому что она помогает перейти от предположений об оптимизации к измерениям
- необходимо различать два понятия: рендеринг React-компонента и изменение DOM
- React может повторно вызвать функцию компонента, но в результате не изменить DOM, если вычисленный результат не требует соответствующих изменений
- поэтому количество вызовов компонента само по себе не является достаточным доказательством проблемы производительности

### как работает профилирование

1. начать запись в Profiler - Открыть вкладку Profiler и запустить запись

2. воспроизвести сценарий - Например, ввод в поле поиска или изменение фильтра

3. остановить запись - Изучить commits, длительность и дерево компонентов

4. найти узкое место - Определить, какие компоненты и операции требуют внимания

- Profiler группирует работу React по commit — этапам, на которых React применяет изменения к дереву приложения
- в профиле можно исследовать длительность commit, компоненты, которые участвовали в обновлении, и время их рендеринга в пределах предоставленных инструментом метрик
- один пользовательский сценарий может вызвать несколько commits, а один commit может включать множество компонентов

### render duration и commit duration

- `actualDuration` — время, затраченное на рендеринг компонента и его поддерева в текущем обновлении, с учётом работы, которую React действительно выполнил
- `baseDuration` — оценка времени рендеринга всего поддерева без учёта выигрыша от пропуска работы благодаря мемоизации; это ориентир, а не гарантированное время следующего обновления
- длительность commit и время рендеринга — связанные, но не тождественные показатели: commit включает этап применения обновлений, а работа React также может включать обработку и подготовку дерева
- при анализе нужно смотреть на конкретные измерения и сценарий, а не делать вывод только по одному числу

### пример: почему перерендеривается весь список

```js
function ProductRow({ product, onSelect }) {
  return <button onClick={() => onSelect(product.id)}>{product.title}</button>;
}

function ProductCatalog({ products }) {
  const [query, setQuery] = useState('');

  const visibleProducts = products.filter((product) => product.title.toLowerCase().includes(query.toLowerCase()));

  function handleSelect(productId) {
    console.log('Selected:', productId);
  }

  return (
    <>
      <input value={query} onChange={(event) => setQuery(event.target.value)} />

      {visibleProducts.map((product) => (
        <ProductRow key={product.id} product={product} onSelect={handleSelect} />
      ))}
    </>
  );
}
```

- при каждом изменении `query` компонент `ProductCatalog` обновляется, потому что меняется его state
- при этом `filter()` создаёт новый массив, а `handleSelect` — новую функцию при каждом вызове `ProductCatalog`
- из-за этого передаваемые в `ProductRow` props могут иметь новые ссылки, даже если сами данные товаров не изменились
- если строки списка дорогие в рендеринге, такие обновления могут стать кандидатом на оптимизацию, но сначала это нужно подтвердить профилированием

### как оптимизировать после профилирования

- один из вариантов — обернуть строку в `React.memo`, а обработчик стабилизировать с помощью `useCallback`

```js
const ProductRow = memo(function ProductRow({ product, onSelect }) {
  return <button onClick={() => onSelect(product.id)}>{product.title}</button>;
});
```

- для полноценной оптимизации в исходном примере нужно также стабилизировать `handleSelect`, если он передаётся в memoized-компоненты

```js
const handleSelect = useCallback((productId) => {
  console.log('Selected:', productId);
}, []);
```

- `React.memo` позволяет пропустить повторный рендеринг компонента, когда его props по поверхностному сравнению не изменились, а `useCallback` сохраняет ссылку на функцию между рендерами, пока не изменятся зависимости
- однако даже после этого `ProductRow` может перерендериваться по другим причинам, например при изменении собственного состояния или используемого контекста
- также не следует автоматически мемоизировать каждый компонент: если его рендеринг дешёвый, а измеримого выигрыша нет, дополнительная сложность может оказаться неоправданной

## 5. Profiler API и измерение производительности в коде

- кроме интерфейса DevTools, React предоставляет компонент `Profiler`, позволяющий программно получать данные о рендеринге определённой части дерева

```js
import { Profiler } from 'react';

function onRenderCallback(id, phase, actualDuration, baseDuration, startTime, commitTime) {
  console.log({
    id,
    phase,
    actualDuration,
    baseDuration,
    startTime,
    commitTime,
  });
}

function App() {
  return (
    <Profiler id='ProductCatalog' onRender={onRenderCallback}>
      <ProductCatalog products={products} />
    </Profiler>
  );
}
```

- `id` идентифицирует профилируемую область, `phase` обозначает тип рендеринга, а остальные аргументы позволяют исследовать время выполнения соответствующей работы
- `phase` обычно имеет значение `mount` при первоначальном монтировании и `update` при последующих обновлениях
- обычная production-сборка не предоставляет стандартный режим профилирования с теми же возможностями, что development-сборка: для профилирования production-поведения требуется соответствующая профилирующая сборка React
- `Profiler` и React DevTools дополняют друг друга: первый позволяет собирать данные программно, второй удобен для визуального исследования дерева и commits

## 6. как сохранять данные и воспроизводить ошибки

- навык работы с DevTools включает не только просмотр текущего значения, но и сохранение достаточного контекста для повторного анализа

### в React DevTools

- изучай props, state и hooks компонента в момент возникновения проблемы
- используй Profiler, чтобы сохранить запись измерений и сравнить поведение до и после оптимизации
- фиксируй конкретный сценарий, который воспроизводит лишние рендеринги

### в Redux DevTools

- исследуй последовательность actions и состояние на каждом шаге
- используй доступные функции экспорта истории или состояния, чтобы сохранить воспроизводимый сценарий
- проверяй, какой action первым привёл к некорректному состоянию

### в Chrome DevTools

- используй `console.log`, breakpoints и панель Sources для исследования выполнения кода
- в Sources можно сохранять значения в Watch и добавлять выражения для наблюдения во время остановки на breakpoint
- в Console можно использовать временные ссылки на объекты, например `$0` для выбранного элемента в Elements, а также хранить диагностические данные в переменных для дальнейшего анализа
- при этом не следует сохранять в логи или экспортируемые файлы токены, персональные данные и другую чувствительную информацию

## 7. типичный алгоритм оптимизации компонента

- на собеседовании полезно уметь описать весь процесс, а не только назвать `React.memo`, `useMemo` или `useCallback`

1. воспроизвести проблему - определить конкретный пользовательский сценарий, в котором интерфейс тормозит или обновляется неожиданно

2. измерить поведение - использовать React Profiler и, если нужно, Chrome Performance

3. найти причину - проверить изменение props, state, контекста, идентичности объектов и функций, а также стоимость вычислений

4. внести минимальное изменение - например, локализовать state, убрать лишнее вычисление или добавить мемоизацию там, где она оправданна

5. повторить измерение - убедиться, что оптимизация действительно улучшила нужный сценарий и не привела к регрессии

## 8. что важно помнить для собеседования

- React DevTools отвечает прежде всего на вопросы о дереве компонентов, props, state, hooks и поведении рендеринга

- Redux DevTools помогает понять, какие actions были отправлены, как менялось состояние и на каком шаге возникла ошибка

- React Profiler помогает локализовать дорогие рендеринги и оценить результат оптимизации

- Chrome Performance нужен, когда необходимо исследовать более широкие причины медленного интерфейса: выполнение JavaScript, длинные задачи главного потока, layout, paint и другие операции браузера

- лишний рендеринг не всегда означает проблему производительности, а отсутствие заметных лишних рендерингов не гарантирует быстрого приложения

- главная мысль этого блока: сначала измерить, затем определить причину, после этого оптимизировать и повторно измерить результат
