# bundle optimization в React

- этот блок посвящён тому, как уменьшать размер JavaScript, который получает браузер, ускорять загрузку приложения, не загружать ненужный код и эффективно использовать кеширование

## 1. базовые понятия: что такое bundle

- в React-приложении код обычно состоит из множества файлов: компонентов, хуков, утилит, стилей и сторонних библиотек
- браузер не обязан получать каждый исходный файл в исходном виде — сборщик вроде Webpack анализирует зависимости и формирует оптимизированные ресурсы
- например, исходный код может выглядеть так

```js
// App.jsx
import { Header } from './Header';
import { Dashboard } from './Dashboard';
import { formatPrice } from './utils/formatPrice';

export function App() {
  return (
    <>
      <Header />
      <Dashboard />
      <p>{formatPrice(1000)}</p>
    </>
  );
}
```

- `App.jsx` зависит от трёх модулей, которые, в свою очередь, могут зависеть от других модулей
- сборщик строит граф зависимостей, обрабатывает модули и формирует файлы, которые браузер может загружать и исполнять

```
                [исходный код]
   React-компоненты, утилиты, библиотеки
                     ↓
                   [сборка]
разрешение зависимостей, трансформация, оптимизация
                     ↓
             [production assets]
 JavaScript chunks, CSS, assets и manifest-файлы
                     ↓
                  [браузер]
загрузка, парсинг, компиляция, выполнение JavaScript
```

- bundle — собранный файл с кодом модулей, а chunk — отдельная часть результата сборки, которая может загружаться независимо от других частей
- один chunk может включать множество модулей, поэтому соответствие «один исходный файл — один production-файл» обычно отсутствует

## 2. зачем оптимизировать bundle

- большой JavaScript увеличивает объём передаваемых данных, а также потенциальные затраты на разбор, компиляцию и выполнение кода
- особенно важно это для мобильных устройств и медленных соединений, где даже хорошо сжатый файл может создавать заметные задержки
- размер bundle — не единственный показатель производительности: важны также количество запросов, кеширование, порядок загрузки ресурсов, время выполнения JavaScript и момент, когда интерфейс становится интерактивным
- например, если приложение использует тяжёлую библиотеку графиков только на одной странице, включение её кода в первоначальный bundle может замедлить открытие всех остальных страниц
- если вынести графики в отдельный chunk, пользователь загрузит соответствующий код только при переходе на страницу с графиками — при условии, что конфигурация сборки и механизм загрузки действительно позволяют это сделать

## 3. lazy-loading

- lazy-loading — это отложенная загрузка ресурса до момента, когда он действительно понадобится
- в React чаще всего речь идёт о динамическом импорте компонентов через `React.lazy()` и использовании `Suspense`

```js
import { lazy, Suspense } from 'react';

const ReportsPage = lazy(() => import('./ReportsPage'));

export function App() {
  return (
    <Suspense fallback={<p>Загрузка отчётов...</p>}>
      <ReportsPage />
    </Suspense>
  );
}
```

- `import('./ReportsPage')` возвращает Promise и позволяет сборщику выделить модуль в отдельную точку загрузки
- `lazy()` сообщает React, что компонент следует получить через динамический импорт, а `Suspense` определяет, что показывать, пока компонент загружается
- фактическое разделение на отдельный chunk зависит от сборщика и его конфигурации
- lazy-loading особенно полезен для страниц, редко используемых функций, тяжёлых редакторов, графиков и модальных окон
- не стоит автоматически откладывать загрузку каждого маленького компонента: дополнительные сетевые запросы и задержки при переходах могут оказаться дороже экономии

## 4. tree shaking

- tree shaking — это удаление неиспользуемого кода из production-сборки
- например, модуль экспортирует несколько функций, но приложение использует только одну из них

```js
// mathUtils.js
export function add(a, b) {
  return a + b;
}

export function subtract(a, b) {
  return a - b;
}

export function multiply(a, b) {
  return a * b;
}
```

```js
// calculator.js
import { add } from './mathUtils';

console.log(add(2, 3));
```

- при подходящих условиях сборщик может оставить в production-коде только `add`, удалив `subtract` и `multiply`
- механизм tree shaking опирается на статический анализ импортов и экспортов ES Modules (`import` / `export`), поэтому сборщику проще определить зависимости заранее
- затем удаление неиспользуемого кода обычно выполняется на этапе оптимизации и минификации

### когда tree shaking работает хуже

- при использовании CommonJS (`require`, `module.exports`) статически определить использование отдельных экспортов зачастую сложнее
- если модуль имеет побочные эффекты, сборщик не всегда может безопасно удалить его, даже когда его экспорты нигде не используются
- если библиотека упакована в один большой модуль с внутренними зависимостями, возможности удалить отдельные части могут быть ограничены
- например, регистрация глобального обработчика или изменение глобального состояния — потенциальные побочные эффекты, из-за которых удаление модуля может изменить поведение приложения

```js
// analytics.js
window.analyticsInitialized = true;

export function trackEvent(eventName) {
  console.log(eventName);
}
```

- здесь импорт модуля может быть нужен не только ради `trackEvent`, но и ради выполнения кода верхнего уровня
- поэтому при настройке tree shaking важно отличать неиспользуемые экспорты от модулей, которые выполняют необходимую работу при импорте

### роль `sideEffects`

- в `package.json` можно указать, какие файлы пакета потенциально имеют побочные эффекты

```js
{
  "sideEffects": false
}
```

- это заявление означает, что модули пакета можно считать свободными от побочных эффектов при соответствующих условиях оптимизации, и оно должно соответствовать реальному поведению кода
- если в проекте есть CSS-файлы или модули, которые регистрируют плагины, бездумная установка `sideEffects: false` может привести к тому, что необходимый код будет удалён

```js
{
  "sideEffects": [
    "*.css",
    "./src/registerPlugins.js"
  ]
}
```

- здесь CSS и файл регистрации плагинов явно сохраняются как потенциально имеющие побочные эффекты, а остальные модули могут оптимизироваться с учётом заданного правила

## 5. import cost

- import cost — это цена, которую приложение платит за подключение зависимости: размер добавленного кода, количество транзитивных зависимостей, затраты на выполнение и возможное влияние на tree shaking
- сам факт, что импорт выглядит коротким, не означает, что он дешёвый

```js
import { debounce } from 'lodash';
```

- в зависимости от версии библиотеки, формата поставки, конфигурации сборщика и способа разрешения импортов такой импорт может приводить к включению большего объёма кода, чем необходимо
- альтернативный вариант для некоторых версий и конфигураций — импорт конкретного модуля

```js
import debounce from 'lodash/debounce';
```

- при этом нельзя утверждать, что первый вариант всегда включает всю библиотеку: современные сборщики могут оптимизировать именованные импорты, если библиотека и её формат этому способствуют
- похожая проблема встречается у библиотек компонентов, иконок, дат и графиков, когда одна небольшая функция приводит к подключению значительного дерева зависимостей

### как оценивать стоимость импорта

- размер после минификации и gzip/Brotli — показывает приблизительный объём передаваемых по сети данных
- транзитивные зависимости — раскрывают, какие дополнительные модули подключаются вместе с библиотекой
- стоимость выполнения — показывает, сколько времени требуется браузеру на инициализацию и выполнение кода
- доля первоначального bundle — помогает понять, действительно ли зависимость необходима при первом отображении приложения
- важно не путать размер сжатого файла с размером JavaScript, который браузеру предстоит разобрать и выполнить: это разные показатели

## 6. webpack optimization

- Webpack — сборщик, который строит граф модулей, применяет загрузчики и плагины, а затем генерирует выходные ресурсы
- для bundle optimization особенно важны production-режим, tree shaking, минификация, code splitting и управление кешируемыми chunks

### production mode

```js
// webpack.config.js
module.exports = {
  mode: 'production',
};
```

- `mode: 'production'` включает набор production-оптимизаций Webpack, в том числе минификацию и оптимизации графа модулей
- это не означает, что все проблемы размера автоматически решены: неиспользуемые зависимости, неудачное разделение chunks и лишний код в точке входа всё ещё могут присутствовать

### минификация

- минификация уменьшает размер исходного кода, удаляя лишние пробелы, комментарии и иногда преобразуя выражения в более короткие эквиваленты
- она отличается от tree shaking: tree shaking удаляет неиспользуемый код, а минификация уменьшает представление кода, который остался

```
// до минификации
function calculateTotal(price, quantity) {
  return price * quantity;
}
```

```
// условный результат минификации
function calculateTotal(a,b){return a*b}
```

- примеры показывают принцип, а не гарантированный результат конкретного минификатора
- минификация не заменяет транспиляцию: транспиляция преобразует синтаксис или конструкции языка для целевых сред, а минификация в первую очередь оптимизирует код для production

### `optimization.splitChunks`

- `splitChunks` позволяет Webpack выделять подходящие общие модули в отдельные chunks вместо того, чтобы повторять один и тот же код в нескольких местах

```js
// webpack.config.js
module.exports = {
  mode: 'production',

  optimization: {
    splitChunks: {
      chunks: 'all',
    },
  },
};
```

- `chunks: 'all'` позволяет применять разделение и к синхронным, и к асинхронным chunks в рамках правил Webpack
- в результате зависимости, которые используются в нескольких местах, могут оказаться в общем chunk, а код динамически загружаемых модулей — в отдельных chunks
- однако создание дополнительных chunks не всегда улучшает производительность: оно может добавить сетевые запросы и усложнить загрузку зависимостей
- оптимальная конфигурация зависит от размера приложения, структуры импортов, HTTP-кеша и поведения пользователей

## 7. chunks и code splitting

- chunk — это часть собранного приложения, которую сборщик может загружать отдельно от других частей
- code splitting — процесс разделения приложения на такие части
- lazy-loading часто использует code splitting, но эти понятия не являются синонимами: разделение кода возможно и без отложенной загрузки каждого выделенного модуля
- рассмотрим типичную структуру приложения

```
src/
  main.jsx
  App.jsx
  pages/
    HomePage.jsx
    ReportsPage.jsx
    SettingsPage.jsx
  components/
    Header.jsx
```

- если все страницы импортируются статически, их код может попасть в первоначально загружаемые chunks, даже когда пользователь открывает только главную страницу
- если страницы загружаются динамически, сборщик может сформировать отдельные chunks для них

```js
import { lazy, Suspense } from 'react';

const HomePage = lazy(() => import('./pages/HomePage'));
const ReportsPage = lazy(() => import('./pages/ReportsPage'));
const SettingsPage = lazy(() => import('./pages/SettingsPage'));

export function App() {
  const currentPage = window.location.pathname;

  let Page = HomePage;

  if (currentPage === '/reports') {
    Page = ReportsPage;
  } else if (currentPage === '/settings') {
    Page = SettingsPage;
  }

  return (
    <Suspense fallback={<p>Загрузка страницы...</p>}>
      <Page />
    </Suspense>
  );
}
```

- в этом примере каждая страница объявлена как ленивый компонент, но загружаться будет код той страницы, которую React действительно отрендерит
- в реальном приложении выбор страницы обычно делегируется React Router или другому маршрутизатору
- общие зависимости могут попасть в отдельные chunks, а точное количество и состав файлов определяет сборщик

### как выбирать границы разделения

- хорошими кандидатами являются страницы, которые нужны не каждому пользователю, тяжёлые редакторы, аналитические панели и редкие административные функции
- код, необходимый для первого отображения интерфейса, обычно не стоит бездумно выносить за пределы первоначального пути загрузки
- если компонент нужен сразу после клика, стоит учитывать задержку между действием пользователя и появлением интерфейса
- дополнительный приём — предварительная загрузка потенциально нужного кода, например при наведении на ссылку или приближении к соответствующей части интерфейса
- это позволяет совместить меньший первоначальный bundle с быстрым последующим переходом, если приложение правильно реализует предварительную загрузку

## 8. caching

- кеширование позволяет повторно использовать ранее загруженные ресурсы вместо того, чтобы скачивать их заново при каждом посещении приложения
- в контексте bundle optimization важно понимать не только браузерный кеш, но и то, как сборщик формирует имена файлов и как сервер сообщает браузеру, когда ресурс можно использовать повторно

### проблема кеширования

- представим, что всё приложение собрано в один файл `app.js`
- разработчик изменил одну небольшую функцию, после чего весь файл изменился и браузеру приходится скачивать его повторно, даже если большая часть кода осталась прежней
- решение — разделить приложение на файлы с независимыми жизненными циклами и использовать content hashing

```js
// webpack.config.js
module.exports = {
  mode: 'production',

  output: {
    filename: '[name].[contenthash].js',
    chunkFilename: '[name].[contenthash].chunk.js',
    clean: true,
  },
};
```

- `[contenthash]` формирует часть имени файла на основе его содержимого, поэтому изменение содержимого обычно приводит к изменению имени
- `clean: true` очищает каталог сборки перед генерацией новых ресурсов, что помогает избежать накопления устаревших файлов в выходной директории
- предположим, приложение содержит такие ресурсы

```
runtime.a12bc.js
vendors.34def.js
main.56abc.js
reports.78def.chunk.js
```

- пользователь загрузил главную страницу, и браузер сохранил подходящие ресурсы в кеше
- разработчик изменил код страницы отчётов, и при новой сборке изменилось имя `reports`-chunk, но имена остальных файлов могут остаться прежними
- браузер сможет повторно использовать ранее закешированные файлы, если их URL не изменился и политика кеширования разрешает повторное использование
- это пример, а не гарантия стабильности имён: изменение графа зависимостей, runtime-кода или алгоритма разбиения может привести к изменению других hashes

### как кешировать правильно

- для файлов с хешированными именами обычно используют долгий срок кеширования, например `Cache-Control: public, max-age=31536000, immutable`, если инфраструктура публикации обеспечивает корректную работу таких URL
- для HTML-документа обычно нужна более частая проверка актуальности, потому что именно HTML сообщает браузеру, какие версии JS и CSS следует загрузить
- если HTML надолго останется в кеше и будет ссылаться на старые ресурсы, это может привести к проблемам после деплоя
- есть ещё одна важная деталь: старые chunks иногда нужны уже открытым вкладкам или лениво загружаемым модулям, поэтому при деплое не стоит бездумно удалять все предыдущие файлы, на которые ещё могут ссылаться клиенты

### runtime и стабильность hashes

- Webpack может генерировать runtime-код, который содержит служебную информацию о модулях и chunks
- если runtime и код приложения объединены неудачным образом, небольшое изменение может вызвать изменение hash более крупного файла
- в Webpack можно выделить runtime в отдельный chunk с помощью `optimization.runtimeChunk`

```js
// webpack.config.js
module.exports = {
  mode: 'production',

  optimization: {
    runtimeChunk: 'single',
    splitChunks: {
      chunks: 'all',
    },
  },
};
```

- отдельный runtime помогает отделить служебный код сборщика от основного кода приложения, но не гарантирует неизменность всех hashes при каждом изменении

## 9. internal React tools

- React сам по себе не выполняет всю оптимизацию production-bundle: за разделение модулей, минификацию и хеширование в основном отвечает сборщик
- при этом инструменты React помогают определить, где оптимизация действительно нужна, а не просто уменьшает размер файлов на бумаге

### React DevTools Profiler

- Profiler позволяет анализировать рендеры компонентов, их длительность и изменения, происходящие при взаимодействии с приложением
- он полезен, когда после загрузки приложения интерфейс тормозит из-за повторных рендеров, дорогих вычислений или неудачной структуры компонентов
- важно различать две проблемы: большой bundle замедляет загрузку и подготовку JavaScript, а неоптимальный рендеринг может замедлять взаимодействие уже после загрузки
- уменьшение bundle не обязательно исправит дорогой рендер, а `React.memo` не уменьшит автоматически размер скачиваемого JavaScript

### React Performance Tracks

- в актуальных версиях React существуют инструменты профилирования, помогающие связывать работу React с событиями и задачами браузера
- они позволяют исследовать, когда React выполняет рендеринг и commit-фазу, и сопоставлять эту работу с остальной активностью на временной шкале
- доступность конкретных возможностей зависит от версии React и используемых инструментов

### Chrome DevTools

- вкладка Network помогает увидеть размер ресурсов, время загрузки, кеширование, waterfall запросов и то, какие chunks загружаются при переходах
- вкладка Performance помогает исследовать парсинг, компиляцию и выполнение JavaScript, а также длинные задачи, которые блокируют главный поток
- Coverage показывает, какая часть загруженного JavaScript и CSS не использовалась во время выбранного сценария, но неиспользованный в одном сценарии код не обязательно является ненужным вообще
- для оптимизации bundle эти инструменты дополняют друг друга: анализатор сборки показывает состав файлов, Network — передачу данных, Performance — стоимость выполнения, а React Profiler — работу React

## 10. практический процесс оптимизации

- на собеседовании важно объяснять не только конкретные настройки, но и последовательность принятия решений

1. измерить исходное состояние - собрать production-версию, изучить размеры assets, проверить Network и определить самые крупные зависимости

2. найти лишний код - проверить дублирующиеся зависимости, тяжёлые библиотеки, неиспользуемые экспорты и возможности tree shaking

3. настроить разделение - определить границы code splitting, применить lazy-loading для подходящих страниц и выделить общие зависимости

4. проверить результат - сравнить размер первоначально загружаемых ресурсов, время до интерактивности, поведение при навигации и повторной загрузке

- полезно отдельно сравнивать первый визит и повторный визит: в первом случае ресурсы могут загружаться из сети, а во втором — частично браться из кеша
- при этом нужно тестировать именно production-сборку, потому что dev-сборка может содержать дополнительный код, карты исходников и инструменты разработки

## 11. что нужно уметь объяснить на собеседовании

- lazy-loading — зачем откладывать загрузку кода и как `React.lazy`, `Suspense` и динамический `import()` работают совместно
- tree shaking — как статические ES Modules и информация о побочных эффектах помогают удалить неиспользуемый код
- import cost — почему небольшая строка импорта может подключать большую транзитивную зависимость и как это проверить
- Webpack optimization — для чего нужны production mode, минификация, `splitChunks` и `runtimeChunk`
- chunks — чем chunk отличается от bundle в разговорной практике и как code splitting влияет на загрузку приложения
- caching — как content hashes, HTTP-заголовки и отдельный runtime помогают повторно использовать неизменившиеся ресурсы
- React и браузерные инструменты — чем анализ размера сборки отличается от профилирования рендеринга компонентов

- ключевая мысль всего блока: оптимизация — это не стремление получить максимальное количество маленьких файлов или минимальный размер одного файла, а поиск баланса между объёмом первоначальной загрузки, количеством сетевых запросов, кешируемостью и стоимостью выполнения JavaScript
