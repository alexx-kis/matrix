# basic react optimization

- начнём с первого блока оптимизации React и разберём его последовательно: от reconciliation и `key` до `shouldComponentUpdate`, `PureComponent`, оптимизации через props и профилирования производительности

## 1. что именно мы оптимизируем в React

- сначала нужно разделить несколько понятий, которые часто ошибочно объединяют под словом «рендеринг»
- рендеринг компонента — React вызывает функцию функционального компонента или метод `render()` классового компонента, чтобы получить описание следующего UI в виде React-элементов
- reconciliation — React сравнивает новое описание UI с предыдущим, чтобы определить, какие изменения необходимо внести в дерево
- DOM commit — React применяет необходимые изменения к DOM, если они нужны
- перерисовка браузером — браузер может пересчитать стили, выполнить layout и paint, чтобы отобразить изменения на экране

Упрощённо процесс выглядит так:

```
изменение props / state / context
              ↓
       вызов компонента
              ↓
     получение React-элементов
              ↓
        reconciliation
              ↓
       commit изменений
              ↓
     обновление изображения
```

- эти этапы связаны, но не тождественны: вызов компонента не обязательно приводит к изменению DOM, а изменение DOM не обязательно вызывает дорогую перерисовку всего экрана
- следовательно, цель оптимизации — не сделать так, чтобы компоненты никогда не рендерились, а уменьшить ненужную работу и стоимость необходимой работы

## 2. как React определяет, что нужно обновить

- прежде чем разбирать `key`, `shouldComponentUpdate` и `PureComponent`, необходимо понять основу — reconciliation
- допустим, у нас есть компонент, который выводит имя пользователя

```js
function UserCard({ name }) {
  console.log('UserCard rendered');

  return <div>{name}</div>;
}

function App() {
  const [count, setCount] = React.useState(0);

  return (
    <>
      <button onClick={() => setCount((value) => value + 1)}>{count}</button>

      <UserCard name='Анна' />
    </>
  );
}
```

- при нажатии на кнопку состояние `App` изменяется, поэтому React повторно вызывает `App`
- при обычном повторном рендеринге родителя React также может вызвать `UserCard`, даже если `name` по-прежнему равно `"Анна"`
- при этом React способен определить, что текст внутри `UserCard` не изменился, и не выполнять соответствующее обновление DOM
- это и есть важный нюанс: повторный рендеринг компонента не означает, что React обязательно изменит DOM
- но вызов компонента тоже имеет стоимость: внутри него могут выполняться вычисления, создаваться новые объекты и React-элементы, вызываться другие компоненты
- поэтому в некоторых случаях полезно предотвращать повторный вызов компонента, а не просто полагаться на то, что React не станет менять DOM
- именно эту задачу в определённых ситуациях решают `React.memo`, `PureComponent` и `shouldComponentUpdate`

## 3. keys — идентификация элементов при reconciliation

### зачем нужны keys

- `key` — специальный атрибут React-элемента, который помогает React определять идентичность элементов среди соседей при сравнении предыдущего и нового дерева
- особенно важен `key`, когда элементы коллекции добавляются, удаляются, перемещаются или заменяются

```js
function TodoList({ todos }) {
  return (
    <ul>
      {todos.map((todo) => (
        <li key={todo.id}>{todo.text}</li>
      ))}
    </ul>
  );
}
```

- здесь `todo.id` позволяет React сопоставить конкретную задачу в новом списке с той же задачей в предыдущем списке
- представим, что исходный список выглядит так:

```
до:     [A, B, C]
после:  [X, A, B, C]
```

- при корректных стабильных ключах React понимает, что `A`, `B` и `C` сохранили свою идентичность, а `X` — новый элемент, который нужно добавить
- без ключей React может ориентироваться на позиции элементов и сопоставлять их менее удачно, из-за чего возможны лишние изменения и некорректное сохранение состояния элементов

### что произойдёт без key

- если не указать `key` для элементов списка, React обычно выдаст предупреждение в development-режиме
- React всё равно попытается сопоставить элементы, используя доступную информацию, в том числе их позиции, поэтому отсутствие ключей не означает, что всё дерево будет пересоздано при каждом обновлении
- проблема становится особенно заметной, когда элементы вставляются в начало, удаляются из середины или меняют порядок
- рассмотрим пример:

```js
function NameList({ names }) {
  return (
    <ul>
      {names.map((name, index) => (
        <li key={index}>
          <input defaultValue={name} />
        </li>
      ))}
    </ul>
  );
}
```

- допустим, исходные данные — `["Анна", "Иван", "Мария"]`, а затем мы удаляем Анну
- при использовании индекса ключи будут выглядеть так:

```
до:
0 → Анна
1 → Иван
2 → Мария

после:
0 → Иван
1 → Мария
```

- React увидит, что элемент с ключом `0` по-прежнему существует, и может сохранить связанное с ним состояние или DOM-узел, хотя теперь этот элемент представляет Ивана, а раньше представлял Анну
- в примере с `defaultValue` это может привести к тому, что в поле ввода останется прежнее пользовательское значение, не соответствующее данным
- аналогичные ошибки возможны с локальным состоянием компонентов, фокусом, выделением текста и другими состояниями DOM

### практическое правило:

- используй стабильный уникальный идентификатор сущности, например `todo.id`
- не используй случайное значение, генерируемое заново при каждом рендеринге
- не используй индекс массива, если список может менять порядок, получать новые элементы в середине или удалять существующие
- индекс допустим для действительно статичного списка, элементы которого никогда не переставляются и не удаляются

### что ещё важно знать о key

- `key` должен быть уникальным среди соседних элементов, но не обязан быть уникальным во всём приложении
- `key` не передаётся компоненту как обычный prop, поэтому `props.key` не даст ожидаемого значения

```js
<UserCard key={user.id} userId={user.id} />
```

- если компоненту необходим идентификатор, его нужно передать отдельно через `userId`
- ключ также влияет на сохранение состояния: если у одного и того же типа компонента меняется `key`, React воспринимает его как другой элемент и может сбросить предыдущее локальное состояние

```js
<ProfileEditor key={userId} userId={userId} />
```

- такой подход может быть полезен, например, когда при переключении пользователя нужно полностью сбросить состояние редактора
- важно: `key` не является механизмом мемоизации — он помогает правильно сопоставлять элементы, но сам по себе не предотвращает повторный вызов компонента

## 4. shouldComponentUpdate

### что это такое

- `shouldComponentUpdate(nextProps, nextState)` — метод жизненного цикла классового компонента, который позволяет определить, следует ли React выполнять обновление компонента при изменении его props или state

```js
class CounterPanel extends React.Component {
  shouldComponentUpdate(nextProps, nextState) {
    return nextProps.count !== this.props.count;
  }

  render() {
    console.log('CounterPanel rendered');

    return <div>{this.props.count}</div>;
  }
}
```

- если `shouldComponentUpdate` возвращает `false`, React может пропустить обычный процесс обновления этого компонента, включая вызов его `render()`
- если возвращает `true`, обновление продолжается обычным образом
- метод получает будущие props и state, тогда как `this.props` и `this.state` содержат текущие значения

### как это работает

```
получены новые props или state
              ↓
   shouldComponentUpdate(...)
              ↓
       ┌──────┴──────┐
       ↓             ↓
     true           false
       ↓             ↓
  render()       обновление
       ↓          пропущено
 reconciliation
```

- схема описывает обычный путь обновления классового компонента, но не все возможные причины обновления React: например, изменение контекста, от которого компонент зависит, требует отдельного рассмотрения

### важный нюанс: false не означает запрет всех обновлений

- `shouldComponentUpdate` — оптимизационная подсказка для обычного процесса обновления, а не универсальный механизм блокировки любых изменений
- в частности, нельзя считать, что возврат `false` гарантированно защитит компонент от обновлений, связанных с контекстом или другими специальными механизмами React
- метод не следует использовать для изменения состояния, выполнения побочных эффектов или изменения props
- если логика сравнения ошибочна и метод возвращает `false`, когда UI на самом деле должен измениться, интерфейс может перестать отражать актуальные данные

### когда это полезно

- например, компонент отображает большое количество данных, а его родитель часто обновляется по причинам, не связанным с этими данными
- если можно надёжно определить, что значимые для отображения props и state не изменились, обновление можно пропустить
- однако писать `shouldComponentUpdate` вручную для каждого компонента не стоит: сравнение само по себе тоже требует времени, а сложная логика сравнения может оказаться дороже самого рендеринга

## 5. Component vs PureComponent

### обычный Component

- `React.Component` сам по себе не реализует автоматическое поверхностное сравнение props и state для решения о пропуске рендеринга
- при обычном обновлении компонента React может вызвать его `render()`, даже если значения props фактически не изменились

### PureComponent

- `React.PureComponent` — базовый класс для классовых компонентов, который реализует поверхностное сравнение текущих и новых props и state

```js
class UserSummary extends React.PureComponent {
  render() {
    console.log('UserSummary rendered');

    return <div>{this.props.user.name}</div>;
  }
}
```

- если все сравниваемые props и state поверхностно равны, React может пропустить обычное обновление компонента
- поверхностное сравнение означает, что сравниваются значения верхнего уровня, а вложенные объекты не сравниваются рекурсивно

```js
const previousUser = { name: 'Анна' };
const nextUser = { name: 'Анна' };

console.log(previousUser === nextUser); // false
```

- объекты имеют одинаковое содержимое, но это две разные ссылки, поэтому поверхностное сравнение считает их разными
- напротив, если объект не был заменён и его ссылка осталась прежней, `PureComponent` не заметит изменения его вложенных свойств

```js
const user = { name: 'Анна' };

user.name = 'Мария';

// ссылка осталась прежней
```

- если передать такой объект в `PureComponent`, изменение `user.name` само по себе не гарантирует, что компонент обновится
- поэтому `PureComponent` особенно хорошо работает в сочетании с неизменяемыми обновлениями данных — когда при изменении объекта создаётся новая ссылка

```js
const updatedUser = {
  ...user,
  name: 'Мария',
};
```

### сравнение Component и PureComponent

- `Component` — обычное поведение, при котором решение об обновлении в общем случае не основывается на автоматическом сравнении props и state
- `PureComponent` — автоматическое поверхностное сравнение props и state, позволяющее пропускать некоторые обновления
- `shouldComponentUpdate` — возможность вручную реализовать критерий, по которому обновление стоит пропустить
- `PureComponent` удобен, когда поверхностного сравнения достаточно; ручной `shouldComponentUpdate` полезен для специальных случаев, но требует особенно внимательно поддерживать корректность сравнения

## 6. как работать с props, чтобы избежать лишних рендеров

- теперь объединим предыдущие концепции: родитель может часто рендериться, а дочерний компонент — получать те же данные
- для функциональных компонентов похожую задачу решает `React.memo`

```js
const UserBadge = React.memo(function UserBadge({ name }) {
  console.log('UserBadge rendered');

  return <span>{name}</span>;
});

function UserPage() {
  const [count, setCount] = React.useState(0);

  return (
    <>
      <button onClick={() => setCount((value) => value + 1)}>{count}</button>

      <UserBadge name='Анна' />
    </>
  );
}
```

- при повторном рендеринге `UserPage` React сравнит прежние и новые props `UserBadge`
- поскольку `name` в обоих случаях равен `"Анна"`, `React.memo` обычно позволит пропустить повторный вызов `UserBadge`, если нет других причин для его обновления
- это сравнение по умолчанию тоже поверхностное, поэтому новые ссылки на объекты, массивы и функции имеют значение

### проблема с объектами и функциями

```js
const UserDetails = React.memo(function UserDetails({ user, onSelect }) {
  console.log('UserDetails rendered');

  return <button onClick={() => onSelect(user.id)}>{user.name}</button>;
});

function UserDirectory() {
  const [count, setCount] = React.useState(0);

  return (
    <>
      <button onClick={() => setCount((value) => value + 1)}>{count}</button>

      <UserDetails user={{ id: 1, name: 'Анна' }} onSelect={() => console.log('selected')} />
    </>
  );
}
```

- здесь при каждом рендеринге `UserDirectory` создаются новый объект `user` и новая функция `onSelect`
- несмотря на одинаковое содержимое объекта и одинаковый код функции, их ссылки отличаются, поэтому поверхностное сравнение props не позволяет пропустить рендеринг `UserDetails`
- именно поэтому стабильность ссылок может быть важна при оптимизации компонентов, использующих `React.memo` или `PureComponent`
- однако это не означает, что каждый объект и каждую функцию необходимо оборачивать в `useMemo` и `useCallback`: сначала следует выяснить, есть ли реальная проблема с производительностью

### что помогает на практике

- передавать только те props, которые действительно нужны дочернему компоненту
- не создавать новые объекты и функции без необходимости, если стабильность ссылок позволяет пропускать дорогие обновления
- использовать неизменяемые обновления объектов и массивов
- разделять большой компонент на более мелкие, если это позволяет изолировать часто меняющуюся часть интерфейса от редко меняющейся
- не забывать, что `React.memo` не гарантирует пропуск всех рендеров: собственное состояние компонента и используемый им контекст могут по-прежнему вызывать обновление

### типичный процесс профилирования

- шаг 1 — воспроизвести проблему: например, ввод текста вызывает заметные задержки или переключение вкладки приводит к зависанию интерфейса

- шаг 2 — записать профиль: открыть React DevTools Profiler, начать запись, воспроизвести действие и остановить запись

- шаг 3 — найти дорогие commits: посмотреть, сколько времени заняли обновления и какие компоненты участвовали в них

- шаг 4 — изучить дерево компонентов: выяснить, какие компоненты рендерились, сколько времени они занимали и какие обновления повторяются без очевидной необходимости

- шаг 5 — проверить причину: например, состояние хранится слишком высоко в дереве, компонент получает новые ссылки на props или выполняет дорогое вычисление

- шаг 6 — внести изменение и сравнить результаты: повторить тот же сценарий профилирования и убедиться, что оптимизация действительно уменьшила затраты

### типичные ошибки при профилировании

- считать каждый рендеринг проблемой — рендеринг дешёвого компонента может быть совершенно нормальным

- добавлять мемоизацию без измерений — сравнение props, поддержка стабильных ссылок и усложнение кода тоже имеют стоимость

- оценивать только количество рендеров, игнорируя их длительность

- сравнивать результаты в разных условиях — например, профиль development-сборки с результатом production-сборки

- забывать, что в Strict Mode в development некоторые операции могут выполняться дополнительно для выявления проблем, поэтому количество вызовов компонента не всегда соответствует поведению production

## 8. как связать всё вместе на собеседовании

- `key` помогает React правильно сопоставлять элементы между рендерами, особенно в списках, но не является механизмом мемоизации

- `shouldComponentUpdate` позволяет классовому компоненту пропустить обычное обновление, если его props и state не требуют нового отображения

- `PureComponent` автоматически использует поверхностное сравнение props и state, поэтому требует аккуратной работы со ссылками и неизменяемыми данными

- `React.memo` предоставляет похожую оптимизацию для функциональных компонентов, сравнивая props по умолчанию поверхностно

- корректная работа с props помогает избежать ненужных обновлений, но стабильные ссылки имеют смысл прежде всего тогда, когда они позволяют избежать реальной лишней работы

- React DevTools Profiler помогает найти дорогие commits и повторные рендеринги, после чего нужно проверить гипотезу и измерить результат оптимизации

- главный принцип: сначала определить реальное узкое место, затем выбрать подходящую оптимизацию и подтвердить её эффект измерениями
