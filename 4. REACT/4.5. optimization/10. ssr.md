# SSR (Server-Side Rendering) в React

- разберём SSR от базовых принципов до внутреннего устройства, гидратации, API `ReactDOMServer` и практического использования в Next.js и Gatsby

## 1. что такое SSR и зачем он нужен

- обычно React-приложение работает по модели CSR (Client-Side Rendering), когда основная работа по построению интерфейса выполняется в браузере

### CSR — client-side rendering

- допустим, приложение использует такой код

```js
import { createRoot } from 'react-dom/client';

function ProductCard() {
  return (
    <article>
      <h1>MacBook Pro</h1>
      <p>Цена: 2000 €</p>
    </article>
  );
}

createRoot(document.getElementById('root')).render(<ProductCard />);
```

- при первоначальной загрузке браузер получает HTML-документ, в котором контейнер приложения может быть практически пустым

```html
<html>
  <body>
    <div id="root"></div>
    <script src="/assets/app.js"></script>
  </body>
</html>
```

- далее браузер загружает JavaScript, выполняет его, React создаёт дерево компонентов и формирует DOM

1. сервер

- Отдаёт HTML-каркас и JavaScript-файлы

2. браузер

- Загружает и выполняет JavaScript

3. React

- Создаёт DOM и подключает обработчики событий

- преимущество CSR — серверу не обязательно формировать HTML для каждого компонента, а приложение может быть полностью интерактивным после выполнения JavaScript
- недостаток — до выполнения JavaScript пользователь может не увидеть основной контент, а поисковые роботы и другие потребители страницы могут получить менее удобный для обработки HTML, в зависимости от их возможностей

### SSR — server-side rendering

- при SSR React выполняет рендеринг компонентов на сервере и формирует HTML, который отправляется браузеру

```js
import { renderToString } from 'react-dom/server';

function ProductCard() {
  return (
    <article>
      <h1>MacBook Pro</h1>
      <p>Цена: 2000 €</p>
    </article>
  );
}

const productHtml = renderToString(<ProductCard />);
```

- результатом будет строка HTML примерно такого вида

```js
<article>
  <h1>MacBook Pro</h1>
  <p>Цена: 2000 €</p>
</article>
```

- браузер может отобразить этот HTML ещё до загрузки и выполнения клиентского JavaScript

1. сервер

- Выполняет React-рендеринг и формирует HTML

2. браузер

- Получает HTML и отображает контент

3. React на клиенте

- Гидратирует HTML, подключая интерактивность

- ключевой момент: SSR сам по себе не делает React-приложение интерактивным — сервер создаёт HTML, но браузеру всё ещё может потребоваться клиентский JavaScript для обработки кликов, обновления состояния и других взаимодействий

## 2. что даёт SSR

- быстрое появление контента — браузеру не всегда нужно ждать загрузки и выполнения основного JavaScript-бандла, чтобы показать текст и разметку
- SEO — поисковый робот получает содержимое непосредственно в HTML, хотя современные поисковики также умеют выполнять JavaScript
- предварительный рендеринг персонализированных страниц — сервер может получить данные пользователя и сформировать соответствующий HTML, если это предусмотрено архитектурой и правилами кеширования
- улучшение воспринимаемой скорости — контент может появиться раньше, чем станут доступны интерактивные элементы

* при этом SSR не гарантирует автоматически лучшую производительность: сервер тратит ресурсы на рендеринг, увеличивается сложность инфраструктуры, а гидратация и выполнение клиентского JavaScript могут оставаться дорогими операциями
* SSR и CSR не являются взаимоисключающими подходами — на практике их часто комбинируют, например сервером формируют начальный HTML, а затем React продолжает работу в браузере

## 3. ReactDOMServer и основные API

- `ReactDOMServer` — историческое название объекта, через который в старых версиях React были доступны серверные методы рендеринга, а в современном React API импортируются непосредственно из `react-dom/server`

- в твоём списке есть четыре метода, но важно понимать, что два потоковых метода устарели и удалены в React 19, поэтому на собеседовании нужно знать их назначение и современные альтернативы

### 3.1. `renderToString`

- преобразует React-дерево в строку HTML

```js
import { renderToString } from 'react-dom/server';

function UserProfile() {
  return (
    <section>
      <h1>Alex</h1>
      <button onClick={() => console.log('Clicked')}>Follow</button>
    </section>
  );
}

const profileHtml = renderToString(<UserProfile />);

console.log(profileHtml);
```

- в результате сервер получает HTML-строку с заголовком и кнопкой, но функция-обработчик `onClick` в HTML не превращается в работающий обработчик браузера

- серверный рендеринг здесь отвечает за первоначальную разметку, а не за выполнение пользовательских действий

- метод синхронный, не поддерживает потоковую передачу HTML и имеет ограниченную поддержку `Suspense`: если компонент при рендеринге приостанавливается, метод не ждёт его завершения, а возвращает ближайший `fallback`

- `renderToString` полезно знать для понимания механики SSR и существующего кода, но для новых серверных приложений в Node.js обычно предпочтительнее потоковый API

### 3.2. `renderToStaticMarkup`

- тоже преобразует React-дерево в HTML-строку, но предназначен для статической разметки, которую не планируют гидратировать с помощью React

```js
import { renderToStaticMarkup } from 'react-dom/server';

function EmailTemplate() {
  return (
    <main>
      <h1>Order confirmed</h1>
      <p>Your order has been accepted</p>
    </main>
  );
}

const emailHtml = renderToStaticMarkup(<EmailTemplate />);
```

- такой подход подходит, например, для генерации HTML-писем, простых статических страниц и разметки, которую будет обрабатывать другая система

- принципиальное отличие: результат `renderToStaticMarkup` нельзя использовать как обычную серверную разметку для последующей React-гидратации

- если планируется интерактивное React-приложение, используй обычный SSR с последующей гидратацией, а не `renderToStaticMarkup`

### 3.3. `renderToNodeStream`

- в старых версиях React метод возвращал Node.js `Readable` stream, из которого HTML можно было передавать частями, не собирая всю строку целиком

```js
import { renderToNodeStream } from 'react-dom/server';

const htmlStream = renderToNodeStream(<App />);

htmlStream.pipe(response);
```

- идея потокового рендеринга состоит в том, что сервер может начать отправлять клиенту HTML до того, как весь документ будет сформирован целиком
- это может уменьшить время ожидания первых байтов ответа и позволить браузеру раньше начать разбор разметки, хотя конкретный эффект зависит от данных, сервера и сетевых условий
- важно для собеседования: `renderToNodeStream` устарел, а в React 19 удалён; его современная замена для Node.js — `renderToPipeableStream`

### 3.4. `renderToStaticNodeStream`

- этот метод также возвращал Node.js stream, но генерировал статическую HTML-разметку, не предназначенную для React-гидратации

- его назначение было близко к `renderToStaticMarkup`, но результат выдавался потоком, а не одной строкой

- в React 19 метод удалён; для современного потокового SSR с интерактивностью следует смотреть на `renderToPipeableStream`, а для статической генерации — на API из `react-dom/static`

### что использовать сейчас

### `renderToPipeableStream`

Node.js SSR

- потоковый рендеринг для Node.js, в том числе для приложений с `Suspense`

### `renderToReadableStream`

Web Streams

- потоковый рендеринг для сред, поддерживающих Web Streams, например современных edge-runtime

### `renderToString`

Legacy / простой SSR

- синхронная HTML-строка без потоковой передачи

### `prerender` и `prerenderToNodeStream`

Static generation

- статическая генерация, которая ожидает завершения загрузки данных для HTML, вместо постепенной отправки контента по мере готовности

- различие последних двух групп важно: потоковый SSR может отправлять готовую часть страницы, пока другие участки ещё ожидают данные, а статический prerendering дожидается завершения работы, необходимой для итогового HTML

## 4. как работает гидратация (hydration)

- гидратация — это процесс, в котором React на клиенте подключается к уже существующей HTML-разметке, сформированной на сервере, и делает её интерактивной
- для понимания важно различать три действия
  - server rendering — React формирует HTML на сервере
  - HTML parsing — браузер преобразует полученную разметку в DOM и отображает её
  - hydration — React в браузере восстанавливает связь между React-деревом и существующим DOM, настраивая обработку взаимодействий
- например, сервер отправил браузеру такой HTML

```js
<div id='root'>
  <button>Count: 0</button>
</div>
```

- браузер способен показать кнопку, даже если клиентский JavaScript ещё не загрузился, но сам HTML не содержит работающего React-обработчика
- на клиенте запускается React

```js
import { hydrateRoot } from 'react-dom/client';

function Counter() {
  const [count, setCount] = React.useState(0);

  return <button onClick={() => setCount((value) => value + 1)}>Count: {count}</button>;
}

hydrateRoot(document.getElementById('root'), <Counter />);
```

- в примере предполагается, что `React` импортирован из пакета `react`, например через `import React from 'react'`, либо что используется соответствующая настройка JSX-трансформации
- после гидратации React может обрабатывать клики и обновлять состояние, используя уже созданную браузером разметку, вместо того чтобы изначально заменять её содержимое с нуля

### почему нельзя использовать `createRoot` вместо `hydrateRoot`

- `createRoot` предназначен для обычного клиентского рендеринга, когда React самостоятельно управляет содержимым корневого контейнера
- `hydrateRoot` предназначен для корня, который уже содержит HTML, сформированный React на сервере

```js
// обычный CSR
createRoot(rootElement).render(<App />);

// SSR + hydration
hydrateRoot(rootElement, <App />);
```

- если вызвать `createRoot` на серверной разметке, React будет рассматривать контейнер как корень для клиентского рендеринга и может очистить существующее содержимое, вместо того чтобы гидратировать его
- поэтому для SSR важно использовать правильный клиентский API

## 5. hydration mismatch — одна из главных проблем SSR

- для успешной гидратации HTML, сформированный сервером, должен соответствовать тому, что React ожидает от первоначального рендера на клиенте
- если сервер и клиент генерируют разную разметку, возникает hydration mismatch — ошибка или предупреждение о несовпадении HTML

### пример проблемы

```js
function CurrentTime() {
  return <p>{new Date().toLocaleTimeString()}</p>;
}
```

- сервер может отрендерить `12:00:00`, а браузер — `12:00:02`, поскольку время вычисляется в разные моменты
- аналогичные проблемы возникают, если первоначальный рендер зависит от `window`, `localStorage`, случайных чисел, часового пояса или других значений, которые отличаются между сервером и клиентом

### как избежать несовпадений

- не обращаться к браузерным API во время серверного рендера — на сервере обычно нет `window`, `document` и `localStorage`
- обеспечивать одинаковые начальные данные — передавать клиенту данные, на основе которых был сформирован HTML
- не использовать случайные значения при первоначальном рендеринге — если значение необходимо, генерировать его заранее и передавать в обе среды
- учитывать локаль и часовой пояс — форматирование даты и чисел может различаться
- переносить браузерно-зависимые действия в `useEffect`, если допустимо показать первоначальное значение, а затем обновить его на клиенте
- например, такой компонент безопаснее с точки зрения SSR

```js
import { useEffect, useState } from 'react';

function BrowserTheme() {
  const [theme, setTheme] = useState('light');

  useEffect(() => {
    const savedTheme = localStorage.getItem('theme');

    if (savedTheme) {
      setTheme(savedTheme);
    }
  }, []);

  return <p>Theme: {theme}</p>;
}
```

- на сервере и при первом клиентском рендере будет `light`, поэтому начальная разметка совпадёт, а после гидратации эффект сможет прочитать сохранённую тему
- у этого решения есть компромисс: пользователь может кратковременно увидеть светлую тему до применения сохранённой; если это критично, нужно продумать архитектуру определения темы и формирования первоначального HTML

## 6. как работает SSR глубже

- SSR — это не просто вызов `renderToString`, а цепочка действий, которую обычно организует серверный фреймворк

1. поступает HTTP-запрос

- Например, пользователь открывает `/products/42`

2. сервер определяет страницу и получает данные

- Выполняет авторизацию, обращается к API или базе данных, если это необходимо

3. React выполняет рендеринг

- Компоненты формируют HTML на основе переданных props и состояния рендера

4. сервер отправляет HTML

- При потоковом SSR разметка может поступать частями

5. браузер загружает JavaScript и гидратирует страницу

- React подключается к существующему DOM и обеспечивает интерактивность

- здесь важно понимать, что серверный React-рендеринг не равнозначен запуску всего приложения в браузере на сервере

- при обычном SSR React формирует разметку, но браузерные эффекты, например `useEffect`, на сервере не выполняются, а обработчики событий не активируются до клиентской гидратации

### что происходит с состоянием компонентов

- состояние, созданное через `useState`, не следует воспринимать как состояние, которое автоматически переносится с серверного процесса в браузер
- сервер выполняет первоначальный рендер, а клиент создаёт своё React-дерево и первоначально должен получить согласованные данные и начальное состояние
- если компонент на сервере показывает список товаров из полученных данных, клиент должен получить совместимый набор данных для первоначальной гидратации, а не независимо запросить совершенно другой список до неё

### что происходит с `useEffect`

- `useEffect` предназначен для побочных эффектов на клиенте и не выполняется во время серверного рендеринга

```js
import { useEffect, useState } from 'react';

function Notifications() {
  const [message, setMessage] = useState('Loading...');

  useEffect(() => {
    setMessage('Notifications loaded');
  }, []);

  return <p>{message}</p>;
}
```

- сервер сформирует HTML с текстом `Loading...`, и первоначальный рендер клиента должен соответствовать ему
- после гидратации эффект выполнится в браузере и изменит состояние
- это один из механизмов, позволяющих безопасно выполнять клиентскую логику после появления первоначального HTML

## 7. потоковый SSR и Suspense

- классический `renderToString` формирует целую HTML-строку синхронно, поэтому не позволяет отправлять готовые части интерфейса постепенно
- потоковый SSR решает эту проблему: сервер может отправить оболочку страницы, а затем передавать готовую разметку отдельных частей по мере их готовности

```js
import { Suspense } from 'react';

function ProductPage() {
  return (
    <main>
      <h1>Product details</h1>

      <Suspense fallback={<p>Loading reviews...</p>}>
        <Reviews />
      </Suspense>
    </main>
  );
}
```

- представим, что отзывы загружаются дольше остальной страницы

- при потоковом рендеринге браузер может раньше получить заголовок и остальную готовую разметку, а содержимое отзывов — позже

- `Suspense` определяет границу, для которой предусмотрено временное состояние загрузки, а потоковый серверный API позволяет постепенно передавать доступный HTML

- важно не путать это с обычным `renderToString`: он не ждёт завершения приостановленного компонента и ограниченно обрабатывает `Suspense`, возвращая `fallback`

- в современных приложениях на Node.js для потокового SSR используется `renderToPipeableStream`

```js
import { renderToPipeableStream } from 'react-dom/server';

function handleRequest(request, response) {
  const stream = renderToPipeableStream(<App />, {
    onShellReady() {
      response.statusCode = 200;
      response.setHeader('Content-Type', 'text/html; charset=utf-8');
      stream.pipe(response);
    },
    onShellError(error) {
      console.error(error);
      response.statusCode = 500;
      response.end('Server rendering failed');
    },
    onError(error) {
      console.error(error);
    },
  });

  return stream;
}
```

- это иллюстрация принципа работы API, а не полноценный production-обработчик: реальному серверу также нужны корректный HTML-документ, обработка отмены запроса, таймаутов и ошибок, а также согласованная передача клиентских скриптов
- `onShellReady` означает, что готова начальная оболочка страницы, а `onShellError` позволяет обработать ошибку, из-за которой её нельзя сформировать
- в production-коде обычно нужно также учитывать `onAllReady`, если необходимо дождаться завершения рендеринга, например для отдельных сценариев генерации статического HTML

## 8. SSR, SSG и CSR: в чём разница

- это три способа организовать первоначальное формирование интерфейса

CSR — Client-Side Rendering

- HTML-интерфейс преимущественно строится в браузере после загрузки JavaScript
- подходит для приложений, где важна насыщенная интерактивность, а серверное формирование HTML не является обязательным

SSR — Server-Side Rendering

- HTML формируется на сервере во время обработки запроса
- подходит для динамических страниц, персонализированного контента и данных, которые должны быть актуальны при запросе

SSG — Static Site Generation

- HTML формируется заранее, обычно во время сборки приложения
- подходит для документации, блогов, маркетинговых страниц и другого контента, который не требуется пересчитывать на каждом запросе

- SSG также может использовать гидратацию: наличие готового HTML ещё не означает, что страница не нуждается в клиентском JavaScript

- в современных приложениях могут сочетаться все три подхода, а также промежуточные варианты — например, отложенная генерация статических страниц и частичное выполнение логики на сервере

## 9. как SSR реализован во фреймворках

### Next.js

- Next.js предоставляет инфраструктуру для серверного и клиентского рендеринга, поэтому разработчику обычно не нужно самостоятельно вызывать `ReactDOMServer`
- в Pages Router SSR можно явно организовать через `getServerSideProps`

```js
export async function getServerSideProps() {
  const response = await fetch('https://example.com/api/products');
  const products = await response.json();

  return {
    props: { products },
  };
}

export default function ProductsPage({ products }) {
  return (
    <main>
      {products.map((product) => (
        <p key={product.id}>{product.name}</p>
      ))}
    </main>
  );
}
```

- функция `getServerSideProps` выполняется на сервере при каждом запросе страницы, а её результат передаётся компоненту через `props`

- в App Router модель другая: React Server Components позволяют выполнять серверную логику непосредственно в серверных компонентах, а клиентские компоненты выделяются с помощью директивы `'use client'`, когда необходимы клиентские возможности

- Server Components и SSR — не синонимы: Server Components определяют, где выполняется компонент и какие возможности ему доступны, а SSR относится к формированию HTML для ответа

### Gatsby

- Gatsby исторически ориентирован на статическую генерацию, но поддерживает разные стратегии рендеринга

- для SSR в Gatsby используется экспортируемая асинхронная функция `getServerData`, которая выполняется при запросе страницы и передаёт результат компоненту через `serverData`

## 10. типичные ошибки, которые стоит знать

- попытка обращаться к `window` или `localStorage` при серверном рендеринге — эти API недоступны в обычной серверной среде
- использование `createRoot` вместо `hydrateRoot` — клиентская точка входа не соответствует существующей серверной разметке
- несовпадение первоначального HTML — сервер и клиент рендерят разные данные или разные значения
- ожидание работы `useEffect` на сервере — эффекты выполняются только на клиенте
- ожидание, что SSR автоматически уменьшит JavaScript-бандл — серверная генерация HTML не гарантирует уменьшения клиентского кода
- использование `renderToStaticMarkup` для интерактивной страницы — результат не предназначен для гидратации
- использование старых потоковых API в новом проекте — `renderToNodeStream` и `renderToStaticNodeStream` удалены в React 19
- игнорирование кеширования и безопасности — персонализированный HTML нельзя бездумно отдавать из общего кеша разным пользователям

## 11. что нужно уметь объяснить на собеседовании

- SSR — React формирует HTML на сервере до того, как браузер завершит выполнение клиентского JavaScript
- Hydration — React на клиенте подключается к серверной разметке и обеспечивает интерактивность, при этом первоначальный рендер должен совпадать с HTML сервера
- `renderToString` — возвращает HTML-строку, не поддерживает потоковую передачу и имеет ограниченную поддержку `Suspense`
- `renderToStaticMarkup` — формирует статический HTML, не предназначенный для гидратации
- `renderToNodeStream` и `renderToStaticNodeStream` — старые потоковые API, удалённые в React 19
- современный SSR — в Node.js использует `renderToPipeableStream`, а в средах с Web Streams — `renderToReadableStream`
- Next.js и Gatsby — фреймворки, которые берут на себя значительную часть организации рендеринга, получения данных и передачи HTML клиенту

- главное понимание для этой темы: SSR решает задачу первоначального формирования HTML, гидратация связывает эту разметку с React на клиенте, а выбор между SSR, SSG и CSR зависит от актуальности данных, требований к интерактивности и стоимости рендеринга
