# service workers в контексте React

- service workers — это тема на стыке JavaScript, браузерных API, сетевых запросов и архитектуры веб-приложений, поэтому для собеседования важно понимать не только API, но и то, как браузер запускает worker, управляет его жизненным циклом и взаимодействует с ним при загрузке приложения

- в React service worker не является частью React и не управляется React-компонентами напрямую — это отдельный механизм браузера, который может улучшить работу приложения, обеспечить офлайн-доступ и управлять кешированием ресурсов

## 1. что такое service worker

- Service Worker — это специальный JavaScript-файл, который браузер запускает в отдельном от основного потока страницы контексте и который может перехватывать сетевые запросы, работать с Cache API, получать сообщения и обрабатывать определённые события даже тогда, когда страница не открыта

- представим обычное React-приложение, которое загружает HTML, JavaScript, CSS и данные с сервера

```
                 браузер
            загружает страницу
                    ↓
            React-приложение
компоненты, состояние, обработчики событий
                    ⇅
              HTTP-запросы
                    ↓
                 сервер
         HTML, JS, CSS, API-данные
```

- без service worker браузер обычно выполняет сетевые запросы согласно обычной логике загрузки ресурсов и настройкам кеширования HTTP

- с зарегистрированным service worker появляется дополнительный слой, через который можно программно обработать запросы контролируемых страниц

```
           React-приложение
                   ↓
             fetch request
                   ↓
            Service Worker
перехватывает запрос через событие fetch
      ↓                      ↓
  Cache API                 сеть
ответ из кеша          запрос к серверу
```

- Worker сам решает, откуда получить ответ, если для запроса предусмотрена соответствующая логика

- важно: service worker не обязан кешировать запросы и не всегда работает как прокси — поведение определяется написанным кодом и стратегией обработки запросов

## 2. зачем service workers нужны в React-приложениях

- основные сценарии использования:

### офлайн-режим

- приложение может открываться без интернета, если необходимые ресурсы были заранее сохранены и логика загрузки поддерживает офлайн-сценарий

### ускорение загрузки

- статические ресурсы и некоторые ответы API можно отдавать из кеша, уменьшая сетевые задержки

### управление обновлениями

- можно подготовить кеш новой версии приложения и контролировать, как клиент переключается на неё

### push-уведомления и фоновые задачи

- worker может принимать push-события и обрабатывать некоторые фоновые события при поддержке браузером и соответствующей инфраструктуре

- service worker особенно полезен для Progressive Web Apps (PWA), но PWA и service worker — не одно и то же: PWA может использовать service worker, однако он не является единственным определяющим признаком PWA

## 3. где выполняется service worker и чем отличается от обычного JavaScript

- чтобы понимать внутреннюю механику, нужно различать три сущности: основной поток страницы, Web Worker и Service Worker
- обычный JavaScript React-приложения выполняется в основном потоке страницы, где доступны `window`, DOM и React API
- Service Worker выполняется в отдельном worker-контексте, не имеет прямого доступа к DOM и не может самостоятельно изменять элементы страницы

```js
// Код страницы
console.log(window.location.href);
document.querySelector('#root');

// Код service worker
self.addEventListener('install', (event) => {
  console.log('Service worker installed');
});
```

- `window` и `document` в service worker недоступны, а `self` ссылается на глобальный объект его контекста
- отдельный контекст позволяет выполнять сетевую и кеширующую логику независимо от JavaScript страницы, но не означает, что worker постоянно работает в фоне

### основные особенности

- Service Worker может быть остановлен браузером после обработки событий, когда он больше не нужен, поэтому нельзя рассчитывать на сохранение его глобальных переменных между запусками
- Service Worker работает с HTTPS или на `localhost` для разработки, поскольку это привилегированный механизм, который должен работать в безопасном контексте
- Service Worker привязан к origin и scope — это определяет, какие страницы он может контролировать
- Service Worker асинхронный — сетевые запросы, кеш и другие операции обычно обрабатываются через Promise
- Service Worker не запускается сам по себе — его необходимо зарегистрировать, после чего браузер управляет его жизненным циклом

## 4. жизненный цикл service worker

- это один из наиболее важных пунктов для собеседования, поскольку многие проблемы с обновлением приложения, кешем и регистрацией связаны именно с жизненным циклом

1. Register - страница регистрирует файл worker

2. Install - установка и подготовка кеша

3. Waiting - ожидание, если ещё работает предыдущая версия

4. Activate - активация новой версии и очистка старого кеша при необходимости

5. Fetch / Message / Push - обработка событий во время работы

### `install`

- событие `install` возникает при первой установке worker или когда браузер обнаруживает новую версию его скрипта
- обычно здесь заранее кешируют критически важные ресурсы, необходимые для запуска приложения

### `activate`

- событие `activate` возникает, когда worker становится активным, и подходит для очистки кешей предыдущих версий или миграции сохранённых данных
- важно различать активацию и управление страницей: активный worker не всегда сразу контролирует уже открытую вкладку, особенно при первой установке

### `fetch`

- событие `fetch` позволяет перехватывать запросы контролируемых страниц и возвращать ответ из кеша, из сети или из другого источника
- это не означает, что браузер автоматически кеширует все запросы — стратегию нужно реализовать самостоятельно или поручить библиотеке

### `waiting` и `skipWaiting()`

- если старая версия worker ещё контролирует открытые страницы, новая версия обычно ждёт, пока старый worker перестанет ими управлять
- вызов `self.skipWaiting()` позволяет новому worker пропустить обычное ожидание, однако это не следует делать бездумно: обновление может затронуть вкладки, которые всё ещё используют старые ресурсы

### `clients.claim()`

- вызов `self.clients.claim()` в событии `activate` позволяет активному worker начать контролировать подходящие открытые страницы в своей области действия, не дожидаясь их следующей навигации
- `skipWaiting()` и `clients.claim()` решают разные задачи: первый влияет на ожидание новой версии, второй — на контроль страниц активным worker

## 5. как зарегистрировать service worker в React

- регистрация выполняется обычным JavaScript страницы, а не внутри React-компонента как часть рендеринга
- рассмотрим минимальную структуру проекта

```
public/
  service-worker.js

src/
  main.jsx
```

- файл `service-worker.js` должен быть доступен браузеру по URL, например `/service-worker.js`, при условии, что он размещён в корне сайта

### регистрация в `main.jsx`

```js
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>,
);

if ('serviceWorker' in navigator) {
  window.addEventListener('load', () => {
    navigator.serviceWorker
      .register('/service-worker.js')
      .then((registration) => {
        console.log('Service worker registered', registration.scope);
      })
      .catch((error) => {
        console.error('Service worker registration failed', error);
      });
  });
}
```

- проверка `"serviceWorker" in navigator` позволяет убедиться, что браузер поддерживает API регистрации
- обработчик `load` откладывает регистрацию до завершения загрузки страницы, чтобы регистрация не конкурировала с начальной загрузкой ресурсов, хотя это не обязательное требование API
- `navigator.serviceWorker.register()` возвращает Promise с объектом `ServiceWorkerRegistration`, через который можно узнать о регистрации и доступных версиях worker
- вызов `register()` не означает, что worker уже контролирует текущую страницу: регистрация, установка, активация и получение контроля — разные этапы

### что такое `scope`

- `scope` определяет набор URL страниц, которыми может управлять worker

```js
navigator.serviceWorker.register('/service-worker.js', {
  scope: '/',
});
```

- в этом примере worker может контролировать страницы сайта в пределах корневой области, если сервер и расположение скрипта позволяют использовать такой scope
- по умолчанию scope определяется директорией, в которой находится файл worker: например, `/app/service-worker.js` обычно получает scope `/app/`
- расширять scope за пределы директории скрипта можно только при соблюдении ограничений браузера, в частности через соответствующий HTTP-заголовок `Service-Worker-Allowed`
- scope определяет контроль над страницами, а не ограничивает worker только запросами к URL внутри этой директории: worker может обрабатывать запросы из контролируемых страниц и к другим ресурсам, если соблюдаются правила браузера и политики безопасности

## 6. работа с Cache API

- Cache API — это браузерный API для сохранения пар «запрос — ответ», которые можно использовать повторно, в том числе без сети
- Cache API не является тем же самым, что HTTP-кеш браузера: у него отдельное управление кешами и содержимым, а выбор сохранённых ответов в логике приложения определяет разработчик
- для service worker обычно используют три основных метода:

```js
// Открыть или создать кеш
const cacheStorage = await caches.open('app-static-v1');

// Сохранить ответ для URL
await cacheStorage.add('/');

// Получить сохранённый ответ
const cachedResponse = await cacheStorage.match('/');
```

- `caches.open()` возвращает Promise с объектом `Cache`, `add()` загружает ресурс и сохраняет ответ, а `match()` ищет подходящую запись и возвращает `Response` либо `undefined`
- кеши могут переживать закрытие вкладки и перезапуск браузера, но браузер вправе удалить их, например при нехватке дискового пространства, поэтому Cache API нельзя считать гарантированным постоянным хранилищем

### полноценный пример service worker

- реализуем простую стратегию для статических ресурсов: предварительно сохраним минимальный набор файлов, будем отдавать кешированные ответы при наличии и использовать сеть, если подходящего ответа нет
- этот пример предполагает, что `/`, `/index.html` и `/offline.html` действительно доступны в production-сборке, а `offline.html` — отдельная подготовленная HTML-страница для офлайн-сценария

```js
const STATIC_CACHE_NAME = 'frontend-static-v1';

const STATIC_ASSETS = ['/', '/index.html', '/offline.html'];

self.addEventListener('install', (installEvent) => {
  installEvent.waitUntil(
    caches.open(STATIC_CACHE_NAME).then((staticCache) => {
      return staticCache.addAll(STATIC_ASSETS);
    }),
  );
});

self.addEventListener('activate', (activateEvent) => {
  activateEvent.waitUntil(
    caches.keys().then((cacheNames) => {
      return Promise.all(
        cacheNames
          .filter((cacheName) => {
            return cacheName.startsWith('frontend-static-') && cacheName !== STATIC_CACHE_NAME;
          })
          .map((cacheName) => caches.delete(cacheName)),
      );
    }),
  );
});

self.addEventListener('fetch', (fetchEvent) => {
  const request = fetchEvent.request;
  const requestUrl = new URL(request.url);

  if (request.method !== 'GET' || requestUrl.origin !== self.location.origin) {
    return;
  }

  fetchEvent.respondWith(
    caches.match(request).then((cachedResponse) => {
      if (cachedResponse) {
        return cachedResponse;
      }

      return fetch(request).catch(async () => {
        if (request.mode === 'navigate') {
          const offlineResponse = await caches.match('/offline.html');

          if (offlineResponse) {
            return offlineResponse;
          }
        }

        return Response.error();
      });
    }),
  );
});
```

- разберём значимые детали, поскольку в этом коде скрыто несколько принципиальных механизмов

1. `installEvent.waitUntil()`

- браузер получает Promise, который сигнализирует, что установка ещё не завершена
- если `addAll()` завершается ошибкой, например потому что один из ресурсов недоступен, установка worker может завершиться неудачей

2. `activateEvent.waitUntil()`

- браузер ждёт завершения очистки старых кешей перед завершением активации
- версионирование имени кеша позволяет отличать набор ресурсов новой версии от старого

3. `fetchEvent.respondWith()`

- передаёт браузеру Promise, результатом которого должен стать ответ на запрос
- если подходящая запись найдена, запрос обслуживается из кеша; в противном случае выполняется `fetch()`

4. обработка сетевой ошибки

- `fetch()` отклоняет Promise при некоторых сетевых ошибках, но HTTP-ответы со статусами `404` или `500` сами по себе не вызывают отклонение Promise
- поэтому для production-приложения недостаточно проверять только `.catch()` — часто нужно проверять `response.ok`, статус ответа, тип ресурса и другие условия

5. ограничение кеширования

- этот пример намеренно упрощён: он использует единый кеш для выбранных ресурсов и не реализует полноценную политику обновления HTML, JS, CSS и API
- в реальном React-приложении не стоит бездумно кешировать все запросы одним способом, особенно если речь идёт о персональных данных, авторизованных API-ответах или ресурсах с меняющимся содержимым

## 7. основные стратегии кеширования

- на собеседовании важно не только знать Cache API, но и уметь объяснить, почему для разных ресурсов выбирают разные стратегии

### Cache First - сначала кеш, затем сеть

- подходит для ресурсов, которые редко меняются, например версионированных изображений или статических файлов

- недостаток: без дополнительной логики можно продолжать отдавать устаревший ответ

### Network First - сначала сеть, затем кеш при сетевой ошибке

- подходит для данных, которым желательно оставаться актуальными, но нужен офлайн-fallback

- недостаток: при медленной сети пользователь ждёт ответ, если не реализован тайм-аут или другая оптимизация

### Stale While Revalidate - сразу кеш, параллельно обновление из сети

- подходит для данных, где важна быстрая выдача, а небольшая устарелость допустима

- недостаток: пользователь может увидеть старые данные до следующего обновления

### Network Only - только сеть

- подходит для запросов, которые нельзя обслуживать из кеша по требованиям приложения

### Cache Only - только кеш

- подходит для ресурсов, которые гарантированно подготовлены заранее

- название стратегии само по себе не гарантирует правильное поведение: необходимо отдельно определить, какие URL ей соответствуют, как обновляются данные, когда удаляются старые записи и что происходит при сетевой ошибке

### пример Cache First для статических файлов

```js
self.addEventListener('fetch', (cacheFirstEvent) => {
  const cacheFirstRequest = cacheFirstEvent.request;

  if (cacheFirstRequest.method !== 'GET' || new URL(cacheFirstRequest.url).origin !== self.location.origin) {
    return;
  }

  cacheFirstEvent.respondWith(
    caches.match(cacheFirstRequest).then((cachedResponse) => {
      if (cachedResponse) {
        return cachedResponse;
      }

      return fetch(cacheFirstRequest);
    }),
  );
});
```

- здесь кеш проверяется первым, а сетевой запрос выполняется только при отсутствии сохранённого ответа
- однако это лишь базовый пример: он не сохраняет успешно загруженный сетевой ответ в кеш и не проверяет статус ответа, поэтому фактически реализует чтение из кеша с сетевым fallback, а не полноценное кеширование новых ресурсов

## 8. как service worker обновляется при новом деплое

- это один из самых важных практических нюансов: разработчик выкладывает новую версию React-приложения, но пользователь продолжает видеть старый интерфейс
- возможная причина — service worker продолжает отдавать закешированные ресурсы
- браузер периодически проверяет скрипт зарегистрированного worker на обновление, а при обнаружении изменений загружает новую версию и запускает её установку
- новая версия обычно проходит через `install`, затем ожидает активации, если старый worker всё ещё контролирует страницы, и после активации может начать управлять ими
- обновление worker не гарантирует, что все открытые вкладки мгновенно перейдут на новые ресурсы: поведение зависит от lifecycle, кеширования и стратегии обновления приложения

### типичная проблема с хешированными файлами

- сборщик вроде Vite может создавать файлы с хешами в именах, например `assets/index-a1b2c3.js`
- при следующем деплое имя изменится, а HTML начнёт ссылаться на новый файл
- если worker отдаёт старый HTML, который ссылается на удалённый JS-файл, пользователь может получить ошибку загрузки приложения
- поэтому в production необходимо продумать кеширование HTML и ассетов, порядок публикации файлов, очистку кеша и поведение при обновлении

## 9. интеграция service worker в React через библиотеки

- вручную реализовывать регистрацию, версионирование кешей, стратегии запросов и обновление приложения полезно для изучения механики, но в реальных проектах часто используют готовые инструменты
- наиболее известный инструмент для этой задачи — Workbox — набор библиотек для работы с service worker и кешированием

- Workbox предоставляет инструменты для регистрации маршрутов, выбора стратегий кеширования, предварительного кеширования ресурсов и управления обновлением кешей

- в приложениях на Vite часто используют vite-plugin-pwa — плагин, который помогает настроить PWA и генерацию service worker, в том числе на основе Workbox

- в старых проектах на Create React App встречается встроенная PWA-инфраструктура, но Create React App уже не рекомендуется как основной способ создания новых React-приложений

- важно понимать, что библиотека автоматизирует инфраструктуру, но не отменяет необходимости выбирать корректные стратегии кеширования и понимать последствия обновления worker

## 10. почему service worker не регистрируется

- на собеседовании желательно уметь не только перечислить причины, но и объяснить, как диагностировать проблему

небезопасный контекст

- на обычном HTTP service worker не регистрируется, кроме доверенных локальных окружений, например `localhost`
- решение: проверить HTTPS и сертификат сайта

неправильный URL или HTTP-ошибка

- файл может отсутствовать, возвращать `404` или быть недоступным
- решение: открыть URL worker напрямую и проверить статус ответа в Network

ошибка JavaScript

- ошибка синтаксиса или исключение в обработчике `install` может помешать успешной установке
- решение: проверить Console и раздел Service Workers в браузерных DevTools

неправильный MIME type или ограничения безопасности

- сервер может возвращать неподходящий тип содержимого, блокировать загрузку или отдавать HTML вместо JS
- решение: проверить заголовки ответа, CSP и фактическое содержимое файла

неподходящий scope

- worker зарегистрирован, но не контролирует нужную страницу из-за ограниченной области действия
- решение: проверить `registration.scope` и `navigator.serviceWorker.controller`

ошибка при предварительном кешировании

- если хотя бы один ресурс в `cache.addAll()` не удаётся загрузить, операция отклоняется, и установка может провалиться
- решение: проверить URL каждого ресурса и ошибки запросов

* важно различать три ситуации: регистрация не удалась, worker зарегистрирован, но ещё не активирован, и worker активен, но не контролирует текущую страницу
* это разные состояния, требующие разной диагностики

### как диагностировать состояние через JavaScript

```js
async function inspectServiceWorker() {
  if (!('serviceWorker' in navigator)) {
    console.log('Service Worker API is unavailable');
    return;
  }

  const currentRegistration = await navigator.serviceWorker.getRegistration();

  console.log('Registration:', currentRegistration);
  console.log('Controller:', navigator.serviceWorker.controller);

  if (currentRegistration) {
    console.log('Scope:', currentRegistration.scope);
    console.log('Installing:', currentRegistration.installing);
    console.log('Waiting:', currentRegistration.waiting);
    console.log('Active:', currentRegistration.active);
  }
}

inspectServiceWorker();
```

- `getRegistration()` помогает получить регистрацию, применимую к текущему документу, если она существует
- `installing`, `waiting` и `active` позволяют увидеть, на каком этапе находится соответствующая версия worker
- `navigator.serviceWorker.controller` показывает worker, который в данный момент контролирует страницу, и может быть `null`, например при первом посещении до получения контроля

## 11. как отлаживать service worker в Chrome DevTools

- открой вкладку Application → Service Workers, чтобы увидеть регистрацию, активную версию, состояние worker и доступные действия для отладки
- во вкладке Application → Cache Storage можно посмотреть сохранённые кеши и их содержимое
- во вкладке Network можно проверить, откуда пришёл ресурс, какой ответ был получен и не загружается ли неожиданно старая версия
- в Console можно увидеть ошибки установки и выполнения worker
- кнопка Update позволяет инициировать проверку обновления, а Unregister — удалить регистрацию для отладки
- очистка данных сайта и кешей может помочь проверить поведение с чистого состояния, но в production не следует рекомендовать пользователям бездумно удалять все данные сайта

## 12. типичные ошибки при использовании service worker

- кеширование всего подряд — API-ответы могут устареть, а приватные данные не следует сохранять без продуманной политики хранения и удаления
- бесконечное использование старого кеша — Cache First без механизма обновления может приводить к тому, что пользователь долго видит устаревшие ресурсы
- неверное управление версиями — очистка кеша новой версией worker должна удалять только принадлежащие приложению устаревшие кеши, а не все кеши сайта
- предположение, что worker всегда работает — браузер может остановить его, поэтому состояние и важные данные нельзя хранить исключительно в глобальных переменных worker
- вызов регистрации при каждом рендере React-компонента — регистрацию обычно выполняют на уровне входного модуля приложения, а не внутри тела компонента
- неправильное использование `skipWaiting()` — немедленная активация новой версии может привести к несовместимости между уже открытой страницей и обновлёнными ресурсами
- ожидание офлайн-работы без кеширования HTML и зависимостей — наличие service worker само по себе не делает приложение доступным без сети

## 13. что нужно уметь объяснить на собеседовании

- базовый уровень — service worker представляет собой отдельный от страницы worker, который может перехватывать запросы, кешировать ресурсы и поддерживать офлайн-сценарии
- уверенный уровень — уметь объяснить регистрацию, `install`, `activate`, `fetch`, scope, Cache API, стратегии кеширования и интеграцию с React
- глубокий уровень — разбираться в обновлении версий, контроле открытых вкладок, `skipWaiting()`, `clients.claim()`, причинах ошибок регистрации, стратегиях кеширования разных типов ресурсов и диагностике через DevTools
- для твоего уровня Frontend-разработчика особенно важно уметь разобрать практический сценарий: после деплоя пользователь видит старую версию приложения или получает ошибку загрузки JS — и объяснить, как проверить worker, кеши, HTML и порядок публикации ресурсов
- главное, что нужно запомнить: React отвечает за UI, а service worker — за отдельный слой браузерной инфраструктуры, связанный с запросами, кешированием, офлайн-доступом и некоторыми фоновыми событиями
