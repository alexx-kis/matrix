# class components

- `Class Component` — это способ описывать React-компонент через JavaScript-класс
- до появления Hooks именно class components были основным способом создавать компоненты, которым нужны `state`, lifecycle и другая сложная логика
- начиная с React 16.8 функциональные компоненты с Hooks получили сопоставимые возможности, поэтому в современном React для нового кода обычно предпочитают функциональный подход
- при этом class components всё ещё важно хорошо понимать, потому что они встречаются в старых проектах, legacy-коде и на собеседованиях

## 1. базовая структура class component

- минимальный class component выглядит так

```jsx
import React from 'react';

class UserCard extends React.Component {
  render() {
    return <div>User card</div>;
  }
}
```

- здесь `UserCard` — JavaScript-класс

- он наследуется от `React.Component`

- `render()` — специальный метод, который должен вернуть описание UI

- использовать компонент можно точно так же, как функциональный

```jsx
<UserCard />
```

- React создаёт экземпляр класса и использует его для работы с компонентом

```
<UserCard />
     ↓
React создаёт экземпляр UserCard
     ↓
вызывает render()
     ↓
получает React element
     ↓
продолжает работу с React tree
```

- поэтому class component — это не функция, которая возвращает JSX, а объектно-ориентированная модель компонента

## 2. почему нужен `extends React.Component`

- `React.Component` — базовый класс, который предоставляет React необходимые механизмы для работы class component

```jsx
class UserCard extends React.Component {
  render() {
    return <div>User</div>;
  }
}
```

- благодаря наследованию экземпляр `UserCard` получает методы и свойства, которые React использует для управления компонентом

- без наследования от `React.Component` обычный JavaScript-класс сам по себе не становится React class component

- также можно импортировать `Component` отдельно

```jsx
import { Component } from 'react';

class UserCard extends Component {
  render() {
    return <div>User</div>;
  }
}
```

- эти два варианта концептуально делают одно и то же

## 3. `render()`

- главным методом class component является `render()`

```jsx
class UserCard extends React.Component {
  render() {
    return <h2>User</h2>;
  }
}
```

- `render()` отвечает за описание того, что компонент должен отображать

- React вызывает его, когда ему нужно получить актуальное представление компонента

- важно не путать `render()` с непосредственным изменением DOM

- `render()` только возвращает описание UI

- React затем использует это описание в своей внутренней работе

- поэтому концептуально

```
state + props
     ↓
render()
     ↓
React elements
     ↓
React reconciliation
     ↓
DOM changes
```

## 4. `props` в class component

- в функциональном компоненте `props` обычно приходят аргументом функции

```jsx
function UserCard(props) {
  return <h2>{props.name}</h2>;
}
```

- в class component `props` доступны через `this.props`

```jsx
class UserCard extends React.Component {
  render() {
    return <h2>{this.props.name}</h2>;
  }
}
```

- использование

```jsx
<UserCard name='Alex' />
```

- React передаст `name` в props экземпляра компонента

```
this.props
    ↓
{
  name: "Alex"
}
```

- `props` являются входными данными компонента и не должны изменяться самим компонентом

## 5. собственное состояние

- главное отличие class component от простого класса заключается в том, что он может иметь собственный `state`

- состояние обычно задаётся в `constructor`

```jsx
class Counter extends React.Component {
  constructor(props) {
    super(props);

    this.state = {
      count: 0,
    };
  }

  render() {
    return <div>{this.state.count}</div>;
  }
}
```

- здесь `this.state` — состояние компонента

- `count` — конкретное значение состояния

- `super(props)` вызывает constructor родительского класса `React.Component`

- это необходимо, чтобы корректно инициализировать экземпляр класса и получить доступ к `this.props`

## 6. современная короткая инициализация state

- `constructor` не всегда нужен
- state можно определить прямо как class field

```jsx
class Counter extends React.Component {
  state = {
    count: 0,
  };

  render() {
    return <div>{this.state.count}</div>;
  }
}
```

- в современном JavaScript/React-коде этот вариант значительно распространённее

## 7. как изменять state

- напрямую изменять `this.state` нельзя

```js
this.state.count = 10;
```

- это изменит JavaScript-объект, но React не получит нормального сигнала о необходимости обновить UI

- для изменения state используется `this.setState()`

```jsx
this.setState({
  count: 10,
});
```

- React получает информацию об обновлении и планирует новый render

```
this.setState(...)
       ↓
React получает update
       ↓
новый render
       ↓
render() выполняется снова
       ↓
новое описание UI
```

## 8. почему `setState` принимает объект

- если состояние выглядит так

```js
this.state = {
  count: 0,
  name: 'Alex',
};
```

- можно изменить только нужное поле

```js
this.setState({
  count: 1,
});
```

- React объединяет обновление с существующим state

- условно

```
старый state:
{
  count: 0,
  name: "Alex"
}

setState:
{
  count: 1
}

результат:
{
  count: 1,
  name: "Alex"
}
```

- это важное отличие class `setState` от обычной замены объекта состояния

## 9. функциональный вариант обновления state

- если новое состояние зависит от предыдущего состояния, лучше передавать функцию

```jsx
this.setState((prevState) => ({
  count: prevState.count + 1,
}));
```

- здесь `prevState` содержит актуальное предыдущее состояние

- это особенно важно, потому что React может группировать несколько обновлений

```jsx
this.setState((prevState) => ({
  count: prevState.count + 1,
}));

this.setState((prevState) => ({
  count: prevState.count + 1,
}));
```

- здесь каждое обновление получает актуальный предыдущий state, поэтому оба increment учитываются

- такой подход концептуально похож на

```jsx
setCount((prevCount) => prevCount + 1);
```

- в функциональном компоненте

## 10. обработчики событий

- class components часто используют методы класса в качестве event handlers

```jsx
class Counter extends React.Component {
  state = {
    count: 0,
  };

  handleIncrement = () => {
    this.setState((prevState) => ({
      count: prevState.count + 1,
    }));
  };

  render() {
    return <button onClick={this.handleIncrement}>{this.state.count}</button>;
  }
}
```

- здесь `handleIncrement` — обработчик события
- при клике вызывается `setState`
- React выполняет новый render

## 11. почему появляется проблема с `this`

- в JavaScript обычный метод класса не всегда автоматически сохраняет `this`

- например

```jsx
class Counter extends React.Component {
  state = {
    count: 0,
  };

  handleIncrement() {
    this.setState({
      count: 1,
    });
  }

  render() {
    return <button onClick={this.handleIncrement}>{this.state.count}</button>;
  }
}
```

- здесь может возникнуть проблема: при передаче метода как callback контекст `this` не обязан автоматически указывать на экземпляр `Counter`

- классический способ решения — `bind`

```jsx
class Counter extends React.Component {
  constructor(props) {
    super(props);

    this.state = {
      count: 0,
    };

    this.handleIncrement = this.handleIncrement.bind(this);
  }

  handleIncrement() {
    this.setState({
      count: 1,
    });
  }

  render() {
    return <button onClick={this.handleIncrement}>{this.state.count}</button>;
  }
}
```

- именно необходимость постоянно думать о `this` и `bind` была одним из неприятных аспектов class components

- современный class field arrow function решает эту проблему

```jsx
handleIncrement = () => {
  this.setState({
    count: 1,
  });
};
```

- стрелочная функция захватывает `this` экземпляра

## 12. lifecycle

- одно из главных преимуществ исторических class components — специальные lifecycle methods

- компонент проходит разные этапы существования

```
mount
  ↓
update
  ↓
unmount
```

- **mount** — компонент создаётся и впервые появляется в React tree

- **update** — его `props` или `state` изменились

- **unmount** — компонент удаляется из React tree

- class components позволяют выполнять определённую логику на этих этапах

## 13. `componentDidMount`

- `componentDidMount()` вызывается после того, как компонент был добавлен в DOM

```jsx
class UserProfile extends React.Component {
  componentDidMount() {
    console.log('mounted');
  }

  render() {
    return <div>Profile</div>;
  }
}
```

- типичные задачи здесь — выполнение действий после появления компонента, например запуск подписки или загрузка данных

- однако важно не воспринимать `componentDidMount` как «метод для любых запросов»

- его смысл гораздо шире — это lifecycle point после mount

## 14. `componentDidUpdate`

- `componentDidUpdate()` вызывается после обновления компонента

```jsx
class UserProfile extends React.Component {
  componentDidUpdate(prevProps, prevState) {
    console.log('updated');
  }

  render() {
    return <div>Profile</div>;
  }
}
```

- React передаёт предыдущие `props` и `state`

```jsx
componentDidUpdate(prevProps, prevState) {
  if (prevProps.userId !== this.props.userId) {
    // реагируем на изменение userId
  }
}
```

- это позволяет выполнять действия только при конкретном изменении

## 15. `componentWillUnmount`

- вызывается непосредственно перед удалением компонента

```jsx
class Chat extends React.Component {
  componentWillUnmount() {
    console.log('cleanup');
  }

  render() {
    return <div>Chat</div>;
  }
}
```

- здесь обычно выполняют очистку ресурсов

- например

```
componentDidMount
     ↓
создали subscription

...

componentWillUnmount
     ↓
удалили subscription
```

- аналогичная концепция в функциональных компонентах реализуется через cleanup функции `useEffect`

## 16. lifecycle и современный React

- у class components существует много lifecycle methods, включая старые методы вроде `componentWillMount`, `componentWillReceiveProps`, `componentWillUpdate`

- эти методы считаются legacy и в современном React-коде их обычно не используют

- часть из них была переименована с префиксом `UNSAFE_`, чтобы явно показать, что использовать их без особой причины не следует

- для собеседования важно понимать основную современную тройку

```
componentDidMount
componentDidUpdate
componentWillUnmount
```

- а также понимать, что современные функциональные компоненты выражают похожую логику через Hooks

## 17. «queries» — работа с запросами

- если под `queries` имеются в виду HTTP/API-запросы, class component сам по себе не предоставляет специального API для запросов
- запрос можно выполнить обычными средствами JavaScript, например `fetch`

```jsx
class UserProfile extends React.Component {
  state = {
    user: null,
    loading: true,
  };

  componentDidMount() {
    fetch('/api/user')
      .then((response) => response.json())
      .then((user) => {
        this.setState({
          user,
          loading: false,
        });
      });
  }

  render() {
    if (this.state.loading) {
      return <div>Loading...</div>;
    }

    return <div>{this.state.user.name}</div>;
  }
}
```

- здесь запрос выполняется в `componentDidMount`
- результат запроса сохраняется в state
- изменение state вызывает новый render

```
componentDidMount()
       ↓
fetch()
       ↓
server response
       ↓
setState()
       ↓
render()
       ↓
UI с полученными данными
```

- если запрос зависит от `props`, например `userId`, то обычно нужно учитывать изменения props

```jsx
class UserProfile extends React.Component {
  state = {
    user: null,
  };

  componentDidMount() {
    this.loadUser();
  }

  componentDidUpdate(prevProps) {
    if (prevProps.userId !== this.props.userId) {
      this.loadUser();
    }
  }

  loadUser = async () => {
    const response = await fetch(`/api/users/${this.props.userId}`);
    const user = await response.json();

    this.setState({
      user,
    });
  };

  render() {
    return <div>{this.state.user?.name}</div>;
  }
}
```

- здесь важен момент, который часто спрашивают на собеседовании
- нельзя просто делать запрос в `componentDidUpdate` без условия, потому что `setState` внутри него вызовет новый update и можно получить бесконечный цикл

```
componentDidUpdate
       ↓
setState
       ↓
componentDidUpdate
       ↓
setState
       ↓
...
```

- поэтому обычно проверяют, действительно ли изменилось нужное значение

## 18. обработка ошибок запросов

- реальный компонент должен учитывать не только успешный ответ

```jsx
class UserProfile extends React.Component {
  state = {
    user: null,
    loading: true,
    error: null,
  };

  componentDidMount() {
    this.loadUser();
  }

  loadUser = async () => {
    try {
      const response = await fetch('/api/user');

      if (!response.ok) {
        throw new Error('Request failed');
      }

      const user = await response.json();

      this.setState({
        user,
        loading: false,
        error: null,
      });
    } catch (error) {
      this.setState({
        loading: false,
        error,
      });
    }
  };

  render() {
    if (this.state.loading) {
      return <div>Loading...</div>;
    }

    if (this.state.error) {
      return <div>Something went wrong</div>;
    }

    return <div>{this.state.user.name}</div>;
  }
}
```

- здесь state хранит три возможных состояния запроса

```
loading
   ↓
success → user
   ↓
error → error
```

- это не особенность class components как таковая
- это обычная организация асинхронного состояния

## 19. Error Boundaries

- у class components есть ещё одна важная особенность — они используются для создания Error Boundaries

```jsx
class ErrorBoundary extends React.Component {
  state = {
    hasError: false,
  };

  static getDerivedStateFromError() {
    return {
      hasError: true,
    };
  }

  componentDidCatch(error, errorInfo) {
    console.error(error, errorInfo);
  }

  render() {
    if (this.state.hasError) {
      return <div>Something went wrong</div>;
    }

    return this.props.children;
  }
}
```

- Error Boundary может перехватывать ошибки в дочернем React-дереве и показывать fallback UI

- это важный нюанс при сравнении функциональных и class components

- хотя функциональные компоненты сегодня предпочтительнее, некоторые специальные возможности React исторически всё ещё связаны с class components, в частности Error Boundaries в традиционном API

## 20. class component и экземпляр класса

- важно понимать внутреннюю модель

- когда React работает с class component, существует экземпляр класса

```
UserProfile class
       ↓
instance
       ↓
this.props
this.state
this.setState()
methods
```

- поэтому внутри метода

```jsx
this.state;
```

- `this` указывает на экземпляр компонента

- это фундаментальное отличие от функционального компонента

- функциональный компонент не представляет собой постоянный экземпляр класса с `this.state`

## 21. почему state сохраняется между render

- нельзя представлять это так, будто React просто один раз создаёт объект класса и навсегда вызывает его `render()`

- правильнее думать, что React управляет экземпляром компонента и его состоянием в рамках своего внутреннего механизма

- `this.state` является частью состояния экземпляра, которым React управляет

- после

```jsx
this.setState({
  count: 10,
});
```

- React планирует обновление и снова вызывает `render()`
- `this.state` при этом содержит актуальное состояние

## 22. плюсы class components

- **понятная объектная модель** — state, props и методы находятся внутри одного экземпляра

- **lifecycle methods** — historically это был основной способ контролировать разные этапы жизни компонента

- **Error Boundaries** — традиционный API Error Boundary основан на class components

- **удобны для понимания legacy-кода** — большое количество старых React-приложений построено именно на них

- **инкапсуляция через класс** — состояние и методы компонента естественным образом находятся внутри одного объекта

## 23. минусы class components

- **сложнее синтаксис** — появляются `class`, `extends`, `constructor`, `super`, `this`, `bind`

- **проблемы с `this`** — методы необходимо правильно привязывать или использовать arrow class fields

- **lifecycle-логика может быть разбросана** — одна функциональная задача может требовать кода в `componentDidMount`, `componentDidUpdate` и `componentWillUnmount`

- **переиспользование логики сложнее** — раньше для переиспользования поведения использовали HOC, render props и другие паттерны

- **больше boilerplate** — простая логика состояния может требовать существенно больше кода

- **хуже сочетаются с современным React API** — современная экосистема React в первую очередь ориентирована на функциональные компоненты и Hooks

## 24. почему функциональные компоненты стали предпочтительнее

- ключевой момент здесь не в том, что React вдруг сделал class components «неправильными»

- проблема в том, что функциональный подход оказался удобнее для построения современной модели React

- сравним простое состояние

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

- и class component

```jsx
class Counter extends React.Component {
  state = {
    count: 0,
  };

  handleIncrement = () => {
    this.setState((prevState) => ({
      count: prevState.count + 1,
    }));
  };

  render() {
    return <button onClick={this.handleIncrement}>{this.state.count}</button>;
  }
}
```

- обе версии делают одно и то же
- функциональная версия обычно короче и не требует `this`, класса и отдельных методов

## 25. главное преимущество Hooks

- самое важное преимущество функциональных компонентов — не просто меньше строк кода

- Hooks позволяют удобно переиспользовать состояние и связанную с ним логику

- например, можно создать custom Hook

```jsx
function useOnlineStatus() {
  // state + effects + related logic
}
```

- затем использовать его в разных компонентах

```jsx
function UserStatus() {
  const isOnline = useOnlineStatus();

  return <div>{isOnline ? 'Online' : 'Offline'}</div>;
}
```

- раньше подобное переиспользование поведения часто требовало HOC или render props, которые создавали дополнительную сложность в структуре React-дерева и API компонентов

## 26. важное сравнение

| class component    | functional component              |
| ------------------ | --------------------------------- |
| `class`            | функция                           |
| `this.props`       | аргумент `props`                  |
| `this.state`       | `useState`                        |
| `this.setState()`  | setter из `useState`              |
| lifecycle methods  | Hooks, например `useEffect`       |
| методы класса      | обычные функции внутри компонента |
| `this`             | нет                               |
| `bind`             | обычно не нужен                   |
| custom logic reuse | custom Hooks                      |
| legacy-подход      | современный основной подход       |

- при этом таблицу нельзя понимать как «class components устарели и больше не работают»
- они полностью остаются частью React
- речь именно о предпочтении при написании нового кода

## 27. самое важное различие в модели мышления

- class component удобно представлять как **объект с состоянием и методами**

```
Component instance
├── props
├── state
├── methods
├── lifecycle
└── render()
```

- functional component удобнее представлять как **функцию, которая выполняется заново для каждого render и использует React Hooks для сохранения состояния и другой информации между render**

```
render
   ↓
function(props)
   ↓
Hooks + logic
   ↓
React elements
```

- именно здесь находится фундаментальная разница между двумя подходами

## 28. что сказать на собеседовании

- если спросят **«что такое class component?»**

- class component — это React-компонент, реализованный через JavaScript-класс, наследующийся от `React.Component`, с методом `render`, который возвращает описание UI, и возможностью использовать `state`, `setState` и lifecycle methods

- если спросят **«как работает state?»**

- состояние хранится в `this.state`, а для его изменения используется `this.setState`, который сообщает React об обновлении и приводит к новому render

- если спросят **«зачем нужен `setState`, почему нельзя изменить `this.state` напрямую?»**

- React должен знать об изменении состояния и запланировать обновление компонента, поэтому используется `setState`, а прямое изменение `this.state` не является корректным способом обновления UI

- если спросят **«как выполнять запросы в class component?»**

- React не предоставляет специального механизма HTTP-запросов, поэтому можно использовать `fetch` или библиотеку для запросов, а lifecycle methods вроде `componentDidMount` и `componentDidUpdate` позволяют определить, когда выполнять такую логику

- если спросят **«почему functional components предпочтительнее?»**

- они имеют более простую модель, не требуют `this` и `bind`, используют Hooks для state и других возможностей React и позволяют удобнее переиспользовать связанную логику через custom Hooks

- если спросят **«есть ли преимущества у class components?»**

- да, они важны для legacy-кода, хорошо известны в старой архитектуре React и используются в традиционном API Error Boundaries, но для нового обычного UI-кода функциональный подход обычно предпочтительнее

- главное, что стоит унести из темы

```
class component
       ↓
class + instance
       ↓
this.props + this.state
       ↓
setState()
       ↓
render()
       ↓
React обновляет UI
```

- функциональный компонент решает ту же основную задачу, но вместо экземпляра класса использует функцию и Hooks

```
functional component
       ↓
function
       ↓
props + Hooks
       ↓
state setter
       ↓
повторное выполнение функции
       ↓
React обновляет UI
```

- поэтому сегодня вопрос обычно не стоит как «class или function — что вообще умеет React»
- оба подхода способны создавать полноценные React-компоненты
- основной вопрос заключается в том, что функциональные компоненты с Hooks дают более простой и удобный способ выражать современную React-логику
