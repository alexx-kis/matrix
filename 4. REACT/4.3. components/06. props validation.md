# 4.3.6. props validation в React

- в этом блоке разберём, как React проверяет входные данные компонентов, что такое `defaultProps` и `PropTypes`, чем проверка типов во время выполнения отличается от статической типизации и зачем нужны Flow и TypeScript

- важно сразу разделить три понятия: передача props, проверка props во время выполнения и проверка типов до выполнения программы — это разные механизмы, которые решают связанные, но не одинаковые задачи

## 1. runtime typing — проверка типов во время выполнения

### что это такое

- `runtime` — это время, когда программа уже выполняется, а `typing` в данном контексте означает проверку типов данных

- допустим, компонент React ожидает получить в `age` число, но родитель передаёт строку

```js
function UserCard({ age }) {
  return <p>возраст: {age}</p>;
}

function App() {
  return <UserCard age='25' />;
}
```

- JavaScript не запрещает передавать строку вместо числа, потому что в нём нет обязательной статической проверки типов для обычных значений переменных и аргументов функций

- React тоже не станет автоматически преобразовывать строку `"25"` в число `25` и не будет автоматически отклонять такой prop

- в данном случае браузер выведет `возраст: 25`, хотя тип переданного значения не соответствует предполагаемому контракту компонента

- контракт компонента — это договорённость о том, какие данные компонент принимает, какие из них обязательны и в каком формате они должны быть представлены

### как проверить типы во время выполнения

- можно самостоятельно написать проверку средствами JavaScript

```js
function ProductCard({ price }) {
  if (typeof price !== 'number') {
    throw new TypeError('price должен быть числом');
  }

  return <p>цена: {price}</p>;
}
```

- теперь при передаче строки `"100"` возникнет ошибка, потому что условие `typeof price !== "number"` будет истинным

- этот подход называется проверкой во время выполнения, поскольку проверка действительно происходит, когда JavaScript исполняет функцию компонента

- однако писать такие проверки вручную для каждого prop неудобно, поэтому для React исторически использовали `PropTypes`, а для более серьёзной проверки данных непосредственно во время выполнения существуют отдельные библиотеки валидации

### зачем вообще проверять props

- props поступают от родительского компонента, поэтому дочерний компонент не всегда контролирует, какие именно значения ему передадут

- ошибки в props могут приводить к неправильному отображению интерфейса, неожиданным результатам вычислений и ошибкам при обращении к свойствам объектов

- например, если компонент ожидает массив товаров, но получает `null`, вызов `products.map(...)` завершится ошибкой

```js
function ProductList({ products }) {
  return (
    <ul>
      {products.map((product) => (
        <li key={product.id}>{product.name}</li>
      ))}
    </ul>
  );
}
```

- если `products` окажется равен `null`, метод `map` вызвать не получится

- проверка типов помогает обнаруживать такие проблемы, но сама по себе не гарантирует, что данные корректны по смыслу: например, значение `-100` имеет тип `number`, хотя цена обычно не должна быть отрицательной

## 2. PropTypes — проверка props в React

### что такое PropTypes

- `PropTypes` — это механизм описания и проверки типов props, который традиционно использовался в React для обнаружения некорректных входных данных во время выполнения

- библиотека позволяет объявить, что компонент ожидает число, строку, массив, объект определённой формы или другой конкретный тип данных

- например, можно явно указать, что `name` должен быть строкой, а `age` — числом

```js
import PropTypes from 'prop-types';

function UserProfile({ name, age }) {
  return (
    <p>
      {name}, возраст: {age}
    </p>
  );
}

UserProfile.propTypes = {
  name: PropTypes.string,
  age: PropTypes.number,
};
```

- сначала импортируем `PropTypes` из отдельного пакета `prop-types`, затем описываем допустимые типы в свойстве `propTypes` самого компонента

- `PropTypes.string` означает, что значение должно быть строкой, а `PropTypes.number` — числом

- поскольку у этих свойств нет `.isRequired`, они считаются необязательными

- если проверка обнаруживает несоответствие, классический механизм PropTypes выводит предупреждение в консоль разработки, но не исправляет значение и обычно не останавливает выполнение программы

- важный нюанс для современных React: начиная с React 19, React больше не выполняет встроенную проверку `propTypes` у функциональных компонентов, поэтому этот механизм не стоит рассматривать как надёжную современную систему валидации; в новых проектах обычно используют TypeScript

### основные валидаторы PropTypes

| Валидатор                    | Что проверяет                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------- |
| `PropTypes.string`           | строку                                                                          |
| `PropTypes.number`           | число                                                                           |
| `PropTypes.bool`             | булево значение                                                                 |
| `PropTypes.func`             | функцию                                                                         |
| `PropTypes.array`            | массив                                                                          |
| `PropTypes.object`           | объект                                                                          |
| `PropTypes.node`             | значение, которое React может отобразить как содержимое                         |
| `PropTypes.element`          | один React-элемент                                                              |
| `PropTypes.elementType`      | тип React-элемента, например компонент или HTML-тег                             |
| `PropTypes.oneOf([...])`     | одно из перечисленных значений                                                  |
| `PropTypes.oneOfType([...])` | одно из перечисленных типов                                                     |
| `PropTypes.arrayOf(...)`     | массив, элементы которого соответствуют заданному валидатору                    |
| `PropTypes.objectOf(...)`    | объект, значения свойств которого соответствуют заданному валидатору            |
| `PropTypes.shape({...})`     | объект с описанной формой                                                       |
| `PropTypes.exact({...})`     | объект с описанной формой, без дополнительных собственных перечисляемых свойств |

- рассмотрим несколько полезных примеров, которые показывают, как описывать не только отдельные типы, но и структуру данных

```js
import PropTypes from 'prop-types';

function OrderSummary({ status, items, customer }) {
  return (
    <p>
      {customer.name}: {status}
    </p>
  );
}

OrderSummary.propTypes = {
  status: PropTypes.oneOf(['pending', 'paid', 'cancelled']),

  items: PropTypes.arrayOf(
    PropTypes.shape({
      id: PropTypes.number.isRequired,
      title: PropTypes.string.isRequired,
      quantity: PropTypes.number,
    }),
  ).isRequired,

  customer: PropTypes.shape({
    name: PropTypes.string.isRequired,
    email: PropTypes.string,
  }).isRequired,
};
```

- `oneOf` ограничивает значение заданным набором вариантов, что удобно для статусов заказа, ролей или вариантов отображения

- `arrayOf` проверяет элементы массива, а не только то, что само значение является массивом

- `shape` описывает ожидаемые поля объекта, причём без дополнительных требований не запрещает остальные поля

- `isRequired` указывает, что значение не должно отсутствовать, то есть не должно быть `null` или `undefined`

- при этом `PropTypes.number.isRequired` не означает, что число обязательно должно быть положительным, целым или находиться в заданном диапазоне — такие ограничения нужно проверять отдельно

### PropTypes и children

- особое значение имеет prop `children`, потому что через него родитель передаёт содержимое внутрь компонента

```js
import PropTypes from 'prop-types';

function Panel({ children }) {
  return <section className='panel'>{children}</section>;
}

Panel.propTypes = {
  children: PropTypes.node,
};
```

- `PropTypes.node` подходит для текста, чисел, React-элементов, массивов отображаемого содержимого и других допустимых React-узлов

- `PropTypes.element` используется, когда ожидается именно один React-элемент, а не произвольное отображаемое значение

- на практике `PropTypes.node` чаще подходит для универсальных контейнеров, а `PropTypes.element` — для API компонента, который намеренно принимает один элемент, например для дальнейшего клонирования через `cloneElement`

## 3. default props — значения по умолчанию

### зачем нужны значения по умолчанию

- не каждый prop обязан передаваться родителем, но компоненту иногда необходимо иметь значение, с которым он сможет работать при отсутствии prop

- например, компонент кнопки может по умолчанию отображать текст «отправить», использовать стандартный размер или быть неактивным только при явном указании соответствующего значения

- `defaultProps` исторически служил механизмом задания таких значений по умолчанию

```js
function Greeting({ name }) {
  return <h1>привет, {name}</h1>;
}

Greeting.defaultProps = {
  name: 'гость',
};
```

- в классических версиях React, а также для классовых компонентов в современных версиях, если `name` не передан или равен `undefined`, используется значение `"гость"`

- но здесь есть важное отличие: если родитель передаст `name={null}`, значение останется `null`, а не заменится на `"гость"`

### современный способ для функциональных компонентов

- в современных функциональных компонентах вместо `defaultProps` рекомендуется использовать значения параметров по умолчанию при деструктуризации props

```js
function Greeting({ name = 'гость' }) {
  return <h1>привет, {name}</h1>;
}
```

- теперь значение `"гость"` используется, если `name` отсутствует или равен `undefined`

- если `name` равен `null`, подстановка не произойдёт

- это обычная возможность JavaScript, а не специальный механизм React

### что важно знать о defaultProps

- начиная с React 19, `defaultProps` больше не поддерживается для функциональных компонентов, поэтому для них следует использовать параметры по умолчанию

- для классовых компонентов `defaultProps` по-прежнему поддерживается

- значение по умолчанию не заменяет проверку типа: если вместо `name` передать число `123`, оно не превратится автоматически в строку

- `defaultProps` и `propTypes` решают разные задачи: первый механизм задаёт значение при определённых условиях, второй исторически проверял соответствие значения ожидаемому типу

## 4. static typing — статическая типизация

### что это такое

- статическая типизация позволяет проверять соответствие типов ещё до выполнения программы, например во время разработки или сборки проекта

- для React это означает, что можно описать ожидаемые props компонента и получить ошибку от инструмента проверки типов, если передать значение неподходящего типа

- в отличие от `PropTypes`, такая проверка не обязана ждать, пока компонент будет вызван в браузере

- важно понимать, что JavaScript сам по себе не обеспечивает такую проверку для обычных типов переменных, поэтому разработчики используют дополнительные инструменты, например TypeScript или Flow

### пример с TypeScript

```tsx
type UserCardProps = {
  name: string;
  age: number;
  isAdmin?: boolean;
};

function TypedUserCard({ name, age, isAdmin = false }: UserCardProps) {
  return (
    <div>
      <p>
        {name}, возраст: {age}
      </p>
      {isAdmin && <p>администратор</p>}
    </div>
  );
}
```

- `type UserCardProps` описывает форму props, которые принимает компонент
- `name: string` означает, что `name` должен быть строкой, а `age: number` — числом
- `isAdmin?: boolean` означает, что prop необязателен, но если он передан, его значение должно быть булевым
- `isAdmin = false` задаёт значение по умолчанию для отсутствующего prop или значения `undefined`
- запись `: UserCardProps` сообщает TypeScript, какой тип имеют props компонента
- расширение `.tsx` обычно используют для файлов TypeScript, содержащих JSX

Теперь попробуем передать неправильные значения

```tsx
<TypedUserCard name={123} age='двадцать пять' />
```

- TypeScript обнаружит две ошибки: `name` передана как число, а `age` — как строка

- при этом TypeScript не исправляет код автоматически и не запрещает JavaScript-движку исполнять его во всех возможных обстоятельствах

- проверка типов выполняется инструментами TypeScript, а типы обычно удаляются при преобразовании TSX в JavaScript

- следовательно, TypeScript помогает обнаруживать ошибки при разработке, но сам по себе не гарантирует корректность данных, полученных от API, пользователя или другого внешнего источника во время выполнения

### что происходит при компиляции

```
TSX-код: компонент + описание типов
↓
проверка типов: TypeScript сообщает о несоответствиях
↓
JavaScript: описания типов удалены
↓
выполнение в браузере: типовые ограничения TS сами по себе уже не проверяются
```

- схема показывает общий принцип, хотя в реальном проекте проверка типов и сборка могут выполняться отдельными инструментами и этапами

- например, сборщик может преобразовать TSX в JavaScript, а TypeScript запускаться отдельно для проверки типов

- если в настройках проекта отключена проверка типов на этапе сборки, наличие TypeScript в проекте ещё не означает, что каждая ошибка типов остановит сборку

## 5. зачем нужны TypeScript и Flow

### TypeScript

- TypeScript — это надстройка над JavaScript, которая добавляет статическую систему типов и позволяет постепенно типизировать существующий JavaScript-код

- TypeScript сохраняет большую часть синтаксиса JavaScript, поэтому разработчики могут использовать привычные функции, объекты, классы и React-компоненты, дополняя их описаниями типов

- в React он помогает проверять props, состояние компонентов, обработчики событий, результаты функций, формы объектов и взаимодействие между разными частями приложения

- TypeScript широко применяется в современных React-проектах благодаря поддержке редакторов кода, автодополнению, рефакторингу и проверке контрактов между компонентами

### Flow

- Flow — это инструмент статической проверки типов для JavaScript, разработанный компанией Meta

- он тоже позволяет описывать типы props и находить потенциальные ошибки до выполнения программы

```js
// @flow

type ProfileProps = {
  username: string,
  followers: number,
};

function ProfileCard({ username, followers }: ProfileProps) {
  return (
    <p>
      {username}: {followers} подписчиков
    </p>
  );
}
```

- здесь `ProfileProps` описывает контракт компонента, а Flow проверяет, соответствуют ли передаваемые значения объявленным типам

- синтаксис Flow отличается от TypeScript, например в записи объектных типов Flow использует запятые, а TypeScript обычно использует точки с запятой или запятые

### зачем нужен отдельный инструмент, если есть PropTypes

- `PropTypes` предназначен для проверки значений во время выполнения и не обеспечивает полноценной статической проверки всего JavaScript-приложения

- TypeScript и Flow позволяют находить ошибки в местах вызова компонентов, проверять совместимость типов между функциями и анализировать гораздо больше, чем только props

- они также помогают редактору кода подсказывать доступные свойства объектов и аргументы функций

- при этом статическая типизация не заменяет проверки внешних данных во время выполнения, поскольку сервер или пользователь может передать данные, которые не соответствуют объявленному типу

- например, если TypeScript считает ответ сервера объектом с полем `id: number`, это описание само по себе не проверит, что реальный JSON действительно содержит числовой `id`

## 6. сравнение подходов

| Критерий                            | PropTypes                                                      | TypeScript / Flow                    |
| ----------------------------------- | -------------------------------------------------------------- | ------------------------------------ |
| Когда выполняется проверка          | во время выполнения, если механизм поддерживается и вызывается | до выполнения программы              |
| Проверка при разработке             | предупреждения во время выполнения                             | диагностика типов до выполнения      |
| Проверка вызовов компонентов        | ограниченная проверка значений                                 | проверка типов props в местах вызова |
| Автодополнение                      | ограниченное                                                   | развитая поддержка редакторов        |
| Проверка типов вне React            | нет полноценной проверки всего приложения                      | да                                   |
| Автоматическая проверка API-ответов | не автоматически                                               | не автоматически                     |
| Исправление некорректных значений   | нет                                                            | нет                                  |

- главное различие заключается не в том, что один подход умеет проверять типы, а другой нет, а в том, когда выполняется проверка, какой объём кода она охватывает и какие ошибки позволяет обнаруживать

## 7. что нужно уметь объяснить на собеседовании

- runtime typing — это проверка типов во время выполнения программы, например проверка полученных значений перед использованием

- PropTypes — механизм декларативного описания ожидаемых типов props, который исторически позволял React выводить предупреждения о некорректных значениях в режиме разработки

- defaultProps — механизм задания значений props по умолчанию, который сохраняется для классовых компонентов, тогда как для функциональных компонентов в React 19 и новее следует использовать параметры по умолчанию

- static typing — проверка типов до выполнения программы, позволяющая находить ошибки и проверять совместимость компонентов ещё при разработке

- TypeScript и Flow — инструменты статической типизации JavaScript, которые позволяют описывать контракты компонентов, проверять вызовы функций и получать подсказки редактора

- важный нюанс — ни TypeScript, ни Flow не обеспечивают автоматическую runtime-валидацию внешних данных, а PropTypes в современных версиях React не следует считать универсальным средством проверки функциональных компонентов
