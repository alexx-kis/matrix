# Context в React — подробный разбор с нуля

- разберём `Context` от самой идеи до нюансов, которые важно понимать на собеседовании: зачем он появился, как работает, как его создавать и использовать, как передавать данные через несколько уровней компонентов и какие у него есть ограничения

## 1. какую проблему решает Context

- начнём с того, как обычно передаются данные в React
- допустим, у нас есть приложение, в котором пользователь авторизовался, и нам нужно показывать его имя в шапке сайта
- структура компонентов выглядит так:

```
               App
    знает имя пользователя
                ↓
              Layout
не использует имя, но передаёт его дальше
                ↓
              Header
        тоже передаёт имя
                ↓
              UserName
    показывает имя пользователя
```

- в такой структуре данные приходится передавать через каждый промежуточный компонент, даже если самому компоненту они совершенно не нужны
- например, `Layout` не использует имя пользователя, но должен принять его через `props` и передать в `Header`, а `Header` должен сделать то же самое для `UserName`
- такой подход называется prop drilling — это ситуация, когда пропсы приходится протаскивать через несколько уровней компонентов к тому компоненту, которому они действительно нужны
- сам по себе `prop drilling` не является ошибкой, но при глубокой и сложной структуре дерева он усложняет поддержку кода

### как это выглядит в коде

```js
function UserName(props) {
  return <p>{props.name}</p>;
}

function Header(props) {
  return <UserName name={props.name} />;
}

function Layout(props) {
  return <Header name={props.name} />;
}

function App() {
  return <Layout name='Алексей' />;
}
```

- обрати внимание: значение `name` используется непосредственно только в `UserName`, но все промежуточные компоненты вынуждены о нём знать
- представь, что между `Layout` и `Header` появится ещё пять компонентов, а имя понадобится только одному из них — количество лишней передачи данных увеличится

## 2. что такое React Context

- Context — это механизм React, который позволяет передавать данные компонентам-потомкам через дерево компонентов без необходимости явно прокидывать эти данные через `props` каждого промежуточного компонента
- с его помощью можно предоставить значение в одной части дерева, а получить его в другом компоненте, находящемся глубже
- например, `App` предоставляет имя пользователя через Context, а `UserName` самостоятельно получает это имя, даже если между ними находятся `Layout` и `Header`

```
                App
создаёт и предоставляет значение Context
                 ↓
               Layout
  не обязан получать имя через props
                 ↓
               Header
   не обязан передавать имя дальше
                 ↓
              UserName
  сам получает значение из Context
```

- важно понять одну тонкость: Context не означает, что данные становятся глобальными для всего приложения автоматически
- доступ к значению определяется тем, находится ли компонент внутри соответствующего Provider в дереве React
- если компонент находится за пределами нужного Provider, он не получит значение от этого Provider
- также Context не заменяет `props` полностью: если данные нужны только ближайшему дочернему компоненту, обычные пропсы часто остаются самым простым и понятным решением

## 3. из каких частей состоит Context

- для работы с Context в функциональных компонентах обычно нужны три вещи: `createContext`, `Provider` и `useContext`

### `createContext` — создаёт объект Context

- сначала нужно создать сам Context, который будет использоваться для передачи определённого типа данных

```js
import { createContext } from 'react';

const UserContext = createContext(null);
```

- `createContext` — это функция из React, которая создаёт объект Context
- `UserContext` — обычная переменная, в которой хранится этот объект
- `null` — значение по умолчанию, которое будет возвращено, если компонент не найдёт подходящего Provider выше себя в дереве
- важно: `createContext` не хранит актуальное состояние пользователя и сам по себе ничего не передаёт компонентам
- он создаёт механизм, с помощью которого React сможет связать предоставленное значение с компонентами, которые его читают
- также обычно Context создают на уровне модуля, а не внутри компонента, чтобы при каждом рендере компонента не создавать новый объект Context

### `Provider` — предоставляет значение

- после создания Context нужно определить, какое значение будет доступно компонентам-потомкам

```js
import { createContext } from 'react';

const UserContext = createContext(null);

function App() {
  const user = {
    name: 'Алексей',
    role: 'admin',
  };

  return (
    <UserContext.Provider value={user}>
      <Header />
    </UserContext.Provider>
  );
}
```

- `UserContext.Provider` — компонент, который предоставляет значение своего Context вложенным компонентам
- `value={user}` — значение, которое будет доступно потребителям этого Context
- `Header` и другие компоненты, отрисованные внутри Provider, могут получить объект `user`, не принимая его через `props`
- сам Provider не обязан быть компонентом `App` — его можно разместить в любом месте дерева, откуда требуется предоставить значение
- например, Context для темы оформления можно разместить вокруг всего приложения, а Context для настроек конкретного редактора — только вокруг редактора

### `useContext` — получает значение

- чтобы прочитать Context в функциональном компоненте, используется хук `useContext`

```js
import { useContext } from 'react';

function Header() {
  const user = useContext(UserContext);

  return <h1>привет, {user.name}</h1>;
}
```

- `useContext(UserContext)` обращается к ближайшему подходящему Provider для `UserContext`, расположенному выше компонента в дереве React
- если значение Provider равно объекту `{ name: 'Алексей', role: 'admin' }`, переменная `user` получит этот объект
- при этом `Header` не нужно принимать `user` через параметры функции и не нужно получать его от родителя через `props`
- в приведённом примере `UserContext` должен быть создан в том же модуле или импортирован из отдельного файла, где он объявлен

## 4. соберём полноценный пример

- теперь объединим всё вместе, чтобы увидеть, как Context решает проблему `prop drilling`

```js
import { createContext, useContext } from 'react';

const UserContext = createContext(null);

function UserName() {
  const currentUser = useContext(UserContext);

  if (currentUser === null) {
    return <p>пользователь не задан</p>;
  }

  return <p>привет, {currentUser.name}</p>;
}

function Header() {
  return (
    <header>
      <UserName />
    </header>
  );
}

function Layout() {
  return (
    <main>
      <Header />
    </main>
  );
}

function App() {
  const currentUser = { name: 'Алексей' };

  return (
    <UserContext.Provider value={currentUser}>
      <Layout />
    </UserContext.Provider>
  );
}

export default App;
```

- когда React отрисует приложение, `App` предоставит значение через `UserContext.Provider`
- затем React отрисует `Layout`, внутри него `Header`, а внутри `Header` — `UserName`
- когда `UserName` вызовет `useContext(UserContext)`, React найдёт Provider выше него в дереве и вернёт предоставленный объект
- в результате на странице появится текст `привет, Алексей`
- обрати внимание, что `Layout` и `Header` вообще не знают о существовании `currentUser` и не передают его дальше
- это и есть основная идея Context: компонент может получать данные из соответствующего контекста, не завися от того, сколько промежуточных компонентов находится между ним и Provider

## 5. как React выбирает значение Context

- это один из важных нюансов для собеседования: React использует значение ближайшего Provider того же Context, расположенного выше компонента-потребителя
- рассмотрим пример с двумя Provider одного Context

```js
import { createContext, useContext } from 'react';

const ColorContext = createContext('black');

function ColorLabel() {
  const currentColor = useContext(ColorContext);

  return <p>{currentColor}</p>;
}

function App() {
  return (
    <ColorContext.Provider value='red'>
      <ColorLabel />

      <ColorContext.Provider value='blue'>
        <ColorLabel />
      </ColorContext.Provider>
    </ColorContext.Provider>
  );
}
```

- первый `ColorLabel` получит значение `red`, потому что ближайший к нему Provider предоставляет именно его
- второй `ColorLabel` получит значение `blue`, потому что находится внутри вложенного Provider со значением `blue`
- вложенный Provider переопределяет значение Context только для своей ветки дерева, а не для всего приложения

```
                    Provider
                  value = "red"
               ↙                ↘
       ColorLabel               Provider
          [red]               value = "blue"
использует внешний Provider        ↓
                               ColorLabel
                                 [blue]
                       использует вложенный Provider
```

- если же компонент вообще не находится внутри Provider этого Context, React использует значение по умолчанию, указанное при вызове `createContext`
- например, `createContext('black')` означает, что без подходящего Provider `useContext(ColorContext)` вернёт `'black'`
- но если Provider существует и передаёт `value={undefined}`, результатом будет именно `undefined`, а не `'black'`
- значение по умолчанию используется как запасной вариант при отсутствии подходящего Provider, а не как значение, которое автоматически подставляется при пустом `value`

## 6. зачем нужен default value

- второй аргумент `createContext` часто вызывает вопросы, поэтому разберём его отдельно

```js
const LanguageContext = createContext('ru');
```

- строка `'ru'` является значением по умолчанию
- если компонент вызывает `useContext(LanguageContext)` и над ним нет соответствующего Provider, он получит `'ru'`
- это удобно, когда у приложения есть осмысленное значение по умолчанию, например язык интерфейса или тема оформления
- для обязательных данных, например текущего пользователя, иногда удобнее использовать `null`, чтобы отсутствие Provider не маскировалось правдоподобным значением

```js
const AccountContext = createContext(null);

function AccountName() {
  const account = useContext(AccountContext);

  if (account === null) {
    throw new Error('AccountName должен находиться внутри AccountContext.Provider');
  }

  return <p>{account.name}</p>;
}
```

- здесь мы намеренно выбрасываем ошибку, если компонент используется без нужного Provider, вместо того чтобы незаметно продолжать работу с некорректными данными
- это не обязательное правило React, а полезный приём для Context, без которого компонент не должен работать

## 7. как Context связан со state

- здесь начинается важный нюанс: Context сам по себе не является хранилищем состояния и не управляет изменениями данных
- в предыдущих примерах значение пользователя создавалось внутри `App`, а Context позволял другим компонентам его прочитать
- но что произойдёт, если пользователь изменит имя, переключит тему или выйдет из аккаунта
- чтобы данные могли меняться, обычно используют `useState` или `useReducer`, а получившееся значение передают через Context

### пример: переключение темы оформления

```js
import { createContext, useContext, useState } from 'react';

const ThemeContext = createContext(null);

function ThemeButton() {
  const themeData = useContext(ThemeContext);

  return <button onClick={themeData.toggleTheme}>текущая тема: {themeData.theme}</button>;
}

function App() {
  const [theme, setTheme] = useState('light');

  function toggleTheme() {
    setTheme((previousTheme) => (previousTheme === 'light' ? 'dark' : 'light'));
  }

  const themeData = {
    theme,
    toggleTheme,
  };

  return (
    <ThemeContext.Provider value={themeData}>
      <main className={theme}>
        <ThemeButton />
      </main>
    </ThemeContext.Provider>
  );
}
```

- здесь `useState` хранит состояние темы, а Context предоставляет его вместе с функцией переключения
- когда пользователь нажимает кнопку, вызывается `toggleTheme`, которая обновляет состояние через `setTheme`
- обновление состояния приводит к повторному рендерингу `App`, после чего Provider получает новое значение `value`
- компоненты, которые читают этот Context, получают актуальное значение и могут обновить отображаемый интерфейс
- обрати внимание, что мы передаём не только данные, но и функцию для их изменения
- именно так можно организовать обратный поток данных: дочерний компонент вызывает функцию, а функция изменяет состояние в компоненте, который его хранит
- это похоже на обычную передачу callback через `props`, только Context позволяет не прокидывать его через каждый промежуточный компонент

## 8. что происходит при изменении Context

- React отслеживает, какие компоненты читают конкретный Context с помощью `useContext`
- когда значение Provider меняется, React обновляет компоненты, которые используют этот Context, даже если промежуточные компоненты не читают его и не получили новых `props`
- по умолчанию React сравнивает старое и новое значения Context с помощью `Object.is`
- если значения различаются, потребители Context получают обновление

### нюанс с объектами

- рассмотрим следующий код

```js
const settings = {
  theme: 'dark',
};

return (
  <SettingsContext.Provider value={settings}>
    <SettingsPanel />
  </SettingsContext.Provider>
);
```

- если Provider продолжает передавать ту же самую ссылку на объект, React считает значения одинаковыми по `Object.is`, даже если кто-то изменил свойство объекта напрямую
- изменение объекта напрямую не является правильным способом обновления состояния React, поскольку React не узнает об изменении автоматически
- теперь представим другой вариант

```js
const settings = {
  theme: theme,
};

return (
  <SettingsContext.Provider value={settings}>
    <SettingsPanel />
  </SettingsContext.Provider>
);
```

- если `App` рендерится повторно и при этом создаётся новый объект `settings`, ссылка на объект меняется, поэтому React считает значение Context изменившимся, даже если поле `theme` осталось прежним
- это может вызвать дополнительные рендеры потребителей Context
- в больших приложениях поэтому важно понимать не только сами данные, но и то, когда создаются новые объекты и функции

### как уменьшить лишние обновления

- один из способов — мемоизировать объект, передаваемый в Provider, если его создание действительно вызывает заметные лишние обновления

```js
import { createContext, useMemo, useState } from 'react';

const PreferencesContext = createContext(null);

function PreferencesProvider({ children }) {
  const [fontSize, setFontSize] = useState(16);

  const preferences = useMemo(
    () => ({
      fontSize,
      setFontSize,
    }),
    [fontSize],
  );

  return <PreferencesContext.Provider value={preferences}>{children}</PreferencesContext.Provider>;
}
```

- теперь объект `preferences` сохраняет свою ссылку между рендерами, пока `fontSize` не изменился
- однако `useMemo` здесь является оптимизацией, а не обязательным условием корректной работы Context
- важно также помнить, что `React.memo` не блокирует обновления компонента, если изменился Context, который этот компонент читает

## 9. какие данные стоит хранить в Context

- Context особенно полезен для данных, которые нужны многим компонентам на разных уровнях дерева и не хочется постоянно передавать через `props`

### тема оформления

- светлая или тёмная тема, цвета и настройки внешнего вида, которые нужны разным частям интерфейса

### локализация

- текущий язык интерфейса и связанные с ним настройки форматирования

### данные пользователя

- сведения о текущем пользователе, необходимые шапке, меню профиля и другим частям приложения

### настройки приложения или компонента

- параметры, которые нужны множеству вложенных компонентов, например конфигурация редактора или формы

- при этом Context не ограничен только перечисленными сценариями — главное, чтобы такой способ передачи данных действительно упрощал структуру приложения

## 10. когда Context не нужен

- распространённая ошибка — использовать Context для любых данных только потому, что он существует
- если данные нужны одному компоненту и его ближайшему потомку, `props` зачастую понятнее и проще
- если состояние используется только в небольшой части интерфейса, разумнее держать его ближе к компонентам, которым оно необходимо
- если приложение содержит большое количество часто меняющихся данных и сложную логику управления состоянием, может оказаться удобнее специализированное решение для состояния, например Redux или Zustand
- это не означает, что Context не подходит для изменяющихся данных — он умеет их передавать и обновлять потребителей, но сам по себе не предоставляет полноценную систему управления состоянием, селекторы и другие возможности специализированных библиотек
- также Context не заменяет серверное хранилище, API или механизм загрузки данных — он лишь передаёт значение по дереву React

## 11. можно ли использовать несколько Context

- да, и это обычная практика
- например, приложению могут понадобиться отдельные Context для пользователя, темы оформления и языка интерфейса

```js
import { createContext } from 'react';

const UserInfoContext = createContext(null);
const ThemeSettingsContext = createContext('light');
const LocaleContext = createContext('ru');

function App() {
  const userInfo = { name: 'Алексей' };

  return (
    <UserInfoContext.Provider value={userInfo}>
      <ThemeSettingsContext.Provider value='dark'>
        <LocaleContext.Provider value='en'>
          <Dashboard />
        </LocaleContext.Provider>
      </ThemeSettingsContext.Provider>
    </UserInfoContext.Provider>
  );
}
```

- в этом примере `Dashboard` и его потомки могут обращаться ко всем трём Context независимо друг от друга
- разделение полезно потому, что разные данные могут изменяться с разной частотой и использоваться разными компонентами
- например, изменение темы не должно само по себе менять значение Context пользователя
- если объединить все данные в один объект Context, любое изменение этого объекта может вызвать обновления всех его потребителей
- поэтому в крупных приложениях нередко создают отдельные Context для логически независимых групп данных

## 12. Context в React 19 и старых версиях

- в современных версиях React есть небольшое синтаксическое отличие, которое полезно знать на собеседовании
- в React 18 и более ранних версиях значение обычно предоставляют через `.Provider`

```js
<UserContext.Provider value={user}>
  <Dashboard />
</UserContext.Provider>
```

- начиная с React 19 сам объект Context можно использовать как Provider

```js
<UserContext value={user}>
  <Dashboard />
</UserContext>
```

- оба варианта предоставляют значение потомкам, но сокращённая запись без `.Provider` относится к React 19 и новее
- `createContext` и `useContext` по-прежнему используются для создания и чтения Context

## 13. как использовать Context в классовых компонентах

- поскольку на собеседовании могут спросить не только про функциональные компоненты, стоит знать и классический способ
- хук `useContext` нельзя вызывать внутри классового компонента, поэтому для чтения Context в классе используется специальное свойство `contextType`

```js
import { Component, createContext } from 'react';

const MessageContext = createContext('привет');

class MessagePanel extends Component {
  static contextType = MessageContext;

  render() {
    return <p>{this.context}</p>;
  }
}
```

- `static contextType = MessageContext` указывает React, какой Context должен быть доступен классу
- значение становится доступно через `this.context`
- при этом такой способ позволяет читать только один Context через `contextType` в рамках одного классового компонента
- если классовому компоненту нужны несколько Context, можно использовать соответствующие потребители через `Context.Consumer` или передать нужные значения в компонент через функциональную обёртку
- в новых приложениях чаще используют функциональные компоненты и `useContext`, потому что этот способ проще комбинировать с другими хуками

## 14. что нужно уверенно объяснить на собеседовании

- что такое Context — механизм передачи данных компонентам-потомкам без явной передачи этих данных через `props` каждого промежуточного компонента
- какую проблему он решает — уменьшает необходимость в `prop drilling`, когда данные протаскиваются через компоненты, которым они не нужны
- что делает `createContext` — создаёт объект Context и задаёт значение по умолчанию
- что делает Provider — предоставляет значение для потребителей в своей ветке дерева
- что делает `useContext` — читает значение ближайшего соответствующего Provider выше компонента, а при его отсутствии возвращает значение по умолчанию
- как Context обновляется — когда значение Provider меняется по сравнению через `Object.is`, React обновляет потребителей этого Context
- является ли Context системой управления состоянием — нет, он передаёт данные, а изменяемое состояние обычно хранится в `useState`, `useReducer` или другом механизме
- когда Context использовать не стоит — когда обычных `props` достаточно или когда для сложного и часто меняющегося состояния лучше подходит специализированный инструмент
- как работает вложенность Provider — потребитель получает значение ближайшего Provider соответствующего Context, а вложенный Provider влияет только на свою ветку дерева
- как читать Context в классе — через `static contextType` и `this.context`, либо с помощью `Context.Consumer`
