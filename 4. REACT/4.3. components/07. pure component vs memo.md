# 4.3.7. PureComponent / memo

- разберём тему с нуля: зачем React нужны оптимизации рендеринга, что такое `PureComponent`, чем он отличается от `Component`, зачем появился `React.memo` и в каких ситуациях эти инструменты действительно помогают

## 1. сначала разберёмся, какую проблему решают эти инструменты

### что такое повторный рендеринг

- вспомним базовую идею React: мы описываем, как интерфейс должен выглядеть при определённых `props` и `state`, а React обновляет отображение, когда эти данные меняются

- допустим, у нас есть родительский компонент, который отображает заголовок и дочерний компонент с информацией о пользователе

```js
import { useState } from 'react';

function UserCard({ username }) {
  console.log('UserCard rendered');

  return <p>пользователь: {username}</p>;
}

function Dashboard() {
  const [counter, setCounter] = useState(0);

  return (
    <section>
      <button onClick={() => setCounter(counter + 1)}>счётчик: {counter}</button>

      <UserCard username='alex' />
    </section>
  );
}
```

- когда мы нажимаем на кнопку, состояние `Dashboard` изменяется, поэтому React повторно вызывает функцию `Dashboard`

- при обычном сценарии обновления родителя React также повторно вызывает `UserCard`, даже если `username` остался равен строке `"alex"`

- это происходит потому, что по умолчанию React не сравнивает все входные `props` каждого обычного дочернего компонента, чтобы решить, стоит ли вызывать его повторно: обновление родителя само по себе может привести к повторному рендерингу дочернего компонента

- важно понимать, что повторный рендеринг компонента и изменение DOM — не одно и то же: React может повторно вычислить описание интерфейса, а затем выяснить, что реальный DOM менять не требуется

### зачем это оптимизировать

- если компонент простой, дополнительный рендеринг может практически ничего не стоить, но если он строит большую таблицу, обрабатывает сотни элементов или запускает сложные вычисления, лишняя работа может стать заметной

- представим список из тысячи карточек товаров, а в родительском компоненте меняется только счётчик корзины

- если данные карточек не изменились, нам может быть выгодно не запускать повторный рендеринг каждой карточки

- для этого React предоставляет механизмы, позволяющие пропускать некоторые повторные рендеринги, если входные данные компонента не изменились

- два механизма, которые нужно знать для собеседования, — `PureComponent` для классовых компонентов и `React.memo` для функциональных компонентов

## 2. что такое `Component`

- `Component` — базовый класс React, от которого наследуются классовые компоненты

```js
import { Component } from 'react';

class UserPanel extends Component {
  render() {
    return <p>имя: {this.props.username}</p>;
  }
}
```

- `UserPanel` получает входные данные через `this.props`, а метод `render()` возвращает описание интерфейса

- когда родитель обновляется и передаёт компоненту новые `props`, React обычно вызывает его `render()` снова, даже если значения этих `props` фактически не изменились

- сам по себе `Component` не включает автоматическую оптимизацию, основанную на поверхностном сравнении предыдущих и новых `props` и `state`

- при этом React не обязан изменять DOM, если результат рендеринга остался прежним

## 3. что такое `PureComponent`

- `PureComponent` — специальный базовый класс для классовых компонентов, который автоматически добавляет проверку: изменились ли `props` или `state` с точки зрения поверхностного сравнения

- если сравнение показывает, что входные данные не изменились, React может пропустить повторный рендеринг этого компонента

- подключается он из `react` так же, как `Component`

```js
import { PureComponent } from 'react';

class UserProfile extends PureComponent {
  render() {
    console.log('UserProfile rendered');

    return <p>пользователь: {this.props.username}</p>;
  }
}
```

- обрати внимание, что мы наследуемся от `PureComponent`, а не от `Component`, и больше ничего специально для оптимизации писать не нужно

### 3.1. как работает `PureComponent`

- представим, что компонент получает такие `props`

```js
{
  username: 'alex',
  age: 25
}
```

- родитель обновился и передал новый набор `props` с теми же значениями

```js
{
  username: 'alex',
  age: 25
}
```

- `PureComponent` поверхностно сравнивает предыдущие и новые `props`, а также предыдущий и новый `state`

- если все сравниваемые поля совпадают, компонент может не вызывать свой `render()` повторно

- если хотя бы одно поле отличается, компонент допускает обновление и React выполняет обычный процесс рендеринга

### схема работы

```
                             родитель обновился
                                     ↓
               React сравнивает старые и новые `props` и `state`
                  ↙                                        ↘
      данные не изменились                              данные изменились
повторный рендеринг можно пропустить      компонент проходит обычный процесс обновления
```

- слово «можно» здесь важно: `PureComponent` оптимизирует определённый сценарий обновления, но не запрещает рендеринг по всем возможным причинам

### 3.2. что означает поверхностное сравнение

- это ключевой нюанс темы, который часто проверяют на собеседованиях

- поверхностное сравнение, или shallow comparison, означает, что React сравнивает значения верхнего уровня, а не рекурсивно проверяет всё содержимое вложенных объектов и массивов

- для примитивных значений вроде строк и чисел сравниваются сами значения, а для объектов и массивов — ссылки на них

- рассмотрим пример

```js
const previousSettings = {
  theme: 'dark',
};

const nextSettings = {
  theme: 'dark',
};

console.log(previousSettings === nextSettings); // false
```

- содержимое объектов одинаковое, но это два разных объекта в памяти, поэтому их ссылки различаются

- теперь другой пример

```js
const sharedSettings = {
  theme: 'dark',
};

const previousProps = {
  settings: sharedSettings,
};

const nextProps = {
  settings: sharedSettings,
};

console.log(previousProps.settings === nextProps.settings); // true
```

- здесь оба набора данных содержат ссылку на один и тот же объект, поэтому поверхностное сравнение поля `settings` считает его неизменившимся

- именно поэтому `PureComponent` не нужно представлять как инструмент, который анализирует всё содержимое объекта и выясняет, поменялось ли хоть одно вложенное поле

### 3.3. опасный случай: изменение объекта на месте

- предположим, что мы передаём в компонент объект `user`, а затем меняем его свойство, не создавая новый объект

```js
import { PureComponent } from 'react';

class UserDetails extends PureComponent {
  render() {
    return <p>{this.props.user.name}</p>;
  }
}

const userData = {
  name: 'alex',
};

userData.name = 'max';
```

- если родитель повторно передаст ту же ссылку `userData`, поверхностное сравнение может решить, что соответствующий `prop` не изменился, и пропустить ожидаемый рендеринг

- это происходит потому, что React видит прежнюю ссылку на объект, а не историю изменений его свойств

- правильный подход — не изменять объект на месте, а создавать новый объект с обновлёнными данными

```js
const updatedUserData = {
  ...userData,
  name: 'max',
};
```

- теперь `updatedUserData` — новый объект, поэтому поверхностное сравнение сможет обнаружить изменение ссылки

- это одна из причин, почему в React так важно придерживаться неизменяемого обновления данных, то есть immutability

### 3.4. а что происходит с `state`

- `PureComponent` сравнивает не только `props`, но и `state`

- если компонент обновляет своё состояние и React определяет, что старое и новое состояние поверхностно равны, это может позволить пропустить рендеринг

- например, если состояние содержит объект и его поле изменили на месте, но сам объект остался тем же, поверхностное сравнение может не обнаружить изменение

- поэтому при обновлении состояния тоже следует создавать новые объекты и массивы, когда меняются их данные

### 3.5. зачем появился `PureComponent`

- обычный `Component` позволяет React повторно вызывать `render()` при обновлениях, даже если входные данные компонента остались прежними

- разработчикам нужен был удобный способ уменьшать лишние рендеринги без необходимости вручную писать одинаковую логику сравнения в каждом классовом компоненте

- `PureComponent` предоставляет эту оптимизацию из коробки: он реализует логику поверхностного сравнения `props` и `state`

- это не другой способ создавать интерфейс и не замена `Component` по возможностям, а вариант классового компонента с дополнительным поведением при проверке необходимости обновления

## 4. различия между `Component` и `PureComponent`

| характеристика                       | `Component`                                                   | `PureComponent`                         |
| ------------------------------------ | ------------------------------------------------------------- | --------------------------------------- |
| назначение                           | базовый класс компонента                                      | базовый класс с оптимизацией обновлений |
| сравнение `props`                    | нет автоматического shallow-сравнения для пропуска рендеринга | есть                                    |
| сравнение `state`                    | нет автоматического shallow-сравнения для пропуска рендеринга | есть                                    |
| обновление при неизменившихся данных | `render()` может вызваться снова                              | рендеринг можно пропустить              |
| проверка вложенных объектов          | автоматически не выполняется                                  | автоматически не выполняется            |
| создание компонента                  | `extends Component`                                           | `extends PureComponent`                 |

- для собеседования важно не говорить, что `Component` всегда рендерится при каждом обновлении родителя, а `PureComponent` никогда не рендерится повторно

- правильнее сказать, что `Component` по умолчанию не использует shallow-сравнение `props` и `state` для такого решения, а `PureComponent` использует

- у классового компонента также можно вручную управлять этим поведением через метод `shouldComponentUpdate()`, если требуется собственная логика проверки

- не стоит одновременно рассчитывать на автоматическое поведение `PureComponent` и пытаться переопределить его `shouldComponentUpdate()` для независимой логики: такой метод у `PureComponent` уже реализован React

## 5. что такое `React.memo`

- `React.memo` решает похожую задачу, но предназначен прежде всего для функциональных компонентов

- он позволяет React запомнить результат предыдущего рендеринга компонента и при последующем рендеринге родителя пропустить повторный вызов функции компонента, если новые `props` поверхностно равны предыдущим

- `React.memo` — это функция высшего порядка, или Higher-Order Component (HOC), которая принимает компонент и возвращает его мемоизированную версию

- мемоизация означает сохранение результата вычисления, чтобы при повторном запросе с теми же входными данными не выполнять вычисление заново

### 5.1. обычный функциональный компонент

```js
function ProductCard({ title, price }) {
  console.log('ProductCard rendered');

  return (
    <article>
      <h2>{title}</h2>
      <p>{price} ₽</p>
    </article>
  );
}
```

- если родитель обновляется, `ProductCard` обычно вызывается повторно, даже когда `title` и `price` остались прежними

- например, родитель может обновлять счётчик корзины, а карточка товара при этом продолжает отображать те же данные

### 5.2. компонент с `React.memo`

```js
import { memo } from 'react';

const MemoizedProductCard = memo(function ProductCardView({ title, price }) {
  console.log('ProductCardView rendered');

  return (
    <article>
      <h2>{title}</h2>
      <p>{price} ₽</p>
    </article>
  );
});
```

- теперь React может пропустить повторный вызов `ProductCardView`, если `title` и `price` не изменились по правилам поверхностного сравнения

- обрати внимание, что мы оборачиваем функцию компонента в `memo`, а не наследуемся от какого-либо класса

- `memo` возвращает компонент, который можно использовать в JSX как обычный компонент

```js
function ProductPage() {
  const [cartCount, setCartCount] = useState(0);

  return (
    <section>
      <button onClick={() => setCartCount(cartCount + 1)}>корзина: {cartCount}</button>

      <MemoizedProductCard title='ноутбук' price={50000} />
    </section>
  );
}
```

- здесь при изменении `cartCount` родитель обновится, но `MemoizedProductCard` получит те же примитивные значения `title` и `price`, поэтому React сможет пропустить его повторный рендеринг

- в этом примере предполагается, что `useState` импортирован из `react`, а приведённые компоненты находятся в одном модуле

## 6. как `React.memo` сравнивает `props`

- по умолчанию `React.memo` использует поверхностное сравнение отдельных значений `props`, при котором для примитивов сравниваются значения, а для объектов, массивов и функций — ссылки

- это означает, что даже при одинаковом содержимом объекта React может посчитать `prop` изменившимся, если объект был создан заново

### пример с объектом

```js
const MemoizedUserCard = memo(function UserCardView({ user }) {
  return <p>{user.name}</p>;
});

function UserDashboard() {
  const [refreshCount, setRefreshCount] = useState(0);

  const currentUser = {
    name: 'alex',
  };

  return (
    <section>
      <button onClick={() => setRefreshCount(refreshCount + 1)}>обновить: {refreshCount}</button>

      <MemoizedUserCard user={currentUser} />
    </section>
  );
}
```

- при каждом рендеринге `UserDashboard` создаётся новый объект `currentUser`

- хотя `name` всегда равен `"alex"`, ссылка на объект меняется, поэтому `memo` не сможет пропустить рендеринг карточки на основании стандартного сравнения `props`

- если создание объекта на каждом рендеринге мешает оптимизации, можно рассмотреть `useMemo`, чтобы сохранить ссылку между рендерингами, пока зависимости не меняются

```js
const currentUser = useMemo(
  () => ({
    name: 'alex',
  }),
  [],
);
```

- в таком случае при обычных последующих рендерингах ссылка на `currentUser` останется прежней

- однако `useMemo` тоже является оптимизацией, а не способом гарантировать семантическую идентичность объекта при любых обстоятельствах

### пример с функцией

- аналогичная ситуация возникает, если передавать дочернему компоненту функцию, созданную заново при каждом рендеринге родителя

```js
const MemoizedActionButton = memo(function ActionButtonView({ onAction }) {
  return <button onClick={onAction}>выполнить</button>;
});

function ActionPanel() {
  const [step, setStep] = useState(0);

  const handleAction = () => {
    console.log('action');
  };

  return (
    <section>
      <button onClick={() => setStep(step + 1)}>шаг: {step}</button>

      <MemoizedActionButton onAction={handleAction} />
    </section>
  );
}
```

- при каждом вызове `ActionPanel` создаётся новая функция `handleAction`, поэтому ссылка на `onAction` меняется и стандартная проверка `memo` обнаруживает изменение `props`

- если функция не зависит от изменяющихся значений компонента, для стабилизации её ссылки можно использовать `useCallback`

```js
const handleAction = useCallback(() => {
  console.log('action');
}, []);
```

- если функция использует изменяющиеся значения из замыкания, необходимые зависимости нужно указать правильно, иначе можно получить устаревшие значения

- не следует добавлять `useMemo` и `useCallback` автоматически повсюду: они тоже имеют стоимость, а мемоизация полезна, когда действительно предотвращает заметную лишнюю работу

- оба инструмента позволяют пропустить некоторые повторные рендеринги, если `props` поверхностно не изменились

- оба чувствительны к новым ссылкам на объекты, массивы и функции

- ни один из них не выполняет глубокое сравнение всех вложенных данных по умолчанию

| характеристика                | `PureComponent`                                                                                       | `React.memo`                                               |
| ----------------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| тип компонента                | классовый                                                                                             | функциональный                                             |
| что используется              | наследование от класса                                                                                | обёртка над компонентом                                    |
| сравнение `props`             | поверхностное                                                                                         | поверхностное по умолчанию                                 |
| сравнение `state`             | поверхностное                                                                                         | нет аналогичной встроенной проверки собственного состояния |
| собственный `state`           | есть                                                                                                  | может использоваться через `useState` и другие хуки        |
| собственная функция сравнения | переопределение `shouldComponentUpdate` не рекомендуется как замена встроенной логике `PureComponent` | можно передать вторым аргументом функцию сравнения         |

- важный нюанс: `React.memo` не запрещает обновления функционального компонента, если изменяется его собственный `state` или контекст, от которого он зависит

- например, если компонент использует `useState`, вызов его setter-функции может привести к рендерингу независимо от того, что его `props` не изменились

- если компонент использует `useContext` и значение контекста, которое он читает, изменилось, он тоже может повторно отрендериться, несмотря на `memo`

- точно так же `PureComponent` не отменяет все возможные причины обновления классового компонента: его собственное состояние, контекст и другие механизмы React продолжают иметь значение

## 8. можно ли передать свою функцию сравнения в `React.memo`

- да, вторым аргументом можно передать функцию, которая самостоятельно сравнит предыдущие и новые `props`

```js
const MemoizedProfile = memo(
  function ProfileView({ name, age }) {
    return (
      <p>
        {name}, возраст: {age}
      </p>
    );
  },
  function arePropsEqual(previousProps, nextProps) {
    return previousProps.name === nextProps.name && previousProps.age === nextProps.age;
  },
);
```

- функция `arePropsEqual` должна возвращать `true`, если предыдущие и новые `props` позволяют безопасно использовать прежний результат рендеринга, и `false`, если требуется обновление

- это может быть полезно, когда нужно задать собственные правила сравнения данных

- однако собственная функция сравнения должна учитывать все `props`, влияющие на результат компонента, в том числе функции обратного вызова, иначе можно случайно сохранить устаревшие обработчики и значения из замыканий

- кроме того, глубокое сравнение больших структур может оказаться дороже самого повторного рендеринга, поэтому такую оптимизацию необходимо обосновывать измерениями

## 9. когда использовать `PureComponent` и `React.memo`

- использовать их стоит не просто потому, что компонент существует, а когда повторные рендеринги действительно создают лишнюю нагрузку или когда измерения показывают, что мемоизация полезна

- особенно полезными они могут быть для больших списков, тяжёлых компонентов, сложных вычислений и компонентов, которые часто получают те же входные данные

- не стоит ожидать, что `memo` автоматически ускорит любой компонент: если компонент дешёвый, а его `props` постоянно получают новые ссылки, выигрыш может отсутствовать

- React также может самостоятельно оптимизировать некоторые обновления, поэтому количество вызовов компонента не всегда напрямую соответствует количеству изменений DOM

- в современных версиях React существует также React Compiler, который при соответствующей настройке способен автоматически выполнять часть оптимизаций мемоизации, поэтому ручное применение `memo` не является обязательным для каждого компонента

## 10. частые ошибки на собеседовании

- ошибка 1: говорить, что `PureComponent` сравнивает всё содержимое объектов — на самом деле он использует поверхностное сравнение

- ошибка 2: говорить, что `React.memo` запрещает повторный рендеринг компонента — он позволяет пропустить некоторые рендеринги, когда входные `props` не изменились по правилам сравнения

- ошибка 3: считать, что если DOM не изменился, то компонент не рендерился — React может повторно вызвать компонент, сравнить результат и не вносить изменения в DOM

- ошибка 4: считать, что `memo` сравнивает только примитивные значения — сравниваются все `props`, но объекты, массивы и функции обычно сравниваются по ссылке

- ошибка 5: считать `PureComponent` и `memo` полностью взаимозаменяемыми — у них сходная цель, но они предназначены для разных типов компонентов и имеют некоторые различия в поведении

## 11. проверка понимания

мини-тест · 3 вопроса

1. родитель обновился, а все примитивные props PureComponent остались прежними — что произойдёт?

-React может пропустить повторный рендеринг

2. в memo-компонент передали новый объект с теми же полями — что произойдёт?

- новая ссылка может привести к повторному рендерингу

3. может ли memo-компонент повторно рендериться при неизменившихся props?

- да, например, при изменении собственного state или используемого контекста

## 12. как ответить на собеседовании

пример хорошего ответа

- `PureComponent` — это базовый класс для классовых React-компонентов, который реализует поверхностное сравнение предыдущих и новых `props` и `state`, позволяя пропускать некоторые ненужные рендеринги
- `Component` такого сравнения по умолчанию не делает
- `React.memo` решает похожую задачу для функциональных компонентов, запоминая результат предыдущего рендеринга и позволяя пропускать повторный вызов компонента, когда его `props` не изменились
- оба механизма используют поверхностное сравнение по умолчанию, поэтому новые ссылки на объекты, массивы и функции могут сводить пользу мемоизации на нет
- при этом они не запрещают обновления из-за собственного состояния или контекста, а применять их стоит тогда, когда это действительно помогает производительности

- главная мысль всей темы: `PureComponent` и `React.memo` помогают React не выполнять повторную работу без необходимости, но их эффективность зависит от того, как устроены `props`, состояние и ссылки на передаваемые значения
