# state в React

- `state` — это внутренние данные компонента, которые могут изменяться во время жизни компонента и изменение которых должно приводить React к обновлению UI
- если `props` приходят в компонент извне, то `state` принадлежит самому компоненту
- типичный пример — значение счётчика, состояние открытия модального окна, введённый текст, выбранный элемент, список загруженных данных

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

- здесь `count` — текущее состояние компонента
- `setCount` — функция, с помощью которой мы просим React изменить состояние
- `0` — начальное значение
- когда состояние меняется, React планирует новый рендер компонента
- во время нового рендера компонент получает уже новое значение `count`

---

## state в функциональных компонентах

- в функциональных компонентах состояние создаётся с помощью `useState`

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>{count}</p>
      <button onClick={() => setCount(count + 1)}>increment</button>
    </div>
  );
}
```

- важно понимать, что `count` здесь не является обычной переменной, которую мы можем изменить через `count = 10`
- значение `count` относится к конкретному рендеру компонента
- `setCount` сообщает React, что состояние нужно изменить
- React затем выполняет новый рендер и во время этого нового рендера `count` уже будет иметь новое значение

---

## почему нельзя изменять state напрямую

- например, так делать неправильно

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    count = count + 1;
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

- здесь мы пытаемся изменить локальную переменную текущего рендера

- React об этом изменении ничего не узнает

- следовательно, React не получит причины выполнить новый рендер

- нужно использовать setter

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

- `setCount` — это не просто функция, которая присваивает новое значение переменной
- это механизм связи между твоим кодом и внутренним механизмом React

---

## state в class components

- в классовом компоненте состояние хранится в `this.state`

```jsx
class Counter extends React.Component {
  state = {
    count: 0,
  };

  render() {
    return <button onClick={() => this.setState({ count: this.state.count + 1 })}>{this.state.count}</button>;
  }
}
```

- изменить состояние нужно через `this.setState()`

```jsx
this.setState({ count: 10 });
```

- нельзя делать так

```jsx
this.state.count = 10;
```

- причина та же: React должен получить уведомление о том, что состояние изменилось
- `setState` как раз и является таким уведомлением

---

## самое важное: setState не является обычным присваиванием

- очень распространённая ошибка новичка — воспринимать `setState` примерно так

```jsx
setCount(10);
console.log(count);
```

- и ожидать, что после `setCount(10)` переменная `count` сразу станет `10`

- это неправильная модель мышления

- вызов setter означает примерно следующее

> React, текущее состояние нужно заменить новым значением, пожалуйста, учти это и выполни необходимую работу по обновлению компонента

- React сам решает, когда применить изменение и когда выполнить следующий рендер

---

## почему setState считается асинхронным

- здесь есть важный нюанс терминологии
- говорить просто «`setState` асинхронный» полезно для начального понимания, но технически это упрощение
- `setState` не является `Promise`, поэтому нельзя понимать слово «асинхронный» как «он возвращает Promise и работает через `await`»

```jsx
setCount(10);

await setCount(10);
```

- `await` здесь не превращает обновление состояния в ожидаемую операцию

- правильнее говорить так: **вызов setter не означает немедленного изменения значения state в текущем выполнении JavaScript**

- React принимает обновление, помещает его в свою систему обновлений и затем решает, когда обработать его

---

## почему React вообще не меняет state немедленно

- главная причина — React хочет иметь возможность эффективно обрабатывать несколько изменений состояния вместе
- представь такой код

```jsx
function handleClick() {
  setCount(count + 1);
  setName('Alex');
  setOpen(true);
}
```

- если бы каждый вызов немедленно вызывал отдельный рендер, React мог бы выполнить несколько последовательных рендеров
- вместо этого React может собрать несколько обновлений и обработать их одной пачкой
- это называется **batching**, или пакетная обработка обновлений

---

## batching

- batching означает, что несколько обновлений состояния группируются перед выполнением рендера

```jsx
function handleClick() {
  setCount(count + 1);
  setName('Alex');
  setOpen(true);
}
```

- здесь произошло три вызова setter

- это не означает автоматически три рендера

- React может обработать эти обновления вместе и выполнить один новый рендер

- концептуально можно представить это так

```
setCount(...)
      ↓
setName(...)
      ↓
setOpen(...)
      ↓
React собирает обновления
      ↓
один новый render
```

- именно batching является одной из главных причин, почему нельзя воспринимать `setState` как обычное синхронное присваивание

---

## functional update

- теперь возникает важная проблема

- что делать, если новое состояние зависит от предыдущего состояния

- например

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

- интуитивно можно ожидать результат `3`

- но после одного вызова `handleClick` результат будет `1`

- почему

- потому что все три выражения используют одно и то же значение `count` из текущего рендера

```
count = 0

setCount(count + 1) → setCount(1)
setCount(count + 1) → setCount(1)
setCount(count + 1) → setCount(1)
```

- React получает три обновления, каждое из которых говорит фактически «сделай состояние равным `1`»
- поэтому итоговое состояние — `1`

---

## как правильно изменить state несколько раз

- если новое значение зависит от предыдущего значения, нужно передавать функцию

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount((previousCount) => previousCount + 1);
    setCount((previousCount) => previousCount + 1);
    setCount((previousCount) => previousCount + 1);
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

- теперь React может последовательно применить обновления

```
начальное значение: 0

update 1: 0 → 1

update 2: 1 → 2

update 3: 2 → 3
```

- поэтому итоговое значение будет `3`

- это называется **functional update**

---

## почему functional update решает проблему

- функция

```jsx
(previousCount) => previousCount + 1;
```

- не говорит React конкретное значение, которое нужно установить

- она говорит, как вычислить новое значение на основе предыдущего

- это принципиально разные вещи

```jsx
setCount(count + 1);
```

- здесь мы передаём конкретное значение

```jsx
setCount((previousCount) => previousCount + 1);
```

- здесь мы передаём инструкцию по вычислению следующего значения

- если несколько обновлений зависят друг от друга, второй вариант является правильным

---

## callback в setState в class components

- у `this.setState` в class components есть ещё один механизм, который часто называют callback

```jsx
this.setState({ count: 10 }, () => {
  console.log(this.state.count);
});
```

- второй аргумент — функция, которая будет вызвана после того, как React применит обновление и выполнит соответствующую работу с компонентом

- это особенно полезно, когда нам нужно выполнить действие **после обновления state**

```jsx
this.setState({ isOpen: true }, () => {
  console.log('state updated');
});
```

- важно отличать этот callback от функции-updater

```jsx
this.setState(
  (previousState) => ({
    count: previousState.count + 1,
  }),
  () => {
    console.log('update finished');
  },
);
```

- здесь есть две разные функции
- первая определяет, **каким должно стать состояние**
- вторая выполняется **после применения обновления**

---

## две формы setState в class components

- у `this.setState` есть две основные формы

```jsx
this.setState({
  count: 10,
});
```

- здесь передаётся объект с изменениями

- либо

```jsx
this.setState((previousState) => ({
  count: previousState.count + 1,
}));
```

- здесь передаётся функция

- React передаёт этой функции актуальное предыдущее состояние

- второй вариант особенно важен, когда новое состояние зависит от предыдущего

---

## callback и functional components

- в функциональном компоненте setter из `useState` не имеет второго аргумента callback такого вида

```jsx
setCount(10, () => {
  console.log('updated');
});
```

- это не является правильным способом работы с `useState`

- вместо этого обычно используют `useEffect`

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    console.log('count changed', count);
  }, [count]);

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

- здесь эффект запускается после того, как React применил изменение `count` и компонент был обновлён

---

## синхронный и асинхронный код

- теперь перейдём к одному из наиболее популярных вопросов на собеседовании

> чем отличаются несколько `setState` вызовов в синхронной и асинхронной функции

- исторически здесь нужно учитывать версию React
- особенно важно различать поведение React до React 18 и современного React

---

## пример с синхронным обработчиком

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    setCount(count + 1);
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

- в современном React эти обновления будут забатчены
- оба вызова используют `count` из одного рендера
- поэтому итоговое значение будет `1`
- React выполнит один новый рендер для этой пачки обновлений

---

## пример с asynchronous callback

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setTimeout(() => {
      setCount(count + 1);
      setCount(count + 1);
    }, 1000);
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

- для современного React 18+ эти обновления также автоматически batch-атся

- поэтому два `setCount` внутри `setTimeout` не обязательно означают два рендера

- они будут обработаны одной пачкой

- это важное отличие современного React от старых версий React

---

## React 17 и более старые версии

- исторически автоматический batching был ограничен определёнными контекстами
- например, обновления внутри React event handler обычно batch-ились

```jsx
function handleClick() {
  setCount(count + 1);
  setName('Alex');
}
```

- React мог обработать их одной пачкой

- но обновления внутри `setTimeout`, Promise callback или некоторых других asynchronous contexts раньше могли не batch-иться автоматически

```jsx
setTimeout(() => {
  setCount(count + 1);
  setName('Alex');
}, 1000);
```

- в React 17 и старше это могло привести к двум отдельным рендерам
- в React 18 automatic batching был расширен на такие случаи

---

## что нужно отвечать на собеседовании

- если вопрос сформулирован без указания версии React, лучше сначала уточнить версию

- если речь идёт о современном React, можно сказать следующее

- React группирует несколько state updates в batch, чтобы уменьшить количество рендеров

- в React 18 automatic batching работает не только внутри React event handlers, но и в большинстве asynchronous contexts

- поэтому несколько `setState` вызовов подряд обычно приводят к одному render, хотя внутри React будет обработано несколько state updates

---

## важное различие: количество setState и количество render

- это две разные вещи

```jsx
function handleClick() {
  setCount((previousCount) => previousCount + 1);
  setCount((previousCount) => previousCount + 1);
  setCount((previousCount) => previousCount + 1);
}
```

- здесь три state updates
- но это не означает три render
- React может обработать три updates одной пачкой и выполнить один render

```
3 state updates
       ↓
React batch
       ↓
1 render
```

- поэтому на собеседовании нельзя говорить «три `setState` = три перерендера»

---

## что происходит внутри batch

- допустим

```jsx
setCount((previousCount) => previousCount + 1);
setCount((previousCount) => previousCount + 1);
setCount((previousCount) => previousCount + 1);
```

- React получает три update
- эти update сохраняются в очереди обновлений
- затем React обрабатывает их последовательно

```
count = 0

update 1 → 1
update 2 → 2
update 3 → 3
```

- после обработки всей пачки React получает итоговое состояние `3`

- затем выполняется render с этим итоговым состоянием

- получается очень важная идея

```
несколько updates
        ↓
очередь updates
        ↓
обработка updates
        ↓
итоговое state
        ↓
render
```

---

## почему говорят «очередь обновлений»

- React не просто хранит последнее значение state

- для state updates существует очередь, которую React должен обработать

- например

```jsx
setCount((previousCount) => previousCount + 1);
setCount((previousCount) => previousCount + 1);
setCount((previousCount) => previousCount + 1);
```

- React может концептуально представить это как

```
[
  previousCount => previousCount + 1,
  previousCount => previousCount + 1,
  previousCount => previousCount + 1
]
```

- затем обработать их последовательно

```
0 → 1 → 2 → 3
```

- именно поэтому functional updater особенно важен при нескольких связанных обновлениях

---

## state и snapshot

- ещё одна фундаментальная идея React — значение state в компоненте можно рассматривать как **snapshot конкретного render**

- например

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    console.log(count);

    setCount(count + 1);

    console.log(count);
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

- оба `console.log(count)` относятся к одному и тому же render

- поэтому они оба напечатают `0`

- после `setCount` переменная `count` внутри уже выполняющегося `handleClick` не превращается магически в `1`

- React создаст новый render

- и уже в новом render `count` будет `1`

```
render #1
count = 0
      ↓
handleClick
      ↓
setCount(1)
      ↓
render #2
count = 1
```

- это одна из самых важных вещей для понимания React state

---

## отличие state от обычной переменной

- обычная переменная внутри функции живёт в рамках конкретного выполнения функции

```jsx
function Example() {
  let value = 0;

  value += 1;

  console.log(value);
}
```

- React state связан с жизненным циклом компонента и сохраняется между render

```jsx
function Example() {
  const [value, setValue] = useState(0);
}
```

- при следующем вызове функции-компонента React снова предоставит этому компоненту сохранённое состояние

```
render #1 → value = 0
             ↓
        setValue(1)
             ↓
render #2 → value = 1
             ↓
        setValue(2)
             ↓
render #3 → value = 2
```

---

## состояние объекта

- если state является объектом, нужно помнить, что setter не делает автоматический глубокий merge в функциональном `useState`

```jsx
function Profile() {
  const [profile, setProfile] = useState({
    name: 'Alex',
    age: 25,
  });
}
```

- если написать

```jsx
setProfile({
  name: 'John',
});
```

- старое поле `age` будет потеряно
- поэтому нужно самостоятельно сохранить старые поля

```jsx
setProfile((previousProfile) => ({
  ...previousProfile,
  name: 'John',
}));
```

- здесь `...previousProfile` копирует существующие свойства, а `name` заменяется новым значением

---

## а что происходит в class components

- здесь есть важное отличие

```jsx
this.setState({
  name: 'John',
});
```

- в class component объект, переданный в `setState`, объединяется с текущим state на верхнем уровне

- условно

```
state:
{
  name: "Alex",
  age: 25
}

setState:
{
  name: "John"
}

result:
{
  name: "John",
  age: 25
}
```

- но это не означает глубокое объединение вложенных объектов
- merge происходит только на верхнем уровне

---

## типичный вопрос про два setState

- допустим есть

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    setCount(count + 1);
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

- вопрос: сколько будет render

- в современном React при одном таком событии — один дополнительный render из-за batch

- вопрос: чему будет равен `count`

- `1`, потому что оба updates вычисляются из одного snapshot `count = 0`

- если заменить их на

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount((previousCount) => previousCount + 1);
    setCount((previousCount) => previousCount + 1);
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

- render всё ещё один дополнительный

- но итоговый `count` будет `2`

- это прекрасная демонстрация того, что **batching отвечает за количество render, а functional updater — за корректную обработку последовательных зависимых updates**

---

## главное, что нужно знать к собеседованию

- `state` — внутренние изменяемые данные компонента
- изменение state может привести к новому render
- в функциональных компонентах state создаётся через `useState`
- в class components state хранится в `this.state`
- в class components изменение выполняется через `this.setState`
- нельзя напрямую изменять state
- setter не означает немедленного изменения переменной в текущем render
- значение state внутри конкретного render можно рассматривать как snapshot
- несколько state updates могут быть объединены React в batch
- количество вызовов setter не равно количеству render
- если новое состояние зависит от предыдущего, используй functional updater
- `setCount(count + 1)` использует значение `count` текущего snapshot
- `setCount(previousCount => previousCount + 1)` получает актуальное значение из очереди обновлений
- в class components `this.setState` может принимать updater-функцию и callback
- updater-функция вычисляет новое состояние
- callback в `this.setState` позволяет выполнить код после применения обновления
- в функциональных компонентах для реакции на изменение state обычно используется `useEffect`
- в React 18 automatic batching значительно шире, чем в старых версиях React
- поэтому при вопросах про batching всегда полезно учитывать версию React
