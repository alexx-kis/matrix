# lifecycle methods в React

- начнём с основ и постепенно дойдём до порядка вызова методов, их назначения, различий между классовыми и функциональными компонентами и типичных вопросов на собеседовании

- в этом блоке важно не просто выучить названия методов, а понять, на каком этапе жизни компонента они вызываются, зачем нужны и что именно в этот момент можно делать

## 1. что такое жизненный цикл компонента

- жизненный цикл (lifecycle) — это последовательность этапов, через которые проходит React-компонент с момента его появления в React-дереве до удаления из него

- компонент не просто один раз вызывается и навсегда остаётся на странице: он может создаваться, обновляться из-за изменения `props` или `state`, а затем удаляться

#### mounting — монтирование - компонент впервые появляется в React-дереве

#### updating — обновление - изменились props или state, и React должен обновить представление

#### unmounting — размонтирование - компонент удаляется из React-дерева

- это три основных этапа жизненного цикла в классических компонентах React

- отдельно существует обработка ошибок дочерних компонентов — error handling, которую тоже необходимо знать для собеседования

### что значит монтирование

- допустим, мы написали компонент `Profile`, который отображает имя пользователя, а затем впервые добавили его в приложение

```js
class Profile extends React.Component {
  render() {
    return <h1>профиль пользователя</h1>;
  }
}
```

- когда React впервые включает `Profile` в своё дерево и создаёт соответствующее представление, компонент проходит этап монтирования

- важно: монтирование не означает, что браузер обязательно впервые открыл страницу, поскольку компонент может появиться и позже, например после нажатия на кнопку или изменения маршрута

### что значит обновление

- после монтирования компонент может получить новые `props` или новый `state`

```js
class Profile extends React.Component {
  state = {
    userName: 'анна',
  };

  render() {
    return <h1>{this.state.userName}</h1>;
  }
}
```

- если состояние изменится с `'анна'` на `'мария'`, React может повторно вызвать `render()`, чтобы получить новое описание интерфейса

- обновление компонента не обязательно означает, что браузер реально изменит DOM: React может вычислить новое представление и обнаружить, что конкретные DOM-изменения не нужны

### что значит размонтирование

- если `Profile` перестал быть частью React-дерева, например родитель перестал его рендерить, компонент размонтируется

```js
class App extends React.Component {
  state = {
    showProfile: true,
  };

  render() {
    return <div>{this.state.showProfile && <Profile />}</div>;
  }
}
```

- когда `showProfile` становится `false`, React удаляет `Profile` из дерева

- именно на этом этапе нужно очищать ресурсы, срок жизни которых был связан с компонентом: отменять подписки, очищать таймеры, снимать обработчики событий, закрывать соединения, если они больше не нужны

## 2. почему React нужны методы жизненного цикла

- React должен управлять не только вычислением интерфейса, но и взаимодействием компонента с внешним миром

- например, компонент может:
  - подписываться на события браузера
  - запускать таймер
  - подключаться к внешнему сервису
  - загружать данные
  - измерять размеры DOM-элемента
  - очищать подписки при удалении

- все эти действия имеют определённый момент, в который их правильно выполнять

- методы жизненного цикла позволяют привязать действия к конкретным этапам существования компонента

- например, подписку нужно создать после того, как компонент смонтирован, а удалить её нужно при размонтировании, иначе подписка может продолжать работать после того, как компонент больше не нужен

## 3. все основные методы жизненного цикла

- прежде всего разделим методы по этапам, на которых они работают

```
этап              методы
-----------------------------------------------
монтирование     | `constructor`,
                 | `getDerivedStateFromProps`,
                 | `render`,
                 | `componentDidMount`
-----------------------------------------------
обновление       | `getDerivedStateFromProps`,
                 | `shouldComponentUpdate`,
                 | `render`,
                 | `getSnapshotBeforeUpdate`,
                 | `componentDidUpdate`
-----------------------------------------------
размонтирование  | `componentWillUnmount`
-----------------------------------------------
обработка ошибок | `getDerivedStateFromError`,
                 | `componentDidCatch`
-----------------------------------------------
```

- некоторые методы относятся сразу к нескольким этапам, например `getDerivedStateFromProps` вызывается и при монтировании, и при обновлении

- кроме того, существуют устаревшие методы жизненного цикла, которые могут встретиться в старом коде: `componentWillMount`, `componentWillReceiveProps`, `componentWillUpdate` и их варианты с префиксом `UNSAFE_`

- разберём актуальные методы классовых компонентов по порядку выполнения

## 4. этап mounting — монтирование

### 4.1. `constructor`

- `constructor` — обычный конструктор JavaScript-класса, который вызывается при создании экземпляра классового компонента

- его основная задача — первоначальная настройка экземпляра: инициализация `state` и привязка обработчиков методов, если это необходимо

```js
class Counter extends React.Component {
  constructor(props) {
    super(props);

    this.state = {
      count: 0,
    };
  }

  render() {
    return <p>{this.state.count}</p>;
  }
}
```

- `constructor` принимает `props`, чтобы начальная настройка компонента при необходимости могла зависеть от входных данных

- вызов `super(props)` необходим, чтобы конструктор родительского класса `React.Component` выполнился, а в конструкторе можно было обращаться к `this.props`

- в современных классовых компонентах начальное состояние часто записывают короче, через публичное поле класса `state = { ... }`, поэтому явно писать `constructor` требуется не всегда

#### что важно помнить на собеседовании

- `constructor` вызывается до первого `render()`

- в нём не нужно вызывать `setState()`, поскольку начальное состояние задаётся напрямую

- не нужно выполнять здесь побочные эффекты: например, запускать таймеры или подписываться на внешние события

- конструктор не вызывается повторно при обычном обновлении компонента

### 4.2. `static getDerivedStateFromProps`

- `getDerivedStateFromProps` позволяет вычислить новое состояние на основе текущих `props` непосредственно перед рендерингом

- метод статический, поэтому у него нет доступа к экземпляру компонента через `this`

```js
class ColorPanel extends React.Component {
  state = {
    color: this.props.initialColor,
  };

  static getDerivedStateFromProps(props, state) {
    if (props.initialColor !== state.previousInitialColor) {
      return {
        color: props.initialColor,
        previousInitialColor: props.initialColor,
      };
    }

    return null;
  }

  render() {
    return <div style={{ color: this.state.color }}>текст</div>;
  }
}
```

- здесь `props` содержит актуальные входные данные, а `state` — текущее состояние компонента

- если метод возвращает объект, React объединяет его поля с текущим состоянием, а если возвращает `null`, состояние не меняется

- пример показывает сам механизм, но в реальном приложении синхронизировать состояние с `props` таким способом обычно не рекомендуется без веской причины: это может создавать два источника истины для одного значения

- чаще лучше использовать `props` напрямую либо хранить самостоятельное состояние, если пользователь должен изменять значение независимо от входных данных

#### что важно помнить

- метод вызывается перед `render()` как при монтировании, так и при обновлении

- он вызывается даже тогда, когда изменение `props` не является причиной текущего обновления

- метод должен быть чистым: нельзя запускать запросы, изменять DOM или выполнять другие побочные эффекты

- `getDerivedStateFromProps` не относится к методам, которые используются для обычной загрузки данных

### 4.3. `render`

- `render` — метод классового компонента, который возвращает описание интерфейса, создаваемое с помощью JSX или других поддерживаемых React-значений

```js
class Greeting extends React.Component {
  render() {
    return <h1>привет, {this.props.userName}</h1>;
  }
}
```

- React использует результат `render()` для определения того, каким должно быть представление компонента

- если `userName` изменится, React может снова вызвать `render()`, получить новое описание интерфейса и согласовать его с предыдущим

### главное правило `render()` — он должен быть чистым

- это означает, что при одинаковых входных данных результат рендеринга должен быть одинаковым и сам метод не должен изменять внешнее состояние

- нельзя непосредственно внутри `render()` запускать запросы, устанавливать таймеры, подписываться на события или изменять DOM вручную

- `render()` может вызываться больше раз, чем компонент фактически обновляет DOM, поэтому побочные эффекты внутри него могут привести к повторным действиям и ошибкам

- в современном React рендеринг также может быть прерван или повторён, поэтому нельзя считать сам вызов `render()` доказательством того, что результат уже появился на экране

### 4.4. `componentDidMount`

- `componentDidMount` вызывается после того, как компонент смонтирован

- это основной метод классового компонента для запуска действий, которые должны выполняться после первоначального монтирования

```js
class UserList extends React.Component {
  state = {
    users: [],
  };

  async componentDidMount() {
    const response = await fetch('/api/users');
    const loadedUsers = await response.json();

    this.setState({ users: loadedUsers });
  }

  render() {
    return (
      <ul>
        {this.state.users.map((user) => (
          <li key={user.id}>{user.name}</li>
        ))}
      </ul>
    );
  }
}
```

- после монтирования компонент запрашивает данные и затем обновляет состояние через `setState()`

- изменение состояния запускает новый цикл обновления, поэтому после завершения запроса компонент обычно снова рендерится

- `componentDidMount` подходит также для установки подписок, запуска таймеров и измерения DOM, если для этого действительно требуется смонтированный элемент

#### нюансы

- `componentDidMount` вызывается после первоначального монтирования, но не после каждого обновления

- метод может вызывать `setState()`, однако это создаст дополнительный рендеринг, поэтому обновление должно быть оправданным

- в режиме разработки с включённым `StrictMode` React может выполнить дополнительный цикл монтирования и очистки, чтобы выявить ошибки в побочных эффектах

- следовательно, запросы и подписки должны быть спроектированы так, чтобы повторный запуск в режиме разработки не ломал приложение

## 5. этап updating — обновление

- обновление начинается, когда React обрабатывает изменение `props` или `state` компонента либо другое обновление, которое приводит к повторному рендерингу

- у классового компонента есть несколько методов, позволяющих управлять этим процессом

### 5.1. `shouldComponentUpdate`

- `shouldComponentUpdate` позволяет классовому компоненту сообщить React, нужно ли продолжать обычный процесс обновления этого компонента

```js
class Score extends React.Component {
  state = {
    points: 0,
  };

  shouldComponentUpdate(nextProps, nextState) {
    return nextState.points !== this.state.points;
  }

  render() {
    return <p>очки: {this.state.points}</p>;
  }
}
```

- метод получает следующие `props` и `state`, которые React рассматривает для обновления, а также может сравнить их с текущими значениями через `this.props` и `this.state`

- если метод возвращает `true`, React продолжает обычный путь обновления компонента и вызывает `render()`

- если метод возвращает `false`, React пропускает обычный рендеринг самого компонента в этом цикле

#### важные нюансы

- `shouldComponentUpdate` — механизм оптимизации, а не место для изменения состояния или выполнения побочных эффектов

- нельзя полагаться на него как на механизм обеспечения корректности логики приложения

- возвращение `false` не означает, что обновление состояния вообще не произошло: состояние может измениться, хотя собственный `render()` компонента будет пропущен

- этот метод не запрещает дочерним компонентам обновляться из-за собственных изменений состояния

- сравнение только отдельных полей может быть некорректным, если другие поля `props` или `state` тоже влияют на результат `render()`

- `React.PureComponent` предоставляет похожую оптимизацию с помощью поверхностного сравнения `props` и `state`, поэтому часто не нужно вручную писать простой `shouldComponentUpdate`

### 5.2. `getSnapshotBeforeUpdate`

- `getSnapshotBeforeUpdate` вызывается после `render()`, но непосредственно перед тем, как React применит изменения к DOM

- метод нужен, когда необходимо прочитать текущее состояние DOM перед обновлением и сохранить полученную информацию для последующего использования в `componentDidUpdate`

- классический пример — сохранение позиции прокрутки в списке, который может измениться после обновления

```js
class MessageList extends React.Component {
  getSnapshotBeforeUpdate(prevProps) {
    if (prevProps.messages.length < this.props.messages.length) {
      const listElement = this.listElement;

      return listElement.scrollHeight - listElement.scrollTop;
    }

    return null;
  }

  componentDidUpdate(prevProps, prevState, snapshot) {
    if (snapshot !== null) {
      this.listElement.scrollTop = this.listElement.scrollHeight - snapshot;
    }
  }

  render() {
    return (
      <div
        ref={(element) => {
          this.listElement = element;
        }}
      >
        {this.props.messages.map((message) => (
          <p key={message.id}>{message.text}</p>
        ))}
      </div>
    );
  }
}
```

- здесь перед изменением DOM сохраняется расстояние от текущей позиции прокрутки до конца списка, а после обновления восстанавливается соответствующая позиция

- таким образом, добавление новых сообщений не обязательно сбросит положение пользователя в списке

#### что важно помнить

- метод вызывается только при обновлении, а не при первоначальном монтировании

- он выполняется после `render()`, но до применения изменений к DOM

- возвращённое значение передаётся третьим аргументом в `componentDidUpdate`

- это специальный метод для чтения DOM в промежутке между рендерингом и применением изменений, а не универсальный способ выполнять побочные эффекты

### 5.3. `componentDidUpdate`

- `componentDidUpdate` вызывается после обновления компонента и применения соответствующих изменений к DOM

- его используют для действий, которые нужно выполнить после обновления: например, синхронизации с внешней системой, изменения размеров, управления фокусом или выполнения запроса при изменении определённых `props`

```js
class SearchResults extends React.Component {
  componentDidUpdate(prevProps) {
    if (prevProps.query !== this.props.query) {
      this.loadResults(this.props.query);
    }
  }

  loadResults(query) {
    // здесь могла бы находиться логика загрузки данных
  }

  render() {
    return <div>{this.props.query}</div>;
  }
}
```

- сравнение предыдущих и текущих `props` позволяет выполнить действие только тогда, когда действительно изменился интересующий параметр

- без такой проверки запрос мог бы запускаться после каждого обновления компонента, даже если поисковая строка не менялась

#### особенно важный нюанс — `setState()` внутри `componentDidUpdate`

- вызывать `setState()` здесь можно, но обновление должно быть защищено условием, которое позволяет избежать бесконечного цикла

```js
componentDidUpdate(prevProps) {
  if (prevProps.userId !== this.props.userId) {
    this.setState({
      selectedUserId: this.props.userId,
    });
  }
}
```

- если условие истинно, компонент обновится ещё раз, поскольку `setState()` инициирует новое обновление

- при следующем вызове `componentDidUpdate` условие уже может быть ложным, и цикл завершится

- если же безусловно вызывать `setState()` при каждом `componentDidUpdate`, можно получить бесконечные повторные обновления

- при необходимости `componentDidUpdate` также получает третий аргумент `snapshot`, возвращённый из `getSnapshotBeforeUpdate`

## 6. этап unmounting — размонтирование

### 6.1. `componentWillUnmount`

- `componentWillUnmount` вызывается непосредственно перед тем, как React удалит компонент из дерева

- его основная задача — очистить ресурсы, которые компонент создал или которыми управляет

```js
class WindowSize extends React.Component {
  state = {
    width: window.innerWidth,
  };

  handleResize = () => {
    this.setState({
      width: window.innerWidth,
    });
  };

  componentDidMount() {
    window.addEventListener('resize', this.handleResize);
  }

  componentWillUnmount() {
    window.removeEventListener('resize', this.handleResize);
  }

  render() {
    return <p>ширина окна: {this.state.width}</p>;
  }
}
```

- при монтировании компонент подписывается на событие `resize`, а перед удалением снимает подписку

- если забыть удалить обработчик, он может продолжать удерживать ссылку на компонент и выполнять ненужную работу после его удаления

- аналогично в этом методе очищают таймеры через `clearTimeout()` или `clearInterval()`, отменяют подписки на внешние события и освобождают другие ресурсы

#### что важно помнить

- `componentWillUnmount` вызывается при удалении компонента, а не при каждом обновлении

- здесь не нужно вызывать `setState()`, поскольку компонент уже собираются удалить

- если компонент только обновился, например получил новые `props`, этот метод не вызывается

- `componentWillUnmount` не гарантирует выполнение при любых обстоятельствах завершения работы приложения: например, нельзя рассчитывать на него как на обработчик закрытия вкладки или аварийного завершения страницы

## 7. обработка ошибок в жизненном цикле

- React предоставляет два специальных метода классовых компонентов для обработки ошибок, возникших при рендеринге или выполнении некоторых методов жизненного цикла дочерних компонентов

### 7.1. `static getDerivedStateFromError`

- `getDerivedStateFromError` позволяет обновить состояние error boundary, чтобы вместо сломанной части интерфейса отобразить запасной интерфейс

- error boundary — это компонент-граница ошибок, который перехватывает определённые ошибки в дочернем дереве

```js
class ErrorBoundary extends React.Component {
  state = {
    hasError: false,
  };

  static getDerivedStateFromError(error) {
    return {
      hasError: true,
    };
  }

  render() {
    if (this.state.hasError) {
      return <h2>не удалось отобразить этот раздел</h2>;
    }

    return this.props.children;
  }
}
```

- если дочерний компонент выбрасывает ошибку, React может перевести границу ошибок в состояние `hasError: true`, после чего она отобразит запасной интерфейс

- метод статический, потому что он возвращает новое состояние, а не выполняет действия через экземпляр компонента

- он должен оставаться чистым: здесь не следует отправлять отчёты об ошибках, обращаться к серверу или выполнять другие побочные эффекты

### 7.2. `componentDidCatch`

- `componentDidCatch` позволяет выполнить действия после того, как граница ошибок перехватила ошибку в дочернем дереве

```js
class LoggingBoundary extends React.Component {
  state = {
    hasError: false,
  };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error, info) {
    console.error('ошибка дочернего компонента:', error);
    console.error('информация о дереве:', info.componentStack);
  }

  render() {
    if (this.state.hasError) {
      return <h2>что-то пошло не так</h2>;
    }

    return this.props.children;
  }
}
```

- `error` содержит объект ошибки, а `info` — дополнительную информацию, в том числе стек компонентов React, в котором возникла ошибка

- этот метод подходит для логирования ошибок, отправки диагностической информации в систему мониторинга и других побочных эффектов

- на практике `getDerivedStateFromError` и `componentDidCatch` часто используются вместе: первый определяет запасное состояние интерфейса, второй регистрирует ошибку

- границы ошибок не перехватывают абсолютно все ошибки приложения: например, обычные ошибки внутри обработчиков событий и ошибки асинхронных callback-функций не перехватываются ими автоматически

## 8. порядок выполнения методов жизненного цикла

- это одна из важнейших частей темы, поскольку на собеседовании часто спрашивают не только назначение методов, но и точную последовательность их вызова

### 8.1. порядок при монтировании

#### 1. constructor - создание и начальная настройка экземпляра

#### 2. getDerivedStateFromProps - вычисление состояния из props, если метод определён

#### 3. render - получение описания интерфейса

#### 4. componentDidMount - действия после монтирования

- `getDerivedStateFromProps` присутствует в этой последовательности только в том случае, если компонент его определяет

- `render()` вызывается до `componentDidMount()`, поэтому нельзя использовать `componentDidMount()` для подготовки данных, которые уже должны присутствовать в первом результате `render()` без дополнительного обновления

- если `componentDidMount()` вызывает `setState()`, после первоначального монтирования запускается дополнительное обновление

### 8.2. порядок при обновлении

#### 1. getDerivedStateFromProps - синхронизация состояния с текущими props, если требуется

#### 2. shouldComponentUpdate - решение, нужно ли продолжать обычный рендеринг

#### 3. render - создание нового описания интерфейса

#### 4. getSnapshotBeforeUpdate - чтение DOM до применения изменений

#### 5. componentDidUpdate - действия после применения изменений

- `getDerivedStateFromProps` и `shouldComponentUpdate` выполняются до `render()`, а `getSnapshotBeforeUpdate` и `componentDidUpdate` относятся к фазам до и после применения изменений к DOM

- если `shouldComponentUpdate()` возвращает `false`, обычный процесс обновления этого компонента останавливается: `render()`, `getSnapshotBeforeUpdate()` и `componentDidUpdate()` для этого обновления не вызываются

- если `getDerivedStateFromProps()` возвращает объект состояния, это само по себе не означает, что React немедленно запустит отдельный дополнительный цикл обновления

- `getSnapshotBeforeUpdate()` и `componentDidUpdate()` нужны не при каждом изменении внутреннего состояния как таковом, а когда React действительно проходит соответствующий путь обновления компонента

### 8.3. порядок при размонтировании

#### 1. `componentWillUnmount()` - очистка ресурсов перед удалением компонента

- у обычного размонтирования нет последующего `componentDidUnmount()`: такого метода в React нет

- `componentWillUnmount()` — последний специальный метод жизненного цикла, который компонент может использовать перед удалением

### 8.4. обработка ошибки

- если ошибка возникает в дочернем компоненте и перехватывается error boundary, React может вызвать `static getDerivedStateFromError()`, чтобы подготовить запасное состояние, а затем выполнить рендеринг запасного интерфейса

- `componentDidCatch()` вызывается для обработки и регистрации перехваченной ошибки

- не следует запоминать обработку ошибок как одну универсальную линейную последовательность, применяемую при любом сбое: точный путь зависит от места возникновения ошибки и того, как React восстанавливает дерево

## 9. как жизненный цикл связан с функциональными компонентами

- до сих пор мы рассматривали классовые компоненты, поскольку перечисленные методы жизненного цикла принадлежат именно им

- в функциональных компонентах нет методов `componentDidMount`, `componentDidUpdate` и `componentWillUnmount`, вместо них для управления побочными эффектами обычно используют хук `useEffect`, а для задач, требующих синхронизации с DOM до отрисовки браузером, — `useLayoutEffect`

### аналогия между классовыми и функциональными компонентами

| классовый компонент        | функциональный компонент                                                 |
| -------------------------- | ------------------------------------------------------------------------ |
| `componentDidMount`        | `useEffect` с пустым массивом зависимостей                               |
| `componentDidUpdate`       | `useEffect` с зависимостями                                              |
| `componentWillUnmount`     | функция очистки из `useEffect`                                           |
| `getSnapshotBeforeUpdate`  | прямого аналога нет, иногда подходит `useLayoutEffect`                   |
| `shouldComponentUpdate`    | `React.memo`, но это не полная замена                                    |
| `getDerivedStateFromError` | прямого аналога нет, для error boundary обычно нужен классовый компонент |
| `componentDidCatch`        | прямого аналога нет, для границ ошибок используют классовый компонент    |

- это соответствия по типичным задачам, а не утверждение, что каждый метод класса можно механически заменить одним хуком

### 9.1. `useEffect` как аналог основных этапов

```js
import { useEffect, useState } from 'react';

function WindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    function handleResize() {
      setWidth(window.innerWidth);
    }

    window.addEventListener('resize', handleResize);

    return () => {
      window.removeEventListener('resize', handleResize);
    };
  }, []);

  return <p>ширина окна: {width}</p>;
}
```

- после монтирования React запускает эффект, который подписывается на изменение размера окна

- функция, возвращаемая из `useEffect`, выполняет очистку эффекта при его повторном запуске с изменившимися зависимостями или при размонтировании компонента

- пустой массив зависимостей `[]` означает, что эффект не зависит от реактивных значений компонента и не должен повторно запускаться из-за изменения таких значений

- однако в режиме разработки с `StrictMode` React может выполнить дополнительный цикл настройки и очистки эффекта, поэтому нельзя считать, что эффект гарантированно запустится ровно один раз за весь процесс разработки

### 9.2. чем функциональный жизненный цикл отличается от классового

- у классовых компонентов есть отдельные методы для конкретных этапов жизненного цикла, а `useEffect` позволяет описывать синхронизацию с внешними системами через зависимости и функцию очистки

- эффект с зависимостями не является буквальным аналогом `componentDidUpdate`, поскольку он может запускаться и после первого монтирования

- функция компонента вызывается заново при рендеринге, но это не означает, что все эффекты запускаются заново: React запускает эффект в соответствии с его зависимостями и правилами работы соответствующего хука

- например, `useEffect(() => {}, [])` не выполняет побочные действия после каждого рендеринга, в отличие от эффекта без массива зависимостей

## 10. устаревшие методы жизненного цикла

- на собеседовании могут спросить о старых методах, особенно если речь идёт о поддержке легаси-кода

#### `componentWillMount` - действие перед первоначальным монтированием

- сейчас обычно используется constructor для начальной настройки или componentDidMount для эффектов

#### `componentWillReceiveProps` - реакция на получение новых props

- сейчас при необходимости используется getDerivedStateFromProps или логика синхронизации

#### `componentWillUpdate` - действия перед обновлением

- сейчас в зависимости от задачи используется getSnapshotBeforeUpdate или другие подходящие методы

- в современном React эти методы считаются устаревшими и имеют варианты с префиксом `UNSAFE_`, который подчёркивает потенциальные проблемы их использования

- их нельзя путать с `getSnapshotBeforeUpdate`, который по-прежнему поддерживается и нужен для определённых задач с DOM

- исторически старые методы выполнялись в фазах подготовки к обновлению, но современный React может повторно запускать или прерывать рендеринг, поэтому побочные эффекты в фазе рендеринга особенно опасны

## 11. краткая шпаргалка

- `constructor` — инициализирует экземпляр и начальное состояние
- `getDerivedStateFromProps` — вычисляет состояние на основе актуальных `props`
- `render` — возвращает описание интерфейса и должен оставаться чистым
- `componentDidMount` — выполняет действия после первоначального монтирования
- `shouldComponentUpdate` — определяет, следует ли продолжать обычный путь обновления
- `getSnapshotBeforeUpdate` — читает DOM непосредственно перед применением изменений
- `componentDidUpdate` — выполняет действия после обновления DOM
- `componentWillUnmount` — очищает ресурсы перед удалением компонента
- `getDerivedStateFromError` — обновляет состояние границы ошибок для отображения запасного интерфейса
- `componentDidCatch` — обрабатывает и регистрирует перехваченные ошибки
- главное для собеседования — уметь объяснить не только назначение каждого метода, но и порядок его вызова, ограничения и последствия изменения состояния внутри него
