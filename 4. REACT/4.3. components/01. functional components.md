# functional components

- функциональный компонент — это обычная JavaScript-функция, которая получает `props` и возвращает описание того, что React должен отобразить
- исторически функциональные компоненты были довольно простыми: они в основном использовались для компонентов без собственного состояния и методов жизненного цикла
- начиная с React 16.8 благодаря Hooks функциональные компоненты получили состояние, эффекты, контекст и другие возможности, поэтому сегодня они являются основным способом написания компонентов в React

## 1. что такое функциональный компонент и зачем он нужен

- компонент в React — это самостоятельная часть интерфейса, которая объединяет некоторую логику и описание UI
- функциональный компонент представляет эту часть интерфейса в виде функции

```jsx
function UserCard(props) {
  return (
    <div>
      <h2>{props.name}</h2>
      <p>{props.email}</p>
    </div>
  );
}
```

- здесь `UserCard` — функциональный компонент
- `props` — объект с входными данными компонента
- результатом выполнения функции является JSX
- React использует этот результат как описание того, что должно появиться в UI

```jsx
<UserCard name='Alex' email='alex@example.com' />
```

- в результате React вызовет компонент примерно с такими данными

```js
UserCard({
  name: 'Alex',
  email: 'alex@example.com',
});
```

- важно понимать, что JSX-компонент не означает, что браузер напрямую вызывает эту функцию
- React сам управляет вызовом компонента в процессе своей работы и использует возвращаемое им значение для построения React-дерева

### компонент как функция

- на базовом уровне полезно мыслить так

```
props → component → React element
```

- например

```
{name: "Alex"} → UserCard → описание UI
```

- при этом компонент не обязан возвращать именно один DOM-элемент
- он может возвращать другой компонент, Fragment, текст, `null` и другие допустимые React-узлы

```jsx
function Greeting() {
  return <h1>Hello</h1>;
}
```

- или

```jsx
function EmptyState() {
  return null;
}
```

- `null` означает, что компонент ничего не должен отображать

## 2. чем компонент отличается от обычной функции

- технически функциональный компонент действительно является JavaScript-функцией
- но React рассматривает функцию как компонент благодаря тому, как она используется в JSX и React-дереве

```jsx
function UserCard() {
  return <div>User</div>;
}
```

- когда мы пишем

```jsx
<UserCard />
```

- мы не просто вызываем функцию самостоятельно

- мы создаём React element, который указывает React, какой компонент нужно использовать

- это принципиальное отличие от

```js
UserCard();
```

- при прямом вызове мы самостоятельно вызываем JavaScript-функцию

- при `<UserCard />` управление компонентом передаётся React

- на собеседовании полезно сформулировать это так

- функциональный компонент — это функция, которую React использует как компонент и которая возвращает React-элемент или другой допустимый React-узел

## 3. props функционального компонента

- `props` — это входные данные компонента, которые передаются от родителя к ребёнку

```jsx
function UserCard(props) {
  return <h2>{props.name}</h2>;
}
```

- использование

```jsx
<UserCard name='Alex' />
```

- React передаст компоненту объект примерно такого вида

```js
{
  name: 'Alex';
}
```

- поэтому можно использовать деструктуризацию

```jsx
function UserCard({ name, email }) {
  return (
    <div>
      <h2>{name}</h2>
      <p>{email}</p>
    </div>
  );
}
```

- `props` принадлежат компоненту как входные данные

- компонент не должен изменять собственные `props`

- это связано с важной моделью React

```
parent state
     ↓
   props
     ↓
child component
     ↓
 rendered UI
```

- если данные родителя изменились, React может заново выполнить дочерний компонент с новыми `props`

## 4. функциональный компонент и состояние

- исторически главным ограничением функциональных компонентов было отсутствие собственного состояния

- раньше состояние обычно ассоциировалось с class components

- после появления Hooks это ограничение исчезло

- для состояния функционального компонента используется `useState`

```jsx
import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

- здесь `count` — текущее состояние
- `setCount` — функция, с помощью которой мы просим React изменить состояние
- `0` — начальное значение

### что происходит при изменении state

- первый рендер происходит с

```js
count === 0;
```

- пользователь нажимает кнопку
- вызывается

```js
setCount(1);
```

- React сохраняет новое состояние

- React планирует обновление компонента

- компонент снова выполняется

- при следующем выполнении

```js
const [count, setCount] = useState(0);
```

- `count` уже будет равен `1`, а не `0`

- `useState(0)` не означает, что при каждом выполнении функции состояние снова становится `0`

- `0` используется как начальное значение при создании состояния

- само состояние хранится React, а не в локальной переменной JavaScript-функции

## 5. почему нельзя просто использовать обычную переменную

- например, такой код не создаёт React state

```jsx
function Counter() {
  let count = 0;

  function increment() {
    count += 1;
  }

  return <button onClick={increment}>{count}</button>;
}
```

- проблема состоит сразу из двух частей

- `count` создаётся заново при каждом выполнении функции

- изменение обычной переменной само по себе не сообщает React, что интерфейс нужно обновить

- поэтому React предоставляет `useState`

```jsx
const [count, setCount] = useState(0);
```

- React хранит значение между рендерами и знает, что вызов `setCount` требует обновления компонента

## 6. почему state не изменяется непосредственно

- у `useState` есть специальный setter

```js
setCount(5);
```

- вместо

```js
count = 5;
```

- это связано с тем, что React должен получить информацию об изменении состояния и запланировать новый render

- поэтому можно мыслить так

```
setState
   ↓
React узнаёт об изменении
   ↓
планируется обновление
   ↓
component выполняется снова
   ↓
получается новое описание UI
```

- при этом вызов setter не означает, что переменная `count` мгновенно изменится прямо в текущем выполнении функции

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(1);
    console.log(count);
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

- при первом клике `console.log(count)` всё ещё может увидеть `0`
- потому что текущее выполнение функции работает со своим значением `count`
- новое состояние будет доступно во время следующего render

## 7. несколько состояний

- функциональный компонент может иметь несколько независимых состояний

```jsx
function UserPanel() {
  const [name, setName] = useState('Alex');
  const [isOnline, setIsOnline] = useState(false);

  return (
    <div>
      <p>{name}</p>
      <p>{isOnline ? 'Online' : 'Offline'}</p>
    </div>
  );
}
```

- каждое состояние имеет свой setter

- React связывает эти состояния с конкретным компонентом и порядком вызова Hooks

- отсюда появляется важное правило Hooks: нельзя вызывать Hooks условно

```jsx
// неправильно
if (isOnline) {
  useState(false);
}
```

- Hooks должны вызываться в одном и том же порядке при каждом render компонента

## 8. functional components и жизненный цикл

- функциональные компоненты не имеют методов жизненного цикла в том же смысле, в котором они есть у class components

- вместо этого используются Hooks

- например, `useEffect` позволяет выполнять побочные эффекты, связанные с жизненным циклом компонента

```jsx
import { useEffect } from 'react';

function UserProfile() {
  useEffect(() => {
    console.log('component rendered');

    return () => {
      console.log('cleanup');
    };
  }, []);

  return <div>Profile</div>;
}
```

- поэтому современный функциональный компонент может иметь практически все основные возможности, которые раньше связывали с class components

```
functional component
├── props
├── state
├── effects
├── context
├── refs
└── другие Hooks
```

## 9. главный плюс — простота модели

- функциональный компонент обычно значительно компактнее class component

- например, современный вариант

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

- в class component пришлось бы работать с экземпляром класса, `this`, `render`, `setState` и другими особенностями классов

- функциональный компонент позволяет воспринимать компонент прежде всего как функцию, которая получает данные и возвращает UI

## 10. повторное выполнение компонента

- одна из важнейших особенностей функциональных компонентов — React может выполнять функцию компонента много раз

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  console.log('render');

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

- при изменении `count` React снова выполняет `Counter`

- поэтому нельзя считать локальные переменные функционального компонента постоянным хранилищем данных

```jsx
function Example() {
  const temporaryValue = 10;

  return <div>{temporaryValue}</div>;
}
```

- `temporaryValue` существует только в рамках конкретного выполнения функции
- если значение должно сохраняться между render, для этого нужны специальные механизмы React, например `useState` или `useRef`

## 11. плюсы функциональных компонентов

- **простота** — компонент является обычной функцией и обычно имеет меньше синтаксического шума

- **Hooks** — состояние, эффекты, refs, context и другие возможности доступны через единый механизм

- **переиспользование логики** — логика может выноситься в custom Hooks

```jsx
function useOnlineStatus() {
  // логика определения online status
}
```

- затем одна и та же логика может использоваться несколькими компонентами

- **нет `this`** — не возникает проблем с контекстом `this`, binding методов и потерей контекста

- **удобное разделение логики** — с помощью Hooks можно группировать код по смыслу, а не только по lifecycle-методам

- **хорошо соответствуют современной архитектуре React** — современные React-приложения в основном строятся вокруг функциональных компонентов и Hooks

## 12. минусы и особенности

- функциональные компоненты не являются автоматически «лучше» во всех возможных ситуациях

- **нужно понимать Hooks** — вместе с функциональными компонентами появляется большое количество правил и концепций: dependency arrays, stale closures, правила Hooks, `useMemo`, `useCallback`, `useEffect` и другие

- **легко неправильно работать с замыканиями** — функция внутри компонента захватывает значения конкретного render

```jsx
function Timer() {
  const [count, setCount] = useState(0);

  function logCount() {
    console.log(count);
  }

  return <button onClick={logCount}>{count}</button>;
}
```

- `logCount` здесь видит `count` того render, во время которого эта функция была создана

- это нормальное поведение JavaScript closures, но оно становится источником ошибок при работе с асинхронным кодом

- **компонент может содержать слишком много Hooks** — если в одном компоненте смешать состояние, запросы, подписки, обработчики и сложную бизнес-логику, функция быстро становится трудной для понимания

- обычно такую логику разделяют на отдельные компоненты и custom Hooks

- **рендер выполняет функцию заново** — поэтому нельзя бездумно помещать в тело компонента тяжёлые вычисления или операции с побочными эффектами

## 13. что важно понимать про производительность

- само по себе наличие функционального компонента не означает плохую производительность

- также неправильно считать, что функциональные компоненты обязательно быстрее class components

- React всё равно должен выполнять необходимую работу по построению нового React-дерева и сравнению изменений

- оптимизация обычно достигается другими механизмами, например `memo`, `useMemo`, `useCallback`, правильной структурой компонентов и управлением состоянием

- поэтому вопрос «functional components быстрее class components?» лучше не сводить к простому «да»

- более корректно сказать, что современный React ориентирован на функциональные компоненты, а производительность зависит прежде всего от того, какую работу выполняет приложение и как организовано обновление дерева

## 14. функциональный компонент в общей картине React

- теперь полезно связать эту тему с тем, что мы уже разбирали про React

```
JSX
 ↓
React element
 ↓
React tree
 ↓
functional component
 ↓
новое описание UI
 ↓
React сравнивает изменения
 ↓
React DOM применяет необходимые изменения
 ↓
Browser DOM
```

- функциональный компонент находится внутри React-части этой цепочки
- он не изменяет Browser DOM напрямую
- его задача — описать, какой UI должен быть представлен при текущих `props` и `state`

## 15. как отвечать на собеседовании

- если спросят **«что такое functional component?»**, хороший базовый ответ будет таким

- функциональный компонент — это JavaScript-функция, которую React использует как компонент, передавая ей `props` и используя её возвращаемое значение как описание UI

- если спросят **«как работает state в функциональном компоненте?»**

- состояние создаётся с помощью Hooks, чаще всего `useState`, при этом само значение хранится React между render, а setter сообщает React, что состояние нужно обновить и компонент необходимо снова выполнить

- если спросят **«почему нельзя использовать обычную переменную вместо state?»**

- обычная переменная создаётся заново при следующем выполнении функции и её изменение не сообщает React о необходимости обновить UI, тогда как state хранится React между render и связан с механизмом обновления компонента

- если спросят **«какие плюсы функциональных компонентов?»**

- основные преимущества — простой синтаксис, отсутствие `this`, Hooks для состояния и других возможностей React, а также удобное переиспользование логики через custom Hooks

- если спросят **«какие минусы?»**

- основная сложность не столько в самих функциональных компонентах, сколько в правильном использовании Hooks и понимании повторных render, closures, зависимостей эффектов и состояния

- ключевая мысль всей темы такая

```
functional component = функция → описание UI

props → входные данные
state → данные, которые React хранит между render
Hooks → способ использовать возможности React
render → повторное выполнение компонента для получения нового UI
```

- и особенно важно не делать ошибочный вывод, что функциональный компонент — это просто функция, которая один раз вызывается и создаёт DOM
- React может выполнять её многократно, а состояние между этими выполнениями хранится не внутри обычных локальных переменных функции, а на стороне React
