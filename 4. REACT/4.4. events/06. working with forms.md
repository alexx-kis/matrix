# working with forms в React

- разберём тему с нуля: как браузерные формы работают сами по себе, как React управляет их значениями, как реализовать собственную форму с валидацией и зачем нужны библиотеки Formik и React Final Form

- главная цель — не просто научиться писать формы, а понять, что происходит с данными при каждом вводе символа, нажатии кнопки Submit, ошибке валидации и отправке запроса на сервер

## 1. что такое форма и как она работает без React

- форма — это элемент интерфейса, который позволяет пользователю ввести данные и отправить их на обработку

- например, форма регистрации может содержать имя, электронную почту, пароль и кнопку отправки

- в обычном HTML форма создаётся с помощью элемента `<form>`, а поля ввода — с помощью `<input>`, `<textarea>` и `<select>`

```js
<form>
  <label for="user-email">email</label>
  <input id="user-email" name="email" type="email" />

  <button type="submit">отправить</button>
</form>
```

- здесь браузер уже умеет многое без JavaScript: отслеживает ввод, предоставляет базовую проверку некоторых типов полей и обрабатывает отправку формы
- атрибут `name` задаёт имя поля, под которым его значение может передаваться при отправке HTML-формы
- атрибут `type="email"` сообщает браузеру, что поле предназначено для электронной почты, и включает соответствующее поведение, но сам по себе не гарантирует, что адрес существует или принадлежит пользователю
- атрибут `for` у `<label>` связывает подпись с полем через совпадающий `id`, благодаря чему по подписи тоже можно нажать и перейти к вводу

### что происходит при отправке формы

- по умолчанию браузер отправляет HTML-форму согласно её атрибутам `action` и `method`, а в типичном случае может перейти на другой URL или перезагрузить страницу
- в React-приложении обычно нужно перехватить отправку, самостоятельно проверить данные и выполнить запрос к серверу, не допуская стандартной отправки браузера
- для этого используется событие `submit` и метод `event.preventDefault()`

```js
function ContactForm() {
  function handleSubmit(event) {
    event.preventDefault();

    console.log('форма отправлена');
  }

  return (
    <form onSubmit={handleSubmit}>
      <input name="email" type="email" />
      <button type="submit">отправить</button>
    </form>
  );
}
```

- `onSubmit` — React-обработчик события отправки формы, а `preventDefault()` отменяет стандартное действие браузера для этого события
- важно: `preventDefault()` не останавливает всплытие события и не блокирует выполнение остального кода обработчика
- также важно различать кнопку отправки и обычную кнопку: внутри формы `<button>` по умолчанию обычно ведёт себя как `type="submit"`, поэтому для кнопки, которая не должна отправлять форму, нужно явно указывать `type="button"`

## 2. controlled и uncontrolled поля

- это один из самых важных вопросов на собеседовании по работе с формами в React

### controlled — контролируемое поле

- контролируемое поле — это поле, текущее значение которого определяется состоянием React, а не только внутренним состоянием браузера

```js
import { useState } from 'react';

function ControlledEmailForm() {
  const [email, setEmail] = useState('');

  return (
    <form onSubmit={(event) => event.preventDefault()}>
      <label>
        email
        <input
          type="email"
          value={email}
          onChange={(event) => setEmail(event.target.value)}
        />
      </label>

      <p>введено: {email}</p>
    </form>
  );
}
```

- разберём, что здесь происходит по шагам

- изначально `email` равен пустой строке, поэтому React отображает пустое поле
- пользователь вводит символ `a`, браузер генерирует событие изменения значения, а обработчик `onChange` получает новое значение через `event.target.value`
- `setEmail()` запрашивает обновление состояния React
- React повторно вызывает компонент и передаёт новое значение в `value`
- поле отображает значение, соответствующее состоянию, а текст под ним тоже обновляется
- получается цепочка: пользовательский ввод → обработчик → состояние → повторный рендер → обновлённое поле
- в controlled-подходе мы можем программно изменять, очищать, форматировать и проверять значение, потому что оно доступно в состоянии React

### почему одного `value` недостаточно

- если указать `value={email}`, но не обновлять `email` при вводе, поле обычно останется на прежнем значении и пользователь не сможет нормально вводить текст

```
<input value="fixed@example.com" onChange={() => {}} />
```

- здесь значение постоянно задано строкой, поэтому ввод пользователя не меняет его
- чтобы сделать поле контролируемым и редактируемым, нужно связывать `value` с состоянием и обновлять состояние в обработчике
- для текстового поля также важно не переключать его неожиданно между контролируемым и неконтролируемым режимами, например сначала передавать `value={undefined}`, а затем строку

### uncontrolled — неконтролируемое поле

- неконтролируемое поле хранит текущее значение преимущественно внутри DOM, то есть в самом элементе браузера, а React не обязан обновлять состояние при каждом вводе

```js
import { useRef } from 'react';

function UncontrolledEmailForm() {
  const emailRef = useRef(null);

  function handleSubmit(event) {
    event.preventDefault();

    const currentEmail = emailRef.current.value;

    console.log(currentEmail);
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        name="email"
        type="email"
        defaultValue=""
        ref={emailRef}
      />

      <button type="submit">отправить</button>
    </form>
  );
}
```

- `useRef(null)` создаёт объект с изменяемым свойством `current`
- React передаёт DOM-элемент поля в `emailRef.current`
- когда пользователь вводит текст, браузер обновляет значение поля самостоятельно
- при отправке формы мы читаем актуальное значение через `emailRef.current.value`
- в этом примере React не хранит введённый email в состоянии, но по-прежнему управляет созданием DOM-элемента
- `defaultValue` задаёт начальное значение неконтролируемого поля, но не служит механизмом постоянной синхронизации значения с React

### как выбрать подход

- controlled-подход удобен, когда значение необходимо постоянно использовать в интерфейсе, например для отображения ошибок, динамических подсказок, зависимых полей или расчёта цены
- uncontrolled-подход удобен, когда достаточно прочитать значение при отправке, а постоянная синхронизация с React не нужна
- для сложных форм с множеством взаимозависимых полей controlled-подход часто упрощает управление логикой, хотя может потребовать больше кода
- uncontrolled-подход может сократить количество состояния и обновлений React, но не отменяет необходимости проверять данные и управлять ошибками
- при этом оба подхода можно использовать в одном приложении, а React не требует, чтобы все поля во всех формах были устроены одинаково

## 3. как организовать данные формы в React

- представим форму регистрации с тремя полями: именем, email и паролем
- для начала можно хранить каждое поле в отдельном состоянии, но по мере роста формы удобнее объединить значения в один объект

```js
import { useState } from 'react';

function RegistrationForm() {
  const [values, setValues] = useState({
    name: '',
    email: '',
    password: '',
  });

  function handleChange(event) {
    const { name, value } = event.target;

    setValues((previousValues) => ({
      ...previousValues,
      [name]: value,
    }));
  }

  function handleSubmit(event) {
    event.preventDefault();

    console.log(values);
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        name="name"
        value={values.name}
        onChange={handleChange}
        placeholder="имя"
      />

      <input
        name="email"
        type="email"
        value={values.email}
        onChange={handleChange}
        placeholder="email"
      />

      <input
        name="password"
        type="password"
        value={values.password}
        onChange={handleChange}
        placeholder="пароль"
      />

      <button type="submit">зарегистрироваться</button>
    </form>
  );
}
```

### как работает общий обработчик `handleChange`

- вместо трёх отдельных обработчиков все поля используют одну функцию
- `event.target` — элемент, на котором произошло событие, а `name` и `value` извлекаются из него с помощью деструктуризации
- свойство `name` определяет, какое именно поле необходимо обновить
- выражение `[name]: value` создаёт свойство объекта с динамическим именем
- например, если пользователь вводит `Alex` в поле имени, обработчик формирует новое состояние, эквивалентное следующему объекту

```js
{
  name: 'Alex',
  email: '',
  password: '',
}
```

- здесь особенно важно понимать, зачем используется `...previousValues`: без него мы заменили бы весь объект и потеряли бы значения остальных полей
- функциональная форма `setValues(previousValues => ...)` позволяет вычислить новое состояние на основе предыдущего, что особенно важно, когда обновления состояния объединяются или откладываются

### почему состояние формы обычно хранится в одном объекте

- все значения относятся к одной логической сущности — форме, поэтому их удобно хранить вместе и передавать на проверку или отправку одним объектом
- однако единый объект не является обязательным правилом, и для небольших форм несколько отдельных `useState` могут быть вполне разумным решением
- для более сложной логики можно использовать `useReducer`, чтобы централизовать обработку действий вроде изменения поля, очистки формы и загрузки данных

## 4. пользовательская валидация формы

- валидация — это проверка введённых данных на соответствие определённым правилам
- например, для формы регистрации можно определить следующие требования
- имя обязательно
- email обязателен и должен иметь подходящий формат
- пароль должен содержать не менее восьми символов
- валидация нужна не только для того, чтобы показать сообщение об ошибке, но и для того, чтобы не отправлять заведомо некорректные данные

### 4.1. создаём отдельную функцию валидации

- хорошая практика — отделять правила проверки от JSX и обработчиков событий, чтобы валидацию можно было повторно использовать и тестировать

```js
function validateRegistration(values) {
  const errors = {};

  if (!values.name.trim()) {
    errors.name = 'введите имя';
  }

  if (!values.email.trim()) {
    errors.email = 'введите email';
  } else if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(values.email)) {
    errors.email = 'проверьте формат email';
  }

  if (values.password.length < 8) {
    errors.password = 'минимум 8 символов';
  }

  return errors;
}
```

- функция получает объект со значениями и возвращает объект ошибок
- если ошибок нет, функция вернёт пустой объект `{}`, а если они есть, в нём появятся свойства, соответствующие полям
- регулярное выражение для email здесь является упрощённой проверкой формата, а не полной реализацией стандарта адресов электронной почты
- например, при следующих данных

```js
{
  name: '',
  email: 'wrong-email',
  password: '123',
}
```

- результат будет выглядеть так

```js
{
  name: 'введите имя',
  email: 'проверьте формат email',
  password: 'минимум 8 символов',
}
```

- отдельная функция валидации ничего не знает о React, DOM или способе отображения формы, и именно это делает её удобной для повторного использования

### 4.2. подключаем ошибки к форме

- теперь добавим состояние ошибок, проверку при отправке и отображение сообщений рядом с полями

```js
import { useState } from 'react';

function ValidatedRegistrationForm() {
  const [values, setValues] = useState({
    name: '',
    email: '',
    password: '',
  });

  const [errors, setErrors] = useState({});

  function handleChange(event) {
    const { name, value } = event.target;

    setValues((previousValues) => ({
      ...previousValues,
      [name]: value,
    }));
  }

  function handleSubmit(event) {
    event.preventDefault();

    const nextErrors = validateRegistration(values);

    setErrors(nextErrors);

    if (Object.keys(nextErrors).length > 0) {
      return;
    }

    console.log('данные готовы к отправке', values);
  }

  return (
    <form onSubmit={handleSubmit} noValidate>
      <label>
        имя
        <input
          name="name"
          value={values.name}
          onChange={handleChange}
        />
      </label>
      {errors.name && <p>{errors.name}</p>}

      <label>
        email
        <input
          name="email"
          type="email"
          value={values.email}
          onChange={handleChange}
        />
      </label>
      {errors.email && <p>{errors.email}</p>}

      <label>
        пароль
        <input
          name="password"
          type="password"
          value={values.password}
          onChange={handleChange}
        />
      </label>
      {errors.password && <p>{errors.password}</p>}

      <button type="submit">зарегистрироваться</button>
    </form>
  );
}
```

- здесь `noValidate` отключает автоматическую проверку формы браузером при отправке, чтобы в этом примере правилами проверки управлял наш код
- состояние `errors` хранит ошибки отдельно от `values`, потому что введённые данные и результаты их проверки — это разные вещи
- `Object.keys(nextErrors).length` показывает количество собственных перечисляемых ключей объекта ошибок, поэтому нулевое значение означает, что объект пуст
- если ошибки найдены, обработчик прекращает выполнение и не доходит до отправки данных
- если ошибок нет, здесь пока выполняется `console.log`, но на практике в этом месте обычно вызывают API
- обратите внимание: `setErrors(nextErrors)` не меняет переменную `errors` немедленно внутри текущего вызова функции, поэтому для проверки мы используем именно локальную переменную `nextErrors`, которую только что вычислили

### 4.3. когда показывать ошибки

- есть несколько распространённых стратегий валидации, и выбор зависит от того, насколько сложна форма и какой пользовательский опыт требуется
- при отправке формы (`onSubmit`) — пользователь заполняет форму и получает список ошибок после нажатия кнопки, такой подход легко реализовать и он не мешает вводу
- при изменении значения (`onChange`) — проверка выполняется после изменения поля, что позволяет быстро сообщать об ошибках, но может раздражать пользователя, если ошибки появляются до того, как он закончил вводить данные
- при потере фокуса (`onBlur`) — поле проверяется, когда пользователь уходит из него, что часто даёт хороший баланс между скоростью обратной связи и удобством
- при повторной проверке после первой ошибки — до первой отправки ошибки не показываются, а после попытки отправки проверка может происходить при каждом изменении поля, чтобы ошибка исчезала сразу после исправления
- в реальных формах эти стратегии часто комбинируются, например первая проверка происходит при отправке, а затем ошибки обновляются при изменении уже затронутых полей

### 4.4. зачем нужно состояние `touched`

- иногда недостаточно знать, есть ли ошибка, — важно понимать, взаимодействовал ли пользователь с полем
- `touched` — это условное название состояния, показывающего, что поле уже было затронуто, обычно после потери фокуса
- без `touched` можно получить ситуацию, когда при первом рендере форма сразу показывает сообщения об ошибках для всех пустых полей, хотя пользователь ещё ничего не вводил
- с `touched` можно отображать ошибку только после взаимодействия с полем или после попытки отправки
- например, логика отображения ошибки может быть такой: `touched.email && errors.email`
- важно различать `touched` и `dirty`: первое обычно означает, что поле было затронуто, а второе — что его значение отличается от исходного, хотя конкретное определение зависит от реализации формы или библиотеки

### 4.5. клиентская и серверная валидация

- клиентская валидация выполняется в браузере и помогает быстрее сообщить пользователю об ошибке, но её можно обойти, поэтому она не является защитой сервера
- серверная валидация выполняется на стороне API и необходима даже тогда, когда клиент уже проверил все поля
- например, клиент может проверить формат email, а сервер дополнительно проверяет, существует ли учётная запись, разрешена ли регистрация и соответствует ли запрос бизнес-правилам
- нельзя доверять данным только потому, что они прошли проверку в React, — сервер должен самостоятельно проверять входящие данные и права доступа

## 5. как отправлять форму на сервер

- до этого момента мы проверяли значения, но ещё не выполняли настоящий запрос, поэтому добавим в форму асинхронную отправку и состояние загрузки

```js
import { useState } from 'react';

function ApiRegistrationForm() {
  const [values, setValues] = useState({
    name: '',
    email: '',
    password: '',
  });

  const [errors, setErrors] = useState({});
  const [isSubmitting, setIsSubmitting] = useState(false);
  const [serverMessage, setServerMessage] = useState('');

  async function handleSubmit(event) {
    event.preventDefault();

    const nextErrors = validateRegistration(values);
    setErrors(nextErrors);
    setServerMessage('');

    if (Object.keys(nextErrors).length > 0) {
      return;
    }

    setIsSubmitting(true);

    try {
      const response = await fetch('/api/register', {
        method: 'POST',
        headers: {
          'Content-Type': 'application/json',
        },
        body: JSON.stringify(values),
      });

      if (!response.ok) {
        throw new Error('не удалось зарегистрироваться');
      }

      setServerMessage('регистрация прошла успешно');
    } catch (error) {
      setServerMessage(error.message);
    } finally {
      setIsSubmitting(false);
    }
  }

  return (
    <form onSubmit={handleSubmit} noValidate>
      <input
        name="name"
        value={values.name}
        onChange={(event) =>
          setValues((previousValues) => ({
            ...previousValues,
            name: event.target.value,
          }))
        }
        placeholder="имя"
      />

      <input
        name="email"
        type="email"
        value={values.email}
        onChange={(event) =>
          setValues((previousValues) => ({
            ...previousValues,
            email: event.target.value,
          }))
        }
        placeholder="email"
      />

      <input
        name="password"
        type="password"
        value={values.password}
        onChange={(event) =>
          setValues((previousValues) => ({
            ...previousValues,
            password: event.target.value,
          }))
        }
        placeholder="пароль"
      />

      <button type="submit" disabled={isSubmitting}>
        {isSubmitting ? 'отправка...' : 'зарегистрироваться'}
      </button>

      {Object.values(errors).map((message) => (
        <p key={message}>{message}</p>
      ))}

      {serverMessage && <p>{serverMessage}</p>}
    </form>
  );
}
```

- в этом примере предполагается, что функция `validateRegistration` из предыдущего раздела уже объявлена в том же модуле
- `isSubmitting` позволяет отображать состояние загрузки и блокировать повторное нажатие на кнопку, пока запрос выполняется
- `try/catch/finally` нужен, чтобы обработать ошибку запроса и гарантированно сбросить состояние загрузки после завершения операции
- `fetch` не выбрасывает исключение автоматически при ответе со статусом `400` или `500`, поэтому мы отдельно проверяем `response.ok`
- настоящий API может возвращать собственные ошибки валидации, которые стоит преобразовать в сообщения рядом с соответствующими полями
- для производственной реализации также нужны обработка сетевых ошибок, безопасное управление чувствительными данными и согласование формата ответа с API
- обрати внимание на важный нюанс: блокировка кнопки не гарантирует защиту от всех повторных отправок, поэтому критичные операции могут дополнительно требовать контроля на сервере

## 6. зачем нужны библиотеки для работы с формами

- теперь представим, что форма содержит 20 полей, несколько зависимых списков, условные секции, вложенные объекты, динамический список телефонов, валидацию при потере фокуса и обработку серверных ошибок
- если самостоятельно реализовывать всё через `useState`, придётся поддерживать множество взаимосвязанных состояний и правил
- типичная форма может потребовать управления следующими данными
- `values` — текущие значения полей
- `errors` — ошибки валидации
- `touched` — поля, с которыми уже взаимодействовал пользователь
- `isSubmitting` — выполняется ли отправка
- `isValidating` — выполняется ли проверка
- `dirty` — отличается ли форма от исходного состояния
- `isValid` — нет ли ошибок согласно текущему состоянию проверки
- `submitCount` — сколько раз предпринималась попытка отправки
- без библиотеки разработчику нужно самому определить правила обновления всех этих значений и обеспечить их согласованность
- библиотеки форм предоставляют готовую инфраструктуру для этой задачи, позволяя сосредоточиться на структуре полей, правилах валидации и логике отправки

## 7. Formik — как работает библиотека

- Formik — библиотека для управления состоянием форм в React, их валидацией и отправкой
- она не заменяет React, а предоставляет более специализированный механизм управления значениями и состоянием формы
- основные понятия Formik:
- `initialValues` — исходные значения полей
- `values` — актуальные значения формы
- `errors` — объект ошибок
- `touched` — информация о взаимодействии с полями
- `handleChange` — обработчик изменения поля
- `handleBlur` — обработчик потери фокуса
- `handleSubmit` — обработчик отправки
- `isSubmitting` — состояние отправки
- `isValid` — признак валидности формы согласно имеющимся ошибкам
- `dirty` — признак отличия значений от исходных

### 7.1. пример формы на Formik

- в этом примере используется `useFormik`, чтобы показать основную механику без дополнительных компонентов библиотеки

```js
import { useFormik } from 'formik';

function FormikRegistrationForm() {
  const formik = useFormik({
    initialValues: {
      name: '',
      email: '',
    },

    validate(values) {
      const errors = {};

      if (!values.name.trim()) {
        errors.name = 'введите имя';
      }

      if (!values.email.trim()) {
        errors.email = 'введите email';
      }

      return errors;
    },

    onSubmit(values, helpers) {
      console.log('отправляем данные', values);

      helpers.setSubmitting(false);
    },
  });

  return (
    <form onSubmit={formik.handleSubmit} noValidate>
      <label>
        имя
        <input
          name="name"
          value={formik.values.name}
          onChange={formik.handleChange}
          onBlur={formik.handleBlur}
        />
      </label>

      {formik.touched.name && formik.errors.name && (
        <p>{formik.errors.name}</p>
      )}

      <label>
        email
        <input
          name="email"
          type="email"
          value={formik.values.email}
          onChange={formik.handleChange}
          onBlur={formik.handleBlur}
        />
      </label>

      {formik.touched.email && formik.errors.email && (
        <p>{formik.errors.email}</p>
      )}

      <button type="submit" disabled={formik.isSubmitting}>
        отправить
      </button>
    </form>
  );
}
```

- предполагается, что Formik установлен в проекте, например через `npm install formik`
- здесь `useFormik()` создаёт состояние и обработчики для формы, а компонент использует их для связи полей с этим состоянием
- `formik.handleChange` определяет поле по `name` и обновляет его значение
- `formik.handleBlur` помогает отслеживать взаимодействие с полями
- `formik.handleSubmit` запускает предусмотренный библиотекой процесс отправки, включая проверку формы, если она настроена
- `onSubmit` получает значения формы и объект вспомогательных методов, с помощью которого можно управлять состоянием отправки и устанавливать серверные ошибки
- в примере отправка имитируется через `console.log`, поэтому `setSubmitting(false)` вызывается сразу, но при реальном асинхронном запросе нужно корректно дождаться его завершения

### 7.2. что происходит внутри Formik

- важно понимать, что библиотека не угадывает состояние формы по внешнему виду полей, а сама хранит данные и предоставляет методы для их обновления
- когда пользователь вводит символ, `handleChange` получает событие, определяет имя поля и обновляет соответствующее значение в `values`
- при изменении состояния React может повторно отрендерить компонент, чтобы поля, ошибки и другие элементы интерфейса получили актуальные данные
- при потере фокуса `handleBlur` обновляет информацию о `touched` и, если включена соответствующая настройка, запускает валидацию
- при отправке `handleSubmit` отменяет стандартное поведение браузера, запускает проверку по настроенным правилам и при успешной проверке вызывает `onSubmit`
- если проверка асинхронная, библиотека должна учитывать её завершение, прежде чем переходить к отправке
- после завершения отправки состояние должно отражать, что операция закончилась
- конкретное поведение зависит от настроек Formik, например `validateOnChange` и `validateOnBlur`, которые определяют, когда запускать валидацию

### 7.3. Formik и схема валидации

- Formik позволяет использовать собственную функцию `validate`, как в предыдущем примере, либо декларативно задавать правила с помощью `validationSchema`
- для схемной валидации часто используют Yup — библиотеку, в которой правила описываются отдельно от JSX

```js
import * as Yup from 'yup';

const registrationSchema = Yup.object({
  name: Yup.string()
    .trim()
    .required('введите имя'),

  email: Yup.string()
    .email('проверьте формат email')
    .required('введите email'),
});
```

- затем эту схему можно передать в `useFormik` через `validationSchema: registrationSchema`
- преимущество такого подхода заключается в том, что правила можно описывать декларативно, повторно использовать и отдельно тестировать
- при этом Yup — не часть самого React и не обязательная зависимость Formik, а отдельная библиотека, которую можно подключать по необходимости

## 8. React Final Form — альтернативный подход

- React Final Form — React-обёртка над библиотекой Final Form, которая отвечает за состояние формы, значения полей, валидацию и отправку
- ключевая идея этой библиотеки — разделить управление состоянием формы и React-компоненты, которые отображают это состояние
- в отличие от подхода, при котором один компонент хранит всё состояние формы, React Final Form предоставляет подписки на изменения, благодаря чему компонент поля может получать только те данные, которые ему нужны

### 8.1. пример формы на React Final Form

```js
import { Form, Field } from 'react-final-form';

function FinalFormRegistrationForm() {
  function validateEmail(value) {
    if (!value) {
      return 'введите email';
    }

    if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(value)) {
      return 'проверьте формат email';
    }

    return undefined;
  }

  async function submitRegistration(values) {
    console.log('отправляем данные', values);
  }

  return (
    <Form
      onSubmit={submitRegistration}
      render={({ handleSubmit, submitting, invalid }) => (
        <form onSubmit={handleSubmit} noValidate>
          <Field name="name">
            {({ input, meta }) => (
              <div>
                <label>
                  имя
                  <input {...input} />
                </label>

                {meta.touched && meta.error && (
                  <p>{meta.error}</p>
                )}
              </div>
            )}
          </Field>

          <Field name="email" validate={validateEmail}>
            {({ input, meta }) => (
              <div>
                <label>
                  email
                  <input {...input} type="email" />
                </label>

                {meta.touched && meta.error && (
                  <p>{meta.error}</p>
                )}
              </div>
            )}
          </Field>

          <button type="submit" disabled={submitting || invalid}>
            отправить
          </button>
        </form>
      )}
    />
  );
}
```

- предполагается, что пакет установлен через `npm install react-final-form final-form`
- `Form` управляет состоянием формы и предоставляет информацию о её состоянии через render prop
- `Field` регистрирует поле с определённым именем и предоставляет его значение, обработчики и метаданные
- `input` содержит свойства, необходимые для связи элемента ввода с библиотекой, включая `value`, `onChange`, `onBlur` и `onFocus`
- `meta` содержит информацию о состоянии поля, например `touched`, `error`, `dirty` и другие метаданные
- `validateEmail` возвращает сообщение об ошибке, если значение не прошло проверку, и `undefined`, если ошибки нет
- `submitting` показывает состояние отправки, а `invalid` отражает состояние валидности формы согласно результатам валидации
- здесь проверяется только email, поэтому имя не имеет правил обязательности, а `invalid` зависит от тех правил, которые действительно заданы

### 8.2. зачем нужны подписки

- представим форму из 50 полей, в которой пользователь меняет значение только одного поля
- если компонент всей формы подписан на каждое изменение всех полей, изменение одного значения может приводить к лишним обновлениям большой части интерфейса
- в React Final Form можно подписывать отдельные компоненты на конкретные части состояния, чтобы они обновлялись только тогда, когда меняются интересующие их данные
- например, поле может получать своё значение и ошибку, а компонент кнопки — состояние `submitting` и `invalid`
- это помогает контролировать область обновлений, но не означает, что любой компонент с React Final Form автоматически никогда не перерендерится

## 9. как устроен жизненный цикл формы

- на собеседовании могут спросить не только, как использовать Formik или React Final Form, но и что происходит внутри библиотеки от первого отображения до отправки данных
- полезно представить жизненный цикл формы как последовательность состояний

1. инициализация - начальные значения и регистрация полей

2. ввод данных - обновление values и реакция интерфейса

3. валидация - проверка полей и вычисление ошибок

4. отправка - проверка формы, вызов обработчика и запрос к API

5. завершение - обработка результата и сброс состояния отправки

- это концептуальная последовательность, а не универсальный внутренний алгоритм каждой библиотеки, поскольку конкретные детали зависят от её реализации и настроек

### этап 1 — инициализация

- библиотека получает начальные значения и создаёт внутреннее состояние формы
- при использовании React Final Form поля регистрируются в системе управления формой, а Formik предоставляет значения и методы через `useFormik` или компоненты библиотеки
- начальные значения могут поступать из константы, данных пользователя или результата загрузки с сервера

### этап 2 — изменение поля

- при вводе пользователь изменяет значение в DOM, после чего обработчик поля сообщает библиотеке об изменении
- библиотека обновляет значение соответствующего поля и при необходимости запускает валидацию
- состояние формы пересчитывается, а подписанные компоненты получают актуальные данные

### этап 3 — валидация

- библиотека запускает заданные функции проверки, формирует ошибки и обновляет метаданные полей
- в зависимости от настроек проверка может запускаться при изменении значения, потере фокуса или отправке формы
- если используется асинхронная валидация, библиотека должна учитывать, что проверка может завершиться позже следующего изменения значения

### этап 4 — отправка

- после попытки отправки библиотека может пометить поля как затронутые, увеличить счётчик отправок и запустить валидацию
- если форма проходит проверку, библиотека вызывает пользовательский обработчик отправки с текущими значениями
- обработчик обычно выполняет запрос к API и возвращает результат, а библиотека обновляет состояние отправки после его завершения

### этап 5 — обработка результата

- при успехе приложение может показать уведомление, перейти на другую страницу или очистить форму
- при серверной ошибке библиотека или пользовательский код могут записать ошибки и показать их рядом с полями
- состояние отправки должно корректно сбрасываться и при успешном результате, и при ошибке

- важный нюанс: React-компонент не обязательно должен повторно отрисовываться при изменении каждого внутреннего свойства формы — это зависит от подписок, способа хранения состояния и реализации библиотеки

## 10. сравнение Formik, React Final Form и собственной реализации

### собственная реализация

- даёт полный контроль над логикой, состоянием и пользовательским интерфейсом
- подходит для небольших форм и ситуаций с особыми требованиями
- требует самостоятельно реализовать валидацию, `touched`, `dirty`, состояние отправки, серверные ошибки и другие механизмы

### Formik

- предоставляет готовые средства управления значениями, ошибками, взаимодействием с полями и отправкой
- поддерживает как собственную валидацию, так и схемы через сторонние библиотеки
- удобен для форм с понятной моделью состояния, но требует учитывать особенности обновлений состояния и подписок

### React Final Form

- разделяет ядро управления формой и React-слой
- позволяет управлять обновлениями через подписки на состояние формы и отдельных полей
- удобен, когда важно гибко контролировать, какие компоненты получают изменения

- нельзя утверждать, что одна из этих библиотек всегда быстрее или лучше остальных, — выбор зависит от размера формы, сложности правил, требований к производительности и поддержки в конкретном проекте

- при выборе библиотеки также полезно проверить актуальность её развития, совместимость с используемой версией React и доступность нужных интеграций

## 11. частые вопросы на собеседовании

почему для поля React обычно используют `value` вместе с `onChange`?

- `value` определяет отображаемое значение контролируемого поля, а `onChange` позволяет обновлять состояние в ответ на ввод пользователя

чем `defaultValue` отличается от `value`?

- `defaultValue` задаёт начальное значение неконтролируемого поля, тогда как `value` связывает отображаемое значение с текущим значением, передаваемым React

зачем нужен `touched`, если уже есть `errors`?

- `errors` содержит результаты проверки, а `touched` помогает определить, взаимодействовал ли пользователь с полем, и решить, когда показывать сообщение об ошибке

почему недостаточно проверять данные только на клиенте?

- клиентскую проверку можно обойти, поэтому сервер обязан самостоятельно проверять входящие данные и соблюдать бизнес-правила и ограничения доступа

зачем нужны библиотеки форм, если React уже предоставляет `useState`?

- `useState` — универсальный механизм состояния, а библиотеки форм предоставляют готовую логику значений, ошибок, взаимодействия с полями, валидации и отправки

что произойдёт, если вызвать `setErrors(nextErrors)` и сразу прочитать `errors`?

- в текущем вызове обработчика переменная `errors` по-прежнему содержит значение из текущего рендера, поэтому для немедленной проверки следует использовать `nextErrors`, а новое состояние будет доступно в последующем рендере

## 12. что нужно уметь объяснить своими словами

- я бы сформулировал основную идею так

> - форма в React — это интерфейс для сбора и отправки данных, в котором нужно управлять значениями полей, проверкой введённых данных, отображением ошибок и состоянием отправки
> - в простой форме можно реализовать эту логику самостоятельно с помощью `useState`, обработчиков событий и отдельных функций валидации
> - по мере усложнения формы появляется необходимость согласованно управлять значениями, ошибками, затронутыми полями, асинхронной проверкой и отправкой, поэтому используются библиотеки вроде Formik и React Final Form
> - такие библиотеки не отменяют работу React, а предоставляют готовую инфраструктуру для управления формой и её жизненным циклом

- для уверенного прохождения собеседования особенно важно уметь самостоятельно реализовать контролируемую форму, написать пользовательскую валидацию, показать ошибки в нужный момент и объяснить, как библиотека управляет состоянием от ввода до завершения отправки
