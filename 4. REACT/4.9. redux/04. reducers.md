# reducers в Redux

- Reducer — одна из ключевых сущностей Redux, которая определяет, как изменяется состояние приложения в ответ на Actions
- в этой теме разберём правила написания Reducers, их работу через `switch/case`, современный подход с Redux Toolkit и принцип Open/Closed из SOLID

## 1. что такое Reducer

- Reducer — это функция, которая принимает предыдущее состояние (`state`) и Action (`action`), а возвращает следующее состояние

```js
function counterReducer(state = 0, action) {
  switch (action.type) {
    case 'counter/increment':
      return state + 1;

    case 'counter/decrement':
      return state - 1;

    default:
      return state;
  }
}
```

- здесь `state` — текущее состояние счётчика, `action` — событие, а возвращаемое значение — новое состояние
- например, если передать `state = 5` и Action типа `counter/increment`, функция вернёт `6`

```js
counterReducer(5, { type: 'counter/increment' }); // 6
counterReducer(5, { type: 'counter/decrement' }); // 4
counterReducer(5, { type: 'unknown' }); // 5
```

- важно: Reducer не изменяет Store напрямую и не отправляет Actions — он только вычисляет результат

### почему он называется Reducer

- название происходит от метода `reduce` в JavaScript: как функция свёртки последовательно обрабатывает элементы массива и накапливает результат, так Redux последовательно применяет Actions к состоянию
- концептуально это можно представить так

```
начальное состояние
       ↓ Action A
новое состояние
       ↓ Action B
новое состояние
       ↓ Action C
текущее состояние
```

- каждый Action обрабатывается на основе состояния, полученного после предыдущего изменения
- при этом Reducer не обязан буквально вызываться через JavaScript-метод `Array.prototype.reduce()` — это аналогия, объясняющая идею последовательного вычисления состояния

## 2. основные правила Reducer

- чтобы Reducer работал предсказуемо, он должен соблюдать несколько важных правил

### правило 1. быть чистой функцией

- чистая функция при одинаковых аргументах возвращает одинаковый результат и не производит побочных эффектов

```js
function counterReducerPure(state = 0, action) {
  if (action.type === 'counter/increment') {
    return state + 1;
  }

  return state;
}
```

- если вызвать эту функцию с состоянием `5` и Action `counter/increment`, она всегда вернёт `6`
- результат не должен зависеть от текущего времени, случайных чисел, сетевых запросов или изменяемых внешних переменных
- поэтому внутри Reducer нельзя выполнять `fetch`, `setTimeout`, изменять DOM или отправлять Actions через `dispatch`

### правило 2. не мутировать предыдущее состояние

- в классическом Redux нужно возвращать новое состояние, не изменяя исходный объект или массив

```js
function cartReducerImmutable(state = { items: [] }, action) {
  switch (action.type) {
    case 'cart/productAdded':
      return {
        ...state,
        items: [...state.items, action.payload],
      };

    default:
      return state;
  }
}
```

- при добавлении товара создаётся новый объект состояния и новый массив `items`
- оператор `...state` сохраняет остальные свойства объекта, а `...state.items` копирует существующие элементы в новый массив
- при этом не нужно глубоко копировать всё дерево состояния: достаточно создать новые объекты на пути к изменяемым данным

### правило 3. обрабатывать неизвестные Actions

- Redux может отправлять Actions в Reducer, которые конкретный Reducer не обрабатывает
- поэтому в классическом `switch/case` обычно нужен `default`, возвращающий текущее состояние

```js
function themeReducer(state = 'light', action) {
  switch (action.type) {
    case 'theme/darkEnabled':
      return 'dark';

    case 'theme/lightEnabled':
      return 'light';

    default:
      return state;
  }
}
```

- если Action не относится к теме оформления, Reducer должен сохранить текущее состояние, а не возвращать `undefined`

### правило 4. корректно обрабатывать начальное состояние

- при создании Store Redux вызывает Reducer с неопределённым состоянием, чтобы получить начальное значение
- поэтому Reducer должен предоставлять начальное состояние, например через параметр `state = initialState`

```js
const initialCounterState = {
  value: 0,
};

function counterObjectReducer(state = initialCounterState, action) {
  switch (action.type) {
    case 'counter/increment':
      return {
        ...state,
        value: state.value + 1,
      };

    default:
      return state;
  }
}
```

- начальное состояние также должно иметь правильную структуру: если компонент ожидает `state.value`, нельзя случайно вернуть вместо объекта число или `undefined`

## 3. написание Reducer через `switch/case`

- `switch/case` — классический способ организовать обработку разных типов Actions в одном Reducer
- каждый `case` соответствует определённому типу события, а `default` обрабатывает все остальные события
- рассмотрим более реалистичный пример с корзиной

```js
const initialCartState = {
  items: [],
};

function shoppingCartReducer(state = initialCartState, action) {
  switch (action.type) {
    case 'cart/productAdded':
      return {
        ...state,
        items: [...state.items, action.payload],
      };

    case 'cart/productRemoved':
      return {
        ...state,
        items: state.items.filter((item) => item.id !== action.payload),
      };

    case 'cart/cleared':
      return {
        ...state,
        items: [],
      };

    default:
      return state;
  }
}
```

- разберём, как работает каждая ветка
- `cart/productAdded` — создаёт новый массив и добавляет товар из `action.payload`
- `cart/productRemoved` — создаёт новый массив, в котором остаются все товары, кроме товара с указанным идентификатором
- `cart/cleared` — возвращает новое состояние с пустой корзиной
- `default` — возвращает текущее состояние, если Action не относится к корзине

### почему в Reducer нужно возвращать новое состояние

- Redux определяет изменение состояния по результату работы Reducer, а React-Redux использует сравнение ссылок, чтобы определить, какие компоненты нужно обновить
- если изменить существующий объект и вернуть ту же ссылку, можно нарушить обнаружение изменений и получить некорректное поведение
- например, такой Reducer написан неправильно

```js
function incorrectCartReducer(state = { items: [] }, action) {
  switch (action.type) {
    case 'cart/productAdded':
      state.items.push(action.payload);
      return state;

    default:
      return state;
  }
}
```

- `push()` изменяет исходный массив, а `return state` возвращает тот же объект, поэтому иммутабельность нарушается
- корректная версия создаёт новый объект и новый массив, как в примере выше

### как Redux объединяет несколько Reducers

- в реальном приложении не обязательно помещать всю логику состояния в один огромный Reducer
- состояние можно разделить на логические области, каждая из которых управляется своим Reducer

```
rootReducer
├── userReducer       → user
├── shoppingCartReducer → cart
└── productsReducer   → products
```

- `combineReducers` объединяет несколько Reducers в один корневой Reducer, который управляет отдельными частями общего состояния

```js
import { combineReducers } from 'redux';

const rootReducer = combineReducers({
  user: userReducer,
  cart: shoppingCartReducer,
  products: productsReducer,
});
```

- в таком случае каждый Reducer получает только свою часть состояния, а итоговый объект Store содержит все перечисленные области
- например, `shoppingCartReducer` работает с `state.cart`, а не со всем деревом `state`

## 4. Redux Toolkit и `createSlice`

- в современных Redux-приложениях рекомендуется использовать Redux Toolkit, который уменьшает количество шаблонного кода и упрощает создание Reducers и Actions
- вместо ручного написания строковых типов Actions, `switch/case` и отдельных Action Creators можно использовать `createSlice`

```js
import { createSlice } from '@reduxjs/toolkit';

const cartSlice = createSlice({
  name: 'cart',
  initialState: {
    items: [],
  },
  reducers: {
    productAdded(state, action) {
      state.items.push(action.payload);
    },

    productRemoved(state, action) {
      state.items = state.items.filter((item) => item.id !== action.payload);
    },

    cartCleared(state) {
      state.items = [];
    },
  },
});

export const { productAdded, productRemoved, cartCleared } = cartSlice.actions;

export default cartSlice.reducer;
```

- `name` задаёт пространство имён для типов Actions, в данном случае `cart`
- `initialState` определяет начальное состояние слайса
- `reducers` содержит обработчики Actions, которые определяют переходы состояния
- `cartSlice.actions` содержит автоматически созданные Action Creators
- `cartSlice.reducer` — готовый Reducer, который можно подключить к Store

### почему здесь допустима запись `state.items.push()`

- на первый взгляд этот код нарушает правило иммутабельности, но Redux Toolkit использует библиотеку Immer
- Immer предоставляет обработчику специальный draft-объект, который позволяет писать изменения в мутабельном стиле, а затем формирует новое иммутабельное состояние

```
исходное состояние
        ↓
draft-состояние Immer
        ↓
изменения внутри Reducer
        ↓
новое иммутабельное состояние
```

- поэтому `state.items.push(action.payload)` внутри `createSlice` — корректный подход
- однако этот же код нельзя бездумно переносить в обычный Redux Reducer, где Immer не используется
- ещё один нюанс: обработчик `createSlice` должен либо изменять draft, либо возвращать новое состояние, но не выполнять оба действия одновременно

### подключение к Store

```js
import { configureStore } from '@reduxjs/toolkit';
import cartReducer from './cartSlice';

const shoppingStore = configureStore({
  reducer: {
    cart: cartReducer,
  },
});
```

- `configureStore` создаёт Store, подключает Reducer и настраивает стандартные middleware, включая проверки распространённых ошибок разработки
- в этом примере состояние корзины доступно по пути `state.cart`
- Actions отправляются через `shoppingStore.dispatch(productAdded(product))`, а Reducer автоматически обрабатывает соответствующий Action

### когда использовать `createReducer`

- Redux Toolkit также предоставляет `createReducer`, если нужно создавать Reducer отдельно от `createSlice`
- однако для большинства обычных случаев `createSlice` удобнее, поскольку он объединяет описание начального состояния, обработчиков и Action Creators в одном месте

## 5. принцип Open/Closed (SOLID) применительно к Reducers

- принцип Open/Closed Principle (OCP) гласит: программные сущности должны быть открыты для расширения, но закрыты для модификации
- это не означает, что код вообще нельзя менять; смысл в том, чтобы добавление новой функциональности по возможности не требовало изменения уже работающего и проверенного кода

### проблема большого `switch/case`

- представим Reducer, который обрабатывает множество событий приложения

```js
function applicationReducer(state = initialApplicationState, action) {
  switch (action.type) {
    case 'user/nameChanged':
      // изменение имени пользователя
      return {
        ...state,
        user: {
          ...state.user,
          name: action.payload,
        },
      };

    case 'cart/productAdded':
      // добавление товара
      return {
        ...state,
        cart: {
          ...state.cart,
          items: [...state.cart.items, action.payload],
        },
      };

    case 'theme/changed':
      // изменение темы
      return {
        ...state,
        theme: action.payload,
      };

    default:
      return state;
  }
}
```

- когда добавляется новая область функциональности, разработчик добавляет ещё одну ветку в общий Reducer
- если таких веток становится много, Reducer сложнее читать, тестировать и изменять без риска затронуть другую логику
- проблема здесь не в самом `switch/case`: для небольшого Reducer это вполне хороший подход
- сложность возникает, когда одна функция начинает отвечать за слишком много независимых областей состояния

### решение 1. разделение Reducers по ответственности

- можно разделить обработку событий на несколько небольших Reducers и объединить их через `combineReducers`

```js
import { combineReducers } from 'redux';

function userReducer(state = { name: '' }, action) {
  switch (action.type) {
    case 'user/nameChanged':
      return {
        ...state,
        name: action.payload,
      };

    default:
      return state;
  }
}

function themeReducer(state = 'light', action) {
  switch (action.type) {
    case 'theme/changed':
      return action.payload;

    default:
      return state;
  }
}

const applicationRootReducer = combineReducers({
  user: userReducer,
  theme: themeReducer,
});
```

- теперь добавление новой независимой области, например `notifications`, не требует изменения логики `userReducer` или `themeReducer`
- достаточно создать новый Reducer и зарегистрировать его в корневом Reducer
- это способствует соблюдению OCP на уровне отдельных модулей: расширяем приложение новыми областями, сохраняя существующие модули независимыми

### решение 2. обработчики через `createSlice`

- в Redux Toolkit обработчики группируются по функциональным областям, поэтому добавление нового события обычно сводится к расширению соответствующего слайса

```js
const notificationSlice = createSlice({
  name: 'notifications',
  initialState: {
    messages: [],
  },
  reducers: {
    notificationAdded(state, action) {
      state.messages.push(action.payload);
    },

    notificationRemoved(state, action) {
      state.messages = state.messages.filter((message) => message.id !== action.payload);
    },
  },
});
```

- обработчики уведомлений находятся отдельно от логики корзины, пользователя или оформления заказа
- при добавлении нового функционального модуля существующие Reducers не нужно переписывать
- важно: добавление нового обработчика в существующий `createSlice` всё равно изменяет конфигурацию этого слайса; OCP не требует абсолютного запрета на изменения, а помогает ограничивать их область и избегать ненужных изменений несвязанных модулей

### нужно ли вообще избегать `switch/case`

- нет, `switch/case` — нормальный способ написания Reducer, особенно когда он отвечает за одну небольшую область состояния
- OCP не означает, что каждый Reducer должен использовать динамическую регистрацию обработчиков или сложную архитектуру
- главное — распределять ответственность разумно и избегать огромного Reducer, который объединяет несвязанные части приложения
- на практике сочетание небольших функциональных слайсов, `combineReducers` и Redux Toolkit обычно обеспечивает достаточно хорошую модульность без лишней сложности

## 6. типичные ошибки при написании Reducers

- мутация исходного состояния в обычном Reducer — приводит к нарушению иммутабельности и может мешать корректному определению изменений
- возврат `undefined` для неизвестного Action — Reducer должен возвращать текущее состояние, если не обрабатывает Action
- побочные эффекты внутри Reducer — HTTP-запросы, таймеры и другие внешние операции должны выполняться за пределами чистого Reducer
- неправильное обновление вложенных объектов — поверхностное копирование корневого объекта недостаточно, если изменяется вложенный объект; нужно создать новые ссылки на всех изменяемых уровнях
- чрезмерно большой Reducer — если функция отвечает за множество независимых областей состояния, стоит разделить её на более мелкие Reducers или слайсы
- одновременное изменение draft и возврат другого состояния в Redux Toolkit — обработчик должен выбрать один подход: изменить draft либо вернуть новое состояние

## 7. как объяснить Reducers на собеседовании

- Reducer — это чистая функция, которая принимает предыдущее состояние и Action, а возвращает следующее состояние
- основные правила Reducer — отсутствие побочных эффектов, предсказуемый результат, корректное начальное состояние и возврат текущего состояния для неизвестных Actions
- в классическом Redux Reducers часто реализуются через `switch/case`, а иммутабельные обновления выполняются с помощью spread-операторов, `map`, `filter` и других операций, создающих новые объекты и массивы
- в современном Redux рекомендуется использовать Redux Toolkit и `createSlice`, который генерирует Action Creators и позволяет писать обработчики с помощью Immer в мутабельном стиле
- принцип Open/Closed применяется к организации Reducers через разделение ответственности: добавление новой функциональности не должно вынуждать переписывать несвязанные части приложения
- главное, что нужно запомнить: Action описывает событие, Reducer вычисляет новое состояние, а Store сохраняет результат; предсказуемость этого механизма зависит от соблюдения правил Reducer и правильной организации логики изменения состояния
