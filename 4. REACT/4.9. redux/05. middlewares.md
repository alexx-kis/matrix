# middlewares в Redux

- Middleware — это механизм, который позволяет перехватывать и обрабатывать `dispatch` Actions до того, как они попадут в Reducer, а также выполнять дополнительную логику вокруг этого процесса
- middleware особенно полезны для логирования, обработки асинхронных операций, аналитики, обработки ошибок и других задач, которые не должны выполняться внутри Reducers
- разберём концепцию от базового устройства до написания собственного middleware и внутренних механизмов Redux

## 1. зачем нужны middleware

- вспомним основной поток Redux: компонент отправляет Action через `dispatch`, Reducer вычисляет новое состояние, а Store уведомляет подписчиков

```
component
    ↓
dispatch
    ↓
reducer
    ↓
new state
    ↓
subscribers
```

- предположим, что нам нужно логировать каждый Action и состояние до и после его обработки
- можно написать этот код внутри каждого обработчика событий, но тогда логирование будет дублироваться и смешиваться с бизнес-логикой
- можно добавить логирование в Reducers, но это нарушит принцип чистой функции, поскольку Reducer не должен выполнять побочные эффекты
- middleware позволяют вынести подобную логику в отдельный слой, не изменяя сами Reducers и компоненты

```
component
    ↓
 dispatch
    ↓
middleware A
    ↓
middleware B
    ↓
 reducer
    ↓
 new state
    ↓
subscribers
```

- middleware получают возможность обработать Action перед передачей дальше, изменить способ обработки или остановить дальнейшее прохождение Action
- важно: middleware не заменяют Reducers и не являются обязательными для каждого Action — они расширяют поведение механизма `dispatch`

## 2. что такое middleware технически

- в Redux middleware — это функция, которая получает доступ к `dispatch` и `getState`, а затем возвращает функцию, принимающую следующий обработчик в цепочке
- классическая сигнатура выглядит так:

```js
const exampleMiddleware =
  ({ dispatch, getState }) =>
  (next) =>
  (action) => {
    // логика до передачи Action дальше

    const result = next(action);

    // логика после передачи Action дальше

    return result;
  };
```

- здесь используются три уровня функций, и важно понимать роль каждого из них

1. `({ dispatch, getState }) => ...`

- получает API Store
- `dispatch` позволяет отправлять Actions, а `getState` — читать текущее состояние

2. `(next) => ...`

- получает следующий обработчик в цепочке middleware
- если текущий middleware последний, `next` передаст Action стандартному обработчику Redux, который вызывает Reducer

3. `(action) => ...`

- получает конкретный Action или, в расширенных сценариях, другое значение, отправленное через `dispatch`
- здесь выполняется логика обработки и решается, вызывать ли `next(action)`

* такая конструкция называется каррированием: функция принимает аргумент и возвращает следующую функцию
* три уровня позволяют Redux сначала предоставить middleware API, затем построить цепочку, а после этого передавать через неё отдельные Actions

## 3. что делают `next`, `dispatch` и `getState`

- это три понятия, которые нужно особенно хорошо различать

### `next(action)`

- передаёт Action следующему middleware в цепочке или стандартному обработчику Redux, если текущий middleware последний

```js
const passThroughMiddleware = () => (next) => (action) => {
  return next(action);
};
```

- такой middleware ничего не делает с Action, а просто передаёт его дальше
- если middleware не вызывает `next(action)`, исходный Action не дойдёт до следующих middleware и Reducer по этому пути

### `dispatch(action)`

- отправляет новый Action через цепочку `dispatch`, начиная с начала цепочки middleware

```js
const notificationMiddleware =
  ({ dispatch }) =>
  (next) =>
  (action) => {
    if (action.type === 'cart/productAdded') {
      dispatch({
        type: 'analytics/cartProductAdded',
      });
    }

    return next(action);
  };
```

- здесь при добавлении товара отправляется дополнительный Action аналитики, а затем исходный Action передаётся дальше
- поскольку новый Action отправляется через `dispatch`, он проходит цепочку заново, начиная с первого middleware
- это может привести к бесконечной рекурсии, если middleware снова и снова отправляет Action, который запускает ту же ветку логики, поэтому нужно предусматривать условия, исключающие такой цикл

### `getState()`

- возвращает актуальное состояние Store на момент вызова

```js
const stateAwareMiddleware =
  ({ getState }) =>
  (next) =>
  (action) => {
    const stateBefore = getState();

    const result = next(action);

    const stateAfter = getState();

    return result;
  };
```

- `stateBefore` содержит состояние до передачи Action дальше, а `stateAfter` — состояние после синхронной обработки Action, если он дошёл до Reducer
- в этом примере `result` сохраняет результат вызова `next(action)`, чтобы middleware не потерял возвращаемое значение следующего обработчика
- если Action остановлен другим middleware или обработан нестандартным способом, нельзя безусловно предполагать, что состояние изменилось

## 4. пишем собственный middleware с нуля

- начнём с практического примера: напишем middleware, который логирует Action, состояние до его обработки и состояние после обработки

```js
const auditMiddleware =
  ({ getState }) =>
  (next) =>
  (action) => {
    console.log('Action:', action);

    const stateBefore = getState();

    console.log('State before:', stateBefore);

    const result = next(action);

    const stateAfter = getState();

    console.log('State after:', stateAfter);

    return result;
  };
```

- разберём последовательность выполнения
- сначала Redux передаёт middleware API, содержащий `getState` и `dispatch`
- когда вызывается `dispatch(action)`, middleware получает Action и читает состояние до его обработки
- вызов `next(action)` передаёт Action дальше по цепочке, где его обрабатывает следующий middleware или Reducer
- после возврата из `next(action)` middleware читает обновлённое состояние
- в конце возвращается `result`, то есть результат вызова следующего обработчика
- это позволяет писать логику как до обработки Action, так и после неё

### подключаем middleware

- в современном Redux Store обычно создаётся через `configureStore` из Redux Toolkit

```js
import { configureStore } from '@reduxjs/toolkit';
import cartReducer from './cartSlice';

const auditedStore = configureStore({
  reducer: {
    cart: cartReducer,
  },
  middleware: (getDefaultMiddleware) => getDefaultMiddleware().concat(auditMiddleware),
});
```

- `getDefaultMiddleware()` возвращает стандартный набор middleware Redux Toolkit, в том числе thunk middleware и проверки типичных ошибок в режиме разработки
- `.concat(auditMiddleware)` добавляет наш middleware к стандартному набору, сохраняя существующие инструменты
- это предпочтительнее, чем полностью заменять стандартные middleware, если для этого нет особой причины
- теперь каждый Action, проходящий через `auditedStore.dispatch()`, будет попадать в `auditMiddleware`

## 5. middleware может остановить Action

- middleware не обязан передавать каждый Action дальше, поскольку решение о вызове `next(action)` находится под контролем самого middleware
- например, можно заблокировать определённые Actions при выполнении некоторого условия

```js
const actionGuardMiddleware =
  ({ getState }) =>
  (next) =>
  (action) => {
    if (action.type === 'cart/productAdded' && getState().cart.items.length >= 100) {
      return;
    }

    return next(action);
  };
```

- если корзина уже содержит 100 товаров, middleware не передаёт Action дальше, поэтому этот Action не дойдёт до Reducer по данной цепочке
- такой подход демонстрирует технические возможности middleware, но бизнес-правила, от которых зависит корректность данных, нельзя полагаться исключительно на клиентский middleware
- например, ограничения оплаты и доступа должны дополнительно проверяться на сервере, поскольку клиентский код можно обойти

### зачем возвращать результат `next(action)`

- возвращаемое значение `next(action)` может использоваться вызывающим кодом, а middleware часто должен сохранять его, чтобы не менять поведение цепочки без необходимости

```js
const resultPreservingMiddleware = () => (next) => (action) => {
  const downstreamResult = next(action);

  return downstreamResult;
};
```

- если вместо этого middleware всегда возвращает `undefined`, он может нарушить ожидаемое поведение `dispatch`, особенно когда другие middleware возвращают полезные значения
- в обычном синхронном Redux вызов `dispatch` обычно возвращает отправленный Action, но middleware могут изменить это поведение

## 6. почему middleware — это функция вокруг `dispatch`

- чтобы глубже понять Redux, важно разобраться, что middleware не просто вызывается Store как отдельный обработчик каждого события
- `applyMiddleware` создаёт цепочку функций, которая оборачивает исходный `dispatch`
- концептуально это выглядит так:

```
исходный dispatch
       ↓
обёртка middleware A
       ↓
обёртка middleware B
       ↓
обёртка middleware C
       ↓
базовый dispatch Redux
       ↓
rootReducer
```

- каждый middleware получает `next`, который ссылается на следующий уровень цепочки, и может выполнять действия до и после вызова этого уровня
- это похоже на декоратор: поведение существующего механизма расширяется без изменения его исходной реализации
- при этом `next` и `dispatch` не взаимозаменяемы: `next` продолжает обработку текущего Action со следующего звена, а `dispatch` начинает новый проход с начала цепочки

### порядок middleware имеет значение

- если middleware подключены как `A`, затем `B`, затем `C`, обработка до `next` происходит в порядке `A → B → C`, а обработка после `next` — в обратном порядке `C → B → A`

```
вход:
A before
  B before
    C before
      Reducer
    C after
  B after
A after
```

- это работает только для middleware, которые действительно вызывают `next(action)` и затем продолжают выполнение после него
- если какой-то middleware не вызывает `next`, дальнейшая цепочка для этого Action не выполняется
- порядок особенно важен, когда один middleware преобразует значение, ожидаемое другим middleware, или когда обработка зависит от результата предыдущего звена

## 7. асинхронность: зачем middleware нужны для запросов

- обычный Redux `dispatch` предназначен для отправки Action-объектов, а Reducers должны оставаться синхронными чистыми функциями
- однако приложениям часто нужно выполнить HTTP-запрос, дождаться ответа и затем обновить состояние
- middleware позволяют организовать такую работу вне Reducers

### пример: thunk middleware

- thunk middleware позволяет передавать в `dispatch` не только Action-объекты, но и функции, которые получают `dispatch` и `getState`
- именно поэтому следующий код работает с Redux Toolkit, где thunk middleware подключён по умолчанию

```js
const loadProductsThunk = async (dispatch, getState) => {
  dispatch({ type: 'products/loading' });

  try {
    const response = await fetch('/api/products');

    if (!response.ok) {
      throw new Error('Products request failed');
    }

    const products = await response.json();

    dispatch({
      type: 'products/loaded',
      payload: products,
    });
  } catch (error) {
    dispatch({
      type: 'products/failed',
      payload: error.message,
    });
  }
};
```

- теперь можно отправить функцию через `dispatch`

```js
auditedStore.dispatch(loadProductsThunk);
```

- без thunk middleware стандартный Redux не сможет обработать такую функцию как обычный Action-объект
- thunk middleware распознаёт функцию и вызывает её, передавая `dispatch` и `getState`; сама функция может выполнять асинхронную работу и отправлять обычные Actions по мере её выполнения
- здесь `loadProductsThunk` — это thunk-функция, а `products/loading`, `products/loaded` и `products/failed` — обычные Action-объекты
- в реальном приложении Reducer должен обрабатывать эти типы Actions, чтобы обновлять статус загрузки, данные и ошибку

### Redux Toolkit и `createAsyncThunk`

- вручную писать thunk-функции полезно для понимания механизма, но в современных проектах для типичных асинхронных операций часто используют `createAsyncThunk`

```js
import { createAsyncThunk } from '@reduxjs/toolkit';

export const fetchProductsThunk = createAsyncThunk('products/fetch', async () => {
  const response = await fetch('/api/products');

  if (!response.ok) {
    throw new Error('Products request failed');
  }

  return response.json();
});
```

- `createAsyncThunk` автоматически генерирует Actions для состояний `pending`, `fulfilled` и `rejected`, а затем позволяет обрабатывать их в Reducer
- это не отдельная замена middleware: механизм thunk по-прежнему используется для выполнения асинхронной логики, а Redux Toolkit упрощает её описание и обработку результата
- более сложные сценарии — например, управление долгоживущими процессами, координация нескольких запросов или реакция на последовательности Actions — могут решаться через другие middleware, например Redux Saga или Redux Listener Middleware

## 8. какие задачи обычно решают через middleware

- middleware полезны, когда нужно выполнять дополнительную логику, связанную с отправкой Actions, не помещая её в компоненты или Reducers
- типичные сценарии применения:

### логирование

- запись Actions и состояния до и после их обработки для отладки

### асинхронные операции

- запросы к API, обработка результатов и отправка Actions о загрузке, успехе или ошибке

### аналитика

- отправка событий аналитики при определённых пользовательских действиях

### обработка ошибок

- централизованное логирование ошибок и отправка информации в систему мониторинга

### реакция на события состояния

- запуск дополнительной логики после определённых Actions, например сохранение настроек или запуск последующих операций

- важно выбирать правильный инструмент для задачи: не всякая асинхронная операция требует собственного middleware, а простой API-запрос часто достаточно реализовать через thunk или RTK Query

## 9. типичные ошибки при написании middleware

- не вызвать `next(action)` — Action не продолжит обычный путь обработки, если middleware намеренно не остановил его

- вызвать `next(action)` дважды — один Action может пройти дальше два раза, что приведёт к повторной обработке и неожиданным изменениям состояния

- перепутать `dispatch` и `next` — `dispatch` начинает новую обработку с начала цепочки, а `next` продолжает текущую

- не вернуть результат `next(action)` — может потеряться результат, который ожидал вызывающий код или другой middleware

- выполнять побочные эффекты в Reducer вместо middleware — это усложняет тестирование и нарушает предсказуемость Reducers

- создать бесконечный цикл — middleware отправляет Action, который снова запускает ту же ветку отправки, и так без конца

- полностью заменить стандартные middleware Redux Toolkit без необходимости — можно случайно потерять thunk middleware и полезные проверки, поэтому обычно стоит расширять результат `getDefaultMiddleware()`

## 10. важные нюансы для глубокого понимания

### middleware и изменение состояния

- middleware не предназначен для прямого изменения Redux State: он может прочитать состояние через `getState()`, отправить дополнительные Actions или изменить поток обработки, но обновление состояния по стандартному пути выполняет Reducer

- если middleware вызывает `next(action)`, а тот доходит до базового обработчика Redux, Reducer вычисляет новое состояние, которое затем сохраняется в Store

### почему middleware может быть асинхронным

- сама внешняя функция middleware и функция, получающая `next`, обычно настраивают цепочку синхронно, но обработчик конкретного Action может использовать `async/await`, Promise и другие асинхронные механизмы

- при этом Redux не ожидает автоматически завершения произвольного асинхронного обработчика middleware, если используемый middleware или вызывающий код специально не организует ожидание результата

- например, thunk middleware может вернуть результат вызова thunk-функции, включая Promise, что позволяет вызывающему коду ожидать завершения операции

### middleware и Redux DevTools

- Redux DevTools позволяет отслеживать Actions и изменения состояния, но сам по себе не является middleware для выполнения бизнес-логики

- middleware можно использовать для дополнительного логирования, мониторинга или отправки аналитических событий, а DevTools — для инспекции Redux-потока и отладки

### middleware и `connect` / Hooks

- `connect`, `useSelector` и `useDispatch` связывают Redux с React-компонентами, а middleware расширяют обработку `dispatch` на уровне Redux

- поэтому middleware не зависит от того, использует приложение `connect` или Hooks: он работает с потоком Redux Actions независимо от способа подключения компонентов

## 11. как объяснить middleware на собеседовании

- Middleware в Redux — это функция, которая расширяет поведение `dispatch` и позволяет выполнять дополнительную логику до и после обработки Action

- middleware получает `dispatch` и `getState`, а через `next` передаёт Action следующему звену цепочки

- с помощью middleware можно логировать Actions, выполнять асинхронные запросы, отправлять аналитические события, обрабатывать ошибки и при необходимости останавливать прохождение Action

- собственный middleware обычно имеет форму `({ dispatch, getState }) => next => action => { ... }`, где первый уровень получает API Store, второй — следующий обработчик, а третий — конкретный Action

- `next(action)` продолжает текущую цепочку, а `dispatch(action)` запускает новую обработку с начала цепочки, поэтому их важно не путать

- в современных приложениях часто используют Redux Toolkit с thunk middleware по умолчанию, `createAsyncThunk` для асинхронных операций и другие инструменты для более сложных сценариев

- главное, что нужно запомнить: middleware располагается между `dispatch` и Reducer, позволяет расширять обработку Actions и помогает сохранять Reducers чистыми, а бизнес-логику — организованной и тестируемой
