# mock servers в контексте React

- mock server — это сервер, который имитирует поведение настоящего backend API и позволяет frontend-приложению взаимодействовать с данными через HTTP-запросы, не обращаясь к полноценному backend
- эта тема связана с предыдущим блоком Working with API: Fetch, Axios, взаимодействие React с сервером, потому что mock server позволяет разрабатывать и тестировать клиентскую часть приложения, пока настоящий backend ещё не готов, недоступен или не нужен

## 1. зачем нужен mock server

- представим, что мы разрабатываем интернет-магазин на React, которому необходимо получать список товаров
- в production-приложении данные приходят от настоящего backend

```
React application
       ↓ GET /api/products
Backend server
       ↓ JSON response
React application
```

- но backend может быть ещё не реализован, поэтому frontend-разработчик не может полноценно работать с каталогом товаров, загрузкой данных и обработкой ошибок
- вместо ожидания backend можно создать mock server, который будет возвращать заранее подготовленные данные

```
React application
       ↓ GET /api/products
Mock server
       ↓ JSON response
React application
```

- для React-приложения взаимодействие при этом почти не отличается от работы с настоящим сервером: оно отправляет HTTP-запрос, получает ответ и обрабатывает данные

### основные сценарии использования

- параллельная разработка — frontend и backend-команды могут работать независимо друг от друга
- прототипирование — можно быстро реализовать интерфейс, не дожидаясь API
- тестирование — удобно проверять отображение пустых списков, ошибок, загрузки и различных наборов данных
- предсказуемость — ответы не зависят от состояния удалённого сервера или реальной базы данных
- демонстрация приложения — интерфейс можно показать без развёртывания полноценного backend

## 2. что именно имитирует mock server

- mock server может имитировать HTTP API целиком или только его отдельные части
- например, frontend ожидает такие endpoints:

```
GET    /api/products       — получить товары
GET    /api/products/1     — получить товар
POST   /api/products       — создать товар
PUT    /api/products/1     — заменить товар
PATCH  /api/products/1     — изменить товар
DELETE /api/products/1     — удалить товар
```

- простой mock server может возвращать статический JSON, а более функциональный — поддерживать CRUD-операции, фильтрацию, пагинацию и сортировку
- важно различать mock data и mock server: mock data — это сами подставные данные, а mock server — механизм, через который клиент получает эти данные, обычно посредством HTTP
- также mock server не обязательно является отдельным сетевым сервером: в тестах можно перехватывать запросы прямо в браузере или тестовом окружении, имитируя ответы без реального HTTP-сервера

## 3. `json-server` — простой mock REST API

- JSON Server — один из самых удобных инструментов для знакомства с mock servers, поскольку он автоматически создаёт REST API на основе файла с данными

- вместо ручной реализации серверных маршрутов достаточно описать данные в JSON-файле

### шаг 1. установка

- в существующем React-проекте можно установить инструмент как dev dependency

```bash
npm install --save-dev json-server
```

- это инструмент для разработки, а не библиотека, которую нужно импортировать в React-компоненты

### шаг 2. создание базы данных

- создадим файл `db.json` в корне проекта

```json
{
  "products": [
    {
      "id": "1",
      "title": "Laptop",
      "price": 1200
    },
    {
      "id": "2",
      "title": "Keyboard",
      "price": 80
    },
    {
      "id": "3",
      "title": "Mouse",
      "price": 40
    }
  ]
}
```

- ключ `products` обозначает коллекцию ресурсов, а каждый объект внутри массива представляет отдельный товар

### шаг 3. запуск сервера

- добавим команду в `package.json`

```json
{
  "scripts": {
    "mock:server": "json-server db.json --port 3001"
  }
}
```

- запускаем mock server

```bash
npm run mock:server
```

- теперь API доступно по адресу `http://localhost:3001`
- в актуальной версии JSON Server базовые маршруты для массива `products` создаются автоматически

```
GET    http://localhost:3001/products
GET    http://localhost:3001/products/1
POST   http://localhost:3001/products
PUT    http://localhost:3001/products/1
PATCH  http://localhost:3001/products/1
DELETE http://localhost:3001/products/1
```

- например, запрос `GET /products` вернёт массив товаров, а `GET /products/1` — один товар
- при выполнении поддерживаемых операций изменения данных сервер может сохранять изменения в JSON-файл, но точное поведение зависит от версии и конфигурации инструмента

## 4. подключаем mock server к React

- теперь используем API так же, как использовали бы настоящий backend, — через `fetch`
- создадим компонент, который загружает товары и отображает их на странице

```js
import { useEffect, useState } from 'react';

const ProductsCatalog = () => {
  const [products, setProducts] = useState([]);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    const loadProducts = async () => {
      try {
        const response = await fetch('http://localhost:3001/products');

        if (!response.ok) {
          throw new Error(`HTTP error: ${response.status}`);
        }

        const data = await response.json();
        setProducts(data);
      } catch (requestError) {
        setError(requestError.message);
      } finally {
        setIsLoading(false);
      }
    };

    loadProducts();
  }, []);

  if (isLoading) {
    return <p>Loading products...</p>;
  }

  if (error) {
    return <p>Error: {error}</p>;
  }

  return (
    <ul>
      {products.map((product) => (
        <li key={product.id}>
          {product.title}: ${product.price}
        </li>
      ))}
    </ul>
  );
};

export default ProductsCatalog;
```

- здесь нет специального кода для mock server — React использует обычный HTTP-запрос
- разберём ключевые моменты
  - `useEffect` запускает загрузку после появления компонента на странице
  - `fetch` отправляет запрос к локальному API
  - `response.ok` проверяет HTTP-статус, потому что `fetch` не отклоняет Promise автоматически при ответах `404` или `500`
  - `response.json()` преобразует тело ответа из JSON в JavaScript-значение
  - `setProducts(data)` сохраняет полученные товары в состоянии React
  - `finally` завершает состояние загрузки независимо от результата запроса
- при успешном запросе цепочка выглядит так

```
useEffect
   ↓
fetch("/products")
   ↓
HTTP response
   ↓
response.json()
   ↓
setProducts(data)
   ↓
React re-render
   ↓
отображение товаров
```

- если в дальнейшем вместо JSON Server появится настоящий backend с совместимым контрактом API, компоненту не потребуется знать, какой именно сервер вернул данные
- однако адрес API лучше вынести в конфигурацию приложения, а не хранить непосредственно в компоненте, чтобы было проще переключаться между окружениями

## 5. `json-graphql-server` — если приложение использует GraphQL

- `json-server` ориентирован на REST API, а json-graphql-server позволяет получить mock GraphQL API на основе JSON-данных

- разница заключается в том, как клиент запрашивает данные

- в REST-приложении мы обращаемся к конкретному endpoint

```js
const productsResponse = await fetch('http://localhost:3001/products');

const productsData = await productsResponse.json();
```

- в GraphQL-приложении мы обычно отправляем запрос на единый endpoint и указываем, какие именно поля нужны

```
query {
  allProducts {
    id
    title
    price
  }
}
```

- `json-graphql-server` позволяет создать тестовый GraphQL API без самостоятельной реализации всех resolver-функций и серверной логики
- его стоит рассматривать, если проект использует GraphQL и необходимо имитировать именно GraphQL-контракт, а не REST API

## 6. другие способы мокирования API

- mock server — это не обязательно отдельный процесс, запущенный на локальном порту
- в frontend-разработке существуют разные подходы, и важно понимать, когда какой подходит

### JSON Server

- запускает локальный REST API на основе JSON-файла
- подходит для прототипирования, разработки CRUD-интерфейсов и обучения работе с API

### Mock Service Worker (MSW)

- перехватывает запросы и возвращает заданные ответы, не требуя отдельного mock backend для каждого сценария
- особенно полезен при написании интеграционных тестов компонентов и разработке интерфейса с реалистичным сетевым взаимодействием

### Ручные моки в тестах

- например, подмена `fetch` или использование mock-функций тестового фреймворка
- подходит для проверки отдельных сценариев, но при большом количестве подмен может затруднять поддержку тестов

- главное различие: JSON Server предоставляет работающий API, MSW имитирует ответы на запросы, а ручные моки позволяют подменять конкретные зависимости

## 7. ограничения mock servers

- mock server не заменяет настоящий backend во всех аспектах, и это важный момент для собеседования
- контракт API — если mock возвращает другие поля, типы данных или структуру ответа, чем реальный backend, интеграция может сломаться после его подключения
- бизнес-логика — автоматическая обработка CRUD-операций не означает, что реализованы настоящие правила доступа, проверки прав, валидация и бизнес-ограничения
- авторизация — наличие mock-ответа с данными пользователя не доказывает, что настоящая система корректно обрабатывает токены, сессии и права доступа
- ошибки и задержки — простой сервер может отвечать слишком быстро и успешно, поэтому необходимо отдельно проверять таймауты, ошибки сети, ответы `4xx` и `5xx`, а также состояния загрузки
- состояние данных — если сервер сохраняет изменения, последующие запросы могут зависеть от предыдущих операций, что необходимо учитывать при тестировании
- CORS — frontend и mock server на разных origin могут требовать корректной настройки CORS, как и при работе с настоящим API

## 8. как это используется вместе с Redux

- если React-приложение использует Redux, архитектурный принцип остаётся прежним: mock server не зависит от того, где хранится состояние на клиенте

```
React component
      ↓
Redux async thunk
      ↓
fetch / Axios
      ↓
Mock server
      ↓
JSON response
      ↓
fulfilled / rejected action
      ↓
Redux reducer
      ↓
Updated state
      ↓
React re-render
```

- например, Redux Toolkit позволяет описать загрузку товаров через `createAsyncThunk`

```js
import { createAsyncThunk } from '@reduxjs/toolkit';

export const fetchProducts = createAsyncThunk('products/fetchProducts', async () => {
  const response = await fetch('http://localhost:3001/products');

  if (!response.ok) {
    throw new Error('Failed to fetch products');
  }

  return response.json();
});
```

- далее reducer обрабатывает `pending`, `fulfilled` и `rejected`, обновляя состояние загрузки, данные или ошибку
- mock server при этом остаётся обычным источником HTTP-ответов, а Redux отвечает за состояние приложения

## 9. что важно уметь объяснить на собеседовании

- что такое mock server — сервер, имитирующий API настоящего backend для разработки и тестирования клиента
- зачем он нужен — позволяет работать независимо от backend, получать контролируемые ответы и проверять различные сценарии
- как поднять mock API — создать JSON-файл с данными, запустить JSON Server и обращаться к созданным endpoints через `fetch` или Axios
- чем отличаются JSON Server и MSW — первый предоставляет локальный API, второй перехватывает запросы и возвращает имитированные ответы
- как использовать с React и Redux — так же, как настоящее API: отправлять запросы, обрабатывать ответы и ошибки, обновлять локальное состояние или Redux store
- какие есть ограничения — mock не гарантирует соответствие настоящему backend по бизнес-логике, авторизации, обработке ошибок и контракту API

## итог

- для базового практического опыта достаточно поднять JSON Server, создать коллекцию товаров и подключить её к React через `fetch`
- для более глубокого понимания важно различать полноценный mock API и мокирование запросов в тестах, а также понимать, что именно имитируется: данные, сетевое взаимодействие или поведение backend
