# server interaction: работа с API в React

- в этом блоке разберём, как React-приложение взаимодействует с сервером, чем отличаются `Fetch` и `Axios`, как организовать запросы в обычном React и в связке React + Redux, а также какие решения важно понимать на уровне собеседования

## 1. как React взаимодействует с сервером

- React сам по себе не выполняет HTTP-запросы и не предоставляет специального API для общения с сервером — он отвечает преимущественно за построение пользовательского интерфейса на основе состояния

- для сетевого взаимодействия используются браузерные API, сторонние библиотеки и инструменты управления состоянием

Типичный сценарий выглядит так:

1. пользователь взаимодействует с UI

- например, открывает страницу или отправляет форму

2. приложение инициирует HTTP-запрос

- Fetch, Axios или другая библиотека

3. сервер обрабатывает запрос

- проверяет права, выполняет бизнес-логику, обращается к БД

4. приложение получает ответ

- статус HTTP, заголовки, тело ответа

5. обновляется состояние UI

- данные, индикатор загрузки или сообщение об ошибке

- например, frontend отправляет `GET /api/users`, сервер возвращает JSON со списком пользователей, а React отображает полученные данные
- важно понимать, что HTTP-запрос и повторный рендер React — разные процессы: запрос получает данные извне, а обновление состояния сообщает React, что интерфейс нужно пересчитать

## 2. что происходит на уровне HTTP

- HTTP — протокол взаимодействия между клиентом и сервером, а Fetch и Axios — инструменты, позволяющие отправлять HTTP-запросы из JavaScript

Основные HTTP-методы, которые нужно знать:

- `GET` — получить данные
- `POST` — создать ресурс или инициировать операцию
- `PUT` — заменить ресурс целиком или выполнить полное обновление согласно контракту API
- `PATCH` — частично обновить ресурс
- `DELETE` — удалить ресурс

Пример запроса:

```
GET /api/users/42 HTTP/1.1
Accept: application/json
Authorization: Bearer <token>
```

- сервер может вернуть ответ со статусом `200 OK` и JSON в теле

```js
{
  "id": 42,
  "name": "Alex"
}
```

- в реальном приложении необходимо различать транспортный уровень, HTTP-статус и формат данных: сам факт получения ответа ещё не означает, что операция завершилась успешно

## 3. Fetch API

- `Fetch` — встроенный браузерный API для выполнения сетевых запросов, поэтому для его использования не нужно устанавливать дополнительные зависимости

### базовый пример

```js
async function loadFrontendUsers() {
  try {
    const response = await fetch('/api/users');

    if (!response.ok) {
      throw new Error(`HTTP error: ${response.status}`);
    }

    const users = await response.json();

    return users;
  } catch (error) {
    console.error('Failed to load users:', error);
    throw error;
  }
}
```

- `fetch()` возвращает `Promise`, который обычно разрешается объектом `Response`, когда браузер получает ответ от сервера
- `response.ok` равен `true` для HTTP-статусов в диапазоне `200–299`
- `response.json()` асинхронно читает тело ответа и преобразует JSON в JavaScript-значение — это тоже возвращает `Promise`
- `catch` обрабатывает сетевые ошибки, ошибки чтения тела и ошибки, которые мы сами выбросили, например при проверке `response.ok`

### важная особенность Fetch

- `fetch()` не отклоняет Promise автоматически при HTTP-ошибках `404`, `500` или `403`
- если сервер вернул `500 Internal Server Error`, браузер всё равно может успешно получить HTTP-ответ, поэтому Promise разрешится объектом `Response`

```js
const response = await fetch('/api/users');

console.log(response.status); // например, 500
console.log(response.ok); // false
```

- поэтому при работе с Fetch проверка `response.ok` обычно обязательна, если приложение должно считать неуспешные HTTP-статусы ошибками
- при этом сетевые ошибки — например, отсутствие соединения или некоторые ошибки CORS — приводят к отклонению Promise

### отправка данных через Fetch

```js
async function createFrontendUser(userData) {
  const response = await fetch('/api/users', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
    },
    body: JSON.stringify(userData),
  });

  if (!response.ok) {
    throw new Error(`HTTP error: ${response.status}`);
  }

  return response.json();
}
```

- `method` задаёт HTTP-метод
- `headers` передают метаданные запроса, в том числе формат тела
- `JSON.stringify()` сериализует JavaScript-объект в строку JSON, поскольку объект нельзя напрямую передать в `body` как JSON
- `Content-Type: application/json` сообщает серверу, что тело запроса содержит JSON
- отдельно нужно помнить, что не каждый успешный ответ содержит JSON: например, `204 No Content` означает, что тело ответа отсутствует, и вызывать `response.json()` в таком случае не следует

## 4. Axios

- Axios — сторонняя библиотека для HTTP-запросов, которая предоставляет более удобный интерфейс для работы с запросами, ответами, заголовками, тайм-аутами и перехватчиками

Установка:

```bash
npm install axios
```

### базовый пример

```js
import axios from 'axios';

async function loadAxiosUsers() {
  try {
    const response = await axios.get('/api/users');

    return response.data;
  } catch (error) {
    console.error('Failed to load users:', error);
    throw error;
  }
}
```

- в отличие от Fetch, Axios по умолчанию преобразует JSON-ответ в JavaScript-значение, доступное через `response.data`
- Axios автоматически отклоняет Promise для HTTP-статусов, которые не проходят его настроенный `validateStatus` — по умолчанию это статусы вне диапазона `200–299`
- в результате для стандартного сценария не нужно самостоятельно проверять `response.ok`, но всё равно нужно обрабатывать ошибки

### отправка данных через Axios

```js
async function createAxiosUser(userData) {
  const response = await axios.post('/api/users', userData);

  return response.data;
}
```

- Axios самостоятельно сериализует обычный JavaScript-объект в JSON для типичного POST-запроса и устанавливает соответствующий заголовок
- при использовании `FormData`, загрузке файлов и нестандартных форматов тела запроса правила работы с заголовками могут отличаться

### Fetch vs Axios

| Возможность    | Fetch                            | Axios                         |
| -------------- | -------------------------------- | ----------------------------- |
| Доступность    | Встроен в браузер                | Нужна зависимость             |
| JSON-ответ     | `response.json()`                | `response.data`               |
| HTTP `4xx/5xx` | Сам по себе не вызывает reject   | По умолчанию вызывает reject  |
| Тайм-аут       | Обычно через `AbortSignal`       | Есть параметр `timeout`       |
| Перехватчики   | Нужно реализовать самостоятельно | Есть interceptors             |
| Отмена запроса | `AbortController`                | Поддерживается через `signal` |

- ни Fetch, ни Axios не делают React-приложение автоматически реактивным и не управляют состоянием компонентов
- выбор зависит от требований проекта: Fetch подходит для многих задач без дополнительных зависимостей, а Axios полезен, когда нужны единая конфигурация клиента, interceptors и другие возможности библиотеки

## 5. работа с API внутри React

- в React недостаточно просто выполнить запрос — нужно связать его жизненный цикл с жизненным циклом интерфейса
- обычно приложение должно хранить как минимум три значения: данные, состояние загрузки и информацию об ошибке

### пример с useEffect

```js
import { useEffect, useState } from 'react';

function FrontendUsersPage() {
  const [users, setUsers] = useState([]);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    const controller = new AbortController();

    async function fetchUsers() {
      try {
        setIsLoading(true);
        setError(null);

        const response = await fetch('/api/users', {
          signal: controller.signal,
        });

        if (!response.ok) {
          throw new Error(`HTTP error: ${response.status}`);
        }

        const usersData = await response.json();
        setUsers(usersData);
      } catch (requestError) {
        if (requestError.name !== 'AbortError') {
          setError(requestError);
        }
      } finally {
        if (!controller.signal.aborted) {
          setIsLoading(false);
        }
      }
    }

    fetchUsers();

    return () => {
      controller.abort();
    };
  }, []);

  if (isLoading) {
    return <p>Loading users...</p>;
  }

  if (error) {
    return <p>Failed to load users: {error.message}</p>;
  }

  return (
    <ul>
      {users.map((user) => (
        <li key={user.id}>{user.name}</li>
      ))}
    </ul>
  );
}
```

- `useState` хранит состояние, которое влияет на отображение интерфейса
- `useEffect` запускает запрос после коммита компонента, а не во время самого рендеринга
- `AbortController` позволяет отменить запрос при очистке эффекта, например когда компонент размонтируется
- проверка `AbortError` нужна, чтобы обычная отмена запроса не отображалась пользователю как ошибка сервера
- `finally` выполняется после успешного завершения или ошибки, поэтому подходит для завершения состояния загрузки

### почему нельзя просто вызвать запрос при рендеринге

```js
function IncorrectUsersPage() {
  const [users, setUsers] = useState([]);

  fetch('/api/users')
    .then((response) => response.json())
    .then((usersData) => setUsers(usersData));

  return <div>{users.length}</div>;
}
```

- здесь запрос выполняется при каждом рендеринге, а `setUsers()` инициирует новый рендеринг, что может привести к бесконечному циклу запросов
- побочные эффекты должны запускаться в подходящем месте: `useEffect`, обработчике события или специализированном слое управления данными

### почему отмена запроса важна

- допустим, пользователь открывает страницу списка, затем быстро уходит с неё, а запрос ещё не завершился
- отмена помогает не тратить ресурсы на ненужную работу, хотя фактическая остановка операции на сервере не гарантируется
- при запросах, зависящих от параметров, например `userId`, важно также предотвращать ситуацию, когда более старый ответ перезаписывает результат нового запроса
- пример выше иллюстрирует базовую организацию запроса, но для сложных приложений такой код в каждом компоненте быстро становится дублирующимся, и поэтому сетевую логику обычно выносят в отдельные функции, хуки или библиотеки управления серверным состоянием

## 6. разделение API-логики и UI

- в реальном приложении не стоит помещать всю сетевую логику внутрь компонентов
- полезно разделять ответственность между компонентами интерфейса, API-клиентом и слоем управления состоянием

Например, структура проекта может выглядеть так:

```
src/
  api/
    httpClient.js
    usersApi.js
  hooks/
    useUsers.js
  components/
    UsersList.jsx
  pages/
    UsersPage.jsx
```

### API-клиент

- файл `httpClient.js` может содержать общую конфигурацию запросов

```js
import axios from 'axios';

export const frontendHttpClient = axios.create({
  baseURL: '/api',
  timeout: 10000,
  headers: {
    Accept: 'application/json',
  },
});
```

- здесь создаётся отдельный экземпляр Axios, чтобы общие настройки не приходилось повторять в каждом запросе

### функции для конкретного ресурса

```js
import { frontendHttpClient } from './httpClient.js';

export async function getFrontendUsers() {
  const response = await frontendHttpClient.get('/users');
  return response.data;
}

export async function getFrontendUserById(userId) {
  const response = await frontendHttpClient.get(`/users/${userId}`);
  return response.data;
}
```

- такой слой скрывает детали HTTP-клиента от компонентов
- если впоследствии понадобится изменить URL, формат обработки ответа или способ отправки запросов, изменения можно локализовать в API-слое
- полезно также централизованно обрабатывать общие ошибки и авторизацию, но не следует бездумно превращать HTTP-клиент в место для всей бизнес-логики приложения

## 7. React + Redux: где выполняются запросы

- Redux предназначен для управления состоянием приложения, но сам по себе не отправляет HTTP-запросы
- для асинхронной логики используется дополнительный механизм: middleware или специализированная библиотека

Основные варианты:

- Redux Thunk — позволяет выполнять асинхронную логику внутри thunk-функций, которые могут получать `dispatch` и `getState`
- Redux Saga — организует сложные асинхронные процессы с помощью генераторов и эффектов
- Redux Toolkit Query (RTK Query) — предоставляет механизм запросов, кэширования и синхронизации серверных данных, интегрированный с Redux Toolkit
- для базового понимания React + Redux достаточно уверенно объяснять Redux Thunk и понимать, какую проблему решает RTK Query

### почему нельзя отправить запрос напрямую внутри reducer

- reducer должен быть предсказуемой функцией, которая вычисляет новое состояние на основе предыдущего состояния и action
- reducer не должен выполнять HTTP-запросы, обращаться к внешним ресурсам или запускать другие побочные эффекты
- асинхронный запрос выполняется вне reducer, после чего результат передаётся в Redux через actions

Упрощённый поток:

```
компонент
   ↓
dispatch(thunk)
   ↓
HTTP-запрос
   ↓
dispatch(success / failure)
   ↓
reducer обновляет state
   ↓
React отображает новые данные
```

### пример с Redux Thunk

- сначала опишем асинхронную операцию загрузки пользователей с помощью Redux Toolkit

```js
import { createAsyncThunk, createSlice } from '@reduxjs/toolkit';

import { getFrontendUsers } from '../api/usersApi.js';

export const fetchFrontendUsers = createAsyncThunk('users/fetchUsers', async (_, { rejectWithValue }) => {
  try {
    return await getFrontendUsers();
  } catch (error) {
    return rejectWithValue(error.response?.data?.message ?? error.message);
  }
});

const frontendUsersSlice = createSlice({
  name: 'users',
  initialState: {
    items: [],
    status: 'idle',
    error: null,
  },
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchFrontendUsers.pending, (state) => {
        state.status = 'loading';
        state.error = null;
      })
      .addCase(fetchFrontendUsers.fulfilled, (state, action) => {
        state.status = 'succeeded';
        state.items = action.payload;
      })
      .addCase(fetchFrontendUsers.rejected, (state, action) => {
        state.status = 'failed';
        state.error = action.payload ?? action.error.message;
      });
  },
});

export default frontendUsersSlice.reducer;
```

- `createAsyncThunk` создаёт thunk и автоматически генерирует три типа действий: `pending`, `fulfilled` и `rejected`
- `pending` отправляется в начале выполнения, `fulfilled` — при успешном завершении, `rejected` — если операция завершилась ошибкой
- `action.payload` в `fulfilled` содержит результат, возвращённый асинхронной функцией
- `rejectWithValue` позволяет передать собственное значение ошибки в `action.payload` для `rejected`
- `extraReducers` позволяет обрабатывать действия, которые созданы вне самого slice
- синтаксис `state.items = action.payload` не означает, что Redux разрешает произвольную мутацию состояния: Redux Toolkit использует Immer, который формирует новое неизменяемое состояние на основе этих операций

### вызов из компонента

```js
import { useEffect } from 'react';
import { useDispatch, useSelector } from 'react-redux';

import { fetchFrontendUsers } from '../store/usersSlice.js';

function FrontendReduxUsersPage() {
  const dispatch = useDispatch();

  const users = useSelector((state) => state.users.items);
  const status = useSelector((state) => state.users.status);
  const error = useSelector((state) => state.users.error);

  useEffect(() => {
    if (status === 'idle') {
      dispatch(fetchFrontendUsers());
    }
  }, [dispatch, status]);

  if (status === 'loading') {
    return <p>Loading users...</p>;
  }

  if (status === 'failed') {
    return <p>{error}</p>;
  }

  return (
    <ul>
      {users.map((user) => (
        <li key={user.id}>{user.name}</li>
      ))}
    </ul>
  );
}
```

- `useDispatch()` предоставляет функцию для отправки действий в Redux
- `useSelector()` читает необходимые данные из Redux store и подписывает компонент на соответствующие изменения
- компонент запускает загрузку, а обновлением состояния занимается Redux
- пример показывает базовый паттерн, но проверка `status === 'idle'` сама по себе не обеспечивает полноценную защиту от повторных запросов во всех сценариях, например при конкурентных вызовах или размонтировании и повторном монтировании компонента

### когда использовать Redux для API-запросов

- если данные нужны разным частям приложения, а централизованное состояние уже организовано через Redux, thunk может быть подходящим решением
- если главная задача — получать серверные данные, кэшировать их, повторно использовать результаты, обрабатывать устаревшие данные и управлять повторными запросами, стоит рассмотреть RTK Query
- локальные данные формы, состояние раскрытого меню и другие UI-состояния необязательно помещать в Redux только потому, что приложение уже использует его

## 8. важные нюансы, которые часто обсуждают на собеседовании

### 8.1. CORS

- CORS (Cross-Origin Resource Sharing) — механизм браузерной безопасности, регулирующий доступ JavaScript к ответам от другого origin
- origin определяется комбинацией протокола, домена и порта, поэтому `http://localhost:3000` и `http://localhost:4000` — разные origin
- сервер должен разрешить соответствующий origin с помощью HTTP-заголовков, а некоторые запросы предварительно проверяются браузером через `OPTIONS` — preflight-запрос
- CORS не является механизмом авторизации и не заменяет серверную проверку прав доступа

### 8.2. повторные запросы и гонки данных

- если пользователь переключается между разными страницами или параметрами поиска, несколько запросов могут выполняться одновременно и завершаться не в том порядке, в котором они были отправлены
- например, запрос для поиска `re` может завершиться позже запроса для `react`, из-за чего устаревший ответ перезапишет актуальные результаты
- проблему решают отменой ненужных запросов, проверкой актуальности результата или использованием библиотеки, которая управляет такими сценариями

### 8.3. повторные запросы в React Strict Mode

- в режиме разработки React Strict Mode может повторно запускать цикл setup/cleanup эффекта, чтобы выявлять проблемы с побочными эффектами
- из-за этого в DevTools можно увидеть два запроса вместо одного
- нельзя просто отключать Strict Mode или считать, что каждый эффект гарантированно выполняется ровно один раз: нужно корректно организовать очистку эффекта, отмену запросов и обработку повторных вызовов
- повторный запуск в Strict Mode не означает, что production-приложение обязательно будет вести себя так же

### 8.4. безопасность токенов и авторизация

- токен авторизации часто передаётся в заголовке `Authorization`, но его хранение и обновление требуют отдельного рассмотрения
- хранение чувствительных токенов в `localStorage` подвергает их риску кражи при XSS-уязвимости
- `HttpOnly` cookies недоступны напрямую из JavaScript, но при cookie-аутентификации необходимо учитывать CSRF и правильно настраивать `SameSite`, `Secure` и другие атрибуты
- interceptors Axios могут централизовать добавление заголовков и обработку `401 Unauthorized`, однако они не заменяют безопасную архитектуру аутентификации на сервере

### 8.5. кэширование серверных данных

- без кэширования повторное открытие страницы может приводить к повторному запросу тех же данных
- Redux Toolkit Query, TanStack Query и SWR предоставляют механизмы кэширования, повторного использования данных, обновления и синхронизации серверного состояния
- это отдельная категория решений: Redux управляет состоянием приложения в целом, а специализированные библиотеки помогают управлять именно состоянием, полученным с сервера

## 9. как ответить на собеседовании

- как React взаимодействует с сервером?
  - React-компонент инициирует запрос через Fetch, Axios или специализированный слой, получает ответ и обновляет состояние, на основе которого React строит интерфейс
- в чём разница между Fetch и Axios?
  - Fetch встроен в браузер и требует самостоятельной проверки HTTP-статусов, а Axios предоставляет дополнительные возможности и по умолчанию отклоняет Promise при неуспешных HTTP-статусах
- как работать с API в React без Redux?
  - для простых случаев можно использовать локальное состояние и `useEffect`, для более сложных сценариев — выделить API-слой и использовать специализированные библиотеки для управления серверными данными
- как работать с API в React + Redux?
  - асинхронную логику выполняют вне reducer, например через Redux Thunk, а результат передают в Redux actions, после чего reducer обновляет состояние, доступное компонентам
- почему нельзя выполнять запрос внутри reducer?
  - reducer должен оставаться предсказуемой функцией без побочных эффектов, чтобы обновления состояния были управляемыми и воспроизводимыми
- как обрабатывать ошибки?
  - нужно различать сетевые ошибки, HTTP-ошибки, ошибки преобразования ответа и ошибки бизнес-логики, а затем отображать подходящее состояние интерфейса
- как избежать повторных и устаревших запросов?
  - нужно корректно управлять жизненным циклом запросов, отменять ненужные операции и при необходимости применять кэширование и механизмы синхронизации данных

## 10. что важно усвоить из этого блока

- Fetch и Axios отвечают за HTTP-взаимодействие, но не управляют состоянием React
- `useEffect` подходит для синхронизации компонента с внешними системами, но не является универсальным решением для всех запросов
- API-функции желательно отделять от UI, чтобы уменьшить связанность и упростить поддержку кода
- Redux Thunk позволяет выполнять асинхронную логику вне reducer, а RTK Query дополнительно решает задачи кэширования и управления серверными данными
- грамотная работа с API включает обработку ошибок, отмену запросов, защиту от гонок, авторизацию и понимание ограничений браузера
- для твоего уровня подготовки особенно важно различать серверное состояние — данные, источником истины для которых является сервер, — и клиентское состояние, например состояние модального окна или выбранной вкладки
- это различие помогает обоснованно выбирать между `useState`, Redux Toolkit и специализированными инструментами вроде TanStack Query или RTK Query, а не складывать все данные в одно глобальное хранилище
