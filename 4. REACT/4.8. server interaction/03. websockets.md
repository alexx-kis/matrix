# websockets with React

- разберём WebSocket от базовых принципов до деталей протокола, интеграции с React, управления соединением и типичных вопросов на собеседовании
- главное, что нужно понять: WebSocket — это способ поддерживать двустороннюю связь между клиентом и сервером через одно длительно существующее соединение, а React отвечает за отображение полученных данных и управление состоянием интерфейса

## 1. зачем нужны WebSocket

### обычный HTTP и его ограничения

- в стандартном HTTP-сценарии клиент обычно отправляет запрос, а сервер возвращает ответ

```
React application
       ↓  HTTP request
     Server
       ↓  HTTP response
React application
```

- например, пользователь открывает страницу с уведомлениями, и React делает запрос:

```js
const notificationsResponse = await fetch('/api/notifications');
const notificationsData = await notificationsResponse.json();
```

- сервер возвращает текущие уведомления, после чего запрос завершён
- если через секунду на сервере появляется новое уведомление, браузер сам об этом не узнает — клиенту необходимо снова запросить данные
- для некоторых приложений это нормально, но есть сценарии, где данные должны обновляться практически в реальном времени:
  - чаты и мессенджеры
  - биржевые котировки и торговые терминалы
  - совместное редактирование документов
  - онлайн-игры
  - live-уведомления и мониторинг
  - отслеживание состояния заказа или выполнения длительной задачи

### polling — простой способ получать обновления

- один из вариантов — периодически отправлять HTTP-запросы, то есть использовать polling

```js
const pollingIntervalId = setInterval(async () => {
  const pollingResponse = await fetch('/api/notifications');
  const pollingData = await pollingResponse.json();

  console.log(pollingData);
}, 3000);
```

- здесь клиент проверяет сервер каждые три секунды, даже если новых данных нет
- у polling есть несколько недостатков:
  - лишние запросы, когда данные не меняются
  - обновление может задержаться до следующего запроса
  - при большом количестве клиентов возрастает нагрузка на сервер и сеть
  - приходится отдельно управлять интервалами, ошибками и повторными запросами
- существуют и другие варианты: long polling, Server-Sent Events (SSE) и WebSocket — выбор зависит от характера взаимодействия

## 2. что такое WebSocket

- WebSocket — это протокол связи, определённый стандартом RFC 6455, который позволяет клиенту и серверу отправлять сообщения друг другу по одному соединению
- в отличие от обычной модели HTTP request-response, после установки WebSocket-соединения сервер может самостоятельно отправлять данные клиенту, а клиент — серверу, не создавая новый HTTP-запрос для каждого сообщения

```
React application                 Server
       |                             |
       |------ Connection ---------->|
       |<----- Connection ready -----|
       |                             |
       |<----- New message -----------|
       |------ User reply ---------->|
       |<----- New notification -----|
       |                             |
       |      Connection open        |
       |                             |
       |------ Close connection ---->|
```

- пока соединение открыто, обе стороны могут отправлять сообщения в любой момент
- соединение обычно сохраняется между множеством сообщений, а не устанавливается заново для каждого из них
- это особенно удобно, когда обновления приходят часто и их нужно доставлять с небольшой задержкой

### сравнение основных подходов

| Подход    | Направление данных                    | Особенности                                    |
| --------- | ------------------------------------- | ---------------------------------------------- |
| HTTP      | Обычно запрос клиента → ответ сервера | Хорошо подходит для обычных API                |
| Polling   | Клиент периодически проверяет сервер  | Просто реализовать, но есть лишние запросы     |
| SSE       | Сервер → клиент                       | Поток обновлений поверх HTTP                   |
| WebSocket | Клиент ↔ сервер                       | Двусторонний обмен через постоянное соединение |

- важно не путать WebSocket с конкретной библиотекой: это протокол, а не React API и не отдельный серверный фреймворк

## 3. как работает WebSocket внутри

- чтобы уверенно объяснять WebSocket на собеседовании, нужно понимать не только то, как вызвать `new WebSocket()`, но и то, как устанавливается соединение и передаются данные

### 3.1. установка соединения — handshake

- в браузере соединение обычно создаётся с помощью стандартного WebSocket API:

```js
const notificationsSocket = new WebSocket('wss://example.com/ws');
```

- адрес начинается с `ws://` или `wss://`, а не с `http://` или `https://`
  - `ws://` — незашифрованное WebSocket-соединение
  - `wss://` — WebSocket поверх TLS, то есть защищённое соединение, аналогичное HTTPS по принципу шифрования транспорта
- при создании соединения браузер начинает процесс установки связи с сервером
- классический WebSocket handshake поверх HTTP/1.1 начинается с HTTP-запроса, в котором клиент просит переключить протокол на WebSocket

Упрощённый пример запроса:

```
GET /ws HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
```

- ключевые заголовки здесь следующие:
  - `Upgrade: websocket` — запрос на переключение протокола
  - `Connection: Upgrade` — указывает на необходимость обновления соединения
  - `Sec-WebSocket-Key` — случайное значение, используемое в процедуре подтверждения handshake
  - `Sec-WebSocket-Version: 13` — версия протокола WebSocket, используемая стандартным браузерным API
- если сервер поддерживает WebSocket и принимает запрос, он возвращает ответ с кодом `101 Switching Protocols`

```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: ...
```

- после успешного handshake стороны начинают обмениваться WebSocket-кадрами, а соединение остаётся открытым до закрытия одной из сторон, сетевого сбоя или другого события, приводящего к разрыву
- в современных системах также встречаются HTTP/2 и HTTP/3, где установление WebSocket использует другие механизмы, поэтому описанный выше handshake относится именно к классическому варианту HTTP/1.1

### 3.2. как передаются сообщения

- после handshake данные передаются в виде кадров — frames
- кадр является единицей передачи протокола, а сообщение — логической единицей данных, которую приложение отправляет или получает
- одно сообщение может состоять из одного кадра или нескольких фрагментированных кадров
- WebSocket поддерживает два основных типа данных приложения:
  - текстовые сообщения, обычно содержащие JSON
  - бинарные сообщения, например `ArrayBuffer` или `Blob`

Пример передачи сообщения:

```js
const chatSocket = new WebSocket('wss://example.com/chat');

chatSocket.addEventListener('open', () => {
  chatSocket.send(
    JSON.stringify({
      type: 'message',
      text: 'Hello, server!',
    }),
  );
});
```

- `send()` отправляет данные по уже установленному соединению, но сам по себе не означает, что сервер получил, обработал или сохранил сообщение
- если приложению важно подтвердить доставку на уровне бизнес-логики, сервер должен прислать отдельное подтверждение, например с идентификатором сообщения
- протокол также использует служебные кадры:
  - `Ping` и `Pong` — механизмы проверки активности соединения
  - `Close` — механизм закрытия соединения
- в браузерном WebSocket API нельзя напрямую отправлять `Ping` и `Pong` кадры: это низкоуровневые механизмы протокола, которыми обычно управляет реализация WebSocket или серверная библиотека

### 3.3. закрытие соединения

- WebSocket-соединение имеет несколько состояний, доступных через `readyState`

```
WebSocket.CONNECTING; // 0
WebSocket.OPEN;       // 1
WebSocket.CLOSING;    // 2
WebSocket.CLOSED;     // 3
```

- состояние можно проверять перед отправкой данных:

```js
if (chatSocket.readyState === WebSocket.OPEN) {
  chatSocket.send(
    JSON.stringify({
      type: 'ping',
    }),
  );
}
```

- при штатном закрытии сторона может отправить close frame, после чего стороны завершают соединение
- в браузере для инициирования закрытия используется `close()`

```js
chatSocket.close(1000, 'Normal closure');
```

- код `1000` означает штатное завершение, а код и текст причины могут быть доступны в событии `close`
- если сеть оборвалась, сервер стал недоступен или соединение было прервано промежуточным устройством, клиент может получить событие `close` без возможности провести полноценное штатное закрытие

### 3.4. почему WebSocket не гарантирует доставку бизнес-сообщения

- WebSocket обеспечивает упорядоченную передачу данных в рамках работающего соединения, опираясь на транспорт TCP, но не гарантирует, что приложение на сервере обработало сообщение
- например, клиент вызывает `send()`, после чего соединение обрывается
- клиент может не знать, успел ли сервер обработать сообщение до разрыва
- если повторить отправку без дополнительной логики, сервер может обработать одну и ту же операцию дважды
- в важных сценариях поверх WebSocket реализуют прикладной протокол:
  - уникальные идентификаторы сообщений
  - подтверждения обработки — acknowledgements
  - повторную отправку после восстановления соединения
  - дедупликацию повторных сообщений
  - хранение истории или возможность восстановить пропущенные события
- это особенно важно для чатов, финансовых операций и других систем, где потеря или повторная обработка события имеет значение

## 4. что требуется для WebSocket в React

- отдельного React API для WebSocket не существует: можно использовать встроенный браузерный объект `WebSocket`
- задача React — организовать жизненный цикл соединения и согласовать получаемые сообщения с состоянием интерфейса

Обычно нужно решить пять задач:

- создать соединение в подходящий момент
- подписаться на события `open`, `message`, `error` и `close`
- обновлять состояние React при получении данных
- корректно удалять обработчики и закрывать соединение
- обрабатывать разрыв связи и восстановление соединения, если это необходимо

### 4.1. простой пример на React

- рассмотрим компонент чата, который устанавливает соединение при монтировании и закрывает его при размонтировании

```js
import { useEffect, useState } from 'react';

export function ChatPanel() {
  const [chatMessages, setChatMessages] = useState([]);
  const [chatConnectionStatus, setChatConnectionStatus] = useState('connecting');

  useEffect(() => {
    const socket = new WebSocket('wss://example.com/chat');

    function handleOpen() {
      setChatConnectionStatus('connected');
    }

    function handleMessage(event) {
      try {
        const incomingMessage = JSON.parse(event.data);

        setChatMessages((previousMessages) => [...previousMessages, incomingMessage]);
      } catch {
        console.error('Received an invalid JSON message');
      }
    }

    function handleError() {
      setChatConnectionStatus('error');
    }

    function handleClose() {
      setChatConnectionStatus('disconnected');
    }

    socket.addEventListener('open', handleOpen);
    socket.addEventListener('message', handleMessage);
    socket.addEventListener('error', handleError);
    socket.addEventListener('close', handleClose);

    return () => {
      socket.removeEventListener('open', handleOpen);
      socket.removeEventListener('message', handleMessage);
      socket.removeEventListener('error', handleError);
      socket.removeEventListener('close', handleClose);

      socket.close();
    };
  }, []);

  return (
    <section>
      <p>Connection: {chatConnectionStatus}</p>

      <ul>
        {chatMessages.map((chatMessage) => (
          <li key={chatMessage.id}>{chatMessage.text}</li>
        ))}
      </ul>
    </section>
  );
}
```

- адрес сервера здесь демонстрационный, поэтому для запуска примера нужен реально работающий WebSocket endpoint, который принимает и отправляет сообщения ожидаемого формата

### 4.2. разбор ключевых частей

- `useEffect` используется потому, что создание сетевого соединения — внешний побочный эффект, который не следует выполнять непосредственно во время рендера компонента
- пустой массив зависимостей означает, что эффект запускается после первоначального монтирования, а cleanup вызывается при размонтировании; в режиме разработки с `StrictMode` React может дополнительно выполнить цикл setup → cleanup → setup для проверки корректности эффекта
- `new WebSocket()` создаёт отдельное соединение, которое существует независимо от рендеров React
- `addEventListener('message', ...)` подписывает компонент на входящие сообщения
- `JSON.parse(event.data)` преобразует текстовое JSON-сообщение в JavaScript-объект, но требует обработки некорректного формата
- `setChatMessages(previousMessages => ...)` использует функциональное обновление состояния, чтобы добавить сообщение к актуальному массиву, а не к значению, захваченному замыканием
- возвращаемая функция `useEffect` удаляет обработчики и закрывает соединение, предотвращая работу старых подписок после размонтирования
- при этом `error` не обязательно означает, что соединение уже окончательно закрыто: для определения фактического завершения соединения важен также `close`
- в реальном приложении статус соединения, повторные подключения и обработка ошибок обычно требуют более продуманной модели, чем четыре строковых значения

## 5. как отправлять сообщения из React

- получение данных — только половина задачи, поэтому добавим отправку сообщения от пользователя к серверу
- здесь важно, чтобы обработчик отправки имел доступ к актуальному WebSocket-соединению, но при этом не вызывал лишние рендеры
- для хранения изменяемого объекта соединения без необходимости перерисовывать компонент обычно подходит `useRef`

```js
import { useEffect, useRef, useState } from 'react';

export function ChatComposer() {
  const composerSocketRef = useRef(null);
  const [composerText, setComposerText] = useState('');
  const [composerStatus, setComposerStatus] = useState('connecting');

  useEffect(() => {
    const socket = new WebSocket('wss://example.com/chat');
    composerSocketRef.current = socket;

    function handleOpen() {
      setComposerStatus('connected');
    }

    function handleClose() {
      setComposerStatus('disconnected');
    }

    socket.addEventListener('open', handleOpen);
    socket.addEventListener('close', handleClose);

    return () => {
      socket.removeEventListener('open', handleOpen);
      socket.removeEventListener('close', handleClose);

      if (composerSocketRef.current === socket) {
        composerSocketRef.current = null;
      }

      socket.close();
    };
  }, []);

  function handleSubmit(event) {
    event.preventDefault();

    const socket = composerSocketRef.current;

    if (!socket || socket.readyState !== WebSocket.OPEN) {
      return;
    }

    const outgoingMessage = {
      type: 'chat-message',
      text: composerText,
      id: crypto.randomUUID(),
    };

    socket.send(JSON.stringify(outgoingMessage));
    setComposerText('');
  }

  return (
    <form onSubmit={handleSubmit}>
      <p>Connection: {composerStatus}</p>

      <input value={composerText} onChange={(event) => setComposerText(event.target.value)} />

      <button type='submit' disabled={composerStatus !== 'connected' || !composerText.trim()}>
        Send
      </button>
    </form>
  );
}
```

- этот пример показывает базовый механизм, но не полноценный протокол чата: идентификатор сообщения нужно использовать для подтверждения, дедупликации и согласования отправленных и сохранённых сообщений на сервере

### почему здесь нужен `useRef`, а не `useState`

- `useRef` хранит значение между рендерами и позволяет изменить `ref.current` без запуска нового рендера
- объект WebSocket сам по себе не является состоянием интерфейса, поэтому обычно его не хранят в `useState`
- статус соединения, список сообщений и другие данные, влияющие на JSX, напротив, хранят в `useState` или в другом хранилище состояния
- распространённая ошибка — хранить только WebSocket в локальной переменной компонента вне эффекта: при каждом рендере такая переменная может создаваться заново, и управление соединением становится ненадёжным
- другая ошибка — проверять `readyState` только в момент рендера и считать, что он останется таким же до отправки: состояние соединения может измениться между этими моментами, поэтому проверка непосредственно перед `send()` необходима

## 6. повторное подключение — reconnection

- соединение WebSocket не гарантированно работает бесконечно
- его могут оборвать из-за потери сети, перезапуска сервера, таймаута прокси, переключения сети на мобильном устройстве или закрытия вкладки
- после закрытия соединения браузерный объект `WebSocket` не подключается заново автоматически
- если приложению необходимо продолжать получать обновления, повторное подключение нужно реализовать самостоятельно либо использовать библиотеку

### как организовать reconnection

- типичная стратегия выглядит так:

```
Connecting
    ↓
Connected
    ↓ connection lost
Waiting before retry
    ↓
Connecting again
    |
    └----> Connected
    |
    └----> Waiting before retry
```

- обычно используют следующие механизмы:
  - повторные попытки подключения после ошибки или закрытия
  - увеличивающуюся задержку между попытками — exponential backoff
  - случайное отклонение задержки — jitter, чтобы множество клиентов не пытались подключиться одновременно
  - максимальный интервал или ограничение числа попыток, если этого требует сценарий
  - восстановление подписок и состояния после подключения
- например, при exponential backoff задержка может увеличиваться примерно так: `1s → 2s → 4s → 8s → 16s`
- на практике задержку ограничивают сверху и часто добавляют случайный компонент
- важно: успешное повторное подключение не означает, что клиент получил все события, пропущенные во время разрыва
- если сервер хранит историю событий, клиент может передать последний обработанный идентификатор и запросить пропущенные данные
- если история не поддерживается, приложению может потребоваться заново загрузить актуальное состояние через HTTP API

### минимальный пример повторного подключения

- следующий пример демонстрирует базовую идею, но не заменяет полноценную реализацию с backoff, jitter и восстановлением состояния

```js
let retrySocket = null;
let retryTimer = null;
let retryAttempt = 0;
let retryStopped = false;

function connectRetrySocket() {
  if (retryStopped) return;

  retrySocket = new WebSocket('wss://example.com/events');

  retrySocket.addEventListener('open', () => {
    retryAttempt = 0;
  });

  retrySocket.addEventListener('close', () => {
    if (retryStopped) return;

    const retryDelay = Math.min(1000 * 2 ** retryAttempt, 30000);
    retryAttempt += 1;

    retryTimer = setTimeout(connectRetrySocket, retryDelay);
  });
}

function stopRetrySocket() {
  retryStopped = true;
  clearTimeout(retryTimer);
  retrySocket?.close();
}
```

- в React такой код нельзя бездумно размещать на уровне модуля, если он должен управляться конкретным компонентом: несколько экземпляров компонента будут совместно использовать переменные
- обычно логику переподключения инкапсулируют в custom hook, отдельный менеджер соединений или библиотеку, а при завершении работы отменяют таймеры и закрывают соединение
- приведённая реализация также не учитывает повторное закрытие во время подключения, обработку `error`, подтверждение пользовательских операций и восстановление пропущенных событий

## 7. использование WebSocket с Redux

- в приложении с Redux часто возникает вопрос: где именно должно жить соединение
- важное различие: WebSocket — это внешний ресурс, а Redux — средство управления состоянием приложения
- объект соединения не стоит помещать в Redux store, потому что он является изменяемым объектом с обработчиками событий и не относится к сериализуемому состоянию интерфейса
- в store, напротив, удобно помещать данные, которые приходят через соединение:

```
{
  chat: {
    messages: [],
    connectionStatus: 'connected',
  },
}
```

- распространённая архитектура выглядит так:

```
WebSocket server
       ↓
WebSocket connection manager
       ↓ incoming message
Redux action
       ↓
Reducer / Redux Toolkit slice
       ↓
React components
```

- менеджер соединения принимает сообщение, проверяет его формат и отправляет соответствующий Redux action
- reducer обновляет состояние, после чего компоненты, подписанные через `useSelector`, получают новые данные
- для исходящих сообщений React-компонент может отправлять action, а middleware или отдельный сервис — передавать сообщение через WebSocket
- например, Redux middleware может обрабатывать action `chat/messageRequested`, проверять готовность соединения и вызывать `socket.send()`
- в Redux Toolkit для асинхронных операций также можно применять listener middleware или собственный middleware, если это соответствует архитектуре приложения
- не следует помещать всю работу с WebSocket в reducer: reducers должны оставаться предсказуемыми функциями, которые вычисляют новое состояние, а не создают сетевые соединения или подписки

## 9. важные нюансы и типичные ошибки

### 9.1. React Strict Mode

- в React Strict Mode в режиме разработки эффекты могут проходить дополнительный цикл создания и очистки
- если cleanup не закрывает соединение или не удаляет обработчики, могут появляться дублирующиеся подключения и повторная обработка сообщений
- правильный эффект должен быть безопасен для последовательности `setup → cleanup → setup`

### 9.2. повторная регистрация обработчиков

- если при каждом рендере создавать новое соединение или подписываться на сообщения без соответствующей очистки, приложение может обрабатывать одно сообщение несколько раз
- обычно соединение создают внутри эффекта, а подписки удаляют в cleanup

### 9.3. устаревшие значения в замыканиях

- обработчик WebSocket может сохранять значения состояния, которые были актуальны на момент создания обработчика
- для обновления накопительных данных часто помогает функциональная форма `setState`, как в примере с сообщениями
- для более сложной логики используют `useRef`, актуальные callbacks или библиотеки, которые предоставляют соответствующие механизмы

### 9.4. слишком частые обновления React

- если сервер отправляет сотни сообщений в секунду, обновление состояния при каждом сообщении может вызвать заметную нагрузку на рендеринг
- в зависимости от задачи можно объединять сообщения в пакеты, буферизовать обновления, ограничивать частоту обновления интерфейса или хранить высокочастотные данные вне React state
- для финансовых графиков и телеметрии это особенно актуально

### 9.5. потеря соединения и heartbeat

- некоторые серверы и промежуточные сетевые устройства закрывают простаивающие соединения
- на серверной стороне часто используют heartbeat с `Ping`/`Pong` или прикладными сообщениями, чтобы обнаруживать неактивных клиентов
- браузерный API не предоставляет прямого управления протокольными `Ping`/`Pong` кадрами, поэтому обычно heartbeat реализуется на сервере, а при необходимости — дополнительным прикладным протоколом

### 9.6. безопасность

- в браузерном приложении следует предпочитать `wss://`, чтобы трафик был зашифрован
- сервер должен проверять авторизацию и права пользователя, а не считать сам факт установленного соединения доказательством доступа ко всем данным
- необходимо учитывать проверку `Origin`, ограничения частоты сообщений, размеры входящих сообщений и валидацию их структуры
- аутентификацию нужно продумывать с учётом ограничений браузерного API: конструктор `WebSocket` не позволяет произвольно задавать HTTP-заголовки, например `Authorization`
- часто используют защищённые cookie, проверку сессии при handshake или предусмотренный сервером механизм авторизации после подключения
- нельзя доверять данным от клиента только потому, что они пришли через WebSocket: все входящие сообщения должны проверяться на сервере

## 10. WebSocket vs SSE: что выбрать

- на собеседовании могут спросить, зачем использовать WebSocket, если существует Server-Sent Events (SSE)

- SSE подходит, когда сервер должен передавать обновления клиенту, но клиенту не нужен полноценный двусторонний канал
- WebSocket подходит, когда обе стороны активно отправляют сообщения: например, в чате, игре или совместном редактировании

* например, для уведомлений о завершении фоновой задачи SSE может быть проще, тогда как для чата с сообщениями в обе стороны естественным выбором часто становится WebSocket
* при этом WebSocket не является автоматически лучшим решением для любого real-time приложения: нужно учитывать частоту событий, требования к задержке, масштабирование серверной части и восстановление состояния

## 11. что нужно уметь рассказать на собеседовании

- что такое WebSocket — протокол двусторонней связи, который позволяет клиенту и серверу обмениваться сообщениями по одному длительно существующему соединению
- чем отличается от HTTP — обычный HTTP чаще работает по модели запрос-ответ, тогда как WebSocket после handshake поддерживает обмен данными в обе стороны без отдельного HTTP-запроса на каждое сообщение
- как устанавливается соединение — браузер инициирует handshake, сервер подтверждает переход на WebSocket, после чего стороны обмениваются кадрами
- как использовать в React — создать соединение в `useEffect`, подписаться на события, хранить данные интерфейса в состоянии и закрывать соединение в cleanup
- зачем нужен `useRef` — для хранения экземпляра WebSocket между рендерами без лишних перерисовок
- что делать при разрыве связи — реализовать переподключение с задержкой, корректно обрабатывать ошибки и при необходимости восстанавливать пропущенные события
- как работать с Redux — передавать входящие сообщения в Redux actions, хранить данные в store, а соединение и сетевые эффекты держать вне reducers
- когда нужна библиотека — когда требуются удобная интеграция с React, переподключение, комнаты, события или другие дополнительные механизмы
- какие есть ограничения — соединение может оборваться, `send()` не гарантирует обработку сообщения сервером, а пропущенные события нужно восстанавливать на уровне приложения
