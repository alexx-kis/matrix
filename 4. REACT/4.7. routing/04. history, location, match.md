# history, location, match в React Router

- в этом блоке разберём три объекта, через которые React Router связывает URL, историю браузера и состояние маршрутизации: `history`, `location` и `match`
- основное внимание уделим классическому API React Router v4/v5, поскольку в твоём плане используются `Switch`, `Redirect` и `match` в их привычном виде, а затем сравним его с современным React Router v6/v7

## 1. базовая модель: что происходит при переходе по маршруту

- прежде чем разбирать отдельные объекты, важно понимать, что маршрутизация в SPA — это не то же самое, что обычная навигация браузера

- при классической навигации браузер запрашивает новый документ у сервера, получает HTML и загружает страницу

- при клиентской маршрутизации React-приложение обычно остаётся загруженным, а библиотека меняет URL, определяет соответствующий маршрут и обновляет отображаемый интерфейс

```
         [действие пользователя]
     например, клик по ссылке `/users/42`
                     ↓
                 [history]
  управляет переходом и историей навигации
                     ↓
                 [location]
     описывает текущий URL и его части
                     ↓
                  [match]
описывает соответствие URL конкретному маршруту
                     ↓
    [React отображает нужный компонент]
  например, страницу пользователя с ID 42
```

- схема упрощённая: `history` не обязан непосредственно вызывать `match`, а `location` не запускает сопоставление самостоятельно — это взаимодействующие части маршрутизатора

## 2. `history` — управление историей навигации

- `history` в React Router v4/v5 — это объект, предоставляющий API для управления навигацией приложения и связанный с механизмами истории браузера
- он позволяет переходить на другие URL программно, возвращаться назад, переходить вперёд и подписываться на изменения навигации

### зачем нужен `history`

- представь, что после успешного входа пользователя нужно перенаправить на страницу профиля
- можно использовать обычный механизм браузера, но присваивание `window.location.href` обычно инициирует полноценную навигацию и перезагрузку документа
- через `history.push()` можно изменить адрес и выполнить клиентский переход без полной перезагрузки страницы

```js
function LoginPage({ history }) {
  function handleLogin() {
    // здесь предполагается, что авторизация уже прошла успешно
    history.push('/profile');
  }

  return <button onClick={handleLogin}>Войти</button>;
}
```

- в этом примере `history` передаётся в компонент через props, как это обычно происходило с компонентами, обёрнутыми в `withRouter`, или с компонентами маршрутов в React Router v5

### основные методы `history`

| Метод                      | Назначение                                         |
| -------------------------- | -------------------------------------------------- |
| `history.push(path)`       | перейти по новому адресу, добавив запись в историю |
| `history.replace(path)`    | заменить текущую запись истории                    |
| `history.go(n)`            | перейти на `n` записей вперёд или назад            |
| `history.goBack()`         | перейти на одну запись назад                       |
| `history.goForward()`      | перейти на одну запись вперёд                      |
| `history.listen(callback)` | подписаться на изменения навигации                 |

- различие между `push` и `replace` особенно важно для понимания поведения кнопки «Назад»

`push('/profile')`

`/home` → `/profile`

- предыдущий адрес сохраняется, поэтому пользователь может вернуться к `/home`

`replace('/profile')`

`/profile` вместо `/home`

- текущая запись заменяется, поэтому кнопка «Назад» не возвращает к заменённой записи `/home`

- `push` обычно используют для обычной навигации, когда переход должен отражаться в истории
- `replace` удобен, например, при перенаправлении после входа, если возвращение на предыдущий адрес нежелательно

### как `history` связан с браузером

- в браузере есть нативный объект `window.history`, а в React Router v4/v5 объект `history` обычно представляет собой библиотечную абстракцию над историей браузера
- эта абстракция также позволяет маршрутизатору отслеживать изменения и обновлять React-интерфейс
- например, вызов `window.history.pushState()` меняет URL и добавляет запись в историю, но сам по себе не вызывает событие `popstate`
- поэтому прямое использование `window.history.pushState()` не уведомляет React Router так, как ожидается при навигации через его собственный API

```js
// нативный API браузера
window.history.pushState({}, '', '/profile');

// URL изменился, но событие popstate не возникает
// React Router не обязан обновить интерфейс в ответ на этот вызов
```

- если же вызвать `history.push('/profile')` у объекта маршрутизатора, библиотека сама организует уведомление подписчиков и обновление маршрутизации

## 3. `location` — описание текущего URL

- `location` — объект, описывающий текущий адрес, с которым работает маршрутизатор
- он нужен, чтобы получить путь, query-параметры, hash и дополнительное состояние навигации

### структура `location`

- допустим, пользователь находится по адресу:

```js
https://example.com/users/42?tab=posts&sort=latest#comments
```

- в React Router v4/v5 объект `location` может содержать следующие свойства:

```js
const routerLocation = {
  pathname: '/users/42',
  search: '?tab=posts&sort=latest',
  hash: '#comments',
  state: undefined,
  key: 'abc123',
};
```

- здесь `key` условный, а `state` может содержать переданные при навигации данные
- `pathname` — путь без query-параметров и hash
- `search` — строка query-параметров, включая начальный `?`
- `hash` — фрагмент URL, включая начальный `#`
- `state` — дополнительные данные, переданные при навигации
- `key` — идентификатор записи location, если он поддерживается и задан используемым history-адаптером

### как читать query-параметры

- `location.search` содержит обычную строку, а не готовый объект с параметрами
- для разбора строки удобно использовать нативный `URLSearchParams`

```js
const usersSearchParams = new URLSearchParams('?tab=posts&sort=latest');

const usersActiveTab = usersSearchParams.get('tab');
const usersSortOrder = usersSearchParams.get('sort');

console.log(usersActiveTab); // 'posts'
console.log(usersSortOrder); // 'latest'
```

- это полезно, когда интерфейс зависит от параметров URL: выбранной вкладки, фильтров, сортировки или поискового запроса

### `location.state`: данные между страницами

- иногда нужно передать информацию при переходе, не кодируя её в URL
- например, со страницы списка можно перейти к деталям пользователя и передать информацию об источнике перехода

```js
import { Link } from 'react-router-dom';

function UsersListPage() {
  return (
    <Link
      to={{
        pathname: '/users/42',
        state: {
          from: 'users-list',
        },
      }}
    >
      Открыть пользователя
    </Link>
  );
}
```

- в React Router v5 на целевой странице это состояние доступно через `location.state`

```js
function UserDetailsPage({ location }) {
  const usersNavigationSource = location.state?.from;

  return <p>Источник перехода: {usersNavigationSource ?? 'неизвестен'}</p>;
}
```

- важно: `location.state` не является частью видимого URL и не предназначен для хранения данных, которые обязаны быть доступны при открытии ссылки напрямую
- если пользователь скопирует URL и откроет его в новой вкладке, переданное состояние может отсутствовать
- не следует хранить в `location.state` секреты или данные, безопасность которых зависит от их скрытости

### как `location` обновляется

- при переходе через `history.push()` или `history.replace()` маршрутизатор получает новый `location`
- React Router использует его для определения активного маршрута и обновления интерфейса
- при навигации кнопками браузера назад и вперёд адрес тоже меняется, и маршрутизатор должен отреагировать на это изменение
- в React Router v5 объект `location` обычно доступен через props компонента маршрута либо через `useLocation()`

```js
import { useLocation } from 'react-router-dom';

function CurrentAddress() {
  const currentAddress = useLocation();

  return <p>Текущий путь: {currentAddress.pathname}</p>;
}
```

- `useLocation()` возвращает текущий объект `location` из контекста маршрутизатора и позволяет компоненту реагировать на его обновления

## 4. `match` — результат сопоставления маршрута с URL

- `match` описывает, как текущий URL соответствует определённому шаблону маршрута
- он особенно важен для динамических маршрутов, в которых часть URL является параметром
- например, есть маршрут `/users/:userId` и адрес `/users/42`
- `:userId` — параметр шаблона, а `42` — его фактическое значение

```js
<Route path='/users/:userId' component={UserDetailsPage} />
```

- если текущий URL равен `/users/42`, маршрутизатор сопоставляет его с шаблоном и формирует объект `match`, примерно такой:

```js
const usersRouteMatch = {
  path: '/users/:userId',
  url: '/users/42',
  isExact: true,
  params: {
    userId: '42',
  },
};
```

- это иллюстративный объект для данного маршрута; значения `path`, `url` и `isExact` зависят от конкретного совпадения

### свойства `match`

- `params` — значения динамических параметров, извлечённых из URL
- `path` — шаблон маршрута, по которому произошло сопоставление
- `url` — часть URL, соответствующая маршруту
- `isExact` — в React Router v5 показывает, совпал ли путь целиком, без дополнительных сегментов в конце
- главное назначение `match` — не просто сообщить, что маршрут подошёл, а предоставить данные, необходимые для работы с ним

### практический пример

```js
function UserDetailsPage({ match }) {
  const usersCurrentId = match.params.userId;

  return <h1>Пользователь: {usersCurrentId}</h1>;
}
```

- при переходе на `/users/42` компонент получит `userId` со значением `'42'`
- при переходе на `/users/108` тот же компонент получит `'108'`
- благодаря этому один компонент обслуживает множество URL, вместо создания отдельной страницы для каждого пользователя
- обрати внимание: параметры маршрута обычно являются строками, даже если выглядят как числа
- если приложению необходимо числовое значение, его нужно преобразовать и при необходимости проверить

```js
const usersNumericId = Number(usersRouteMatch.params.userId);
```

- при реальном использовании преобразование следует выполнять над параметром, полученным из текущего `match`, и учитывать возможность некорректного значения

### вложенные маршруты и `match`

- `match` также помогает определять относительный путь внутри вложенных маршрутов
- например, маршрут `/users/:userId` может содержать дочерние страницы `/posts` и `/settings`
- `match.url` можно использовать как основу для формирования ссылки, а `match.path` — для построения шаблона дочернего маршрута

```js
function UserSectionPage({ match }) {
  return (
    <>
      <Link to={`${match.url}/posts`}>Посты</Link>

      <Route path={`${match.path}/posts`} component={UserPostsPage} />
    </>
  );
}
```

- если `match.url` равен `/users/42`, ссылка ведёт на `/users/42/posts`
- если `match.path` равен `/users/:userId`, шаблон дочернего маршрута будет `/users/:userId/posts`
- это различие принципиально: `url` содержит конкретные значения, а `path` сохраняет шаблон параметров
- в больших приложениях нужно внимательно следить за тем, как вычисляются `match.url` и `match.path`, чтобы не дублировать сегменты и не создавать ошибочные вложенные пути

## 5. чем отличаются `history`, `location` и `match`

- эти три сущности связаны между собой, но решают разные задачи

### `history` — действие

- отвечает на вопрос: «как перейти на другой URL или вернуться назад?»
- примеры: `push()`, `replace()`, `goBack()`

### `location` — текущее состояние адреса

- отвечает на вопрос: «какой URL сейчас открыт и какие данные в нём содержатся?»
- примеры: `pathname`, `search`, `hash`, `state`

### `match` — результат сопоставления

- отвечает на вопрос: «какому маршруту соответствует URL и какие параметры извлечены?»
- примеры: `params`, `path`, `url`, `isExact`

* рассмотрим один сценарий: пользователь открывает `/users/42?tab=posts`
* `history` обеспечивает навигацию к этому адресу
* `location.pathname` содержит `/users/42`, а `location.search` — `?tab=posts`
* `match.params.userId` содержит `'42'`, если URL сопоставлен с маршрутом `/users/:userId`
* приложение отображает страницу пользователя с ID `42` и может выбрать вкладку постов по query-параметру

## 6. чем отличаются от нативной реализации браузера

- в первую очередь нужно различать нативные Web API и абстракции React Router

### `window.history` и router `history`

- нативный `window.history` предоставляет методы `pushState()`, `replaceState()`, `back()`, `forward()` и `go()`
- объект `history` из React Router v5 предоставляет API навигации, совместимый с внутренним механизмом маршрутизатора
- главная разница в том, что браузер сам по себе не знает, какой React-компонент должен соответствовать URL
- React Router отслеживает навигацию, сопоставляет URL с маршрутами и обеспечивает обновление интерфейса

### `window.location` и router `location`

- `window.location` — нативный объект браузера, содержащий URL текущего документа
- `location` из React Router — объект, описывающий текущее состояние маршрутизации
- например, `window.location.pathname` и `useLocation().pathname` могут содержать одинаковый путь, но это не означает, что объекты взаимозаменяемы
- у нативного `window.location` есть дополнительные свойства и методы для работы с URL и навигацией, а React Router предоставляет собственный объект для отслеживания состояния маршрута
- при присваивании `window.location.href` обычно происходит переход браузера к новому документу
- при клиентской навигации через React Router приложение обычно не перезагружается

### `match` и нативный браузер

- у браузера нет встроенного объекта `match`, который автоматически определяет соответствие URL шаблону React-маршрута
- сопоставление с `/users/:userId` выполняет маршрутизатор
- в обычном JavaScript аналогичную задачу можно решить вручную с помощью регулярных выражений, разбора URL или собственной логики маршрутизации
- например, браузер знает, что текущий путь — `/users/42`, но сам по себе не знает, что `42` является параметром `userId` в шаблоне `/users/:userId`

## 7. как это изменилось в React Router v6 и v7

- поскольку API менялся между версиями, важно не переносить примеры из v5 в современный проект без проверки

| React Router v5             | React Router v6/v7                                                 |
| --------------------------- | ------------------------------------------------------------------ |
| `history.push('/users')`    | `useNavigate()` и `navigate('/users')`                             |
| `history.replace('/users')` | `navigate('/users', { replace: true })`                            |
| `useHistory()`              | `useNavigate()`                                                    |
| `match.params`              | `useParams()`                                                      |
| `match.url` и `match.path`  | зависит от задачи; используются относительные маршруты и новые API |
| `useLocation()`             | `useLocation()`                                                    |

- в v6 библиотека отказалась от прежнего публичного подхода `useHistory()` и передачи привычного объекта `history` в props маршрута
- вместо него для навигации используется `useNavigate()`, а параметры маршрута можно получать через `useParams()`

```js
import { useLocation, useNavigate, useParams } from 'react-router-dom';

function ModernUserPage() {
  const modernNavigate = useNavigate();
  const modernLocation = useLocation();
  const modernParams = useParams();

  function goToProfile() {
    modernNavigate('/profile');
  }

  return (
    <>
      <h1>Пользователь: {modernParams.userId}</h1>
      <p>Путь: {modernLocation.pathname}</p>

      <button onClick={goToProfile}>Перейти в профиль</button>
    </>
  );
}
```

- этот пример предполагает, что компонент находится внутри маршрута с параметром `:userId` и внутри контекста маршрутизатора
- `useParams()` возвращает параметры активного маршрута, `useLocation()` — текущий объект адреса, а `useNavigate()` — функцию программной навигации
- в v6/v7 объект `match` всё ещё встречается в отдельных API, например в `useMatch()` и данных сопоставления маршрутов, но привычные props `match`, `history` и `location` из v5 больше не являются стандартным способом получения этих данных

## 8. что важно уметь объяснить на собеседовании

- `history` — механизм управления навигацией, позволяющий добавлять или заменять записи истории и реагировать на переходы
- `location` — объект, описывающий текущий адрес: путь, query-параметры, hash и, при наличии, состояние навигации
- `match` — результат сопоставления URL с шаблоном маршрута, содержащий параметры и информацию о совпадении
- отличие от нативных API — браузер предоставляет механизмы работы с URL и историей документов, а React Router использует их для организации клиентской маршрутизации и связи URL с React-компонентами
- разница версий — в v5 активно использовались `history` и `match` через props и хуки, тогда как в v6/v7 основной интерфейс строится вокруг `useNavigate()`, `useLocation()` и `useParams()`
- самое важное — не заучивать три определения изолированно, а понимать последовательность: навигация меняет адрес, `location` описывает новый адрес, а маршрутизатор сопоставляет его с маршрутом и предоставляет параметры, необходимые компоненту
